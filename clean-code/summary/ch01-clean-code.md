# Chapter 1: Clean Code (깨끗한 코드) - 요약

> 상세 노트: [ch01-clean-code.md](../notes/ch01-clean-code.md)

**핵심 질문**: 깨끗한 코드란 무엇이며, 왜 그것이 프로그래머의 생존과 직결되는가?

## 핵심

- **코드는 사라지지 않는다**: 코드는 요구사항을 기계가 실행할 수 있을 만큼 정밀하게 표현하는 유일한 수단이다. 추상화 수준이 올라가도 그 표현 자체가 코드다.
- **나쁜 코드는 회사를 망하게 한다**: 킬러 앱을 만들고도 엉망인 코드 때문에 망한 회사의 실화. "나중에 정리하자"는 르블랑의 법칙에 걸린다 - 나중은 결코 오지 않는다.
- **나쁜 코드의 악순환**: 수정마다 엉뚱한 곳이 터지고, 생산성이 0에 수렴하고, 인력을 추가하면 설계 의도를 모르는 새 인력이 나쁜 코드를 더 양산한다. 원대한 재설계(타이거 팀)는 10년 경주가 되고, 따라잡을 즈음 새 팀이 또 재설계를 요구한다.
- **잘못은 프로그래머에게 있다**: 일정을 밀어붙이는 것이 관리자의 책임이라면 좋은 코드를 사수하는 것은 프로그래머의 책임이다. 환자가 요구해도 손 씻기를 거부하지 않는 의사처럼 - 위험은 우리가 더 잘 안다.
- **원초적 난제**: "기한을 맞추려면 나쁜 코드를 짤 수밖에 없다"는 착각이다. 나쁜 코드는 즉시 속도를 늦춘다. 빨리 가는 유일한 방법은 코드를 최대한 깨끗하게 유지하는 것이다.
- **대가들의 정의**: 스트롭스트룹(우아함과 효율, 한 가지를 제대로), 부치(잘 쓴 문장처럼 읽히는 명쾌한 추상화), 데이브 토마스(고치기 쉬움 + 테스트 없는 코드는 깨끗하지 않다), 페더스(누군가 주의care 깊게 짰다는 느낌), 제프리스(켄트 벡의 단순한 코드 규칙 - 테스트 통과, 중복 없음, 설계 아이디어 표현, 최소화), 커닝햄(짐작한 대로 동작해 놀랄 일이 없는 코드).
- **우리는 저자다**: 코드 읽기와 쓰기 비율은 10:1을 넘는다. 읽기 쉽게 만들면 짜기도 쉬워진다.
- **보이스카우트 규칙**: 캠프장을 처음보다 깨끗하게 하고 떠나라. 체크아웃 때보다 조금 더 깨끗하게 체크인하면(변수명 하나, 함수 분할 하나, 중복 하나) 코드는 절대 나빠지지 않는다.

> **핵심 통찰**: 깨끗한 코드는 미적 취향이 아니라 생존 전략이다. 코드 감각(code-sense)은 나쁜 코드를 알아보는 데서 끝나지 않고 개선 방안과 이동 경로를 떠올리는 능력이다.
