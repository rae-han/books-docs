# Chapter 1: Clean Code (깨끗한 코드) - 요약

**핵심 질문**: 깨끗한 코드란 무엇이며, 왜 그것이 프로그래머의 생존과 직결되는가?

## 코드는 사라지지 않는다

코드의 종말을 예견하는 사람들이 있지만 불가능하다. 코드는 요구사항을 기계가 실행할 수 있을 정도로 정밀하게 표현하는 유일한 수단이며, 그 상세한 명시 작업이 곧 프로그래밍이다. 추상화 수준이 높아지고 도메인 특화 언어가 늘어도 이 본질은 변하지 않는다.

## 나쁜 코드로 치르는 대가

한때 인기 있던 킬러 앱을 만든 회사가 있었다. 출시에 바빠 코드를 마구 짰고, 기능을 추가할수록 코드는 엉망이 되어 결국 감당 불가능한 수준에 이르렀다. **회사가 망한 원인은 나쁜 코드였다.** 시간에 쫓겨서, 상사에게 욕먹을까 봐, 빨리 끝내려고 - 우리 모두 "나중에 정리하자"고 다짐하지만 **르블랑의 법칙**이 말한다: 나중은 결코 오지 않는다.

나쁜 코드가 쌓이는 경로는 정해져 있다. 고칠 때마다 엉뚱한 곳이 터지고, 간단한 변경이 사라지고(매번 얽힌 코드를 해독해서 더 얽힌 코드를 추가), 팀 생산성이 0에 수렴한다. 관리층이 인력을 추가하지만 새 인력은 설계 의도를 모른 채 나쁜 코드를 더 양산한다. 결국 팀이 반기를 들어 **원대한 재설계**(타이거 팀)가 시작되는데, 이 경주는 10년 이상 걸리기도 하고, 새 시스템이 기존 시스템을 따라잡을 즈음이면 초창기 팀원은 다 떠나고 새 팀원들이 또 재설계를 요구한다.

## 태도: 잘못은 전적으로 프로그래머에게 있다

우리는 요구사항 변경, 촉박한 일정, 멍청한 관리자를 탓하지만, 일정과 요구사항을 밀어붙이는 것이 관리자의 책임이라면 **좋은 코드를 사수하는 것은 프로그래머의 책임**이다.

> **Uncle Bob의 경험**: 환자가 시간이 걸린다며 수술 전 손 씻기를 생략하라고 요구해도 의사는 단호히 거부한다. 질병과 감염의 위험은 환자보다 의사가 더 잘 알기 때문이다. 나쁜 코드의 위험을 모르는 관리자의 말을 그대로 따르는 것은 전문가답지 못하다.

여기서 원초적 난제가 나온다. 나쁜 코드가 업무 속도를 늦춘다는 것은 사실인데, "기한을 맞추려면 나쁜 코드를 짤 수밖에 없다"는 것은 **착각**이다. 나쁜 코드는 즉시 속도를 늦춰 오히려 기한을 놓치게 한다. **기한을 맞추는 유일한 방법, 빨리 가는 유일한 방법은 언제나 코드를 최대한 깨끗하게 유지하는 습관이다.**

## 대가들이 말하는 깨끗한 코드

깨끗한 코드와 나쁜 코드를 구분할 줄 안다고 깨끗한 코드를 작성할 줄 아는 것은 아니다. 나쁜 모듈을 알아보는 데서 그치지 않고 개선 방안과 이동 경로를 떠올리는 **코드 감각(code-sense)**이 필요하다. 대가들의 정의가 그 감각의 좌표가 된다.

- **비야네 스트롭스트룹**(C++ 창시자): 우아하고 효율적인 코드. 논리가 간단해야 버그가 숨지 못하고, 의존성이 적어야 유지보수가 쉽다. **깨끗한 코드는 한 가지를 제대로 한다.** 나쁜 코드는 나쁜 코드를 유혹한다(깨진 창문).
- **그래디 부치**: 단순하고 직접적이며 **잘 쓴 문장처럼 읽힌다**. 설계자의 의도를 숨기지 않고 명쾌한 추상화와 단순한 제어문으로 가득하다.
- **데이브 토마스**: 작성자가 아닌 사람도 읽기 쉽고 **고치기 쉽다**(둘은 다르다). 의미 있는 이름, 한 가지 목적에 한 가지 방법. 그리고 **테스트 케이스가 없는 코드는 깨끗한 코드가 아니다.**
- **마이클 페더스**: 모두를 아우르는 특징은 **주의(care)**. 누군가 시간을 들여 꼼꼼하게 신경 썼다는 느낌을 주고, 고치려고 살펴봐도 딱히 손댈 곳이 없다.
- **론 제프리스**: 켄트 벡의 단순한 코드 규칙 - 모든 테스트를 통과하고, 중복이 없고, 설계 아이디어를 모두 표현하고, 클래스와 메서드 수를 최소로 줄인다.
- **워드 커닝햄**: 읽으면서 **짐작했던 기능을 각 루틴이 그대로 수행하면** 깨끗한 코드다. 코드가 문제를 풀기 위한 언어처럼 보이면 아름다운 코드다. 언어를 단순해 보이게 만드는 것은 언어가 아니라 프로그래머다.

## 우리는 저자다 + 보이스카우트 규칙

`@author` 필드가 말해주듯 우리는 저자이고, 저자에게는 독자와 소통할 책임이 있다. 코드를 읽는 시간과 짜는 시간의 비율은 **10:1을 훌쩍 넘는다** - 새 코드를 짜면서 우리는 끊임없이 기존 코드를 읽는다. 그러므로 급할수록, 서둘러 끝내려면, **읽기 쉽게 만들면 된다.** 읽기 쉬운 코드가 짜기도 쉽다.

잘 짠 코드가 전부는 아니다. 시간이 지나도 깨끗하게 유지해야 한다. **보이스카우트 규칙**: 캠프장은 처음 왔을 때보다 더 깨끗하게 해놓고 떠나라. 체크아웃할 때보다 조금 더 깨끗한 코드를 체크인하면 코드는 절대 나빠지지 않는다. 거창할 필요 없다 - 변수 이름 하나 개선, 긴 함수 하나 분할, 중복 약간 제거, 복잡한 if 문 하나 정리면 충분하다.

> **핵심 통찰**: 깨끗한 코드는 미적 취향이 아니라 생존 전략이다. 시간을 들여 깨끗한 코드를 만드는 노력은 비용을 절감하는 방법일 뿐 아니라 전문가로서 살아남는 길이다.
