# Chapter 0: 들어가며 (왜 웹 성능이 중요한가)

## 핵심 질문

하드웨어가 좋아지고 프레임워크가 최적화를 대신해주며 AI가 코드를 써주는 시대에, 왜 여전히 웹 성능을 깊이 알아야 하는가? 그리고 성능 최적화는 언제 시작해야 하며 무엇을 먼저 봐야 하는가?

## 1. 왜 웹 성능이 중요한가

개발자는 비교적 획일적이고 고사양인 기기를 쓰는 업무 환경에서 일한다. 하지만 실제 서비스 환경에서는 국가와 지역별로 네트워크 속도가 천차만별이고 모바일 기기의 스펙과 브라우저 상황도 다양하다. 사내 인트라넷 전용 애플리케이션이라 해도 사용자 수가 늘고 처리할 작업이 많아지면 결국 성능을 되돌아볼 수밖에 없다.

그래서 "왜 웹 성능이 중요한가"라는 질문은 사실상 **"어떤 사용자도 불편 없이 서비스를 이용하게 만들 수 있는가"**에 대한 문제다.

### 1.1 과거와 달라진 환경, 그에 맞춰 달라진 우선순위

과거에는 메모리나 CPU가 늘 부족했기 때문에 개발자들이 코드 한 줄도 아꼈다. 웹 개발도 마찬가지여서 이미지를 최대한 압축하고, 자바스크립트와 CSS를 합쳐 요청 수를 줄이고, DOM 조작 횟수를 최소화했다.

지금은 상황이 다르다. 데스크톱뿐 아니라 스마트폰의 하드웨어 성능도 비약적으로 발전했고, 클라우드 대중화로 서버를 늘리거나 고사양 스펙을 고르는 일이 간편해졌다. 여기에 빠른 시장 출시를 중시하는 MVP(*Minimum Viable Product - 최소 기능 제품*) 중심 개발이 확산되면서 "초기에는 기능 구현에 집중하고 이후 점진적으로 개선한다"는 접근법이 일반화됐다.

이 흐름에는 분명 장점이 있다. 하지만 마냥 좋은 것만은 아니다.

> **핵심 통찰**: 현대 프레임워크와 빌드 도구는 개발 생산성을 극적으로 높였지만 '공짜 점심'은 없다. 추상화는 개발 속도를 높여준 대신 **성능 비용(*Performance Cost*)을 블랙박스 안에 숨겨버렸다.** 번들러가 코드 스플리팅과 트리 셰이킹을 자동화해주는 것은 사실이지만, 런타임의 불필요한 리렌더링·최적화되지 않은 이미지 로딩·잘못된 리소스 우선순위·메인 스레드를 블로킹하는 긴 태스크는 여전히 개발자가 이해하고 해결해야 한다.

### 1.2 병목의 이동: 서버에서 클라이언트로

하드웨어와 네트워크가 변하는 동안 웹 애플리케이션 아키텍처도 근본적으로 바뀌었다. 지난 10년간 웹 개발의 가장 큰 흐름은 **'로직의 이동'**이었다.

- **과거의 웹(MPA, *Multi Page Application*)**: 서버가 데이터베이스를 조회하고 HTML을 완성해 브라우저에 던져주면 끝이었다. 병목은 대부분 느린 SQL 쿼리나 서버 처리량에 있었고, 브라우저는 HTML을 보여주는 뷰어에 불과했다.
- **오늘날의 웹(SPA, *Single Page Application*)**: 더 풍부한 인터랙션을 위해 렌더링과 라우팅 로직이 서버에서 브라우저로 대거 이동했다. 리액트·뷰는 훌륭한 DX와 UX를 제공했지만 그 대가로 사용자의 브라우저에 막대한 연산 부담을 지웠다. **성능 병목이 서버가 아니라 사용자 기기의 메인 스레드로 이동한 것이다.**

이 문제를 해결하려고 도입한 SSR(*Server Side Rendering*)과 하이드레이션(*hydration*)은 또 다른 복잡성을 낳았다. 서버가 HTML을 빠르게 내려주어 FCP는 개선됐지만, 브라우저가 자바스크립트를 실행하고 이벤트 리스너를 연결하기 전까지는 화면에 보이는 버튼이 동작하지 않는다. **화면은 떴는데 눌러도 반응이 없는 '불쾌한 골짜기'**가 생긴 것이다. 과거에는 이를 TTI로 측정했지만 지금은 더 정교한 INP가 그 역할을 대신한다.

여기에 마이크로 프런트엔드(*Micro-Frontends*) 아키텍처가 더해지면 복잡도는 더 올라간다. 여러 팀의 독립 배포라는 장점 뒤에는 중복 라이브러리 로딩과 초기화 비용 증가라는 성능 부채가 숨어 있다.

> **핵심 통찰**: 결국 현대의 프런트엔드 성능 최적화는 "이미지를 줄이고 코드를 압축하는 것"을 넘어선다. **"이 로직을 서버에서 실행할 것인가, 클라이언트에서 실행할 것인가?", "사용자의 메인 스레드를 얼마나 점유할 것인가?", "하이드레이션 비용을 어디까지 허용할 것인가?"** 같은 아키텍처 레벨의 의사결정이 성능을 좌우한다.

### 1.3 웹 성능은 자연스럽게 좋아지지 않는다

하드웨어와 네트워크가 발전했음에도 웹사이트 성능은 자연스럽게 향상되지 않는다. 오히려 웹사이트가 복잡해지면서 성능 저하가 두드러진다.

HTTP Archive 데이터에 따르면 **모바일 환경의 자바스크립트 부팅 시간(Boot-up Time) 중앙값은 2018년 0.9초에서 2025년 3.3초로 약 267% 증가**했다. 하드웨어 성능은 꾸준히 발전했지만 웹사이트가 복잡해지면서 실행 속도는 나아지기는커녕 느려지는 추세다.

서버나 사용자 기기 성능만으로는 한계가 명확하며, 자원이 제한된 모바일·임베디드 환경에서는 성능 최적화가 더욱 중요하다.

## 2. 성능 최적화의 투자 시점

모든 프로젝트가 0.1초의 로딩 속도에 목숨을 걸 필요는 없다. 시장 검증을 시작한 MVP 단계라면 성능보다 기능 구현 속도가 훨씬 중요할 수 있다. 섣부른 최적화(*premature optimization*)는 오히려 비즈니스의 기민함을 해치는 독이 된다.

하지만 서비스가 성장하고 트래픽이 늘어나는 **규모 확장(Scale-up) 단계**가 오면 이야기가 달라진다. 이때부터 성능은 곧 비용(cloud cost)이자 매출(conversion rate)이 된다.

- 전 아마존 엔지니어 그렉 린든(Greg Linden)에 따르면 페이지 로딩 시간이 **100ms 느려질 때마다 매출이 1% 감소**했다.
- 구글은 검색 결과 페이지 로딩이 **0.5초 늦어지면 트래픽이 20% 감소**한다고 발표했다.

> **핵심 통찰**: "언제 최적화를 시작해야 하는가", "어디까지 최적화해야 비용 대비 효과가 가장 좋은가"를 아는 것이야말로 시니어 엔지니어가 가져야 할 비즈니스 감각이다.

## 3. AI와 프레임워크가 해주는데 왜 알아야 하나

### 3.1 AI는 '어떻게'는 알려주지만 '무엇을'은 모른다

성능 최적화는 코드 몇 줄을 고치는 문제가 아니라 **시스템 전체의 문제**다. 다음은 각각 다른 영역에서 발생하며 하나만 고쳐서는 해결되지 않는다.

- 리액트 컴포넌트를 `useMemo`·`useCallback`으로 완벽히 메모이제이션해도, 최적화되지 않은 5MB JPEG이 있으면 LCP는 여전히 느리다.
- 코드 스플리팅으로 번들을 줄여도, 리소스 로딩 순서가 잘못돼 있으면 네트워크 워터폴이 발생한다.
- 트리 셰이킹으로 코드를 제거해도, 메인 스레드를 200ms 이상 블로킹하는 긴 태스크가 있으면 INP는 악화된다.
- 클라이언트를 아무리 최적화해도 서버 응답이 3초면 사용자는 기다린다.

AI에게 "성능을 최적화해줘"라고 요청할 수는 있다. AI는 `useMemo`를 추가하고, 이미지에 `loading="lazy"`를 붙이고, 번들 분석 도구 설정을 생성해줄 것이다. 하지만 **"지금 이 서비스의 병목이 어디인지"는 AI가 알 수 없다.** 라이트하우스 점수는 90점인데 실사용자가 느리다고 할 때, 개발 환경은 빠른데 프로덕션만 느릴 때, 데스크톱은 괜찮은데 모바일만 문제일 때 원인을 추적하는 것은 시스템 전체를 이해하는 개발자만이 할 수 있다.

> **핵심 통찰**: "어떻게 고칠까"는 AI가 도와주지만 **"무엇을 고쳐야 하는가"를 결정하는 것은 개발자다.** 병목을 진단하고, 우선순위를 정하고, 비즈니스 임팩트가 가장 큰 곳에 리소스를 집중하는 능력이 AI 시대에 개발자가 증명해야 할 가치다.

### 3.2 프레임워크가 자동화해도 원리를 알아야 하는 네 가지 이유

1. **프레임워크의 기본값이 항상 최적은 아니다**: Next.js `Image` 컴포넌트는 훌륭하지만 `priority` 속성을 잘못 설정하면 LCP가 오히려 나빠진다. `font-display: swap`과 `optional` 중 무엇을 쓸지, 청크 크기를 어떻게 잡을지는 프레임워크가 정해주지 않는다. **옵션은 제공하지만 선택은 개발자의 몫이다.**
2. **문제가 생겼을 때 원인을 찾으려면 원리를 알아야 한다**: "왜 LCP가 느리지?", "CLS가 왜 발생하지?"에 답하려면 브라우저가 리소스를 어떤 순서로 로드하는지, 렌더 블로킹이 무엇인지, 트리 셰이킹이 어떻게 작동하는지 알아야 한다. 라이트하우스 경고의 의미를 모르면 해결할 수 없다.
3. **프레임워크를 벗어난 상황은 반드시 온다**: 레거시 jQuery 프로젝트 유지보수, 프레임워크 없는 가벼운 랜딩 페이지, 프레임워크가 지원하지 않는 최적화 등.
4. **프레임워크는 바뀌지만 원리는 남는다**: 5년 전에는 Create React App, 지금은 Next.js와 비트, 5년 후에는 또 다른 도구다. 하지만 브라우저의 리소스 로드 방식·렌더링 파이프라인·캐싱 메커니즘은 크게 바뀌지 않는다.

> **핵심 통찰**: 프레임워크를 잘 아는 사람은 그 프레임워크의 수명과 함께하겠지만, **웹을 잘 아는 사람은 웹과 함께할 수 있다.**

## 4. 핵심 웹 지표의 기본 개념

핵심 웹 지표(*Core Web Vitals*)는 이 책 전반에 반복적으로 등장하므로 각 지표가 무엇을 측정하고 왜 중요한지 명확히 이해해야 한다.

### 4.1 LCP (Largest Contentful Paint)

뷰포트 내에서 **시각적으로 가장 큰 콘텐츠 요소가 렌더링되는 시간**을 측정한다. 사용자가 "페이지가 로딩됐다"고 인지하는 시점을 나타내며 로딩 성능을 대표한다.

| 등급 | 기준 |
|---|---|
| 좋음(Good) | 2.5초 이하 |
| 개선 필요(Needs Improvement) | 2.5초 ~ 4.0초 |
| 나쁨(Poor) | 4.0초 초과 |

- **측정 대상 요소**: `<img>` 태그, `<video>` 요소의 포스터 이미지, CSS `url()` 배경 이미지가 적용된 블록 레벨 요소, 큰 텍스트 블록
- **동작 방식**: 브라우저는 로드되는 동안 뷰포트 내 가장 큰 요소를 계속 추적하며 사용자가 상호작용을 시작하기 전까지 값을 갱신한다. 로딩 중 더 큰 요소가 나타나면 LCP 후보가 바뀔 수 있다.
- **기준선**: 실제 사용자 데이터의 **75번째 백분위수**를 기준으로 평가한다.

### 4.2 INP (Interaction to Next Paint)

사용자가 페이지와 상호작용한 순간부터 **다음 화면이 그려지기까지의 전체 시간**을 측정한다. 클릭·탭·키보드 입력이 모두 대상이며, 2024년 3월부터 FID(*First Input Delay*)를 대체해 핵심 웹 지표에 포함됐다.

| 등급 | 기준 |
|---|---|
| 좋음(Good) | 200ms 이하 |
| 개선 필요(Needs Improvement) | 200ms ~ 500ms |
| 나쁨(Poor) | 500ms 초과 |

FID는 페이지 로딩 중 **첫 번째** 입력의 지연만 측정했기 때문에 이후 상호작용의 응답성은 알 수 없었다. 반면 INP는 페이지 전체 생명주기 동안의 모든 상호작용을 추적하고, 각 상호작용마다 **입력 지연 + 처리 시간 + 표현 지연**을 모두 합산한다. 또한 **98번째 백분위수**를 사용하므로 거의 모든 상호작용이 빨라야 좋은 점수를 받는다.

### 4.3 CLS (Cumulative Layout Shift)

페이지 생명주기 동안 발생하는 **예기치 않은 레이아웃 이동의 누적 심각도**를 측정한다. 글을 읽는 중 광고가 나타나 텍스트를 밀어내거나, 버튼을 누르려는 순간 위치가 바뀌는 현상을 수치화한다.

| 등급 | 기준 |
|---|---|
| 좋음(Good) | 0.1 이하 |
| 개선 필요(Needs Improvement) | 0.1 ~ 0.25 |
| 나쁨(Poor) | 0.25 초과 |

**계산식**은 다음과 같다.

```
레이아웃 이동 점수 = 영향 분율(Impact Fraction) × 거리 분율(Distance Fraction)

영향 분율: 이동한 요소가 뷰포트에서 차지하는 영역의 비율
거리 분율: 요소가 이동한 거리 ÷ 뷰포트 크기

예) 화면의 50%를 차지하는 요소가 화면 높이의 10%만큼 이동
    → 0.5 × 0.1 = 0.05점
```

브라우저는 레이아웃 이동을 **세션 윈도우**로 그룹화한다. 1초 이내 연속 발생한 이동은 하나의 윈도우로 묶이며 각 윈도우는 최대 5초까지 지속된다. 페이지 전체 수명 동안 발생한 세션 윈도우 중 **가장 큰 점수가 최종 CLS 값**이 된다. 단, 사용자 입력 후 500ms 이내에 발생한 레이아웃 변화는 예상된 변화로 간주해 계산에서 제외된다.

### 4.4 TTFB (Time to First Byte)

브라우저가 요청을 보낸 후 **첫 번째 응답 바이트를 받기까지의 시간**이다. 서버 응답성을 나타내는 선행 지표로, 모든 성능 지표의 출발점이다.

| 등급 | 기준 |
|---|---|
| 좋음(Good) | 0.8초 이하 |
| 개선 필요(Needs Improvement) | 0.8초 ~ 1.8초 |
| 나쁨(Poor) | 1.8초 초과 |

TTFB는 다음 다섯 단계로 구성된다.

1. DNS 조회 시간(도메인 → IP 주소 변환)
2. TCP 연결 설정 시간(3방향 핸드셰이크: SYN → SYN-ACK → ACK)
3. TLS 협상 시간(HTTPS의 경우 인증서 교환 및 암호화 스위트 협상)
4. 서버 처리 시간(DB 조회, 비즈니스 로직, 템플릿 렌더링)
5. 첫 바이트 전송 시간(네트워크 왕복 시간)

TTFB가 느리면 LCP·FCP 등 모든 후속 지표가 자동으로 느려진다.

### 4.5 FCP (First Contentful Paint)

첫 번째 DOM 콘텐츠(텍스트, 이미지, SVG, 비흰색 캔버스)가 화면에 렌더링되는 시간이다.

| 등급 | 기준 |
|---|---|
| 좋음(Good) | 1.8초 이하 |
| 개선 필요(Needs Improvement) | 1.8초 ~ 3.0초 |
| 나쁨(Poor) | 3.0초 초과 |

FCP와 LCP의 차이는 명확하다. FCP는 **첫 번째** 콘텐츠, LCP는 **가장 큰 의미 있는** 콘텐츠를 본다. 로딩 스피너가 0.5초에 표시되면 FCP는 0.5초지만, 메인 이미지가 2.0초에 표시되면 LCP는 2.0초다. **FCP는 "무언가 일어나고 있다"는 신호, LCP는 "의미 있는 콘텐츠를 볼 수 있다"는 신호다.**

### 4.6 TTI와 TBT

- **TTI(*Time to Interactive*)**: 페이지가 완전히 상호작용 가능한 상태가 되는 시점. 조건은 FCP 발생 + 50ms 이상 긴 작업 없음 + 주요 네트워크 요청 완료다. 라이트하우스에서 쓰이지만 실제 사용자 측정(RUM, *Real User Monitoring*)에서는 사용하기 어렵다.
- **TBT(*Total Blocking Time*)**: FCP와 TTI 사이에 메인 스레드가 차단된 총 시간. 50ms 이상 걸리는 긴 작업의 **초과분(50ms를 뺀 시간)** 합계다. 70ms 작업이면 20ms가, 200ms 작업이면 150ms가 TBT에 더해진다. INP와 상관관계가 높아 라이트하우스에서 병목 진단에 유용하다.

## 6. 브라우저 렌더링 기본 개념

### 6.1 렌더링 파이프라인

```
HTML 파싱  ──▶ DOM 트리 생성   ┐
                              ├──▶ 렌더 트리 생성
CSS 파싱   ──▶ CSSOM 트리 생성 ┘
                                     │
                                     ▼
                          레이아웃(Reflow) — 각 요소의 위치와 크기 계산
                                     │
                                     ▼
                          페인트(Repaint) — 각 요소를 픽셀로 그리기
                                     │
                                     ▼
                          합성(Composite) — 레이어를 합쳐 최종 화면 생성
```

### 6.2 크리티컬 렌더링 패스

페이지를 처음 로딩할 때 화면에 무언가 보이기까지의 **최소 경로**다.

```
HTML 다운로드(TTFB)
  → HTML 파싱(DOM 생성)
  → CSS 다운로드(렌더 블로킹)
  → CSS 파싱(CSSOM 생성)
  → 자바스크립트 다운로드(파서 블로킹)
  → 자바스크립트 실행
  → 렌더 트리 생성
  → 레이아웃
  → 페인트
  → FCP(First Contentful Paint)
```

**CSS는 CSSOM이 완성될 때까지 렌더링을 막고, 자바스크립트는 실행이 끝날 때까지 HTML 파싱을 막는다.** 이 경로를 최적화하는 방법은 Ch7에서 다룬다.

### 6.3 메인 스레드와 블로킹

브라우저는 자바스크립트 실행, DOM 조작, 스타일 계산, 레이아웃을 **하나의 메인 스레드**에서 처리한다. 이 스레드가 바쁘면 다른 일을 할 수 없다.

```ts
// 메인 스레드를 3초 동안 블로킹
function blockMainThread(): void {
  const start = Date.now();
  while (Date.now() - start < 3000) {
    // 아무것도 안 함
  }
}

button.addEventListener('click', () => {
  blockMainThread();
  // 이 3초 동안 화면이 멈춤 — 스크롤, 클릭, 입력 모두 반응 없음
});
```

이 책에서 "메인 스레드 블로킹을 줄여라"는 **긴 작업을 쪼개거나 웹 워커로 옮기라**는 의미다.

### 6.4 레이아웃 스래싱 (Layout Thrashing)

DOM을 읽고 쓰는 작업을 번갈아 반복하면 레이아웃 계산이 강제로 여러 번 발생한다.

```ts
// ❌ 나쁜 예: 레이아웃 스래싱
elements.forEach((el) => {
  const height = el.offsetHeight;          // 레이아웃 읽기
  el.style.height = `${height + 10}px`;    // 레이아웃 쓰기
  // 매번 레이아웃 재계산이 발생
});

// ✅ 좋은 예: 읽기와 쓰기 분리
const heights = elements.map((el) => el.offsetHeight); // 읽기 한 번에
elements.forEach((el, i) => {
  el.style.height = `${heights[i] + 10}px`;            // 쓰기 한 번에
});
// 레이아웃 계산이 한 번만 발생
```

이 개념은 Ch21에서 자세히 다룬다.

### 6.5 레이어와 합성 (Compositing)

브라우저는 페이지를 여러 레이어로 나눠 그린 후 합성한다. `transform`, `opacity` 같은 속성은 **합성 단계에서만** 변경되므로 성능이 좋다.

```css
/* ❌ 나쁜 예: 레이아웃 + 페인트 발생 */
.box {
  transition: left 0.3s;
}
.box:hover {
  left: 100px; /* 레이아웃 재계산 */
}

/* ✅ 좋은 예: 합성만 발생 */
.box {
  transition: transform 0.3s;
}
.box:hover {
  transform: translateX(100px); /* GPU 가속 */
}
```

이 책에서 "GPU 가속을 활용하라", "합성 레이어를 사용하라"는 이 개념을 가리킨다.

## 7. 이 책의 범위와 개발 환경

### 7.1 이 책에서 다루지 않는 것

- **백엔드 성능**: DB 쿼리 최적화, API 설계(REST/GraphQL/gRPC), 서버 스케일링. TTFB 개선은 다루지만 서버 코드 최적화는 "서버가 느리면 백엔드를 최적화하라" 정도만 언급한다.
- **인프라 레벨 최적화**: CDN 구축(활용법은 다룸), 컨테이너 최적화, 네트워크 라우팅(BGP·Anycast), 보안(DDoS·WAF). 인프라는 이미 구축돼 있고 프런트엔드가 활용한다고 가정한다.
- **모바일 앱 네이티브 성능**: 리액트 네이티브 브릿지·헤르메스 엔진, 플러터 위젯 트리, 스위프트·코틀린 튜닝.
- **SEO**: 핵심 웹 지표가 검색 순위에 영향을 준다는 점만 언급하고 메타 태그·구조화된 데이터·사이트맵·키워드 전략은 다루지 않는다.
- **디자인과 UX**: UI/UX 디자인, 인터랙션 디자인, 사용성 테스트. "빠른 것"과 "좋은 것"은 다르며 이 책은 "빠르게 만드는 것"에 집중한다.

### 7.2 개발 환경

- **브라우저**: 크롬 140 이상(2025년 9월 출시 기준). 크롬을 택한 이유는 ① 약 65%의 압도적 시장 점유율, ② 가장 강력한 개발자 도구, ③ Priority Hints·Speculation Rules 등 최신 성능 API를 가장 먼저 지원, ④ 구글의 핵심 웹 지표 측정 기준이 크롬 기반이라는 점이다. 엣지·브레이브·오페라 같은 크로미움 기반 브라우저도 대부분 동일하게 동작하지만, 사파리와 파이어폭스는 일부 기능이 미지원이거나 다르게 동작한다.
- **Node.js**: v22 이상(v24 LTS 권장)
- **패키지 관리자**: npm, yarn, pnpm 중 하나
- **예제 코드**: `https://github.com/yceffort/web-performance-deep-dive-example`

> **실무 팁**: 리소스 우선순위 규칙·캐시 정책·브라우저 휴리스틱은 크롬 업데이트에 따라 개선되거나 변경된다. **책에서 설명하는 원리는 동일하지만 세부 수치나 동작은 달라질 수 있다는 점**을 항상 염두에 두고, 최종 판단은 직접 측정한 데이터로 내린다.

## 요약

- 웹 성능은 "어떤 사용자도 불편 없이 서비스를 이용하게 만들 수 있는가"의 문제다. 개발자 환경과 실제 사용자 환경의 격차가 핵심이다.
- 추상화는 개발 속도를 높인 대신 성능 비용을 블랙박스에 숨겼다. 자동화된 도구 뒤의 원리를 모르면 문제를 진단할 수 없다.
- 지난 10년의 '로직의 이동'으로 성능 병목이 서버에서 **사용자 기기의 메인 스레드**로 옮겨갔다. SSR과 하이드레이션은 FCP를 개선했지만 "보이는데 눌러도 안 되는" 구간을 만들었다.
- 하드웨어가 좋아져도 웹은 빨라지지 않았다. 모바일 자바스크립트 부팅 시간 중앙값은 2018년 0.9초에서 2025년 3.3초로 267% 증가했다.
- MVP 단계의 섣부른 최적화는 독이지만, 규모 확장 단계에서 성능은 비용이자 매출이다(100ms 지연 = 매출 1% 감소).
- AI는 "어떻게"를 도와주지만 "무엇을 고쳐야 하는가"는 개발자가 결정한다.
- 핵심 웹 지표 3종: **LCP 2.5초(로딩)**, **INP 200ms(응답성)**, **CLS 0.1(시각적 안정성)**. 보조 지표로 TTFB 0.8초, FCP 1.8초, TBT가 있다.
- 렌더링 파이프라인(DOM+CSSOM → 렌더 트리 → 레이아웃 → 페인트 → 합성)과 크리티컬 렌더링 패스는 책 전반의 공통 언어다.
- 메인 스레드 블로킹, 레이아웃 스래싱, 합성 레이어 세 가지 개념이 런타임 최적화의 기초다.

## 다른 챕터와의 관계

- **Ch1~7(1부 네트워크와 로딩)**: "가장 빠른 네트워크 요청은 요청하지 않는 것"이라는 원칙 아래 전송 경로·크기·순서를 다룬다. 여기서 정의한 TTFB·FCP·LCP가 주요 대상 지표다.
- **Ch8~15(2부 번들과 리소스)**: "추상화가 숨긴 성능 비용"을 번들 분석으로 가시화하고, 전송할 데이터 자체를 줄인다.
- **Ch16~21(3부 렌더링과 런타임)**: 이 장에서 설명한 메인 스레드·레이아웃 스래싱·합성 레이어 개념이 INP·CLS 개선으로 이어진다. 특히 Ch16은 "병목의 이동"에서 언급한 하이드레이션 문제를 정면으로 다룬다.
- **Ch22~25(4부 프레임워크와 고급 주제)**: "프레임워크의 기본값이 항상 최적은 아니다"를 리액트·뷰·스벨트별로 구체화한다.
- **Ch26(마치며)**: 어디서부터 시작할지, 어떻게 측정 문화를 만들지 정리한다.
- **부록 A(핵심 웹 지표의 역사)**: 4절에서 정의한 지표들이 왜 지금의 모습이 됐는지 5년간의 변화를 추적한다.
