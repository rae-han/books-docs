# 프런트엔드 성능 최적화 Deep Dive

> 김용찬 지음, 위키북스, 2026 (프로그래밍&프랙티스 시리즈 039, 1,448쪽)<br>부제: 핵심 개념과 동작 원리를 중심으로 배우는 프런트엔드 성능 최적화의 모든 것

네트워크에서 렌더링, 프레임워크, 차세대 웹 표준까지 - 프런트엔드 성능 최적화의 전 영역을 핵심 웹 지표(LCP·INP·CLS)라는 하나의 렌즈로 꿰어내는 한국어 저술서. 모든 기법을 "왜 그런가(동작 원리) → 어떻게 하는가(구현) → 어떻게 확인하는가(측정)"의 3박자로 다루며, 크롬 개발자 도구 실측과 실무 사례가 전 장을 관통한다.

## 개요

"라이트하우스 점수는 90점인데 사용자는 느리다고 한다" - 이 책은 그 간극에서 출발한다. 0부(들어가며)에서 성능이 이탈률·전환율·매출로 이어지는 비즈니스 근거를 세우고, 1부 네트워크와 로딩(CDN·압축·캐시·우선순위), 2부 번들과 리소스(폴리필·트리 셰이킹·스플리팅·이미지·폰트·CSS), 3부 렌더링과 런타임(하이드레이션·데이터 캐싱·긴 작업·메모리·CLS·애니메이션), 4부 프레임워크와 고급 주제(컴포넌트·서드파티·다국어·차세대 표준)로 확장한다. 부의 순서 자체가 "투자 대비 효과가 큰 것부터"라는 실행 전략이다.

책의 일관된 태도는 **측정 없는 최적화는 추측**이라는 것이다. 모든 장이 크롬 개발자 도구(Performance·Network·Memory·Coverage·Layers·Rendering 탭)와 Performance API, RUM 수집 코드로 "측정하는 법"을 함께 다루며, 마지막 장은 기법이 아니라 우선순위 결정·성능 예산·CI 통합·성능 문화라는 지속 가능성을 다룬다. 예제는 Next.js/리액트 중심이되 뷰·스벨트의 대응 개념을 병기해 프레임워크 간 원리 비교가 가능하다.

노트는 각 장을 책 없이도 학습 가능한 수준으로 재구성했다. 원서의 실측 수치·사례·체크리스트를 보존하되, 코드는 TypeScript로 통일하고 장마다 `자주 하는 실수`(원인·해결 표)와 `측정과 검증` 절을 표준화해 실무 참조서로 쓸 수 있게 했다.

## 학습 가이드

부 순서 자체가 "투자 대비 효과 큰 것부터"이므로 **순차 읽기가 기본**이다. 상황별로는 다음 경로를 추천한다.

- **처음 최적화를 시작한다면**: Ch0 → Ch1~3(네트워크·캐시) → Ch12(이미지) → Ch26(로드맵). 26장의 "단기 개선 7가지"가 곧 이 경로의 실행 요약이다.
- **라이트하우스 점수는 좋은데 사용자가 느리다고 할 때(INP 문제)**: Ch16(하이드레이션) → Ch18(긴 작업) → Ch17(데이터 캐싱) → Ch22(리렌더링) → Ch25.3(LoAF 디버깅).
- **레이아웃이 흔들린다(CLS)**: Ch12(이미지 크기) → Ch14(폰트) → Ch20(동적 콘텐츠) → Ch21(transform 애니메이션).
- **번들이 너무 클 때**: Ch9(제거 우선) → Ch8(폴리필) → Ch10(스플리팅) → Ch11(서버 이동) → Ch24(다국어 리소스).
- **오래 쓰면 느려지는 SPA**: Ch19(메모리) → Ch18(실행) → Ch17(캐시 상한).
- **서드파티가 원인일 때**: Ch23 단독으로 완결(측정→제거→지연→파사드→워커→격리).
- **리액트/Next.js 관점 종단 읽기**: Ch10 → Ch11 → Ch16 → Ch17 → Ch22.

장 간 의존은 느슨하지만, Ch7↔Ch15(크리티컬 CSS), Ch16↔Ch17(SSR과 데이터 캐싱), Ch18↔Ch19(실행과 메모리 = 런타임 양대 축), Ch20↔Ch21(레이아웃과 컴포지터)은 짝으로 읽으면 좋다.

## 핵심 개념 맵

- **핵심 웹 지표가 전 장의 공통 언어**: LCP는 1~2부(전송·리소스)가, INP는 3~4부(실행·리렌더링·서드파티)가, CLS는 12·14·20·21장이 담당한다 - 부록 A가 이 지표들의 유래를 설명한다.
- **"덜 보내고, 늦게 보내고, 가까이서 보낸다"**: 압축(Ch2)·제거(Ch9)·스플리팅(Ch10)이 덜 보내기, 지연 로딩(Ch12·23)·우선순위(Ch4)가 늦게 보내기, CDN·엣지(Ch1·24)가 가까이서 보내기다.
- **메인 스레드는 하나뿐**: 파서 블로킹(Ch5~6) → 하이드레이션(Ch16) → 긴 작업(Ch18) → GC(Ch19) → 리렌더링(Ch22) → 서드파티(Ch23)가 모두 같은 스레드를 두고 경쟁한다 - INP 문제는 이 사슬 어딘가에 있다.
- **캐시의 3계층**: 브라우저 HTTP 캐시(Ch3, 정적 리소스) → 앱 메모리의 서버 상태 캐시(Ch17, API 응답) → 엣지 캐시(Ch24, 언어별 콘텐츠) - 모두 stale-while-revalidate 철학을 공유한다.
- **"생성했으면 해제한다"**: 리스너·타이머·구독(Ch19), will-change(Ch21), rAF 루프(Ch21), 캐시 상한(Ch17)에 반복되는 생명주기 원칙.
- **점진적 향상이 신기술 도입의 문법**: 기능 감지 + 폴백(Ch8 폴리필, Ch25 차세대 표준) - 미지원 브라우저에서 조용히 무시되는 API가 이상적인 도입 대상이다.
- **측정→개선→재측정 사이클**: 장마다 개발자 도구 탭이 하나씩 주인공이 된다(Network=1~4장, Performance=16·18·21장, Memory=19장, Coverage=9·15장, Layers/Rendering=21장) - 26장이 이를 성능 예산과 CI로 제도화한다.

## 시그니처 요소와 표기 규칙

- 각 노트는 `## 핵심 질문`(일반 텍스트) → 번호 섹션 → `## 자주 하는 실수`(실수·왜 문제인가·해결 3열 표) → `## 측정과 검증` → `## 체크리스트`(`- [ ]` 그룹) → `## 요약` → `## 다른 챕터와의 관계` 구조를 따른다.

- 코드는 TypeScript 우선 변환(tsx·next.config.ts 등), nginx·bash·http·css는 원형 유지. OCR 훼손 표·다이어그램은 ASCII로 재구성.
- 원서의 실측 수치(예: 강제 동기 레이아웃 346배, 파사드 224배, 사전 압축 98%)와 실무 사례를 최대한 보존.

## origin 분리

- 구성: `0.origin.md`(표지·서문·목차, 1~1,440행) + `1.origin.md`~`26.origin.md`(각 장) + `27.origin.md`(부록 A 핵심 웹 지표의 역사) + `99.origin.md`(찾아보기) = **29개 파일**. 부 표지는 각 부 첫 챕터 파일 맨 앞에 포함(1부=1, 2부=8, 3부=16, 4부=22).
- 검증: 분리 파일 재결합본이 원본 `origin.md`(44,612행)과 **byte 단위 완전 일치**(cksum 3610109612, 2,584,852 bytes).
- 페이지 번호: 러닝 헤더/푸터 기준 **1,377개(약 96%) 캡처, 순차 검증 통과**. 누락 55개는 전부 챕터/부 표지 페이지(정상 패턴).
- ⚠️ OCR 특성: 한글 자간 공백 삽입, 코드 식별자 훼손(`usestate`→`useState`, `1/`→`//`, 소문자화된 API명), 표·다이어그램 구조 붕괴 - 노트 작성 시 원문 이해 후 재구성함. 원본 `origin.md`는 그대로 보존.

## Notion DB 구조

- **위치**: `Raehan's Must reads` → **프런트엔드 성능 최적화 Deep Dive**(아이콘 ⚡) 페이지 안의 인라인 DB.
- **속성**: `Done`(checkbox), `Title`, `Part`(select), `Chapter`(number), `핵심 단어`(text), `핵심 요약`(text). 값의 소스는 위 **목차 표**다 - 재업로드 시 목차 표 기준으로 채운다.
- **`Part` 딱지**: `들어가며` / `Part 1 네트워크와 로딩` / `Part 2 번들과 리소스` / `Part 3 렌더링과 런타임` / `Part 4 프레임워크와 고급` / `부록`. 부록 A(핵심 웹 지표의 역사)는 `Chapter` 27로 두어 맨 뒤에 정렬된다.
- **뷰**: `SHOW "Done", "Title", "Part", "핵심 단어", "핵심 요약"; SORT BY "Chapter" ASC`. 제목에 `ChNN.` 접두어가 있으므로 `Chapter` 열은 숨긴다(숨겨도 정렬은 유지된다).
- **업로드 순서**: 챕터 페이지는 **번호 역순**(부록 A → Ch26 → … → Ch0)으로 생성한다. Notion DB는 최신 생성이 위로 오므로 이렇게 해야 정렬을 걸지 않아도 목차 순서로 읽힌다.
- ⚠️ **한글 손상 주의**: `create-pages`의 JSON 파라미터로 한글을 보내면 음절이 깨지는 사례가 반복됐다(봉쇄→봉샄, 통째로→통쨰로, 없애라→없얰라). **① 페이지는 속성만으로 먼저 생성 → ② `update-page`(`replace_content`)로 본문을 한글 리터럴 입력**하는 2단계가 안전하다. 속성 값도 생성 직후 반환값을 눈으로 확인한다.
