# Chapter 17: 데이터 캐싱과 낙관적 업데이트로 체감 속도를 높여라

## 핵심 질문

네트워크 탭의 서버 응답은 200ms인데 사용자는 클릭마다 1초를 기다린다 — 5분 전에 가져온 장바구니를 왜 또 요청하고, 좋아요 하나에 왜 로딩 스피너를 보여주는가? 목표는 "빠른 API"가 아니라 **"API를 덜 부르고, 부를 때도 기다리지 않는 아키텍처"**다. 캐싱·백그라운드 재검증·낙관적 업데이트는 각각 어떤 대기를 없애는가?

Ch16이 초기 로딩~인터랙티브(TTI)의 첫인상을 개선했다면, 이후의 모든 인터랙션 경험은 이 장이 결정한다. Ch3의 브라우저 HTTP 캐시가 정적 리소스(JS·CSS·이미지)를 **네트워크 레벨**에서 캐싱한다면, 이 장의 데이터 캐싱은 API 응답을 **애플리케이션 메모리 레벨**에서 관리한다.

## 1. 서버 상태 vs 클라이언트 상태

### 1.1 이름만 같은 두 상태

상품 목록에서 정렬 옵션을 바꾸면 즉시 반영되는데, 카테고리를 바꾸면 스피너가 돈다. 둘 다 "상태"를 바꾸는데 왜 다른가 — **상태가 어디에 있느냐**의 차이다.

- **클라이언트 상태**: 브라우저 메모리에 있고 앱이 완전히 제어한다. 검색 키워드, 필터 선택, 정렬 방식, 페이지네이션 위치, 뷰 토글. 동기적이고, 실패하지 않고, 일관성이 보장된다. `useState` 한 줄이면 끝.
- **서버 상태**: 서버에서 빌려온 복사본이다. 상품 목록, 재고, 할인 정보, 리뷰 평점. 네트워크 요청·로딩·에러가 따라오고, **시간이 지나면 오래된다(stale)** — 서버가 진실의 원천(source of truth)이고 클라이언트 데이터는 스냅숏일 뿐이다.

"상태"라고 부르는 이유: 한 번 가져오고 끝이 아니라 **로딩 중인지, 에러인지, 언제 갱신했는지, 아직 유효한지**의 메타 정보와 함께 지속 관리해야 하는 대상이기 때문이다.

### 1.2 서버 상태 관리의 5가지 복잡성

1. **중복 요청**: `ProductDetails`·`ReviewList`·`RelatedProducts`가 각자 `useEffect`로 같은 `/api/products/123`을 부르면 요청 3번 — 200ms 응답이 최대 600ms 대기, 50KB가 150KB 다운로드가 된다. 캐싱이 필요한데, 캐시를 어디에 두고 키를 어떻게 정할지부터 문제다.
2. **캐시 무효화**: 리뷰 하나를 작성하면 리뷰 목록·상품 정보(리뷰 개수·평점)·평점순 목록·내가 쓴 리뷰까지 무효화해야 한다. "관련된 캐시"를 어떻게 추적하나?
3. **경쟁 조건**: 검색창에 "노트북"을 타이핑하면 글자마다 요청이 나가는데, '노트북' 응답보다 '노트' 응답이 늦게 도착하면 잘못된 결과가 화면을 덮는다. 디바운싱·AbortController·최신 요청만 적용하는 로직을 전부 수동 구현해야 한다.
4. **로딩 상태 조율**: 상품+카테고리 두 요청이면 상태 변수가 6개(`loading`×2, `error`×2, `data`×2)로 불어난다.
5. **재검증 전략**: 언제 다시 가져올 것인가 — 시간 기반? 탭 포커스? 네트워크 재연결? API마다 다른 전략이 필요하다.

### 1.3 전통적인 상태 관리 도구의 한계

리덕스는 **클라이언트 상태용으로 설계**되어 서버 상태에는 근본적 한계가 있다.

- **보일러플레이트**: 액션 타입 3종 + 액션 생성자 + thunk + 리듀서 + 컴포넌트 = 60줄 이상. 리액트 쿼리로는 `useQuery` 10줄 — 캐싱·재검증·중복 요청 방지까지 자동이다.
- **캐싱 전략 부재**: 리덕스는 상태를 저장할 뿐 "언제 다시 불러올지"를 모른다. `lastFetched` 타임스탬프를 저장하고 비교하는 로직을 직접 짜야 하고, 그래봐야 시간 기반뿐 — 포커스·재연결 재검증은 또 별도다.
- **중복 요청 방지의 어려움**: `loading` 플래그 체크는 두 컴포넌트가 동시에 디스패치하면 뚫린다. 진짜 방지는 진행 중 Promise를 추적·재사용해야 한다. 리액트 쿼리는 같은 쿼리 키의 동시 호출을 하나의 요청으로 합치는 것이 기본이다.
- **뮤테이션 후 무효화**: 관련 액션을 수동으로 전부 디스패치해야 하고 하나라도 빠지면 오래된 화면이 남는다. 리액트 쿼리는 쿼리 키 패턴 무효화로 해결한다.
- **RTK Query**: 리덕스 팀의 답안으로 훌륭하지만 리덕스 의존이 한계 — 리덕스 없는 프로젝트에서 못 쓰고, 리덕스 개발자 도구에 서버 상태가 섞인다. 리액트 쿼리·SWR은 독립적이고 전용 개발자 도구가 있다.

> **핵심 통찰**: 서버 상태는 클라이언트 상태 관리 도구가 아니라 **서버 상태 전용 라이브러리**로 관리한다. 리덕스를 완전히 대체할 필요는 없다 — 서버 상태만 리액트 쿼리로 옮기고 UI 상태는 리덕스에 남겨도 된다.

## 2. SWR과 리액트 쿼리 캐싱 전략

### 2.1 SWR — stale-while-revalidate 패턴

버셀(Next.js 팀)이 만든 라이브러리. 이름 그대로 HTTP 캐시 헤더 `stale-while-revalidate`에서 왔다. 동작은 3단계: ① 캐시된 데이터를 **즉시** 보여준다 → ② 백그라운드에서 새 데이터를 가져온다 → ③ 도착하면 화면을 업데이트한다. 사용자는 1단계에서 이미 콘텐츠를 보고 있어 기다림을 느끼지 않는다.

```tsx
import useSWR from 'swr';

function ReviewList() {
  const { data: reviews } = useSWR('/api/reviews', fetcher);
  return <ul>{reviews?.map((review) => <li key={review.id}>{review.content}</li>)}</ul>;
}
```

포커스 재검증(`revalidateOnFocus`)·네트워크 재연결 재검증(`revalidateOnReconnect`)이 **기본으로 켜져 있다.** 설정이 적고 학습 곡선이 완만하다. 주의: 잠깐이라도 오래된 데이터가 보이므로 실시간성이 극도로 중요한 데이터(주식 가격·경매 입찰가)에는 전략 조정이 필요하다.

### 2.2 리액트 쿼리 — 쿼리 키와 캐시 3상태

TanStack이 관리하는 서버 상태 라이브러리(리액트 외 뷰·스벨트·솔리드 버전도 제공). SWR이 stale-while-revalidate에 집중한다면 리액트 쿼리는 **더 세밀한 캐시 제어**를 준다.

캐시는 **쿼리 키(배열)** 중심으로 동작한다 — `['products', category]`처럼. 키가 같으면 캐시를 공유하고 중복 요청이 없다(같은 키의 동시 호출은 같은 Promise를 공유).

**캐시 3상태**

- **fresh**: 신선한 상태. `staleTime` 동안 유지되며 재검증이 일어나지 않는다 — 같은 쿼리를 아무리 호출해도 캐시만 반환.
- **stale**: 오래된 상태. 버리지 않고 **캐시를 먼저 반환하되 백그라운드에서 재검증**한다(SWR 패턴과 동일). `staleTime` 경과 시 자동 전이.
- **inactive**: 모든 컴포넌트가 언마운트되어 아무도 안 쓰는 캐시. `gcTime`(기본 5분, v5에서 `cacheTime`→`gcTime` 개명) 동안 메모리에 보관 후 가비지 컬렉션 — 그 안에 재사용하면 재활용된다.

부가 기능: 요청 실패 시 **자동 재시도 3회 + 지수 백오프**(1초→2초→4초), 그리고 모든 쿼리의 fresh/stale/inactive 상태를 시각화하고 수동 무효화·재검증까지 가능한 **개발자 도구**(`ReactQueryDevtools`).

### 2.3 staleTime과 gcTime 설정

캐싱은 잘못 설정하면 독이다 — 너무 길면 오래된 데이터, 너무 짧으면 성능 이점 소멸. **데이터가 얼마나 자주 변하는가**로 정한다.

| 데이터 특성 | 예시 | staleTime |
|---|---|---|
| 거의 안 변함 | 국가 목록, 카테고리, 정책 문서 | 10분~1시간 (또는 `Infinity`) |
| 중간 | 상품 목록, 게시글, 프로필 | 30초~5분 |
| 자주 변함 | 재고, 좋아요 수, 실시간 알림 | 0(기본값)~몇 초 |

```ts
// 상품 목록: 목록↔상세 왕복 패턴에 맞춘 설정
const { data: products } = useQuery({
  queryKey: ['products', category],
  queryFn: () => fetchProducts(category),
  staleTime: 1000 * 60 * 2, // 2분간 fresh — 재검증 없이 캐시만
  gcTime: 1000 * 60 * 10,   // 언마운트 후 10분 보관 — 재방문 시 재활용
});

// 주식 가격: 항상 재검증 + 짧은 보관 + 폴링
const { data: stockPrice } = useQuery({
  queryKey: ['stock', symbol],
  queryFn: () => fetchStockPrice(symbol),
  staleTime: 0,
  gcTime: 1000 * 60,
  refetchInterval: 5000,
});
```

전역 기본값은 `QueryClient`의 `defaultOptions.queries`로 설정하고 특별한 쿼리만 오버라이드한다.

> **실무 팁 — 흔한 두 가지 설정 실수**: ① `staleTime`을 기본값 0으로 방치 — 매번 재검증이 일어나 네트워크 요청이 전혀 줄지 않는다. ② `gcTime < staleTime` — 캐시가 너무 빨리 사라져 재활용 기회를 잃는다. **항상 gcTime ≥ staleTime**이어야 컴포넌트 재마운트 시 캐시를 살릴 수 있다.

### 2.4 프리페칭 — 요청 전에 미리 가져오기

사용자 행동을 예측해 미리 데이터를 가져오면 클릭 시점에 이미 캐시가 준비되어 있다.

```tsx
// ① 마우스 오버 프리페칭
function ProductCard({ product }) {
  const queryClient = useQueryClient();
  const handleMouseEnter = () => {
    queryClient.prefetchQuery({
      queryKey: ['product', product.id],
      queryFn: () => fetchProductDetail(product.id),
      staleTime: 1000 * 60 * 5,
    });
  };
  return <div onMouseEnter={handleMouseEnter}>{/* ... */}</div>;
}
```

- **페이지네이션**: 현재 페이지를 보는 동안 다음 페이지를 프리페칭(`useEffect` + `hasNextPage` 확인). 현재 쿼리에는 `placeholderData: keepPreviousData`로 페이지 전환 중 이전 데이터를 유지한다.
- **탭 전환**: 활성 탭이 아닌 나머지 탭 데이터를 백그라운드 프리페칭 — 클릭 시 즉시 전환.
- **라우터 결합**: Next.js `<Link>`는 뷰포트 진입 시 페이지 코드를 자동 프리페칭한다. `onMouseEnter`에 데이터 프리페칭을 더하면 코드와 데이터가 동시에 준비된다.
- SWR은 `preload(key, fetcher)` 함수를 제공한다.

주의: **과도한 프리페칭은 대역폭 낭비**다. 다음 페이지 하나만(10페이지까지 미리 갖지 않기 — 대부분 2~3페이지만 보고 떠난다), 마우스가 올라간 항목만. 모바일 데이터 요금제도 고려해 `navigator.connection.effectiveType === '4g'`일 때만 활성화하는 가드를 둘 수 있다.

## 3. 캐시 무효화와 재검증

캐싱을 도입하면 곧바로 다음 문제가 온다: **캐시가 오래됐을 때 어떻게 할 것인가.** 무효화 전략이 없으면 캐싱은 독이 된다 — 상품을 담았는데 장바구니가 비어 보이고, 댓글을 썼는데 목록에 없다.

### 3.1 무효화 시점의 4원칙

1. **데이터를 변경하는 모든 작업 후 관련 캐시를 무효화한다.** `invalidateQueries`는 쿼리를 stale로 만든다 — 화면에서 사용 중인 쿼리는 즉시 재검증되고, 미사용 쿼리는 다음 사용 시 재검증된다.

```ts
const mutation = useMutation({
  mutationFn: (productId: string) =>
    fetch('/api/cart', { method: 'POST', body: JSON.stringify({ productId }) }),
  onSuccess: () => {
    queryClient.invalidateQueries({ queryKey: ['cart'] });
  },
});
```

2. **연관 캐시를 함께 무효화한다.** 리뷰 작성이면 리뷰 목록·상품 상세·리뷰 통계까지. 일일이 나열하기 번거로우면 **쿼리 키를 계층적으로 설계**한다 — `['products', category]`를 무효화하면 `['products', category, 'list']`·`['products', category, 'stats']`가 프리픽스 매칭으로 함께 무효화된다.
3. **불필요한 무효화를 피한다.** 프로필 이미지 변경에 상품 목록까지 무효화하지 않기. 정확히 그 키만 무효화하려면 `exact: true`.
4. **시간 기반 무효화를 고려한다.** 실시간성이 낮은 데이터(뉴스 목록)는 뮤테이션 연동 대신 `staleTime` + `refetchInterval` 5분으로 충분하다.

SWR은 `mutate('/api/cart')`로 무효화하고, 패턴 무효화는 predicate 함수(`(key) => key.startsWith('/api/products')`)를 쓴다.

> **실무 팁**: 가장 흔한 버그는 **무효화를 깜빡하는 것** — 변경했는데 새로고침해야 반영되는 증상이고 찾기도 어렵다. 해결은 뮤테이션 훅(`useAddToCart` 등)으로 무효화를 캡슐화해 사용처에서는 신경 쓰지 않게 하는 것이다.

### 3.2 백그라운드 재검증 4종

| 트리거 | 리액트 쿼리 | SWR | 용도 |
|---|---|---|---|
| 탭 포커스 | `refetchOnWindowFocus`(기본 true) | `revalidateOnFocus`(기본 true) | 이메일·장바구니 — 다른 탭에 갔다 돌아올 때 |
| 네트워크 재연결 | `refetchOnReconnect`(기본 true) | `revalidateOnReconnect`(기본 true) | 지하철→지상 시나리오 |
| 인터벌 폴링 | `refetchInterval` | `refreshInterval` | 대시보드·주가·스포츠 점수 |
| 마운트 | `refetchOnMount`(기본 true) | `revalidateOnMount` | 페이지 재진입 시 최신 보장 |

- 인터벌 폴링은 기본적으로 **포커스 있을 때만** 돈다(`refetchIntervalInBackground` / `refreshWhenHidden` 기본 false).
- 마운트 재검증은 `staleTime`이 남아 있으면(fresh) 건너뛴다 — 무시하고 강제하려면 `refetchOnMount: 'always'`.
- 정적 데이터는 `staleTime: Infinity` + 포커스 재검증 off로 모든 재검증을 끈다.
- 데이터별 조합 예: 상품 목록 = staleTime 5분 + 포커스/재연결만, 장바구니 = staleTime 1분 + 포커스, 알림 = staleTime 0 + 30초 폴링.
- 모바일 배려: 저속 네트워크(`effectiveType`이 2g 계열)면 폴링 간격을 늘리고, 배터리 사용 중이면 낮추는 **적응형 인터벌 훅**을 만들 수 있다(Battery API는 미지원 환경 try-catch).

### 3.3 뮤테이션 후 캐시 업데이트 — 직접 업데이트 vs 무효화

이미 아는 결과(좋아요 +1)를 굳이 서버에서 다시 가져올 필요가 없다 — `setQueryData`로 캐시를 직접 수정하면 요청이 줄고 반응이 즉각적이다.

- **직접 업데이트(`setQueryData`)**: 단순하고 예측 가능한 데이터 — 좋아요 수, 팔로우 상태, 북마크. 여러 캐시(상세+목록)를 동시에 수정할 수 있다.
- **무효화(`invalidateQueries`)**: 복잡하거나 서버에서 계산되는 데이터 — 댓글 작성 시 개수·최신순·통계가 모두 변하면 서버에서 다시 가져오는 것이 안전하다.

직접 업데이트의 함정은 **서버 값과의 불일치**다(다른 사용자도 좋아요를 눌러 실제는 +2). 해법: `onMutate`에서 낙관적으로 +1 → `onSuccess`에서 서버 응답으로 교체. 목록에 항목을 추가할 때는 **임시 ID 패턴** — `onMutate`에서 임시 ID로 추가하고 `onSuccess`에서 서버가 준 실제 ID로 교체한다.

## 4. 낙관적 업데이트로 즉각적인 피드백

### 4.1 개념 — 순서를 뒤집는다

- 전통 방식: 클릭 → 서버 요청 → **로딩 표시** → 응답 → UI 업데이트. 수백 ms의 지연을 사용자가 느끼고 INP가 나빠진다.
- 낙관적 업데이트: 클릭 → **UI 즉시 업데이트** → 백그라운드 요청 → 성공이면 그대로, 실패면 롤백. 피드백이 0ms — 네이티브 앱처럼 느껴진다.

"대부분의 요청은 성공한다"는 가정이 전제다. 99%가 성공한다면 99%에게 즉각적 경험을 주고 1%는 롤백으로 처리한다.

**적합**: ① 거의 실패하지 않는 작업(좋아요·북마크·팔로우 토글) ② 결과가 예측 가능한 작업(+1 확실) ③ 즉각 피드백이 중요한 인터랙션. **부적합**: ① 자주 실패하는 작업(결제·재고 확인) ② 서버 계산이 필요해 결과 예측 불가 ③ 실패 시 롤백이 어려운 연쇄 영향 작업.

### 4.2 리액트 쿼리 구현 — onMutate / onError / onSettled

```tsx
const toggleMutation = useMutation({
  mutationFn: (todoId: string) =>
    fetch(`/api/todos/${todoId}/toggle`, { method: 'POST' }),
  onMutate: async (todoId) => {
    // ① 진행 중인 재검증 취소 — 낙관적 업데이트를 덮어쓰지 않게
    await queryClient.cancelQueries({ queryKey: ['todos'] });
    // ② 이전 상태 저장(롤백용)
    const previousTodos = queryClient.getQueryData(['todos']);
    // ③ 캐시 즉시 업데이트 — 체크 표시가 바로 보인다
    queryClient.setQueryData(['todos'], (old: Todo[]) =>
      old.map((t) => (t.id === todoId ? { ...t, completed: !t.completed } : t)),
    );
    // ④ 롤백을 위해 context로 반환
    return { previousTodos };
  },
  onError: (err, todoId, context) => {
    // 실패 시 이전 상태로 롤백
    queryClient.setQueryData(['todos'], context.previousTodos);
  },
  onSettled: () => {
    // 성공/실패 무관하게 최종 재검증으로 서버와 동기화
    queryClient.invalidateQueries({ queryKey: ['todos'] });
  },
});
```

- 댓글 작성처럼 목록 추가는 임시 ID(`temp-...`) + `isPending: true` 플래그로 "서버 확인 전" 상태를 표시하고, `onSuccess`에서 실제 ID로 교체한다.
- 여러 캐시(게시글 상세 + 목록)를 낙관적으로 함께 업데이트할 때는 둘 다 `cancelQueries` → 둘 다 이전 값 저장 → `onError`에서 둘 다 롤백.
- SWR은 `mutate(key, newData, false)`(재검증 없이 캐시만) → 서버 요청 → `mutate(key)`(재검증)의 3단계다.

> **참고 — `cancelQueries`가 막는 것**<br><br>진행 중인 재검증/조회 응답이 방금 적용한 낙관적 업데이트를 **덮어쓰는 것**을 막는 용도다. 연속 뮤테이션(좋아요→취소 연타)의 순서 보장은 이것으로 해결되지 않는다 — 요청 타임스탬프/버전 비교, 서버 멱등성 처리 같은 별도의 순서 제어가 필요하다.

### 4.3 실패 시 롤백 처리

- **완전 롤백**: `onMutate`에서 저장한 이전 상태로 전부 되돌린다. 가장 안전하고 간단 — 대부분 이걸로 충분하다.
- **부분 롤백**: 여러 캐시 중 실패한 부분만 되돌린다. 복잡하지만 UX가 낫다.
- **재시도 후 롤백**: 일시적 네트워크 오류는 `retry: 3` + 지수 백오프로 재시도하고, 전부 실패했을 때만 롤백한다.

롤백 시 반드시 **사용자에게 알린다** — 조용히 되돌리면 혼란스럽다. 토스트가 흔하고, 에러 종류별 메시지를 나눈다(401 "로그인이 필요합니다" / 403 "권한이 없습니다" / 5xx "서버 오류"). 그리고 **롤백 전환을 부드럽게** — 낙관적 상태 동안 투명도를 낮춰 "아직 확정 전"을 표현하면 즉시 롤백의 깜빡임이 완화된다.

### 4.4 주의사항 6가지

1. **서버 응답과의 불일치**: 낙관적 +1 vs 실제 +2 — `onSuccess`에서 서버 응답으로 캐시를 교체해 최종 정합성을 확보한다.
2. **복잡한 관계 데이터**: 할 일 토글이 완료 수·진행 수·진행률에 연쇄되면 **관련 캐시를 전부 함께** 낙관적으로 업데이트한다. 하나라도 빠지면 UI가 서로 안 맞는다.
3. **네트워크 순서**: 좋아요→취소 연타에서 응답 순서가 뒤집힐 수 있다 — 요청에 타임스탬프를 실어 **더 오래된 응답은 무시**한다.
4. **실패율 높은 작업 금지**: 실패율 10% 이상이면 잦은 롤백으로 오히려 신뢰를 잃는다. 결제·계좌 이체·재고 확인은 `onMutate` 없이 서버 응답을 기다리고 로딩을 보여주는 게 낫다.
5. **권한 확인**: 서버가 403으로 거부하면 롤백 + 명확한 메시지("삭제 권한이 없습니다").
6. **오프라인 지원**(고급, PWA): `navigator.onLine`이 false면 낙관적 업데이트만 하고 요청을 큐에 저장 → `online` 이벤트에서 큐를 재처리. 오프라인 컨텍스트는 롤백하지 않는다.

|---|---|---|
| 리덕스/주스탄드로 서버 데이터 관리 | 캐싱·재검증·중복 방지를 전부 수동 구현 — 60줄 보일러플레이트 + 버그 | 서버 상태는 리액트 쿼리/SWR, UI 상태만 클라이언트 도구 |
| 컴포넌트마다 `useEffect` + fetch | 같은 API 중복 요청(3컴포넌트 = 3요청), 경쟁 조건 무방비 | 같은 쿼리 키로 `useQuery` — 요청 자동 공유 |
| `staleTime` 기본값 0 방치 | 매번 재검증 — 캐싱 도입 효과가 없음 | 데이터 변경 주기에 맞게 설정(중간 데이터 30초~5분) |
| `gcTime < staleTime` | 캐시가 너무 빨리 GC되어 재활용 기회 상실 | 항상 gcTime ≥ staleTime |
| 뮤테이션 후 무효화 누락 | 변경이 화면에 반영 안 됨 — 새로고침해야 보이는 버그 | 뮤테이션 훅으로 `invalidateQueries` 캡슐화 |
| 평평한 쿼리 키 설계 | 연관 캐시를 일일이 나열해야 하고 누락 발생 | 계층적 키(`['products', category, 'list']`)로 프리픽스 무효화 |
| 모든 변경에 광범위 무효화 | 캐싱 효과 소멸 — 성능 저하 | 정확한 키만, 필요 시 `exact: true` |
| 정적 데이터에 포커스 재검증 유지 | 국가 목록 등을 탭 전환마다 재요청 — 낭비 | `staleTime: Infinity` + 재검증 off |
| 낙관적 업데이트에서 `cancelQueries` 생략 | 진행 중 재검증 응답이 낙관적 값을 덮어씀 | `onMutate` 첫 줄에서 관련 쿼리 취소 |
| 롤백 시 이전 상태 미저장 | 실패해도 되돌릴 수 없음 — 데이터 불일치 | `onMutate`에서 `getQueryData` 저장 후 context 반환 |
| 조용한 롤백 | 사용자가 상태 변화를 이해 못 함 | 토스트 + 에러 종류별 메시지 |
| 결제에 낙관적 업데이트 적용 | 실패율 높은 작업의 잦은 롤백 — 신뢰 상실 | 중요 작업은 서버 응답 대기 + 로딩 표시 |
| 전 목록 항목 무차별 프리페칭 | 안 볼 데이터까지 다운로드 — 대역폭·요금 낭비 | 호버 항목/다음 페이지만, 4g일 때만 |

## 측정과 검증

- **네트워크 탭**: 도입 전후 중복 요청 제거 확인 — 같은 엔드포인트가 여러 번 나가는지, 페이지 재방문 시 요청이 생략되는지.
- **INP**: 사용자 액션 후 다음 페인트까지 200ms 이하 목표. 낙관적 업데이트 적용 액션(좋아요·토글)의 개선 폭 측정.
- **리액트 쿼리 개발자 도구**: 쿼리별 fresh/stale/inactive 상태, 캐시 히트 여부, 수동 무효화 테스트.
- **RUM**: web-vitals `onINP`로 실사용자 INP 분포 수집 — 낙관적 업데이트 전후 비교.
- **A/B 테스트**: 프리페칭·낙관적 업데이트의 체감 개선을 전환율 지표로 검증.

## 요약

- 서버는 빠른데 앱이 느린 이유: 중복 요청 + 불필요한 대기 + 페이지 전환마다 재로딩. 해법의 원칙은 **"캐싱 가능한 것은 캐싱하고, 대기 가능한 것은 낙관적으로 처리하라"**다.
- **서버 상태 ≠ 클라이언트 상태**: 서버 상태는 비동기·stale해짐·중복 요청·무효화 판단이 따라오는 별개의 관리 대상이다. 리덕스(클라이언트 상태용)로 다루면 보일러플레이트와 수동 캐싱 로직에 시달린다 — 전용 라이브러리(리액트 쿼리·SWR)를 쓴다.
- **SWR** = stale-while-revalidate 집중(캐시 즉시 표시 → 백그라운드 재검증), 단순·완만한 학습 곡선. **리액트 쿼리** = fresh/stale/inactive 3상태 + staleTime/gcTime 세밀 제어 + 자동 재시도 + 강력한 개발자 도구.
- 설정의 핵심: `staleTime`은 데이터 변경 주기(거의 안 변함 30분+ / 중간 30초~5분 / 실시간 0), `gcTime`은 재방문 재활용 기간 — **gcTime ≥ staleTime**. 기본값 0 방치가 최다 실수.
- **프리페칭**(호버·다음 페이지·탭 전환·라우터 결합)으로 클릭 전에 데이터를 준비한다 — 단 다음 페이지 하나만, 호버 항목만, 4g에서만.
- **무효화 4원칙**: 변경 직후 관련 캐시 무효화 / 계층적 쿼리 키로 연관 캐시 그룹 무효화 / 불필요한 무효화 회피(`exact`) / 시간 기반 고려. 무효화 누락이 가장 흔하고 찾기 어려운 버그 — 뮤테이션 훅으로 자동화한다.
- **백그라운드 재검증 4종**: 포커스·재연결(기본 on)·인터벌·마운트. 데이터 특성별로 조합하고 저속 네트워크·배터리에 적응형 간격을 적용한다.
- **낙관적 업데이트** = 순서 뒤집기(UI 먼저, 서버 나중). `onMutate`(취소+저장+업데이트) / `onError`(롤백) / `onSettled`(재검증)의 3훅 패턴. 적합한 곳(토글류·예측 가능·실패 드묾)에만 — 결제류는 금지. 롤백은 토스트로 알리고 서버 응답으로 최종 교체한다.
- 오늘 당장: API 호출을 `useQuery`로 감싸고, `staleTime` 5분을 주고, 좋아요 버튼에 낙관적 업데이트를 적용하라 — INP가 눈에 띄게 개선된다.

## 다른 챕터와의 관계

- **Ch3(브라우저 캐시 설계)**: HTTP 캐시(정적 리소스·네트워크 레벨)와 이 장의 데이터 캐싱(API 응답·메모리 레벨)은 같은 stale-while-revalidate 철학이 다른 계층에서 반복되는 것이다.
- **Ch11(서버로 로직 이동)·Ch16(하이드레이션)**: Ch16의 서버 컴포넌트 캐싱 트레이드오프(Next.js 15 fetch 기본 no-store)가 서버 측 캐싱이라면, 이 장은 클라이언트 측 서버-상태 캐싱이다. 하이드레이션이 첫인상, 데이터 캐싱은 그 이후의 지속적 경험을 담당한다.
- **Ch4(리소스 우선순위)**: 프리페칭의 철학(사용자 행동 예측)은 `<link rel="prefetch">`와 동일 — 대상이 리소스에서 데이터로 바뀌었을 뿐이다.
- **Ch18(자바스크립트 실행)**: INP 개선의 다음 단계 — 낙관적 업데이트로 네트워크 대기를 없앤 뒤에도 메인 스레드가 막히면 INP는 나쁘다. 긴 작업 분할을 다음 장이 다룬다.
- **Ch23(서드파티)**: 폴링 간격·프리페칭 가드 같은 네트워크 예산 관리 감각이 서드파티 리소스 통제로 확장된다.
