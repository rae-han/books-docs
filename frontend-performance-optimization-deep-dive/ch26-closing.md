# Chapter 26: 마치며

## 핵심 질문

25가지 기법을 다 배웠다 — 그래서 이제 뭘 해야 하지? 어디서부터 시작하고, 무엇을 우선하며, 어떻게 지속하는가? 이 장의 답은 기술이 아니라 태도다: **측정하고, 우선순위를 정하고, 지속 가능하게 유지하라.** 완벽한 최적화보다 측정 가능한 개선이 중요하고, 100가지 계획보다 3가지 실행이 낫다.

> **핵심 통찰**: 25가지 기법은 각각 독립적으로 효과가 있지만 **함께 적용될 때 시너지**를 낸다. LCP를 3초→1.5초로 만들려면 이미지 최적화만으로는 부족하다 — 프리로드+CDN+캐시가 함께 가야 한다. 성능 최적화는 단일 기법의 효과가 아니라 **복합적 개선의 누적 효과**다. 그리고 진짜 어려움은 기술이 아니라 **우선순위 결정** — 스타트업 MVP는 초기 로딩이, 대규모 SaaS는 반복 사용 시의 체감 속도가 우선이다. 정답은 하나가 아니다.

## 1. 어디서부터 시작할 것인가

투자 대비 효과가 큰 것부터 — 빠른 성과가 다음 최적화의 동력(모멘텀)이 된다. 어려운 것부터 시작하면 지치고 포기한다.

### 1.1 빠른 효과의 단기 개선 7가지

| 기법 | 효과 | 비용 |
|---|---|---|
| 이미지 WebP/AVIF 전환 | 페이로드 50%+가 이미지 — 20~50% 용량↓, LCP 30~50%↓ | Next.js `<Image>`·CDN 자동 변환이면 코드 무수정 |
| CDN 도입 | 로딩 30~60%↓(특히 해외 사용자) | DNS 설정 변경 수준, HTTP/2·3 활성화 확인 |
| 브라우저 캐시 설정 | 재방문 시 네트워크 요청 자체를 생략 | 정적 에셋 `max-age=31536000, immutable`+해시, HTML `no-cache`, API SWR — 5분 |
| 번들 분석 후 라이브러리 제거 | 수백 KB 단위 감축 | moment.js→date-fns/Intl, lodash 부분 임포트 — 트리 셰이킹보다 제거가 확실 |
| 브로틀리 활성화 | Gzip 대비 15~20% 추가 압축 | 서버 설정 몇 줄(정적은 레벨 11 사전 압축, 동적은 4~6) |
| preload/prefetch | 핵심 리소스 3~4개만으로 LCP 20~30%↓ | LCP 이미지·크리티컬 폰트 preload |
| async/defer | 렌더 블로킹 제거 — FCP·LCP 개선 | 서드파티 스크립트에 속성 추가 |

이 7가지만으로 대부분의 사이트는 라이트하우스 20~30점이 오른다. 구현은 며칠, 효과는 즉각적, 그리고 **숫자로 증명 가능**("LCP 3.2초→1.8초") — 팀과 경영진 설득의 근거가 된다.

### 1.2 중장기 투자 기법

단기 성과 후 근본 개선에 투자한다(1~2주~몇 달, 아키텍처 변경 수반 가능):

- **코드 스플리팅 전략**(Ch10): 라우트 자동 분할 너머의 컴포넌트 레벨 설계 — 청크 크기와 개수의 균형.
- **상태 범위 축소**(Ch22): 콜로케이션 + 안정적 키 + 측정 후 메모이제이션 — 상태 설계가 메모이제이션보다 효과적.
- **SSR·하이드레이션**(Ch16): 스트리밍·부분 하이드레이션·RSC — 단 서버 인프라·캐싱·에러 처리까지 고려해 신중히.
- **메모리 관리**(Ch19): SPA 장시간 사용의 안정성 — 힙 스냅샷·Performance Monitor.
- **60fps 애니메이션**(Ch21): transform/opacity·will-change·rAF — 16.67ms 예산.

### 1.3 상황별 우선순위

- **스타트업/MVP**: 첫 방문 이탈 방지 — LCP 3초·FCP 1초 이하. 이미지·CDN·캐시·번들에 집중, SSR·정교한 스플리팅은 나중에. "완벽한 성능"보다 "충분히 빠른 성능".
- **이커머스/콘텐츠**: LCP가 매출 직결 — WebP/AVIF·srcset·지연 로딩으로 상품 LCP 1.5초 이하 + **CLS 최소화**(구매 버튼이 밀리면 이탈).
- **SaaS/대시보드**: 반복 사용·긴 세션 — 초기 로딩보다 **INP와 메모리**. 캐시 적극 활용 + 데이터 캐싱(SWR/React Query) + 상태 범위 + 웹 워커. 1시간 사용해도 느려지지 않게.
- **글로벌/다국어**: 사용자 언어·지역에 맞는 코드만(Ch24) — 동적 번역 로드·Intl API·지역별 CDN.
- **레거시**: 전체 리팩터링 금지 — 번들 분석으로 low-hanging fruit(라이브러리 하나 제거로 30% 개선되기도) → 새 기능부터 올바른 패턴 → **파레토 법칙**(20% 노력으로 80% 효과).

## 2. 측정하지 않으면 개선할 수 없다

"느리다"는 느낌이 아니라 "LCP 3.8초, INP 400ms, 번들 2.3MB"라는 숫자로 현재를 파악한다. 측정 없이는 개선 여부도, 투자 방향도, 설득 근거도 없다.

### 2.1 핵심 웹 지표 수집 — Lab + Field

- **Lab(라이트하우스)**: 재현 가능, 디버깅용. **Field(RUM)**: 실제 사용자 경험 — 둘 다 봐야 한다.
- web-vitals 라이브러리로 onCLS·onLCP·onINP·onFCP·onTTFB를 수집해 애널리틱스/자체 서버(sendBeacon)로 전송(FID는 2024-03부로 INP로 대체). GA·Datadog RUM·Sentry·Vercel Analytics가 시각화·알림 제공.

### 2.2 성능 예산

"LCP 2.5초 이내, 번들 500KB 이내" 같은 기준선. 예산이 없으면 기능 추가마다 "조금쯤은 괜찮겠지"로 성능이 잠식된다.

- **라이트하우스 CI**: `lighthouserc.json`의 assertions(performance minScore 0.9, LCP maxNumericValue 2500, CLS 0.1, TBT 300 등)로 예산 초과 시 빌드 실패.
- **번들 예산**: 웹팩/비트의 chunkSizeWarningLimit, bundlesize 등으로 PR마다 확인.
- 예산은 **팀 전체가 공유하는 기준**이 되어야 한다 — 습관이 되면 성능 회귀가 배포되는 일이 사라진다.

### 2.3 데이터 기반 의사결정

가설("지연 로딩이 LCP를 개선할 것") → A/B 테스트(10% 적용) → 검증 → 배포 또는 다른 시도. 세그먼트 분석(모바일이 데스크톱보다 2배 느림, 지역별 편차)으로 우선순위 도출. **"이게 좋을 것 같아서"가 아니라 "측정 결과 가장 효과적이어서"** — 측정→개선→재측정 사이클이 빨라질수록 성능도 빨리 좋아진다.

## 3. 성능 최적화는 일회성이 아니라 문화다

한 번 개선해도 새 기능·라이브러리 업데이트·트래픽 증가로 다시 나빠진다. **"빠르게 만드는 것"보다 "빠른 상태를 유지하는 것"이 어렵다.**

- **새 기능마다 성능 질문**: 무거운 라이브러리 추가 전 대안 검토, 번들 확인, 코드 리뷰 체크 항목에 성능 포함("이 컴포넌트 매번 리렌더링되는데요?"가 자연스럽게 나오는 팀). 프레임워크 기능도 올바르게(클라이언트 컴포넌트 남용·`<img>` 직접 사용이면 이점 소멸).
- **정기 성능 리뷰**(월/분기): 서치 콘솔 핵심 웹 지표 리포트, 라이트하우스 CI 히스토리, 번들 크기 추이. **비난이 아니라 개선의 기회** — "왜 늘었나요?"가 아니라 "원인을 찾아 개선 방법을 논의합시다".
- **회귀 방지의 시스템화**: 배포 후 발견은 늦다 — CI/CD에 라이트하우스 CI(예산 초과 시 머지 차단) + 번들 분석 경고 + PR 자동 성능 코멘트. **"실수하지 말자"가 아니라 "실수를 시스템으로 막자"** — 사람은 실수하지만 자동화는 하지 않는다.
- **성능은 모두의 책임**: 백엔드(API 응답 시간)·디자이너(이미지 무게)·기획(서드파티 스크립트)·PM(비즈니스 영향 이해). 성과를 비즈니스 언어로 번역해 공유한다 — "LCP 1초 개선 = 전환율 5% 향상", "번들 절반 = 모바일 이탈률 20% 감소".

## 4. 다음 단계: 지속적인 학습

웹 성능은 계속 진화한다 — FID→INP 교체, View Transitions·Speculation Rules 등장, HTTP/3·AVIF 보급. **5년 전의 최적화가 지금은 안티 패턴일 수 있다.**

추천 리소스: **web.dev/learn**(구글 성능 학습)·**MDN Web Performance**·**Chrome for Developers**(신 API 최선단) / **DebugBear Blog**·**Perf Calendar**(매년 12월 전문가 아티클)·**web.dev Case Studies** / **PageSpeed Insights**·**WebPageTest**(지역·네트워크별 테스트, Filmstrip·Waterfall) / web-performance Slack·Frontend Focus 뉴스레터.

학습은 읽기로 끝나지 않는다 — 사이드 프로젝트에서 시도 → 효과 확인 → 실무 적용 → 팀 공유. 성능 최적화에 정답은 없다. 프로젝트·사용자·환경마다 다르므로 **우리 상황에 맞게 조정하고 검증**한다. 측정하고, 실험하고, 실패하고, 배운다 — 이 과정이 성장이다.

## 5. 마무리 — 사이클과 본질

책을 덮는 순간이 시작이다. 실행 사이클:

1. **측정**: 라이트하우스 + 핵심 웹 지표 수집 + 번들 분석 — 현재를 숫자로.
2. **우선순위**: 단기 개선 목록에서 가장 효과 클 것 하나.
3. **적용**: WebP 전환, CDN 도입, 라이브러리 제거…
4. **재측정**: 전후 비교, 효과를 숫자로 증명.
5. 반복 — LCP 5초→3초→2초→1.5초, 번들 3MB→2MB→1MB. 단계마다 UX·전환율·비즈니스 성과가 따라온다.

> **핵심 통찰**: 성능 최적화는 기술의 문제가 아니라 **사용자 경험의 문제**다. 사용자는 브로틀리도 코드 스플리팅도 모른다 — 그저 "빠르다/느리다"만 느낀다. 기다림 없이 콘텐츠를 보고, 클릭하면 즉시 반응하고, 레이아웃이 밀리지 않는 경험 — 이것이 본질이다. **빠르게 동작하는 경험 자체가 하나의 기능**이며, 때로는 눈에 보이는 기능보다 중요하다. 모든 최적화의 끝에는 사용자가 있다.

## 요약

- 이 책의 여정: 0부(왜) → 1부(네트워크·로딩) → 2부(번들·리소스) → 3부(렌더링·런타임) → 4부(프레임워크·차세대 표준). 25가지 기법은 **함께 적용될 때 시너지** — 단일 기법으로는 측정 도구에만 보이고 사용자는 체감하지 못할 수 있다.
- 시작은 **투자 대비 효과 순**: 이미지 포맷·CDN·캐시·라이브러리 제거·브로틀리·preload·async/defer의 7가지로 라이트하우스 20~30점을 며칠 만에 — 이 모멘텀으로 중장기(스플리팅·상태 설계·SSR·메모리·애니메이션)에 투자한다.
- 우선순위는 상황이 결정한다: MVP는 초기 로딩, 이커머스는 LCP+CLS, SaaS는 INP+메모리, 글로벌은 사용자별 리소스, 레거시는 파레토.
- **측정이 전부의 출발점**: Lab+Field 병행, 성능 예산을 CI로 강제, A/B와 세그먼트 분석으로 데이터 기반 의사결정. 측정→개선→재측정 사이클.
- 성능은 **문화**다: 새 기능마다 성능 질문, 정기 리뷰(비난 아닌 개선), 회귀를 시스템으로 차단, 전 직군의 책임 + 비즈니스 언어로 공유.
- 웹 성능은 계속 진화한다 — 지속 학습하되, 배운 것은 우리 상황에 맞게 검증한다. 그리고 잊지 말 것: **사용자는 "빠르다/느리다"만 느낀다. 기다리지 않게 만드는 것이 기능이다.**

## 다른 챕터와의 관계

- **전 챕터의 종합**: 단기 개선 7가지는 Ch12(이미지)·Ch1(CDN)·Ch3(캐시)·Ch9(불필요 리소스)·Ch2(압축)·Ch4(우선순위)·Ch6(async/defer)의 실행 요약이고, 중장기 목록은 Ch10·22·16·19·21로의 되돌아가기 지도다.
- **Ch0(왜 성능인가)**: 성능=비즈니스라는 출발점이 "성과를 비즈니스 언어로 번역하라"는 결론으로 완결된다.
- **Ch25(차세대 표준)**: "측정하고 판단하고 점진 도입"의 태도가 이 장의 문화론과 이어진다 — 기법은 바뀌어도 판단 기준은 남는다.
