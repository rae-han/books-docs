# Chapter 2: 네트워크 압축으로 전송 크기 줄이기

## 핵심 질문

CDN과 HTTP/3로 빠른 경로를 확보했다면, 그 위로 흐르는 데이터 자체는 어떻게 줄일 것인가? Gzip과 브로틀리는 무엇이 다르며 압축 레벨은 어디까지 올려야 하는가? 그리고 왜 어떤 파일은 압축하면 오히려 손해인가?

## 1. 리소스 압축의 원리와 효과

아무리 빠른 고속도로를 건설해도 트럭에 짐이 가득하면 여전히 시간이 오래 걸린다. 물리적 거리와 프로토콜 효율을 개선했다면 이제는 전송 크기 자체를 줄여야 한다.

압축이 네트워크 최적화에서 가장 확실한 ROI를 보이는 이유는 세 가지다. 첫째, 빌드 도구 플러그인 설정 몇 줄이면 끝난다. 둘째, 버셀·넷리파이·클라우드플레어 같은 정적 호스팅 서비스는 아예 기본으로 압축을 제공하므로 확인만 하면 된다. 셋째, **압축은 투명하게 작동한다**. 서버가 압축하고 브라우저가 압축 해제하는 과정이 자동으로 처리되므로 개발자는 HTML이나 자바스크립트 코드를 전혀 바꿀 필요가 없다.

### 1.1 압축 알고리즘 작동 방식

텍스트 데이터는 반복 패턴이 많다. 자바스크립트 코드에는 `function`, `return`, `const` 같은 키워드가 수없이 반복되고, JSON은 키 이름이 반복되며, HTML은 태그 구조가, CSS는 속성명과 값이 반복된다. 압축 알고리즘은 바로 이 반복을 찾아 짧은 참조로 대체한다.

**Gzip과 DEFLATE**

Gzip은 가장 널리 사용되는 압축 알고리즘으로, LZ77과 허프만 코딩(*Huffman Coding*)을 결합한 DEFLATE 알고리즘을 기반으로 한다.

- **LZ77**: 이전에 나온 데이터 패턴을 찾아 "N바이트 전으로 돌아가서 M바이트 복사"라는 형태로 참조한다. 예를 들어 `function test() { return 123; } function main() { return 456; }`에서 두 번째 `function`은 "40바이트 전에 나온 8글자"처럼 위치와 길이만 저장한다.
- **허프만 코딩**: 자주 나오는 문자를 짧은 비트로, 드문 문자를 긴 비트로 인코딩한다. 모스 부호와 비슷하게 영어에서 자주 쓰는 `e`는 3비트 정도로 짧게, 드문 `z`는 8비트 정도로 길게 표현한다.

**브로틀리의 두 가지 개선**

브로틀리는 구글이 2015년에 공개한 더 발전된 알고리즘으로, 현재 모든 주요 브라우저가 지원한다.

1. **더 넓은 참조 범위**: Gzip은 최근 32KB까지만 이전 패턴을 찾을 수 있지만 브로틀리는 최대 16MB까지 참조한다. 책을 읽으면서 앞 내용을 참조할 때, Gzip은 최근 몇 페이지만 기억하지만 브로틀리는 책 전체를 기억하는 것과 같다.
2. **웹 특화 정적 사전**: `<html>`, `<script>`, `function`, `background-color` 같은 흔한 패턴이 미리 사전에 등록돼 있다. Gzip은 파일 안에서 두 번 이상 나와야 압축 효과가 있지만, 브로틀리는 **한 번만 나와도** 사전 번호로 참조해 압축할 수 있다.

**실제 압축률 비교**

| 리소스 | Gzip 압축 후 | 브로틀리 압축 후 |
|---|---|---|
| jQuery 3.2.1 (JS) | 원본의 30%(70% 압축) | 원본의 25%(75% 압축) |
| Bootstrap (CSS) | 원본의 17%(83% 압축) | 원본의 13%(87% 압축) |
| 4.23MB JPEG 이미지 | 거의 압축 안 됨 | 거의 압축 안 됨 |

CSS는 속성명과 값의 반복이 많아 자바스크립트보다 압축률이 높다. 반면 JPEG는 자체 압축 포맷이므로 추가 압축 효과가 없다.

> **핵심 통찰**: Compression Ratio(압축 비율)는 `압축 후 크기 ÷ 압축 전 크기`로 계산하며 **값이 낮을수록 잘 압축된 것**이다. 0.3이면 원본의 30%로 줄었다는 의미다. "압축률 70%"와 "Compression Ratio 0.3"은 같은 상태를 가리키므로 지표를 읽을 때 방향을 혼동하지 않아야 한다.

### 1.2 압축 레벨과 트레이드오프

Gzip과 브로틀리 모두 레벨 1(최소 압축)부터 최대 레벨(Gzip은 9, 브로틀리는 11)까지 지원한다. 레벨이 높을수록 압축률은 좋아지지만 압축 시간과 CPU 사용량이 크게 증가한다.

압축은 수행 시점에 따라 두 가지로 나뉜다.

- **동적 압축(*dynamic compression*)**: 요청이 들어올 때마다 응답을 압축한다. 엔진엑스나 아파치가 지원하지만 레벨이 높으면 응답 지연이 발생한다. 브로틀리 레벨 11로 1MB 파일을 압축하는 데 수백 밀리초에서 수 초가 걸릴 수 있고, 이 시간이 모든 사용자 요청에 추가된다.
- **정적 압축(*static compression*)**: 빌드 타임에 미리 파일을 압축해둔다. `app.js`와 함께 `app.js.br`, `app.js.gz`를 만들어두면 웹 서버가 브라우저의 `Accept-Encoding` 헤더를 보고 압축된 파일을 그대로 전송한다. 런타임 압축 비용이 전혀 없고 최고 레벨을 쓸 수 있다.

**레벨별 특성 비교**

- **최고 레벨(브로틀리 11 vs Gzip 9)**: 텍스트 파일 기준 브로틀리 11이 Gzip 9보다 약 15~20% 더 작다. 하지만 소요 CPU 시간은 Gzip 9보다 수십 배 이상 길다. 빌드 타임에 한 번만 수행하는 정적 압축이라면 감수할 가치가 충분하지만 실시간 요청 처리에는 부적합하다.
- **중간 레벨(브로틀리 4~5 vs Gzip 6)**: 실시간 압축에서 권장되는 조합이다. 아카마이(Akamai) 연구에 따르면 브로틀리 레벨 4는 Gzip 레벨 6보다 파일 크기가 작으면서도 압축 속도는 더 빠르거나 비슷하다. 서버 부하를 크게 늘리지 않으면서 더 나은 압축률을 제공하는 균형점이다.
- **낮은 레벨(브로틀리 1 vs Gzip 1)**: 속도가 최우선이면 Gzip 1이 미세하게 더 빠를 수 있다. 하지만 폴 칼바노(Paul Calvano)의 벤치마크에 따르면 브로틀리는 모든 레벨에서 Gzip보다 나은 압축률을 제공하므로, 극도로 제한된 CPU 환경이 아니라면 낮은 레벨에서도 브로틀리가 유리하다.

**한계 수익 체감 지점**

브로틀리 압축 레벨별 실측 데이터를 보면 트레이드오프가 명확해진다.

| 레벨 | 압축 후 크기(바이트) | Compression Ratio | Gzip 대비 개선율 |
|---|---|---|---|
| 1 | 70,470 | 2.52 | -13% |
| 2 | 64,985 | 2.73 | -4% |
| 3 | 64,309 | 2.81 | -1% |
| 4 | 63,016 | 2.81 | -1% |
| 5 | 59,542 | 2.98 | +4% |
| 6 | 59,033 | 3.00 | +5% |
| 7 | 58,698 | 3.02 | +6% |
| 8 | 58,533 | 3.03 | +6% |
| 9 | 58,429 | 3.04 | +6% |
| 10 | 55,113 | 3.22 | +12% |
| 11 | 54,206 | 3.27 | +13% |

주목할 지점은 **레벨 5 이후의 한계 수익 체감**이다. 레벨 5에서 Gzip을 처음 능가하고, 레벨 6은 1% 개선에 그치며, 레벨 7~9는 6%로 정체된다. 레벨 10에서야 12%로 뛴다. 반면 압축 시간은 레벨이 올라갈수록 기하급수적으로 증가한다. 이것이 **동적 압축은 중간 레벨(4~5), 정적 압축은 최고 레벨(11)**을 권장하는 이유다.

압축 해제 속도는 두 알고리즘 모두 매우 빠르다. 브로틀리가 JS·CSS·JPEG 모두에서 Gzip보다 짧은 해제 시간을 기록했고, 절댓값 자체도 밀리초 미만이라 사용자 체감에는 거의 영향이 없다.

> **실무 팁**: 위 압축률·압축 시간 수치는 캐치포인트(Catchpoint)가 2017년 Intel i7-6600U(2.60GHz) + 8GB RAM 환경에서 측정한 값이다. Node.js 버전, 라이브러리 구현, CPU 세대에 따라 절댓값은 달라지므로 실제 서비스 환경에서 brotli/gzip 모듈을 직접 벤치마크해보는 것이 좋다.

**어떤 방식을 언제 쓸 것인가**

- **정적 압축 대상**: 자바스크립트, CSS처럼 빌드 타임에 내용이 결정되는 파일과 앱에 포함된 정적 JSON(설정, 사전 데이터). 항상 정적 압축을 우선한다.
- **동적 압축 대상**: 사용자별로 달라지는 HTML, 런타임 API가 반환하는 JSON 응답.
- **동적 압축 레벨 선택**: CPU 크레딧이 제한된 서버리스나 엣지 런타임에서는 브로틀리 3~4, Gzip 5. 전통적인 VM/컨테이너 환경에서는 브로틀리 5, Gzip 6이 기본값으로 무난하다.
- **CDN을 사용하는 경우**: 압축된 응답이 CDN에 캐싱되므로 첫 요청에만 압축 비용이 발생하고 이후에는 캐시된 압축 데이터가 전송된다.

### 1.3 압축 대상 선정과 Content-Encoding

모든 파일이 압축에 적합한 것은 아니다.

**압축 효과가 큰 리소스**: HTML, CSS, 자바스크립트, JSON, XML, SVG, 그리고 WOFF2가 아닌 TTF/OTF 웹폰트. 압축률이 높아 압축 오버헤드를 충분히 상쇄한다.

**재압축하면 안 되는 리소스**: JPEG·PNG·WebP·AVIF 같은 이미지 포맷은 자체 압축을 사용하고, MP4·WebM 같은 비디오도 이미 고도로 압축돼 있다. WOFF2 웹폰트는 브로틀리 기반 압축이 내장돼 있다. 이런 파일을 재압축하면 크기가 줄지 않거나 오히려 늘어나며 CPU만 낭비한다.

**Content-Encoding 협상 과정**

```
브라우저 ──▶ 요청 헤더:  Accept-Encoding: gzip, deflate, br
                          "나는 이 알고리즘들을 지원해"

서버     ──▶ 응답 헤더:  Content-Encoding: br
                          Vary: Accept-Encoding
                          "브로틀리로 압축해서 보낸다"

브라우저 ──▶ 자동으로 압축 해제 후 자바스크립트 엔진에 전달
```

이 과정은 완전히 투명하므로 개발자가 코드에서 신경 쓸 필요가 없다.

주의할 점이 두 가지 있다.

- **매우 작은 파일(1KB 미만)은 압축하지 않는다**: 압축 오버헤드가 크기 절감보다 클 수 있다. 엔진엑스는 `gzip_min_length` 설정으로 최소 크기를 지정한다. 보통 1KB 또는 256바이트를 기준으로 한다.
- **`Vary: Accept-Encoding` 헤더를 반드시 추가한다**: 이 헤더는 CDN과 브라우저 캐시에게 압축 여부에 따라 다른 버전이 존재함을 알린다. 빼먹으면 압축 버전이 압축을 지원하지 않는 클라이언트에 전달되어 깨진 응답이 보일 수 있다.

### 1.4 프런트엔드 개발자가 해야 할 압축 설정

**첫째, CDN 또는 호스팅 서비스의 자동 압축 확인하기**

실제로 많은 경우 별도 작업 없이 압축이 이미 적용돼 있다. 클라우드플레어는 브로틀리와 Gzip을 자동 적용하고, 버셀과 넷리파이도 배포 시 자동으로 처리한다. AWS 클라우드프런트는 "Compress Objects Automatically" 옵션을 켜면 활성화된다.

가장 먼저 할 일은 실제로 압축이 적용되고 있는지 확인하는 것이다. 크롬 개발자 도구의 Network 탭에서 리소스를 선택하고 Headers 탭에서 `Content-Encoding` 헤더를 찾는다. 설정이 꺼져 있다면 클라우드플레어는 `Speed → Optimization → Brotli`, AWS 클라우드프런트는 캐시 정책의 "Compress objects automatically"를 활성화한다.

이러한 서비스는 대부분 동적 압축을 쓰지만 충분히 빠른 레벨(브로틀리 4~5)이므로 실용적이다.

**둘째, 빌드 타임 정적 압축 설정하기**

CDN 없이 엔진엑스나 아파치를 직접 운영한다면 정적 압축이 최선이다. 빌드 타임에 한 번만 압축하면 되므로 최고 레벨로 압축해도 사용자 경험에 영향을 주지 않는다.

```ts
// vite.config.ts
import { defineConfig } from 'vite';
import viteCompression from 'vite-plugin-compression';

export default defineConfig({
  plugins: [
    // 브로틀리 압축
    viteCompression({
      algorithm: 'brotliCompress',
      ext: '.br',
      threshold: 1024,          // 1KB 이상만 압축
      deleteOriginFile: false,  // 원본 파일도 유지
    }),
    // Gzip 압축(폴백)
    viteCompression({
      algorithm: 'gzip',
      ext: '.gz',
      threshold: 1024,
    }),
  ],
});
```

```js
// webpack.config.js
const CompressionPlugin = require('compression-webpack-plugin');

module.exports = {
  plugins: [
    new CompressionPlugin({
      filename: '[path][base].br',
      algorithm: 'brotliCompress',
      test: /\.(js|css|html|svg)$/,
      compressionOptions: {
        level: 11, // 브로틀리 최고 레벨
      },
      threshold: 1024,
      minRatio: 0.8,
      deleteOriginalAssets: false,
    }),
    new CompressionPlugin({
      filename: '[path][base].gz',
      algorithm: 'gzip',
      test: /\.(js|css|html|svg)$/,
      threshold: 1024,
      minRatio: 0.8,
    }),
  ],
};
```

빌드 후 `dist/` 폴더에 `app.js`, `app.js.br`, `app.js.gz` 세 파일이 생성된다. **핵심은 이 세 파일을 모두 서버에 배포해야 한다는 것이다.** 원본만 올리고 압축 파일을 빠뜨려 정적 압축이 작동하지 않는 실수가 흔하다. `dist/` 폴더 전체를 배포하거나 CI/CD 파이프라인에서 `.br`과 `.gz`도 함께 업로드하도록 설정해야 한다.

HTML에서는 여전히 `<script src="/app.js"></script>`처럼 **원본 파일명을 참조한다.** 웹 서버가 `Accept-Encoding` 헤더를 보고 자동으로 `.br` → `.gz` → 원본 순으로 선택한다. 따라서 HTML·CSS·자바스크립트 어디에서도 `.br`이나 `.gz` 확장자를 명시할 필요가 없다.

**셋째, 웹 서버에서 정적 압축 파일을 제공하도록 설정하기**

빌드 도구가 압축 파일을 생성했더라도 웹 서버가 이를 전송하도록 설정해야 한다. 엔진엑스에서 정적 Gzip을 제공하려면 `ngx_http_gzip_static_module`이 포함된 빌드여야 하고, 브로틀리는 서드파티 모듈 `ngx_brotli` 설치가 필요하다.

```nginx
http {
    # 정적 압축 파일 제공(app.js.gz, app.js.br 등 미리 생성된 파일 사용)
    gzip_static on;      # .gz 파일이 있으면 우선 제공
    brotli_static on;    # .br 파일이 있으면 우선 제공(ngx_brotli 모듈 필요)

    # 동적 압축 설정(정적 파일이 없을 때 폴백)
    brotli on;                 # 실시간 브로틀리 압축 활성화
    brotli_comp_level 5;       # 동적 리소스는 중간 레벨 권장(0~11 범위)
    brotli_min_length 1024;    # 1KB 미만 파일은 압축하지 않음
    brotli_types text/plain text/css application/json application/javascript
                 text/xml application/xml application/xml+rss image/svg+xml;

    gzip on;                   # 브로틀리 미지원 브라우저용
    gzip_types text/plain text/css application/json application/javascript
               text/xml application/xml application/xml+rss text/javascript;
    gzip_min_length 1024;
    gzip_comp_level 6;         # 1~9 범위, 기본값은 1이므로 반드시 조정

    # Vary 헤더 추가(CDN/프락시에서 압축 버전별로 캐시 분리)
    gzip_vary on;
    # 참고: brotli 모듈은 Vary: Accept-Encoding을 자동 추가하므로 별도 설정 불필요
}
```

`text/html`은 압축 대상 MIME 타입에 기본 포함되고, 이미지는 제외한다. 아파치는 `mod_brotli`와 `mod_deflate` 모듈로 비슷하게 설정한다. 버셀이나 넷리파이는 전송 압축을 자동 제공하지만 사전 압축 파일 제공 여부는 서비스별 문서를 확인해야 한다.

**넷째, 압축 효과 검증하기**

크롬 개발자 도구의 Network 탭에서 리소스를 클릭하면 Headers 탭에서 확인할 수 있다.

```http
Content-Encoding: br
Content-Length: 54206
Vary: Accept-Encoding
```

Size 칼럼에는 두 숫자가 표시된다. `54.2 KB / 250 KB`처럼 나오는데 앞이 네트워크로 전송된 압축 크기, 뒤가 압축 해제 후 실제 크기다. 압축률은 간단한 나눗셈으로 계산한다.

```
54.2 ÷ 250 = 0.217 → 원본의 21.7%(78.3% 압축률)
```

> **실무 팁**: 압축률이 90% 이상(즉 10% 미만으로 줄었다면) 뭔가 잘못됐을 가능성이 높다. 이미 압축된 파일을 재압축했거나 잘못된 설정일 수 있으니 대상 MIME 타입을 다시 확인한다.

## 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|---|---|---|
| 빌드 산출물 중 원본 파일만 배포 | `.br`/`.gz`가 서버에 없으므로 정적 압축이 전혀 작동하지 않는다 | `dist/` 폴더 전체 배포 또는 CI/CD에서 압축 파일 업로드 확인 |
| HTML에서 `.br`/`.gz` 파일을 직접 참조 | 브라우저가 압축 해제를 못 하거나 폴백이 불가능해진다 | 항상 원본 파일명을 참조하고 서버가 협상하도록 둔다 |
| 동적 압축에 브로틀리 레벨 11 사용 | 모든 요청마다 수백 밀리초의 압축 지연이 추가된다 | 동적은 4~5, 정적은 11로 분리한다 |
| 이미지·동영상·WOFF2까지 압축 대상에 포함 | 크기가 줄지 않거나 오히려 늘고 CPU만 낭비한다 | `brotli_types`/`gzip_types`에서 제외한다 |
| `Vary: Accept-Encoding` 누락 | CDN이 압축 버전을 미지원 클라이언트에 전달해 깨진 응답이 나온다 | `gzip_vary on` 설정(브로틀리 모듈은 자동) |
| 1KB 미만 파일까지 압축 | 압축 오버헤드가 절감 효과를 넘어선다 | `gzip_min_length 1024` 설정 |
| `gzip_comp_level`을 기본값으로 방치 | 엔진엑스 기본값은 1이라 압축률이 낮다 | 동적 압축 기준 6으로 조정 |

## 측정과 검증

- **크롬 개발자 도구 Network 탭**: 리소스 선택 후 Headers 탭에서 `Content-Encoding: br` 또는 `gzip` 확인. Size 칼럼의 `전송 크기 / 원본 크기` 두 숫자로 압축률을 계산한다.
- **WebPageTest**: 여러 지역·여러 브라우저에서 압축이 제대로 적용되는지 검증한다. CDN 노드별로 설정이 다른 경우를 잡아낼 수 있다.
- **라이트하우스**: "Enable text compression" 항목이 압축 미적용 리소스를 찾아준다.
- **직접 벤치마크**: 프로덕션과 동일한 CPU·Node.js 버전에서 brotli/gzip 모듈의 레벨별 압축 시간을 측정해 동적 압축 레벨을 정한다.

## 체크리스트

**압축 적용 확인**

- [ ] CDN 사용 시: 자동 압축 활성화 확인(클라우드플레어, 버셀, 넷리파이는 기본 제공)
- [ ] 클라우드플레어 사용 시: `Speed → Optimization → Brotli` 설정 확인
- [ ] AWS 클라우드프런트 사용 시: Compress Objects Automatically 옵션 활성화
- [ ] 크롬 개발자 도구 Network 탭에서 `Content-Encoding: br` 또는 `gzip` 헤더 확인

**직접 서버 운영 시: 정적 압축 설정**

- [ ] 비트 또는 웹팩에 압축 플러그인 추가(`vite-plugin-compression`, `compression-webpack-plugin`)
- [ ] 빌드 산출물에 `.br`, `.gz` 파일이 생성되는지 확인
- [ ] 배포 시 압축 파일도 함께 업로드(`dist/` 폴더 전체 또는 CI/CD 설정)
- [ ] 엔진엑스에서 `gzip_static on`, `brotli_static on` 활성화
- [ ] 아파치 사용 시: `mod_brotli`, `mod_deflate` 모듈 활성화
- [ ] `Vary: Accept-Encoding` 헤더가 응답에 포함되는지 확인

**압축 레벨 선택**

- [ ] 정적 리소스(JS, CSS)는 빌드 타임에 브로틀리 레벨 11로 압축
- [ ] 동적 리소스(HTML, API)는 런타임에 브로틀리 레벨 4~5 또는 Gzip 레벨 6 사용(서버리스/엣지 환경이라면 브로틀리 3~4, Gzip 5로 조정)
- [ ] 이미 압축된 포맷(JPEG, PNG, MP4, WOFF2)은 압축 대상에서 제외
- [ ] 1KB 미만의 작은 파일은 압축하지 않도록 설정(`gzip_min_length 1024`)
- [ ] 이미지 CDN이나 미디어 서버가 별도로 있다면 동일 리소스를 중복 압축하지 않는지 확인

## 요약

- 압축은 전송 크기 자체를 60~80% 줄인다. 1MB 자바스크립트가 브로틀리로 250KB가 되면 Slow 4G(1.44Mbps) 환경에서 약 4.2초를 단축한다.
- Gzip은 LZ77(반복 패턴 참조) + 허프만 코딩(빈도 기반 비트 할당)의 DEFLATE 알고리즘을 쓴다.
- 브로틀리는 **참조 범위 확대(32KB → 16MB)**와 **웹 특화 정적 사전** 두 가지로 Gzip을 앞선다. 사전 덕분에 파일 안에서 한 번만 등장하는 패턴도 압축된다.
- 압축 레벨은 한계 수익 체감이 뚜렷하다. 브로틀리는 레벨 5부터 Gzip을 능가하고 레벨 7~9는 정체된다. 따라서 **정적 압축은 레벨 11, 동적 압축은 레벨 4~5**로 분리하는 것이 원칙이다.
- 정적 압축이 가능한 리소스(JS, CSS, 정적 JSON)는 항상 정적 압축을 우선한다. 사용자별 HTML과 API 응답만 동적 압축 대상이다.
- 이미 압축된 포맷(JPEG, PNG, WebP, MP4, WOFF2)의 재압축은 효과가 없거나 역효과다. 반드시 압축 대상에서 제외한다.
- `Content-Encoding`/`Accept-Encoding` 협상은 완전히 투명하다. HTML은 항상 원본 파일명을 참조하고 서버가 알아서 압축 버전을 고른다.
- `Vary: Accept-Encoding` 누락은 CDN 캐시 오염으로 이어지므로 반드시 설정한다.
- 압축 효과 검증은 Network 탭의 `Content-Encoding` 헤더와 Size 칼럼의 두 숫자만 보면 끝난다.

## 다른 챕터와의 관계

- **Ch1(네트워크 최적화)**: 이 장은 Ch1이 만든 "빠른 경로" 위에 "가벼운 짐"을 얹는다. CDN·HTTP/3와 압축은 함께 적용할 때 시너지가 가장 크다.
- **Ch3(브라우저 캐시)**: 압축한 응답을 CDN·브라우저가 어떻게 캐싱하는지, `Vary` 헤더가 캐시 키에 어떤 영향을 주는지를 본격적으로 다룬다. "가장 빠른 요청은 요청하지 않는 것"이 다음 단계다.
- **Ch12·13·14(이미지·동영상·폰트)**: 이 장에서 "재압축하면 안 되는 포맷"으로 제외한 리소스들은 각자의 전용 최적화 기법(포맷 선택, 비트레이트, 서브셋)이 따로 있다.
- **Ch25(차세대 웹 표준)**: 공유 압축 사전(Compression Dictionary Transport)으로 브로틀리 정적 사전의 개념을 사이트 전용 사전으로 확장하는 기법을 다룬다.
