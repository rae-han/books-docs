# 부록 A: 핵심 웹 지표의 역사

## 핵심 질문

이 책 전체를 관통하는 핵심 웹 지표(LCP·INP·CLS)는 어떻게 지금의 모습이 되었나? 2020년부터 약 5년의 진화 과정을 알면 **왜 지금 이 지표들이 중요한지, 앞으로 어떻게 변할지** 예측할 수 있다. (주요 참고: 애디 오스마니 — 크롬 팀 엔지니어링 리더 — 의 "The History of Core Web Vitals".)

## 1. 핵심 웹 지표 이전 — 성능 측정의 한계

- 2010년 구글 검색이 데스크톱에서 **사이트 속도를 랭킹 신호로 첫 도입**. 하지만 당시 지표들은 사용자 경험과 괴리:
  - `DOMContentLoaded`·`load` = 브라우저 내부의 기술적 시점일 뿐, 콘텐츠가 보이는 시점이 아님.
  - Speed Index = 시각적 완성도를 재지만 계산이 복잡하고 일관성 부족.
  - TTFB = 서버 응답만 측정, 클라이언트 렌더링 미고려.
- 2015년 **AMP**: 제한된 HTML + 사전 승인 JS로 빠른 로딩을 강제 — 효과는 있었지만 개발 자유 제한과 구글 종속 문제.
- 2018년 Speed Update로 모바일 랭킹에도 속도 반영 — 그러나 "무엇을 어떻게 개선하나"의 가이드 부재.

이 배경에서 구글은 "페이지가 로드되었다"가 아니라 **"사용자가 콘텐츠를 본다 / 입력에 반응한다 / 화면이 안정적이다"** 를 직접 측정하는 접근을 택했다.

## 2. 연대기

### 2020년 5월 — 탄생

핵심 웹 지표 공식 발표. 사용자 경험의 3차원을 대표하는 3개 지표:

| 지표 | 측정 대상 | 목표 | 포착하는 순간 |
|---|---|---|---|
| **LCP** | 주요 콘텐츠 표시 시점(로딩) | 2.5초 이하 | "얼마나 기다려야 하나" — 빈 화면·스피너의 좌절 |
| **FID** | 첫 상호작용~응답 지연(반응성) | 100ms 이하 | "클릭했는데 왜 반응이 없지" — 메인 스레드 바쁨 |
| **CLS** | 예기치 않은 레이아웃 이동(안정성) | 0.1 이하 | 광고 로드로 텍스트가 밀리고 버튼이 이동 |

수년간의 연구로 선정 — 객관적 수치와 사용자 인식의 상관관계 분석 결과, 이 셋이 만족도와 가장 강한 상관. **세 임곗값을 모두 충족하는 페이지는 로드 중 이탈 확률이 24% 낮았다.**

### 2021년 6월 — 검색 랭킹 통합

**페이지 경험 업데이트**로 핵심 웹 지표가 랭킹 요소에 포함. 두 가지 전환점:

1. 성능 최적화가 "여유 있으면 하는 것"에서 **SEO·마케팅 성과와 직결된 필수 요소**로 — 개발자가 경영진을 "SEO 점수 향상"이라는 비즈니스 언어로 설득 가능해졌고, 많은 기업이 분기 목표에 포함하기 시작.
2. **AMP 의존성 제거**: 모바일 톱 스토리 노출에 AMP가 필수였으나, 이후 좋은 지표를 가진 모든 페이지가 AMP 여부와 무관하게 추천 — 개방형 웹 표준으로의 신호.

### 2024년 3월 — FID → INP

**INP(Interaction to Next Paint, 목표 200ms)가 FID를 대체.** FID의 한계: 페이지 로드 직후 **첫** 상호작용만 측정 — 필터 변경·장바구니 추가·댓글 작성 등 이후 상호작용의 지연을 포착하지 못했고, 실제로 많은 앱은 첫 상호작용보다 이후가 더 느렸다. INP는 **페이지의 모든 상호작용**을 평가해 전체 여정의 일관된 응답성을 요구한다 — 무거운 JS 실행, 비최적 이벤트 핸들러, 메인 스레드 블로킹이 모두 직접 반영된다.

## 3. 생태계의 변화와 성과

- **누적 효과**: 2023년 한 해에만 사용자들의 페이지 로드 대기 시간이 10,000년+ 절약, 상호작용 대기 1,200년+ 절약 — 2024년에는 약 30,000년 규모로 증가.
- **비즈니스 사례**: 이코노믹 타임스(INP 1초→257ms → 페이지 뷰 +43%, 이탈률 -50%), 레드버스(CLS·TTI 개선 → 모바일 전환율 +80~100%), 미쇼(LCP 6.9→2.5초 → 이탈률 -17%, 전환율 +3%), 윅스(지표 통과율 4%→33%+).
- **프레임워크·CMS 대응**: 워드프레스(웹의 ~43% 구동) 6.3에서 블록 테마 LCP 27% 개선, Next.js `next/script`, 앵귤러 `NgOptimizedImage`. 2022년 CWV 통과율 — Next.js 20.4%→27.3%, 앵귤러 7.6%→13.2%.
- **브라우저 자체 최적화**(코드 수정 없이 자동 적용): 크롬이 뷰포트 내 첫 5개 이미지 우선순위 자동 상향(LCP 3.1→2.5초), 백/포워드 캐시(즉각적 뒤로 가기), Prerender2(검색창 예측으로 LCP 500~700ms 개선).
- **현재**: 2025년 9월 기준 전체 웹사이트의 **53%가 모든 기준 충족**(2020년 초 ~30%). 개발자의 ~51%가 지표를 추적하며, CrUX·BigQuery로 누구나 공개 데이터 접근 가능.

## 4. 앞으로의 방향

- **새 지표 연구**: SPA 소프트 내비게이션 측정을 위한 Soft Navigation API 실험, 애니메이션 부드러움 지표 연구 중. 구글 내부 지표가 아니라 **웹 표준 커뮤니티와 함께 만드는 개방형 표준**.
- **2025년 측정 방식 개선**: TTFB가 2월부터 103 Early Hints 응답 포함, LCP는 크로스 오리진 이미지 정확도 개선, INP는 텍스트 선택 중 스크롤 가장자리 상호작용 제외.
- **크로스 브라우저 확대**: 파이어폭스 144(2025-10)가 INP 공식 지원, 사파리도 기술 미리보기에서 LCP·INP 테스트 — 크롬 전용이던 CrUX 데이터가 더 포괄적으로.

## 요약

- 핵심 웹 지표는 "기술적 로드 시점"이 아니라 **사용자 경험의 3차원**(로딩 LCP·반응성 FID→INP·안정성 CLS)을 직접 측정하려는 5년의 진화다.
- 연표: 2010 속도 랭킹 신호 → 2015 AMP → **2020 CWV 탄생** → **2021 검색 랭킹 통합**(성능 = 비즈니스, AMP 종속 해제) → **2024 FID→INP**(첫 상호작용 → 모든 상호작용) → 2025 측정 개선 + 파이어폭스·사파리 확대.
- 효과는 실측된다: 이탈 확률 24% 감소, 기업 사례들의 전환율·이탈률 개선, 웹 전체 통과율 30%→53%. 브라우저·프레임워크·개발자 인식이 함께 만든 결과다.
- 이 책의 모든 기법은 이 역사 위에 있다 — 핵심 웹 지표는 숫자가 아니라 **사용자 경험 개선과 비즈니스 성과를 잇는 공통 언어**다.

## 다른 챕터와의 관계

- **Ch0(왜 성능인가)**: 성능=비즈니스라는 책의 전제가 이 부록의 역사(2021 랭킹 통합, 기업 사례)로 뒷받침된다.
- **Ch16~21(3부)**: FID→INP 전환의 의미 — 하이드레이션·긴 작업·메모리·애니메이션 등 "로드 이후"의 최적화가 중요해진 배경이다.
- **Ch25(차세대 표준)**: Soft Navigation API·측정 방식 개선이 "지표도 진화한다"는 이 부록의 결론과 만난다 — 판단 기준을 갖추고 변화를 따라가는 것이 개발자의 몫이다.
