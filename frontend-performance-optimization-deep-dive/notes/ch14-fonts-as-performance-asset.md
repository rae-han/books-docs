# Chapter 14: 폰트는 디자인보다 성능 자산으로 관리하라

## 핵심 질문

약 87%의 웹사이트가 웹 폰트를 쓰고, 한글 완성형 폰트는 2~5MB에 달한다. 폰트를 "디자이너가 고른 파일을 `@font-face`로 추가"하는 디자인 자산으로만 다루면 무슨 일이 생기는가? FOIT·FOUT·CLS를 만들지 않으면서 브랜드 폰트를 빠르게 보여주는 로딩 전략은 무엇인가?

## 1. FOIT, FOUT, FOFT - 폰트 로딩의 세 가지 문제

웹 폰트를 로드할 때 브라우저는 "폰트가 도착하기 전에 텍스트를 어떻게 표시할 것인가"를 선택해야 하고, 그 선택에 따라 사용자는 세 문제 중 하나를 겪는다.

- **FOIT(*Flash of Invisible Text*)**: 폰트 로드 중 텍스트를 아예 숨기는 현상. 크롬·파이어폭스는 **최대 3초** 동안 숨기고, **사파리는 타임아웃이 없어 무한정** 기다린다. 텍스트가 주요 콘텐츠라면 FCP·LCP가 그만큼 지연된다.
- **FOUT(*Flash of Unstyled Text*)**: 폴백 폰트로 먼저 표시한 뒤 웹 폰트로 교체되며 깜빡이는 현상. FOIT보다는 낫지만 **폴백과 웹 폰트의 메트릭 차이만큼 레이아웃이 이동해 CLS가 발생**한다(Arial 100px 높이 문단이 Roboto로 바뀌며 110px가 되면 아래 콘텐츠가 10px 밀린다).
- **FOFT(*Flash of Faux Text*)**: Regular만 로드되고 Bold/Italic이 없을 때 브라우저가 만드는 **synthetic bold/italic**(픽셀 확장·기울임)이 나중에 진짜 폰트로 교체되는 현상. synthetic bold는 글자가 뭉개져 가독성이 떨어진다. 해결은 모든 변형을 명시적으로 로드하는 것 - 하지만 요청이 3배가 되므로 **가변 폰트가 더 나은 답**이다(4절).

| 브라우저 | 타임아웃 | FOIT 기간 |
|---|---|---|
| 크롬/파이어폭스 | 3초 | 최대 3초 |
| 사파리 | 없음 | **무한정** |
| 엣지(크로미움) | 3초 | 최대 3초 |

> **핵심 통찰**: 성능 지표와의 관계 - **FOIT → FCP·LCP 지연**(텍스트가 LCP 요소면 직접 타격), **FOUT → CLS**(메트릭 차이가 클수록 커짐). 사파리의 무한 FOIT 때문에라도 `font-display`를 반드시 명시해야 하며, 라이트하우스는 미설정 폰트에 "Ensure text remains visible during webfont load" 경고를 표시한다.

## 2. font-display 속성으로 로딩 전략을 제어하라

`font-display`는 폰트 로딩을 **차단 기간(Block, 텍스트 숨김) → 교체 기간(Swap, 폴백 표시 후 교체) → 실패 기간(Failure, 폴백 유지)**으로 나누어 제어한다.

| 값 | 차단 기간 | 교체 기간 | FOIT | FOUT | CLS 위험 | 사용 사례 |
|---|---|---|---|---|---|---|
| `auto` | ~3초 | 무한 | 예 | 예 | 높음 | 권장하지 않음 |
| `block` | ~3초 | 무한 | 예 | 예 | 높음 | 브랜드 로고, 아이콘 폰트 |
| `swap` | **0** | 무한 | 없음 | 예 | 중간 | **일반 텍스트(가장 일반적)** |
| `fallback` | ~100ms | ~3초 | 짧음 | 제한적 | 낮음 | 빠른 네트워크에서만 폰트 적용 |
| `optional` | ~100ms | **0** | 짧음 | **없음** | **없음** | CLS 절대 방지, 성능 우선 |

### 2.1 swap - 텍스트를 즉시 보여주는 전략

차단 기간이 0이므로 **폰트 다운로드가 시작되는 즉시 폴백 폰트로 텍스트를 표시**한다. FOIT가 없어 FCP·LCP가 폰트 로딩과 무관해진다. 구글 폰트의 기본값이며 라이트하우스도 권장한다.

```css
@font-face {
  font-family: 'BodyFont';
  src: url('/fonts/body.woff2') format('woff2');
  font-display: swap; /* FOIT 없음, 즉시 폴백 표시 */
}
```

트레이드오프는 FOUT로 인한 CLS다. 완화책은 **폴백 폰트 메트릭 조정**(6절)이다.

### 2.2 optional - 레이아웃 시프트를 차단하는 전략

약 100ms만 기다리고, 이 안에 폰트가 도착하지 않으면 폴백을 쓰며 **이후 절대 교체하지 않는다**(교체 기간 0). FOUT가 없으므로 폰트 교체로 인한 CLS도 없다. 브라우저는 네트워크 상태를 보고 느린 연결에서는 아예 다운로드를 포기할 수도 있으며, 캐시에 있으면 즉시 쓴다.

트레이드오프는 명확하다 - **느린 네트워크에서는 웹 폰트가 전혀 적용되지 않는다.** "디자인을 희생하고 성능을 선택한다"는 의사결정이다. CLS를 절대적으로 지켜야 하는 뉴스·블로그, 시스템 폰트로도 충분한 콘텐츠, 신흥 시장 대상 서비스에 적합하다.

### 2.3 콘텐츠 유형별 권장값

| 콘텐츠 유형 | 권장 값 | 이유 | CLS 완화 전략 |
|---|---|---|---|
| 본문 텍스트 | `swap` | FCP/LCP 즉시 개선, 가독성 우선 | 시스템 폰트 스택 |
| 헤드라인 | `swap` | 브랜드 폰트 확실히 적용 | 폴백 폰트 크기 조정(6절) |
| 블로그 글 | `optional` | 폰트 CLS 방지, 시스템 폰트로도 충분 | 폰트 교체 없음 |
| 브랜드 로고 | `block` | 정확한 렌더링 필수 | 없음(FOIT 허용) |
| 아이콘 폰트 | `block` | 아이콘 깨짐 방지 | SVG 아이콘으로 대체 검토 |
| 장식용 텍스트 | `optional` | 필수 아님, 성능 우선 | 폰트 교체 없음 |
| 뉴스 사이트 | `optional` | 빠른 FCP + 폰트 CLS 방지 | 폰트 교체 없음 |
| 이커머스 제품명 | `swap` | 브랜드 일관성 + 즉시 가독성 | 폴백 폰트 크기 조정 |

> **핵심 통찰**: **모든 폰트에 같은 전략을 쓰지 않는다.** 본문·헤드라인은 `swap`, 장식용은 `optional`, 아이콘은 `block`의 하이브리드가 FCP·LCP·CLS 모두를 균형 있게 개선한다. 성능 지표 기준으로는 - FCP/LCP 우선이면 `swap`/`optional`, **CLS 우선이면 `optional`**, 디자인 일관성 우선이면 `swap`/`block`. 시스템 폰트 스택(`-apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, sans-serif`)을 쓰면 폰트 문제가 원천적으로 사라진다는 선택지도 있다.

## 3. 서브셋 폰트로 용량을 대폭 줄여라

### 3.1 왜 한글 폰트가 문제인가

영문은 대소문자·숫자·특수문자를 합쳐 200자 내외지만 **한글 완성형은 11,172자(가~힣)**다. Noto Sans KR 완전판은 약 3.5MB인데, **가장 많이 쓰이는 2,350자(KS X 1001) 서브셋은 400KB - 88% 감소**다. 일반 웹사이트 콘텐츠의 99% 이상을 커버한다.

| 서브셋 유형 | 문자 수 | 파일 크기 | 완성형 대비 | 사용 사례 |
|---|---|---|---|---|
| `text=` 파라미터(10자) | 10 | 15KB | 0.4% | 로고, 고정 헤더 |
| **2,350자 서브셋** | 2,350 | **400KB** | 11% | **일반 웹사이트(최적 균형점)** |
| KS X 1001 확장(4,888자) | 4,888 | 800KB | 23% | 전문 용어 많은 사이트 |
| 완성형 전체 | 11,172 | 3.5MB | 100% | 사용자 입력 많은 서비스 |
| 자모 포함 완전판 | 17,388 | 5.2MB | 149% | 에디터(비추천) |

3.5MB는 Slow 4G에서 약 19.4초, 400KB는 약 2.2초다. 대역폭 관점에서도 월 방문 10만 기준 월 270GB를 절약한다. 단점은 서브셋에 없는 문자가 폴백 폰트로 렌더링된다는 것 - 사용자 입력이 많은 서비스는 더 큰 서브셋이나 하이브리드 전략을 쓴다.

### 3.2 적용 전략

실무에서 폰트 파일을 직접 가공할 필요는 거의 없다. ① **구글 폰트**는 `unicode-range`로 나뉜 서브셋을 자동 제공하고, 고정 텍스트에는 `text=` 파라미터로 초소형 폰트를 받을 수 있다(텍스트가 절대 안 변하는 경우만). ② **한글 웹폰트 서비스**(눈누, Spoqa Han Sans 등)는 이미 서브셋된 WOFF2를 제공한다. ③ **자체 호스팅**은 이미 서브셋된 파일을 받아 자기 CDN에 올리는 방식으로, 추가 DNS 조회가 없고 캐싱을 완전히 제어한다.

> 실전 사례: 한 뉴스 사이트가 Noto Sans KR 완전판(3.5MB)을 2,350자 서브셋(400KB) + 자체 CDN으로 교체 → **FCP 3.2초 → 1.6초(50% 개선), LCP 4.1초 → 2.3초, CDN 비용 87% 절감.**

서브셋 적용 후에는 반드시 여러 페이지를 샘플링해 드문 문자 렌더링을 테스트하고, 특히 사용자 입력 영역(댓글·검색)을 확인한다. 콘텐츠가 계속 추가되는 사이트는 4,888자처럼 여유 있는 서브셋이 안전하다.

### 3.3 unicode-range로 동적 로딩

`unicode-range`는 해당 `@font-face`가 담당할 문자 범위를 지정하며, **브라우저는 페이지에 그 범위의 문자가 실제로 있을 때만 폰트를 다운로드한다.**

```css
/* 라틴 문자 - 약 50KB */
@font-face {
  font-family: 'CustomFont';
  src: url('/fonts/custom-latin.woff2') format('woff2');
  unicode-range: U+0000-00FF, U+2000-206F, U+20AC, U+2122;
  font-display: swap;
}

/* 한글 기본(2,350자) - 약 400KB */
@font-face {
  font-family: 'CustomFont';
  src: url('/fonts/custom-korean-basic.woff2') format('woff2');
  unicode-range: U+AC00-D0FF, U+D200-D4FF, U+D600-D7A3; /* 예시 범위 */
  font-display: swap;
}

/* 한글 확장(드문 문자) - 약 2MB, 필요할 때만 로드 */
@font-face {
  font-family: 'CustomFont';
  src: url('/fonts/custom-korean-extended.woff2') format('woff2');
  unicode-range: U+D100-D1FF, U+D500-D5FF;
  font-display: swap;
}
```

영문만 있는 페이지는 50KB, 일반 한글은 450KB, 드문 한글이 있을 때만 2.45MB - **페이지 콘텐츠에 따라 다운로드 크기가 자동 조절**된다. 구글 폰트가 Noto Sans KR을 100개 이상의 작은 서브셋으로 쪼개 제공하는 것이 바로 이 방식이다.

> **실무 팁**: ① **범위가 겹치지 않게** 한다(겹치면 어느 파일을 쓸지 모호). ② `unicode-range`는 **다운로드 여부만 제어하고 렌더링은 제어하지 않는다** - `font-display: swap`을 함께 쓴다. 실전 사례로 3단계 서브셋(라틴 50KB/기본 400KB/확장 2MB) 적용 후 평균 폰트 다운로드가 3.5MB → 520KB로 85% 절감됐다.

## 4. 가변 폰트로 HTTP 요청을 줄여라

### 4.1 개념과 장점

가변 폰트(variable font)는 **하나의 파일에 모든 weight·width 변형을 담는다.** 가장 얇은(100)과 가장 두꺼운(900) 글리프를 저장하고 그 사이 값은 수학적 보간으로 실시간 계산한다. `wght`(weight)·`wdth`(width)·`slnt`(slant) 같은 축(axis)으로 제어한다.

- **HTTP 요청 감소**: weight 6개 = 정적 폰트 6요청 → 가변 폰트 **1요청**
- **파일 크기 절감**: 직관과 반대로 가변 폰트가 더 작다. weight가 많을수록 차이가 커진다.
- **디자인 자유도**: 450, 625 같은 중간값을 자유롭게 사용, 반응형 weight 미세 조정 가능

| 폰트 | 정적(3 weights) | 정적(6 weights) | 가변(100~900) | 절감률(6기준) |
|---|---|---|---|---|
| Roboto(Latin) | 135KB | 270KB | 120KB | 56% |
| Inter(Latin) | 140KB | 280KB | 140KB | 50% |
| Pretendard(한글) | 1,260KB | 2,520KB | 500KB | **80%** |
| Noto Sans KR | 1,200KB | 2,400KB | 600KB | 75% |

한글은 글리프 수가 많아 보간의 효과가 더 크다. **3개 이하 weight면 정적이 작을 수도 있지만 4개 이상부터는 가변 폰트가 확실히 유리**하다.

### 4.2 실전 적용

```css
/* 가변 폰트 선언 */
@font-face {
  font-family: 'Inter var';
  src: url('/fonts/Inter-Variable.woff2') format('woff2-variations');
  font-weight: 100 900; /* 지원하는 weight 범위 */
  font-display: swap;
}

body { font-family: 'Inter var', sans-serif; font-weight: 400; }
h1 { font-weight: 700; }
.subtitle { font-weight: 450; } /* 중간값도 가능 */
```

`format('woff2-variations')`는 미지원 브라우저가 선언을 무시하게 하는 안전장치다(지원율 95%+, 크롬 62+/사파리 11+). 폴백은 두 가지: ① 가변 폰트 선언 뒤에 정적 폰트 `@font-face`를 추가(점진적 향상, 서버 용량 증가), ② 가변 폰트만 제공하고 구형 브라우저는 시스템 폰트로.

축 제어는 `font-weight`·`font-stretch`가 표준적이고, 여러 축 동시 제어에는 `font-variation-settings: 'wght' 450, 'wdth' 95`를 쓴다. 구글 폰트에서는 `wght@100..900` 표기(점 두 개가 범위)가 가변 폰트다.

> 실전 사례: 한 디자인 시스템이 10단계 weight를 정적 폰트(10개 파일 약 450KB) 대신 Inter Variable(140KB, 1요청)로 구현 → **FCP 2.1초 → 1.4초(33% 개선)** + 디자이너의 정밀한 weight 제어.

## 5. 폰트 프리로드로 로딩을 앞당겨라

### 5.1 왜 프리로드인가

웹폰트는 CSS 안에 숨어 있어 발견이 늦다: `HTML → CSS 링크 발견 → CSS 다운로드 → @font-face 파싱 → 폰트 다운로드`. 느린 네트워크에서 이 지연이 1~2초에 달한다. `<link rel="preload">`는 CSS를 기다리지 않고 즉시 폰트를 최고 우선순위로 다운로드한다.

```html
<head>
  <!-- 폰트 프리로드: CSS보다 먼저 로드됨 -->
  <link rel="preload" href="/fonts/NotoSansKR-Regular.woff2"
        as="font" type="font/woff2" crossorigin />
  <link rel="stylesheet" href="/styles.css" />
</head>
```

실측으로 자체 호스팅 + 프리로드 전환 후 로드 시간이 6초 → 3초로 50% 단축된 사례가 있다. 페이지 로드가 1→3초로 늘면 이탈률이 32%, 1→5초면 90% 증가한다는 구글 연구를 고려하면 폰트 프리로드는 비즈니스 지표에 직결된다.

### 5.2 필수 속성: crossorigin과 type

> **핵심 통찰 - 폰트 프리로드 최다 실수**: **`crossorigin`을 빠뜨리면 폰트가 두 번 다운로드된다.** 폰트는 같은 도메인이어도 브라우저가 "익명 CORS 요청"으로 처리하는 리소스다. `crossorigin` 없는 프리로드는 non-CORS 요청이 되고, CSS의 `@font-face`는 CORS 요청이라 **브라우저가 둘을 별개로 보고 각각 다운로드한다.** Network 탭에서 같은 폰트가 두 번 보이면 이 문제다. 값 없이 `crossorigin`만 쓰면 `anonymous`와 동일하다.

`type="font/woff2"`는 미지원 브라우저의 쓸모없는 다운로드를 막는다(모던 브라우저는 모두 WOFF2를 지원하므로 실질 영향은 작지만 표준 권장).

### 5.3 optional + preload 조합

`font-display: optional`(100ms 차단)과 프리로드를 결합하면 **100ms 안에 폰트가 도착할 확률이 크게 올라간다.**

- **빠른 네트워크**: 폰트가 100ms 안에 도착 → 웹폰트 표시
- **느린 네트워크**: 시스템 폰트로 즉시 표시, **레이아웃 시프트 없음**
- **재방문**: 캐시로 즉시 웹폰트

이 조합이 "폰트 교체 CLS가 0"인 이상적 경험을 만든다. 단 브랜딩이 필수라면 느린 네트워크에서도 결국 웹폰트가 표시되는 `swap` + 프리로드가 낫다.

### 5.4 프리로드 판단 기준

**프리로드해야 하는 것**: ① 첫 화면에 즉시 보이는 텍스트의 폰트(LCP 요소가 텍스트면 필수), ② 브랜드 정체성에 필수적인 커스텀 폰트, ③ `optional`과 조합할 때.

**프리로드하지 말아야 하는 것**: ① **3개 이상**(다른 중요 리소스가 밀린다 - 권장 1~2개), ② 스크롤 아래·모달 등 상호작용 후에만 보이는 폰트, ③ **구글 폰트의 폰트 파일 자체**(URL이 브라우저마다 동적이므로 대신 `preconnect`를 쓴다).

```html
<!-- 구글 폰트: preconnect가 정답 -->
<link rel="preconnect" href="https://fonts.googleapis.com" />
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin />
```

검증 3종: `crossorigin` 존재 확인 / Network 탭에서 중복 다운로드 없음 확인 / 프리로드 개수 2개 이하 확인.

## 6. 폴백 폰트 설계로 레이아웃 시프트를 방지하라

`swap`의 FOUT-CLS는 폰트마다 **메트릭**(ascent 베이스라인 위 높이, descent 베이스라인 아래, line gap 줄 간격, size)이 다르기 때문에 발생한다. CSS 폰트 메트릭 오버라이드로 폴백 폰트를 웹폰트와 거의 같은 크기로 강제 조정할 수 있다.

```css
@font-face {
  font-family: 'Roboto Fallback';
  src: local('Arial');
  ascent-override: 92.49%;   /* 베이스라인 위 높이 */
  descent-override: 24.34%;  /* 베이스라인 아래 */
  line-gap-override: 0%;     /* 줄 간격 */
  size-adjust: 100.3%;       /* 전체 크기 비율 */
}

@font-face {
  font-family: 'Roboto';
  src: url('/fonts/Roboto-Regular.woff2') format('woff2');
  font-display: swap;
}

body {
  font-family: 'Roboto', 'Roboto Fallback', sans-serif;
}
```

- `size-adjust`는 전체 크기만 조정하므로 이것만으로는 부족하다 - ascent/descent 오버라이드를 함께 쓴다.
- 값을 수동 계산하기는 어렵다. **Capsize**(`@capsizecss/core`)가 두 폰트의 메트릭을 비교해 조정 CSS를 자동 생성한다.
- **Next.js는 이 기능을 내장**한다: `next/font`의 `adjustFontFallback: true`가 빌드 시점에 조정된 폴백 CSS를 자동 생성한다.

```ts
import { Inter } from 'next/font/google';

const inter = Inter({
  subsets: ['latin'],
  adjustFontFallback: true, // 자동 폴백 조정
  fallback: ['Arial', 'sans-serif'],
});
```

> **핵심 통찰**: 메트릭 조정은 **웹폰트가 결국 로드된다는 전제**의 기술이다. `swap`/`fallback`과 궁합이 좋다. `optional`은 폰트를 포기할 수 있는 대신 CLS 0을 보장하고, 메트릭 조정은 웹폰트를 쓰면서 CLS를 최소화한다 - 상황에 따라 선택한다.

## 7. 구글 폰트 vs 자체 호스팅

**구글 폰트의 장점**: `<link>` 한 줄의 간편함, 자동 서브셋(`unicode-range`·`text=`), 글로벌 CDN. 단 **"교차 사이트 캐시 공유" 장점은 사라졌다** - 2020년 이후 모든 주요 브라우저가 파티션드 캐시를 도입해 도메인별로 캐시가 분리된다.

**구글 폰트의 한계**: ① 두 도메인(googleapis.com CSS + gstatic.com 폰트) 연결로 **100~500ms 추가 지연**, ② 폰트 URL·캐시 정책 제어 불가, ③ **GDPR 이슈**(사용자 IP가 구글에 전송 - 2022년 독일 법원이 위반 판결), ④ 구글 차단 지역(중국 등)에서 작동 불가.

**자체 호스팅의 장점**: 실측 200~300ms 더 빠름(단일 도메인 + 프리로드 가능), 완전한 제어권(font-display·캐시·서브셋·메트릭 조정), 개인정보 보호, 외부 장애 무관. 단점은 초기 설정 복잡성, 수동 업데이트, 서버 트래픽(1년 캐시 `Cache-Control: public, max-age=31536000, immutable`로 완화).

**선택 기준**

- **자체 호스팅**: 성능이 크리티컬한 서비스(이커머스·금융·뉴스), GDPR 준수 필요, 중국·제한 네트워크 지원, 세밀한 제어 필요
- **구글 폰트**: 프로토타입·MVP, 디자인 실험 단계(폰트를 빠르게 바꿔보기), 리소스가 제한적인 팀, 내부 도구
- **하이브리드**: 개발은 구글 폰트 → 출시 전 자체 호스팅 전환 / 크리티컬 폰트는 자체 호스팅 + 프리로드, 장식 폰트는 구글 폰트 지연 로딩

> **핵심 통찰**: **대부분의 프로덕션 서비스는 자체 호스팅이 낫다.** 초기 설정 비용은 있지만 성능(200~300ms)·제어권·법적 안정성에서 장기 이득이 크다.

## 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|---|---|---|
| `font-display` 미설정(`auto` 방치) | 크롬 3초 FOIT, **사파리는 무한 FOIT** | 모든 `@font-face`에 `swap`/`optional` 명시 |
| 일반 텍스트에 `block` | 3초간 텍스트가 안 보여 FCP·LCP 지연 | `block`은 로고·아이콘 폰트만 |
| 한글 완성형 폰트를 그대로 로드 | 3.5MB → Slow 4G에서 약 19.4초 | 2,350자 서브셋(400KB)으로 88% 절감 |
| 프리로드에 `crossorigin` 누락 | CORS 불일치로 **폰트 이중 다운로드** | 모든 폰트 프리로드에 `crossorigin` |
| 폰트 3개 이상 프리로드 | CSS·JS·이미지 등 중요 리소스가 밀림 | 크리티컬 1~2개만 |
| 구글 폰트의 폰트 파일 프리로드 | URL이 브라우저마다 동적이라 무의미/오작동 | `preconnect` 2개(googleapis + gstatic) |
| Bold/Italic 파일 미정의 | synthetic bold/italic → FOFT + 가독성 저하 | 모든 변형 정의 또는 가변 폰트 |
| weight 4개 이상을 정적 폰트로 | 요청 수·용량 모두 손해 | 가변 폰트로 통합(한글은 80% 절감) |
| `unicode-range` 범위 중복 | 어떤 파일을 쓸지 모호해짐 | 범위를 정확히 분리 |
| 폴백 폰트 메트릭 방치 | `swap` 교체 시 레이아웃이 크게 밀려 CLS | Capsize/`adjustFontFallback`으로 조정 |
| WOFF 또는 TTF 제공 | WOFF2 대비 30% 이상 큼 | WOFF2 단일 제공(모던 브라우저 전부 지원) |
| 프로덕션에서 구글 폰트 + 유럽 사용자 | GDPR 위반 판결 사례(IP 제3자 전송) | 자체 호스팅으로 전환 |

## 측정과 검증

- **Performance 패널**: FCP 마커가 폰트 다운로드 완료보다 앞에 있는지(swap 적용 확인), Experience 절의 Layout Shift가 폰트 로드 시점과 일치하는지(FOUT-CLS 진단) 확인한다.
- **Network 탭**: 폰트 다운로드 크기·타이밍 확인, **같은 폰트가 두 번 나타나지 않는지**(crossorigin 누락 진단), 스로틀링(Slow 4G)으로 FOIT/FOUT 동작 테스트.
- **라이트하우스**: "Ensure text remains visible during webfont load" 경고 확인.
- **CLS 측정**: `PerformanceObserver({ type: 'layout-shift' })`로 폰트 교체 시점의 시프트를 수집한다. 목표 0.1 이하.
- **`document.fonts.ready` / `document.fonts.check()`**: 폰트 로드 완료 시간과 실제 적용된 폰트를 코드로 확인한다.
- **목표 기준**: 페이지 총 폰트 용량 200KB 이하(서브셋 적용 후), 개별 파일 100KB 이하.

## 요약

- 폰트는 디자인 자산이기 전에 **성능 자산**이다. 로딩 전략(`font-display`) + 용량(서브셋·가변 폰트) + 시점(프리로드) + 폴백 설계(메트릭 조정)의 4축으로 관리한다.
- 세 가지 문제의 지도: **FOIT**(텍스트 실종 - 크롬 3초, 사파리 무한) → FCP/LCP 타격, **FOUT**(폰트 교체 깜빡임) → CLS, **FOFT**(가짜 볼드) → 가변 폰트로 해결.
- `font-display` 선택: **일반 텍스트 = `swap`**(FOIT 제거), **CLS 절대 방지 = `optional`**(교체 자체가 없음), **로고·아이콘 = `block`**. 콘텐츠 중요도별 하이브리드가 최적이다.
- 한글 폰트의 답은 **2,350자 서브셋**(3.5MB → 400KB, 88% 절감)이다. 사용자 입력이 많으면 `unicode-range` 3단 구성(라틴/기본/확장)으로 페이지 콘텐츠에 따라 자동 조절되게 한다.
- **가변 폰트는 weight 4개 이상부터 확실히 이득**이다. 한글은 80% 절감(Pretendard 2,520KB → 500KB). FOFT도 원천 차단된다.
- 프리로드의 3원칙: **crossorigin 필수**(없으면 이중 다운로드), **1~2개만**, **구글 폰트에는 preconnect**. `optional` + 프리로드 조합이 "CLS 0 + 웹폰트 높은 적용률"의 이상형이다.
- FOUT-CLS의 정밀 해법은 **폰트 메트릭 오버라이드**(`size-adjust`·`ascent-override`·`descent-override`)다. Capsize나 Next.js `adjustFontFallback`이 자동 계산한다.
- 호스팅: **프로덕션은 자체 호스팅**(200~300ms 빠름 + GDPR + 제어권). 구글 폰트의 캐시 공유 장점은 파티션드 캐시 도입으로 소멸했다. 프로토타입 → 출시 전 전환이 실용적 경로다.
- 우선순위: 본문 Regular부터 → 자주 쓰는 Bold/Medium → 드문 weight. 자동화(빌드 서브셋·프레임워크 기능·해시 버전 관리)를 구축해야 성능이 유지된다.

## 다른 챕터와의 관계

- **Ch4(리소스 우선순위)**: 폰트가 CSS 뒤에 숨어 발견이 늦는 문제와 `preload as="font" crossorigin`의 원리를 다뤘다. 이 장은 그것을 폰트 도메인 전체로 확장한다.
- **Ch2(네트워크 압축)**: WOFF2에 브로틀리 기반 압축이 내장돼 있어 재압축 대상에서 제외해야 한다는 사실이 여기와 연결된다.
- **Ch3(브라우저 캐시)**: 자체 호스팅 폰트의 1년 캐시 + 파일명 해시 전략, 그리고 파티션드 캐시(트리플 키 캐싱)가 구글 폰트 캐시 공유 신화를 깬 배경이 이 장의 호스팅 논의와 맞닿는다.
- **Ch7(렌더링 블로킹 리소스)**: 크리티컬 CSS에 폰트 스타일을 포함해야 FOUC를 막는다는 원칙이 폰트 로딩 전략과 함께 작동한다.
- **Ch12(이미지 최적화)**: `fetchpriority`·프리로드·포맷 폴백이라는 같은 도구 상자를 이미지와 폰트가 공유한다.
- **Ch20(CLS)**: FOUT로 인한 레이아웃 시프트와 메트릭 오버라이드가 CLS 장의 폰트 절에서 재등장한다.
- **Ch24(다국어)**: 언어별 폰트 서브셋 조건부 로딩이 다국어 최적화 전략의 일부로 확장된다.
