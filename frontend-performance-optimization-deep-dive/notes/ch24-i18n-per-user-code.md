# Chapter 24: 다국어는 사용자별로 코드를 달리 제공하라

## 핵심 질문

번들 분석기를 열면 `ko.json`·`en.json`·`ja.json`·`zh.json`이 전부 한 번들에 있다 - 각 50KB면 총 200KB인데 사용자는 그중 50KB만 필요하다. moment.js는 로캘 파일까지 300KB가 넘는다. 문제는 대부분의 i18n 라이브러리(react-i18next·vue-i18n·next-i18next)가 **기본적으로 모든 번역을 초기 번들에 포함**한다는 것 - 언어가 10개, 20개로 늘면 낭비가 기하급수적으로 커진다. 글로벌 서비스 = 모든 사용자에게 모든 언어가 아니다. **지원 언어가 10개든 100개든 각 사용자의 번들 크기는 동일해야 한다** - 이것이 진짜 다국어 최적화다.

## 1. 사용자 언어를 정확히 감지하고 라우팅하라

감지에 실패하면 기본 언어 리소스를 먼저 로드한 뒤 전환하며 재다운로드 + 리렌더링이 일어난다. 첫 방문부터 올바른 언어가 성능의 출발점이다.

### 1.1 세 가지 감지 소스

- **Accept-Language 헤더**: `ko-KR,ko;q=0.9,en-US;q=0.8` - q(품질 계수)는 브라우저가 언어 목록 순서대로 자동 부여(첫 언어 1.0은 생략). 파싱해 지원 언어와 매칭한다. 한계: 브라우저 설정 고정(한국 거주 외국인이 한국어 OS면 실제 선호와 다름), 공용 PC, 프락시 변조 - **초기 힌트로만** 쓰고 명시적 선택을 우선한다.
- **URL 경로**(`/ko/`, `/en/`): 가장 명확한 방식. 북마크·링크 공유 시 언어가 보존되고 SEO에서 언어별 인덱싱이 정확하다.
- **쿠키/로컬스토리지**: 사용자의 명시적 선택을 기억.

### 1.2 URL 라우팅 전략

서브패스(`example.com/ko/`)가 도메인 분리(`ko.example.com` - DNS·SSL·CDN 개별 설정)보다 일반적이다. 서브패스 3전략:

| 전략 | 동작 | 특징 |
|---|---|---|
| `prefix_except_default` | 기본 언어만 무접두어(`/about` = 한국어, `/en/about`) | 기본 언어 URL 짧음, 페이지 라우터 기본 |
| `prefix` | 전 언어 접두어(`/ko/about`, `/en/about`) | 일관성 최고, 루트는 감지 후 리다이렉트 |
| `prefix_and_default` | 기본 언어는 둘 다 접근 가능 | **중복 콘텐츠** - canonical 필수 |

Next.js 페이지 라우터는 `i18n` 설정으로 자동, **앱 라우터는 middleware.ts로 직접 구현**(next-intl 조합). 넉스트는 `@nuxtjs/i18n`의 `strategy` 옵션.

### 1.3 쿠키 vs 로컬스토리지

- **쿠키**: 요청마다 서버로 전송 → **SSR이 첫 HTML부터 올바른 언어로 렌더링 가능.** 설정: `max-age` 1년, `SameSite=Lax`, `Secure`(HTTPS만), **HttpOnly는 설정하지 않음**(클라이언트 JS가 읽고 써야 함). 크기는 언어 코드 2~3바이트만.
- **로컬스토리지**: 서버가 읽을 수 없어 SSR 초기 렌더링에 반영 불가 → 클라이언트에서 전환하며 **FoWL**(Flash of Wrong Language) 발생. SSR 환경에서는 쿠키가 정답.

### 1.4 우선순위와 폴백

**우선순위: URL 경로 > 쿠키 > Accept-Language > 기본 언어.** URL은 명시적 의도, 쿠키는 과거 선택, 헤더는 힌트다. 미들웨어에서 이 순서로 확인해 리다이렉트하고, matcher로 API·정적 파일은 제외한다.

지원하지 않는 언어의 폴백: ① 가장 가까운 언어(zh-CN→zh-TW, en-GB→en - 매핑 테이블 + 베이스 코드 추출) ② 영어 ③ 서비스 기본 언어. 어떤 전략이든 "요청한 언어 미지원" 안내 + 언어 전환 UI를 눈에 띄게 제공한다.

## 2. 프레임워크별 언어 코드 스플리팅

번들러는 언어별 스플리팅을 자동으로 해주지 않는다 - **동적 임포트 또는 라이브러리의 lazy 기능을 명시적으로** 써야 한다.

### 2.1 Next.js

- **next-intl(앱 라우터)**: `getRequestConfig`에서 `await import(\`./messages/${locale}.json\`)` - 해당 언어만 동적 로드, 번들러가 언어별 청크로 자동 분리. 페이지별로도 나눠 common+해당 페이지 번역만 병합 가능. `AppConfig.Messages` 타입 확장으로 키 자동완성·컴파일 타임 검증.
- **next-i18next(페이지 라우터)**: **네임스페이스** 개념 - `public/locales/{lang}/{ns}.json` 구조 + `serverSideTranslations(locale, ['common', 'login'])`로 페이지가 필요한 네임스페이스만 프롭으로 전달. 로그인 페이지는 dashboard.json을 로드하지 않는다.

### 2.2 넉스트

- `@nuxtjs/i18n`: **`lazy: true` + `langDir` 설정만으로** 언어별 청크 자동 분리. 페이지별 분리는 공식 미지원 - `mergeLocaleMessage`로 페이지 진입 시 동적 임포트해 병합.
- **nuxt-i18n-micro**: 성능 특화 대안 - 10MB 번역 기준 @nuxtjs/i18n v10이 100초/8.8GB 메모리인 반면 8.6초/1GB. 페이지별 번역 분리가 기본(`locales/{lang}/pages/{page}.json`), 정규식 라우팅으로 언어 수와 무관하게 라우트 2개만 생성.

### 2.3 리액트 SPA(react-i18next)

- **i18next-http-backend**: `loadPath: '/locales/{{lng}}/{{ns}}.json'`으로 런타임 HTTP 로드 + Suspense.
- **동적 임포트**: 번들에 포함하되 스플리팅 - 감지된 언어만 `import(\`./locales/${locale}.json\`)` 후 init. 언어 전환은 `addResourceBundle` + `changeLanguage`(로드된 언어 캐싱).

### 2.4 검증 - 번들 분석과 CI

설정했다고 끝이 아니다 - **webpack-bundle-analyzer**(Next.js·CRA) / **rollup-plugin-visualizer**(비트·넉스트)로 언어 파일이 별도 청크인지 확인한다. 전부 main.js에 있다면 동적 임포트가 작동하지 않는 것.

실측 예: 4개 언어 × 50KB - 스플리팅 전 main 850KB → 후 main 650KB + 언어별 50KB = 사용자당 700KB(**-18%**). 10개 언어면 450KB 절약. **bundlesize**로 CI에 청크별 임곗값을 걸어 번역 증가에 따른 비대화를 자동 감지한다.

### 2.5 번역 관리 플랫폼(Crowdin·Lokalise·Contentful) 연동

- **빌드 타임 다운로드**(권장 기본): 빌드 스크립트에서 플랫폼 API/CLI로 JSON을 받아 정적 파일화 - 런타임 API 호출 0, CDN 캐싱·압축·코드 스플리팅 전부 적용. 단점: 번역 업데이트 = 재빌드.
- **런타임 API**: 실시간 업데이트가 필요할 때. 초기 렌더링이 API를 기다리므로 **CDN 캐싱**(`max-age` + `s-maxage`)과 **서버 메모리 캐싱** 필수.
- **하이브리드**: 기본 번역은 번들에 포함 + `partialBundledLanguages: true`로 API 최신본을 백그라운드 병합(reloadInterval 5분) - 핵심 UI는 안정적으로, 마케팅 문구·이벤트 안내만 실시간으로.

## 3. 번역 파일을 네임스페이스로 나누어 지연 로딩하라

언어별 분리 후에도 한국어 파일이 100KB면 홈 방문자가 대시보드 번역까지 받는다. **페이지·기능별 분리**가 다음 단계다.

### 3.1 3계층 분리 전략

- **Global(common)**: 헤더·버튼·검증 메시지 등 모든 페이지 공통 - **10~20KB로 작게 유지**(모든 페이지가 로드하므로).
- **Feature**: auth·ecommerce·dashboard 등 기능 묶음 - 20~30KB, 해당 기능 사용 시 로드.
- **Page**: 특정 페이지 전용 - 5~10KB, 방문 시에만.

안티 패턴 둘: ① **과도한 세분화**(1KB짜리 5개 파일 - HTTP 오버헤드가 데이터보다 큼, HTTP/2라도 1개가 빠름) ② **전부 common에**(150KB - 관리자 패널 번역을 전 사용자가 다운로드). 판단 기준: **80% 이상의 페이지에서 쓰면 common**, 기능 묶음은 Feature, 페이지 전용은 Page.

### 3.2 라우트 기반 자동 로딩

페이지마다 로딩 코드를 반복하지 말고 자동화한다:

- 라우트 설정에 `namespaces: ['common', 'dashboard']` 메타데이터 → RouteLoader가 `i18n.loadNamespaces()` 후 렌더링.
- 또는 경로에서 유추: `/dashboard/settings` → `['common', 'dashboard', 'dashboard/settings']`(경로 누적).
- Next.js 페이지 라우터는 `serverSideTranslations`에 명시, 앱 라우터는 페이지 컴포넌트에서 `Promise.all`로 common+페이지 번역 병합.

### 3.3 캐싱과 프리로딩

- **브라우저 캐시**: 번역 파일은 잘 안 변함 - `max-age=31536000`, 해시 파일명이면 immutable 영구 캐싱.
- **중복 요청 방지**: 여러 컴포넌트가 동시에 같은 네임스페이스를 요청해도 loadingPromises Map으로 HTTP 1회.
- **프리로딩**: 링크 hover 시 대상 페이지의 네임스페이스를 미리 로드(PrefetchLink), 또는 IntersectionObserver로 링크가 뷰포트에 들어오면 프리로드 - 페이지 전환이 즉각적이 된다.

## 4. CDN을 활용해 언어별 콘텐츠를 효율적으로 전달하라

### 4.1 엣지에서 언어 감지

클라우드플레어 워커(전 세계 300+ PoP)나 버셀 엣지 미들웨어에서 Accept-Language를 파싱해 **오리진까지 가지 않고** 10~50ms 안에 리다이렉트한다. 엣지 감지는 오리진 기반보다 TTFB가 50~70% 빠르고, 감지 결과를 쿠키에 저장해 다음 요청을 더 빠르게 한다.

### 4.2 Vary 헤더와 캐시 키 정규화

`Vary: Accept-Language`는 헤더 문자열이 조금만 달라도(순서·q값) 다른 캐시로 취급해 **히트율이 추락**한다.

> **핵심 통찰 - 정규화 + 커스텀 헤더 패턴**: 엣지에서 Accept-Language를 파싱해 `ko`/`en`/`ja`/`zh` 중 하나로 **정규화**하고 `X-User-Language` 커스텀 헤더로 오리진에 전달, `Vary`도 그 커스텀 헤더로 설정한다 - 캐시 키가 언어 수만큼(4개)만 생겨 히트율이 극대화된다. 쿠키 기반도 마찬가지: `Vary: Cookie`는 모든 쿠키 조합이 캐시 키가 되므로, 언어 쿠키만 추출해 커스텀 헤더로 변환한다.

### 4.3 언어별 캐싱 전략

- **SSR 페이지**: `Cache-Control: public, s-maxage=600, stale-while-revalidate=86400` + Vary 커스텀 헤더 - 같은 언어 사용자에게 엣지 즉시 응답(TTFB 500ms→50ms, 오리진 부하 90%↓). 워커 Cache API로 캐시 키에 언어를 직접 포함시키면 더 세밀한 제어.
- **API 응답**: 상품·카테고리 등 변경 빈도 낮은 API는 `s-maxage=1800` + 언어 분리.
- **번역 파일**: 해시 파일명 + `max-age=31536000`(1년) 영구 캐싱, 또는 ETag/304.
- **Geo 기반 우선순위**: `CF-IPCountry`로 지역 기본 언어 매핑(KR→ko) - 한국 접속자에게 한국어 우선 추천. 단 **사용자의 명시적 선택(쿠키)이 항상 우선**.
- **PoP 캐시 워밍**: 배포 후 주요 언어×URL 조합을 스크립트로 요청해 서울 PoP엔 한국어, 도쿄 PoP엔 일본어를 미리 적재 - 첫 사용자도 캐시 히트.

### 4.4 리다이렉션 최적화

- **308 영구 리다이렉트 주의**: 브라우저가 강하게 캐시해 사용자가 언어를 바꿔도 이전 경로로 계속 간다 - 언어 전환이 있는 사이트는 **302/307이 안전**.
- **최선은 리다이렉션 제거**: `NextResponse.rewrite()` - 사용자에겐 `/`를 보여주며 내부적으로 `/ko/`를 렌더링. 왕복 1회가 사라져 TTFB 200ms+ 개선. 단 SEO를 위해 canonical 태그 필수.

## 5. 다국어 이미지와 폰트를 조건부로 로드하라

### 5.1 언어별 이미지

텍스트가 든 배너·스크린샷·튜토리얼은 언어별 제작물 - 영어 사용자가 한국어 배너를 받을 이유가 없다.

- **디렉터리 구조화**: `/images/ko/`, `/images/en/` + `/images/common/`(언어 무관).
- **서버 컴포넌트 렌더링**(최선): 서버가 언어에 맞는 `<img>`만 생성 - 불필요한 이미지는 아예 다운로드되지 않는다. `<picture>` + JS 조작은 SSR 호환은 좋지만 JS 실행 전 로드 위험.
- **CDN 라우팅**: 프런트엔드는 언어 무관 URL(`/images/hero.webp`)을 쓰고 엣지 워커가 언어별 경로로 변환 - 코드 무수정. 캐시 키에 언어 포함 필수.
- **언어 전환 시 프리로드**: 새 언어의 이미지들을 `new Image()`로 먼저 로드 완료한 뒤 전환 - 빈 화면 없이 부드럽게.

### 5.2 다국어 폰트 - CJK가 진짜 문제

라틴 폰트는 ~200자로 충분하지만 **한글 11,172자·일본어 수천 자·중국어 2만+ 자** - 전체 CJK 폰트는 5~10MB다.

- **언어별 @font-face CSS 분리**: `/fonts/ko.css`(Noto Sans KR), `/fonts/en.css`(Roboto)를 현재 언어만 동적 로드(또는 SSR layout에서 lang별 link). 한국어 사용자는 한국어 폰트만.
- **CSS 변수 전환**: `:root[lang='ko'] { --font-family: 'NotoSansKR' }` - lang 속성 변경만으로 즉시 전환. 단 모든 폰트 선로드가 전제라 **CSS 분리와 조합**이 최적.
- 구글 폰트는 언어별 서브셋을 자동 제공하고 User-Agent별 최적 포맷을 반환한다.

### 5.3 CJK 서브세팅 전략

1. **빈도 기반 서브셋**: 한글 상용 2,350자, 중국어 간체 3,500자, 일본어 가나 142자+상용한자 2,136자 - `pyftsubset --text-file=... --flavor=woff2`. 나머지는 시스템 폰트 폴백.
2. **다단계 로딩**: 1단계(빈도 상위, `font-display: swap`, preload) → 2·3단계(백그라운드에서 FontFace API로, `font-display: optional`) - LCP는 1단계만으로 결정된다.
3. **동적 서브셋**(정적 사이트 한정): 빌드 시 HTML을 파싱해 **실제 사용된 글자만** 추출·서브셋 - 95%+ 절감. CMS·UGC에는 부적합.
4. **unicode-range**: 파일 단위가 아닌 **문자 단위** 조건부 로드 - 브라우저는 페이지에 해당 범위 문자가 있을 때만 그 폰트 파일을 다운로드한다. 라틴(U+0000-00FF)·한글(U+AC00-D7AF)·가나(U+3040-30FF)·CJK 한자(U+4E00-9FFF)를 같은 font-family의 다른 @font-face로 선언하면, "Hello, 홍길동님!"에서 문자별로 맞는 폰트만 자동 적용된다. 구글 폰트의 Noto Sans KR이 100+개 서브셋으로 분할된 것이 이 방식이다. CJK 한자는 빈도별 tier로 추가 분할.

## 6. 다국어 SEO를 성능과 함께 고려하라

### 6.1 hreflang - 언어별 페이지 명시

검색 엔진에 "이 페이지의 한국어판·영어판은 여기"라고 알리는 장치. 제공 방법 3가지: **HTML `<head>`**(페이지 적을 때 - 직관적이나 언어 추가 시 전 페이지 수정), **XML 사이트맵**(페이지 많을 때 - HTML 깔끔), **HTTP Link 헤더**(PDF 등 비HTML 전용).

필수 규칙: ① **자기 참조 포함**(한국어 페이지에도 hreflang="ko") ② **양방향**(ko→en이면 en→ko도) ③ **절대 URL** ④ **x-default**(언어 감지 실패 시 기본). 언어 코드는 ISO 639-1(+필요 시 zh-Hans/zh-Hant, es-ES/es-MX).

흔한 오류: 양방향 누락, 자기 참조 누락, `kr`(→`ko`), 상대 URL, 대상이 404/리다이렉트.

### 6.2 사이트맵과 canonical

- **언어별 사이트맵 분리**: sitemap-index + sitemap-ko/en/ja - 50MB 제한 회피 + 검색 엔진이 필요한 것만 다운로드. 동적 생성 + CDN 1시간 캐싱, gzip 압축(80~90%↓). 서치 콘솔 제출(과거 ping 엔드포인트는 2023-06 폐지 - `lastmod`를 정확히 유지하는 것이 대안).
- **canonical은 언어별 자기 참조**: 각 언어 페이지가 자신을 가리킨다. **전 언어가 영어판을 canonical로 가리키면 다른 언어가 중복 취급되어 인덱싱되지 않는다** - 치명적 실수. URL 파라미터(`?lang=ko`) 방식이면 파라미터 포함 전체 URL을 canonical로(애초에 경로 기반이 유리). hreflang 대상은 **최종 canonical URL만**(리다이렉트되는 URL 금지).

### 6.3 크롤 버짓과 성능 균형

- 사이트맵의 `priority`는 **구글이 무시** - `lastmod`가 실제로 활용되는 힌트다.
- robots.txt로 admin·검색 결과 등 불필요 경로 차단 + Sitemap 지시어. 중요 페이지는 홈에서 3클릭 이내 내부 링크.
- 크롤링 서버 부하는 **CDN 캐싱**으로 흡수(봇도 캐시 히트). `Crawl-delay`는 구글이 무시하고 서치 콘솔 속도 제한도 2024-01 폐지 - 조절은 5xx/429 응답 또는 robots.txt 차단으로.
- 구글봇 분기 응답은 클로킹 가이드라인 위반 주의 - 콘텐츠는 동일하게, 불필요한 JS 제거 정도만.
- SPA는 빈 HTML 문제 - SSR/SSG + CDN 캐싱 조합으로 SEO와 성능을 함께.

> **참고 - Intl API로 로캘 라이브러리 제거**<br><br>moment.js(로캘 포함 300KB+)를 버리고 브라우저 네이티브 `Intl.DateTimeFormat`·`Intl.NumberFormat`·`Intl.RelativeTimeFormat`을 쓰면 **번들 크기 0**으로 날짜·숫자·상대 시간 포매팅이 해결된다. 다국어 번들 다이어트의 가장 값싼 첫걸음이다.

## 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|---|---|---|
| 모든 언어 JSON을 초기 번들에 | 사용자당 1개 언어만 필요 - 언어 수에 비례해 낭비 | 동적 임포트/lazy 옵션 + 번들 분석으로 검증 |
| moment.js + 전체 로캘 | 300KB+ 대부분이 미사용 언어 데이터 | Intl API(번들 0) |
| 로컬스토리지에만 언어 저장 | SSR이 못 읽어 FoWL(잘못된 언어 깜빡임) | 쿠키(SameSite=Lax, HttpOnly 없이) |
| Accept-Language만 신뢰 | 거주지·공용 PC에서 실제 선호와 불일치 | URL > 쿠키 > 헤더 우선순위, 명시 선택 존중 |
| 언어 리다이렉트에 308 | 브라우저 강캐시로 언어 전환이 무시됨 | 302/307, 최선은 엣지 rewrite |
| `Vary: Accept-Language` 그대로 | 헤더 변형마다 캐시 분리 - 히트율 추락 | 엣지 정규화 + X-User-Language 커스텀 헤더 |
| 번역을 1~2KB 단위로 과분할 | HTTP 오버헤드 > 데이터 | 3계층(common 10~20KB/Feature/Page) |
| 관리자·특정 기능 번역을 common에 | 전 사용자가 다운로드 | 80%+ 페이지 사용만 common |
| CJK 폰트 전체 로드 | 5~10MB - 초기 로딩 파괴 | 빈도 서브셋 + 다단계 + unicode-range |
| 모든 언어 폰트 선로드(CSS 변수만) | 안 보는 언어 폰트까지 다운로드 | 언어별 CSS 분리와 조합 |
| hreflang 자기 참조/양방향 누락 | 검색 엔진이 오류로 간주하고 무시 | 규칙 4종 준수 + 도구 검증 |
| 전 언어 canonical을 영어로 | 비영어 페이지가 인덱싱 안 됨 | 언어별 자기 참조 canonical |
| 사이트맵 priority에 의존 | 구글이 무시하는 값 | lastmod를 정확히 유지 |
| 스플리팅 설정 후 미검증 | 설정 오류로 여전히 전체 포함 | 번들 분석기 + bundlesize CI |

## 측정과 검증

- **번들 분석기**: 언어 파일이 별도 청크인지, main에 섞였는지 트리맵으로 확인. 스플리팅 전후 사용자당 다운로드 크기 비교(예: 850→700KB).
- **bundlesize CI**: main·언어 청크별 임곗값 - 번역 증가에 따른 회귀 차단.
- **Network 탭**: 첫 방문 시 현재 언어의 번역·폰트·이미지만 로드되는지, 페이지 전환 시 해당 네임스페이스만 추가되는지.
- **엣지 캐시 히트율**: 커스텀 헤더 정규화 전후 CDN 대시보드 비교. TTFB 개선 측정.
- **hreflang 검증**: 서치 콘솔 + Screaming Frog/Ahrefs/Semrush - 양방향·자기 참조·상태 코드.
- **FoWL 확인**: 쿠키 저장 후 재방문 시 첫 페인트부터 올바른 언어인지.

## 요약

- 다국어 최적화의 원칙: **사용자별로 필요한 리소스만.** 한국어 사용자가 일본어 번역·한자 폰트·중국어 배너를 받는 일은 없어야 하며, 지원 언어가 늘어도 사용자당 번들은 일정해야 한다.
- **감지와 라우팅**: URL 경로(명시적) > 쿠키(기억된 선택, SSR 호환) > Accept-Language(힌트) > 기본 언어. 서브패스 라우팅 + 명확한 폴백. 로컬스토리지 단독은 FoWL을 만든다.
- **코드 스플리팅**: 라이브러리 기본값은 전체 포함 - next-intl 동적 임포트, next-i18next 네임스페이스, 넉스트 `lazy: true`, react-i18next backend/동적 임포트를 명시적으로 설정하고 **번들 분석기로 검증 + bundlesize CI**. 번역 플랫폼은 빌드 타임 다운로드 기본, 실시간 필요 시 하이브리드.
- **네임스페이스 3계층**(common 10~20KB / Feature / Page) + 라우트 기반 자동 로딩 + 캐싱·hover 프리로딩 - 과분할도 통합도 안티 패턴이다.
- **CDN**: 엣지 언어 감지(TTFB 50~70%↓), **정규화 + 커스텀 헤더**로 캐시 키를 언어 수만큼만, SSR/API 엣지 캐싱, 302/307(308 금지), 최선은 rewrite.
- **이미지·폰트**: 언어별 디렉터리 + 서버 렌더링/CDN 라우팅, 전환 시 프리로드. CJK는 서브세팅 필수 - 빈도 기반 + 다단계 + unicode-range로 90%+ 절감. moment.js는 Intl API로 대체(번들 0).
- **SEO**: hreflang(자기 참조·양방향·절대 URL·x-default), 언어별 사이트맵 + lastmod, 언어별 자기 참조 canonical(영어 몰아주기 금지), 크롤 버짓은 robots.txt + CDN 캐싱으로 - SEO와 성능은 트레이드오프가 아니라 함께 간다.

## 다른 챕터와의 관계

- **Ch3(브라우저 캐시)·Ch1(네트워크)**: Vary 헤더·s-maxage·SWR·엣지 캐싱의 기초가 언어별 캐시 분리로 응용된다.
- **Ch10(코드 스플리팅)**: 동적 임포트의 대상이 코드에서 번역 리소스로 확장된 것이 이 장이다.
- **Ch12(이미지)·Ch14(폰트)**: 이미지 포맷·폰트 서브셋·font-display·unicode-range의 심화 - CJK라는 최악 조건에서의 실전 적용.
- **Ch23(서드파티)**: "필요한 사용자에게 필요한 것만"의 원칙이 서드파티에서 언어 리소스로 이어진다. 조건부 로딩·프리로딩 패턴도 동일.
- **Ch11(서버로 이동)·Ch16(하이드레이션)**: 엣지 미들웨어·서버 컴포넌트가 언어별 렌더링의 실행 기반이다.
