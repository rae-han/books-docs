# Chapter 16: 하이드레이션은 줄이는 것이 아니라 제거하는 것이다

## 핵심 질문

SSR로 FCP 0.8초를 만들었는데 TTI는 3.5초 - 사용자는 완성돼 보이는 화면에서 버튼을 눌러도 아무 반응을 얻지 못한다. 라이트하우스 점수는 90점인데 왜 "버튼이 안 돼요"라는 피드백이 오는가? 하이드레이션을 **빠르게** 하는 것이 아니라 **줄이고, 나아가 제거하는** 세 가지 축(스트리밍·부분 하이드레이션·Resumability)은 각각 무엇을 해결하는가?

## 1. 하이드레이션이 TTI를 지연시키는 이유

### 1.1 SSR과 하이드레이션의 동작 원리

하이드레이션은 리액트만의 개념이 아니다. 뷰의 `createSSRApp().mount()`, 스벨트의 `hydrate: true`, 앵귤러 유니버설, 솔리드의 `hydrate()` - SSR을 쓰는 모든 프레임워크에서 같은 작업이 일어난다: **서버가 만든 HTML에 클라이언트 자바스크립트를 연결해 인터랙티브하게 만드는 것**.

```tsx
// app/page.tsx
'use client';
import { useState } from 'react';

export default function Counter() {
  const [count, setCount] = useState(0);
  return (
    <div>
      <h1>카운터: {count}</h1>
      <button onClick={() => { setCount(count + 1); }}>증가</button>
    </div>
  );
}
```

접속 시 벌어지는 일의 순서:

1. **서버가 HTML 생성**: 컴포넌트를 실행해 `카운터: 0` HTML 문자열을 만들어 전송 → 브라우저 렌더링 → **FCP 발생**. 그러나 이 HTML은 정적이다 - `onClick` 핸들러는 HTML에 담을 수 없다. 클릭해도 무반응.
2. **JS 번들 다운로드**: 리액트 런타임 + 컴포넌트 코드. Slow 4G에서 1MB면 수 초.
3. **파싱·컴파일**: 메인 스레드 블로킹. 중저사양 모바일에서 수백 ms.
4. **하이드레이션**(`hydrateRoot()`): ① 컴포넌트 트리 재생성(가상 DOM) → ② 서버 DOM과 비교(Reconciliation) → ③ 일치 확인(불일치 시 경고 + 클라이언트 DOM으로 교체) → ④ 이벤트 리스너 연결 → ⑤ `useState(0)` 상태 초기화.
5. 완료 시점에 비로소 **TTI** 달성.

```
SSR 하이드레이션 타임라인 (Slow 4G, 중저사양 모바일 예시)

HTML 렌더링(FCP)   ▓▓ 800~1000ms
JS 번들 다운로드          ▓▓▓▓▓▓ 500~3000ms
파싱 + 하이드레이션              ▓▓ 0~500ms
인터랙션 가능(TTI)                    ▲ ~3000ms
                   └── FCP~TTI 간격: 사용자가 "멈춘 화면"을 보는 시간 ──┘
```

> **핵심 통찰**: 서버가 이미 렌더링했는데 클라이언트가 왜 다시 하나? **HTML은 구조와 콘텐츠만 표현할 수 있고, 이벤트 핸들러와 상태는 담을 수 없기 때문**이다. 클라이언트는 핸들러를 추출하려고 컴포넌트를 전부 재실행한다 - 이것이 전통적 SSR의 근본 한계이고, 하이드레이션 시간이 **컴포넌트 수에 비례**하는 이유다. 2부에서 번들을 500KB→100KB로 줄여도 하이드레이션은 비례해서 줄지 않는다 - 다운로드가 아니라 DOM 비교 + 이벤트 연결이라는 별도 작업이기 때문이다.

TTI는 라이트하우스 10(2023년 초, 크롬 112)부터 점수 산정에서 제외됐지만 "완전히 상호작용 가능한 시점"을 이해하는 데 여전히 유용하다. 실사용자 응답성은 INP로 측정한다.

### 1.2 불쾌한 골짜기 문제와 INP

**불쾌한 골짜기(Uncanny Valley)** - 완성된 것처럼 보이는데 클릭에 반응하지 않는 상태. 로봇공학 용어에서 온 비유로, "거의 완벽하지만 미묘하게 불완전한 상태"가 오히려 강한 거부감을 준다.

- 하이드레이션 전 클릭은 이벤트 리스너 미등록으로 브라우저가 **완전히 무시**한다. 이 클릭은 **INP 측정에 포함되지 않지만** 사용자 체감은 극도로 나쁜 INP와 같다 - 지표에 안 잡히는 최악의 경험. 필드 메트릭(INP)으로도 부분적으로만 보이고, 라이트하우스는 FCP만 보고 높은 점수를 준다.
- 더 나쁜 시나리오: 리액트 18의 선택적 하이드레이션은 하이드레이션 전 클릭을 **이벤트 큐에 쌓았다가 완료 후 한꺼번에 처리**한다. "장바구니 담기"를 4번 눌렀다면 4개가 담긴다. `isAdding` 중복 클릭 방지 플래그는 무력하다 - 핸들러 자체가 등록 전이었고, 큐 처리 시 각 클릭의 체크가 독립적으로 통과하기 때문이다.
- 유형별 피해: 뉴스(링크 무반응 → 뒤로가기 후 재클릭 → 불필요한 재로드), SaaS(저장 무반응 → 새로고침 → 입력 데이터 유실), SNS(좋아요 연타 → 하이드레이션 후 홀수 번 토글).

해결책 하나는 버튼을 HTML `<form>`으로 감싸 **서버 액션**으로 처리하는 것 - 폼 제출은 HTML 기본 기능이라 하이드레이션 전에도 작동한다.

### 1.3 하이드레이션 시간 측정

**크롬 Performance 패널** - 패널 안의 Reload 버튼으로 프로파일링 시작(일반 새로고침 아님).

- **Timings**: FCP(초록 선)·LCP(파랑 선)·DCL·Load 마커.
- **Main Thread 불꽃 차트**: 노란색 = JS 실행, 보라색 = 렌더링, 초록색 = 페인팅. FCP 이후를 확대해 `Evaluate Script`(길면 번들이 큼)와 리액트 하이드레이션 호출을 찾는다. 개발 빌드에선 `hydrateRoot`가 명확히 보이지만 **프로덕션 빌드는 축소화되어 짧은 함수명**으로 나온다.
- **TTI 수동 판단**: FCP 이후 5초 길이 quiet window(진행 중 GET 요청 2개 이하 + 50ms 이상 긴 작업 없음)가 기준이지만, 실무적으로는 **마지막 하이드레이션 관련 작업이 끝난 시점**으로 본다.

**문제 신호 3가지**

1. **FCP 이후 1초 이상 이어지는 노란색 블록**: JS 실행이 너무 길다 - 하이드레이션이 느리거나 무관한 초기화 코드가 많다.
2. **반복되는 `Recalculate Style` + `Layout`**: 강제 동기 레이아웃(Forced Synchronous Layout). DOM 읽기와 쓰기를 번갈아 하면 매번 레이아웃을 재계산한다.

```ts
// ❌ 나쁜 예: 읽기/쓰기 교대 - 요소 수만큼 Layout 발생
elements.forEach((el) => {
  const height = el.offsetHeight;        // 읽기 (레이아웃 계산 유발)
  el.style.height = `${height + 10}px`;  // 쓰기
});

// ✅ 좋은 예: 모든 읽기 먼저, 모든 쓰기 나중 - Layout 1회
const heights = elements.map((el) => el.offsetHeight);
elements.forEach((el, i) => {
  el.style.height = `${heights[i] + 10}px`;
});
```

요소 500개 실측에서 나쁜 예 69.2ms vs 좋은 예 0.2ms - **346배 차이**. 요소가 늘수록 격차는 커진다(일반적으로 5~20배).

3. **50ms 이상 긴 작업**(빨간 삼각형 경고): 메인 스레드 차단으로 입력이 무시된다. 하이드레이션 중 여러 개 보이면 컴포넌트 분할이나 스트리밍 SSR이 필요하다는 신호다.

**리액트 개발자 도구 Profiler** - "Reload and start profiling" → Flamegraph에서 **컴포넌트별** 렌더링 시간 확인. `<DataTable>`이 하이드레이션에 400ms를 쓴다면 `React.lazy` 분리 또는 서버 컴포넌트 전환 후보다.

**Performance API 프로그래매틱 측정** - 앱 라우터에서는 측정 코드를 별도 클라이언트 컴포넌트로 분리하고 `layout.tsx`는 서버 컴포넌트로 유지하는 것이 올바른 패턴이다.

```tsx
// app/PerformanceMonitor.tsx (클라이언트 컴포넌트)
'use client';
import { useEffect } from 'react';

export function PerformanceMonitor() {
  useEffect(() => {
    if (!PerformanceObserver.supportedEntryTypes?.includes('paint')) {
      return;
    }
    const observer = new PerformanceObserver((list) => {
      for (const entry of list.getEntries()) {
        if (entry.name === 'first-contentful-paint') {
          const fcpTime = entry.startTime;
          const hydrationTime = performance.now() - fcpTime;
          console.log(`FCP: ${Math.round(fcpTime)}ms`);
          console.log(`Hydration: ${Math.round(hydrationTime)}ms`);
        }
      }
    });
    observer.observe({ type: 'paint', buffered: true });
    return () => { observer.disconnect(); };
  }, []);
  return null;
}
```

**RUM(실사용자 측정)** - 개발 환경과 실사용자 환경(저사양 기기·느린 네트워크)은 다르다. `web-vitals` 라이브러리(`onFCP`/`onLCP`/`onINP`)로 수집해 애널리틱스로 전송하거나, 버셀 배포라면 `<SpeedInsights />` 한 줄로 자동 수집한다(단 TTI는 제공되지 않음).

## 2. 스트리밍 SSR로 점진적 렌더링 - 시간 축 분산

### 2.1 작동 원리

전통적 SSR은 **모든 데이터를 기다린 후** 완성된 HTML을 한 번에 보낸다. 가장 느린 요청 하나가 전체를 지연시킨다.

```tsx
// 전통적 SSR: fetchComments(2000ms)가 전체 TTFB를 결정
export default async function Page() {
  const user = await fetchUser();         // 100ms
  const posts = await fetchPosts();       // 50ms
  const comments = await fetchComments(); // 2000ms ← 병목!
  return (/* ... */);
}
```

스트리밍 SSR은 리액트 18 서스펜스와 결합해 **준비된 부분부터 청크 단위로 전송**한다.

```tsx
import { Suspense } from 'react';

export default function Page() {
  return (
    <div>
      <Header />        {/* 즉시 렌더링 */}
      <UserProfile />   {/* 즉시 렌더링 */}
      <Suspense fallback={<Skeleton />}>
        <Comments />    {/* 준비되면 스트리밍 */}
      </Suspense>
    </div>
  );
}
```

서버는 `<Header>`·`<UserProfile>`을 즉시 전송하고 `<Comments>` 자리에 `<Skeleton>`을 보낸다. 브라우저는 부분 HTML을 즉시 렌더링(FCP 빠름)하고, 백그라운드에서 준비된 댓글 HTML이 스트리밍되면 스켈레톤을 교체한다. Next.js 13+ 앱 라우터에서는 별도 설정 없이 기본 지원된다.

이점: **TTFB 개선**(느린 데이터를 안 기다림) + **FCP 개선**(부분 HTML 즉시 렌더링) + **점진적 하이드레이션**(먼저 온 부분부터 처리).

### 2.2 서스펜스 경계를 어디에 둘 것인가

- 데이터 로딩이 **상대적으로 긴 컴포넌트**를 감싼다.
- **첫 화면 콘텐츠에는 자제**한다(FCP 우선) - 스크롤해야 보이는 콘텐츠에 적극 활용한다.
- **독립적인 위젯은 각각** 감싸서 병렬 로딩한다 - 경계마다 독립적으로 스트리밍·하이드레이션되므로 하나가 느려도 다른 부분은 영향받지 않는다.
- 너무 많으면 복잡하고, 너무 적으면 효과가 없다.

```tsx
export default function Dashboard() {
  return (
    <div>
      {/* Above-the-fold: 즉시 렌더링 */}
      <Header />
      <UserInfo />
      <QuickStats />
      {/* Below-the-fold: 경계별 독립 스트리밍 */}
      <Suspense fallback={<ChartSkeleton />}><RevenueChart /></Suspense>
      <Suspense fallback={<TableSkeleton />}><TransactionsTable /></Suspense>
      <Suspense fallback={<ListSkeleton />}><RecentActivities /></Suspense>
    </div>
  );
}
```

> **실무 팁 - SEO 주의**: 구글은 스트리밍된 콘텐츠를 색인할 수 있지만 크롤링 큐와 별도의 렌더링 큐를 쓰므로 **색인이 지연될 수 있다.** 제목·메타 정보·첫 화면 핵심 콘텐츠는 서스펜스 밖에 두는 것이 안전하다.

## 3. 부분 하이드레이션 - 공간 축 축소

스트리밍이 하이드레이션을 **시간적으로** 분산했다면, 부분 하이드레이션(Partial Hydration)은 **공간적으로** 줄인다 - 모든 컴포넌트를 하이드레이션할 필요가 없다는 발상이다. 블로그 페이지에서 헤더(로고+링크), 본문(정적 마크다운), 사이드바(목차)는 인터랙션이 없는데도 리액트는 전부 하이드레이션한다. 정작 필요한 건 댓글 폼뿐인데.

판단 기준: **"이 페이지에서 자바스크립트 없이 읽을 수 있는 부분이 대부분인가?"** Yes면 고려 대상(블로그·문서·랜딩·상품 페이지). 실시간 협업 도구·게임처럼 전부 인터랙티브하면 전통적 SPA가 낫다.

### 3.1 아스트로 아일랜드 - 정적 기본 + 인터랙티브 섬 추가

아스트로는 기본적으로 **모든 페이지를 정적 HTML로 렌더링**한다(JS 0). 인터랙티브가 필요한 컴포넌트만 "아일랜드"로 지정한다.

```astro
---
import Header from '../components/Header.astro';      // 정적
import CommentForm from '../components/CommentForm.tsx'; // 리액트 컴포넌트
---
<Header />                      <!-- HTML만, JS 없음 -->
<article>
  <h1>블로그 글 제목</h1>
  <p>본문...</p>
</article>
<CommentForm client:load />     <!-- 이것만 하이드레이션 -->
```

하이드레이션 전략 디렉티브:

- `client:load` - 페이지 로드 시 즉시
- `client:visible` - 뷰포트 진입 시(지연 로딩)
- `client:idle` - 브라우저 idle 상태일 때
- `client:media="(max-width: 768px)"` - 미디어 쿼리 일치 시에만
- 디렉티브 없음 - 정적 HTML만(기본)

댓글까지 외부 서비스(Disqus 등)로 빼면 **JS 0KB - 하이드레이션이 없으므로 TTI가 FCP와 동시에 달성**된다.

### 3.2 넉스트 아일랜드 - 하이드레이션 기본 + 정적 섬 제외

넉스트 3는 반대 방향이다: 기본적으로 모두 하이드레이션되고, **`.server.vue` 확장자로 정적 부분을 명시적으로 제외**한다. 서버 전용 컴포넌트의 JS(예: `marked` 마크다운 파서)는 클라이언트 번들에서 완전히 빠진다. 기존 뷰/넉스트 앱을 전체 재작성 없이 점진적으로 개선할 수 있다는 것이 강점이다.

`<NuxtIsland>`는 더 유연한 런타임 제어가 필요할 때 쓴다 - `name`으로 `components/*.server.vue`를 지정하고 `:props`로 데이터를 전달하면, 클라이언트 마운트 시 서버에 렌더링을 요청해 HTML을 받아온다. `#fallback` 슬롯으로 로딩 UI를 지정한다.

- **`.server.vue` 직접 사용**: 빌드 타임 분류, 초기 SSR에 이미 포함되어 로딩 상태 없음. 단순 정적 콘텐츠에 적합.
- **`<NuxtIsland>`**: 동적 프롭, 같은 컴포넌트를 여러 곳에서 다른 프롭으로, 로딩 상태 세밀 제어, 조건부 렌더링에 적합.
- **`lazy` 옵션**: 기본적으로 `<NuxtIsland>`는 서버 응답을 기다리며 페이지 렌더링을 차단하는데, `lazy`를 켜면 비차단 - 페이지 먼저 렌더링 + 폴백 표시 + 백그라운드 로드. 리액트 서스펜스와 유사한 UX.

> **참고 - 아스트로 vs 넉스트의 제어 대상**<br><br>아스트로 `client:visible`은 **"언제 하이드레이션할 것인가"**(클라이언트 JS 로딩 시점)를 제어하고, 넉스트 `lazy`는 **"서버 응답을 기다릴 것인가"**(서버 컴포넌트 렌더링 차단 해제)를 제어한다. 이름은 비슷해도 목적이 다르다. 주의: `.server.vue` 안에서는 `ref()`·`reactive()` 같은 반응형 API를 쓸 수 없고(클라이언트 상태가 없으므로), 서버 컴포넌트 에러는 클라이언트에서 처리하기 어려우니 에러 바운더리를 설정한다.

### 3.3 Next.js 서버 컴포넌트 - 하이드레이션 제거의 리액트식 구현

서버 컴포넌트는 하이드레이션되지 않는다. 서버에서만 실행되고 결과만 전송되므로 재실행·이벤트 연결이 없다. 전략: **정적 콘텐츠 = 서버 컴포넌트, 인터랙티브 = 클라이언트 컴포넌트** - 그리고 서버 컴포넌트 안에 클라이언트 컴포넌트를 포함할 수 있다.

```tsx
// app/blog/[slug]/page.tsx (서버 컴포넌트)
import CommentForm from './CommentForm'; // 클라이언트 컴포넌트

export default async function BlogPost({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;
  const post = await getPost(slug);
  return (
    <article>
      {/* 하이드레이션 안 됨 - JS 0 */}
      <h1>{post.title}</h1>
      <div dangerouslySetInnerHTML={{ __html: post.content }} />
      {/* 이 부분만 하이드레이션 */}
      <CommentForm postId={slug} />
    </article>
  );
}
```

서버는 댓글 폼 자리에 플레이스홀더를 남기고, 브라우저는 그 위치에만 리액트를 실행해 이벤트를 연결한다. 서버 컴포넌트의 소스코드는 클라이언트 번들에 포함되지 않는다(단, 초기 HTML과 함께 RSC 페이로드와 클라이언트 컴포넌트 참조는 전달된다).

### 3.4 서버 컴포넌트는 만능이 아니다 - 5가지 트레이드오프

1. **서버 부하**: CDN 정적 파일은 한 번 빌드해 수백만 명이 공유하지만, 서버 컴포넌트는 **요청마다 서버가 렌더링**한다. 트래픽 많은 서비스는 서버 비용이 증가한다.
2. **네트워크 워터폴**: 중첩 서버 컴포넌트가 각각 페칭하면 부모가 끝나야 자식이 시작된다(CSR은 동시 마운트로 병렬 가능했다). 페칭을 위로 끌어올려 `Promise.all`로 병렬화한다.

```tsx
// ❌ 순차: fetchUser(1초) → fetchPosts(1초) = 2초
// ✅ 병렬: URL에서 userId를 미리 알 수 있다면
const [user, posts] = await Promise.all([fetchUser(userId), fetchPosts(userId)]);
```

3. **캐싱 전략 필수**: Next.js 13~14는 `fetch`가 기본 자동 캐싱(`force-cache`)이라 같은 URL을 여러 컴포넌트에서 불러도 한 번만 요청됐다. **Next.js 15부터 기본이 `no-store`로 변경** - 캐싱하려면 `cache: 'force-cache'`를 명시해야 한다. DB 클라이언트 직접 사용이나 POST 요청도 캐싱되지 않는다. 캐싱 없이 쓰면 같은 데이터를 여러 번 조회해 오히려 느려진다.
4. **직렬화 제약**: 서버→클라이언트 프롭은 리액트가 직렬화 가능한 값만. 일반 함수·클래스 인스턴스는 불가(Date 객체는 가능). 핸들러는 클라이언트 컴포넌트 안에서 정의하고 데이터만 넘긴다.
5. **디버깅**: 서버 컴포넌트의 콘솔 로그는 서버 터미널에 출력된다. 브라우저 개발자 도구로 디버깅할 수 없어 초기 학습 곡선이 있다.

판단 예시 - 블로그: 마크다운 파싱은 서버(파서 라이브러리도 번들 제외), 댓글 폼은 클라이언트. 상품 페이지: 정보·설명·이미지는 서버(DB 조회·가격 계산 로직 비노출), 장바구니 버튼·수량 선택·리뷰 폼은 클라이언트. 관리자 대시보드: 실시간 차트·필터링 테이블·드래그 앤드 드롭·`localStorage`·`matchMedia`는 모두 클라이언트가 적합하다.

## 4. Resumability - 하이드레이션 제거

### 4.1 하이드레이션의 근본 비효율

서버는 컴포넌트를 실행해 상태를 만들고 JSX를 HTML로 변환한다. 문제는 **HTML로 변환되는 순간 상태와 핸들러 정보가 소실**된다는 것이다. `count`가 0이라는 상태, `onClick`이 어떤 함수인지는 HTML에 담기지 않는다. 그래서 클라이언트는 같은 작업을 처음부터 반복한다 - 이것이 하이드레이션의 본질적 비효율이다.

Resumability의 발상: **"서버가 만든 상태를 버리지 말고 HTML과 함께 보내면?"** 상태를 JSON으로 직렬화해 HTML에 포함시키고, 이벤트 핸들러의 위치를 HTML 속성에 기록하면 - 클라이언트는 재실행 없이 서버가 멈춘 지점에서 **재개(Resume)** 하면 된다.

> 전통적 하이드레이션은 서버가 영화를 1시간 지점까지 봤는데 클라이언트에게 제목만 알려주고 "처음부터 다시 보라"는 것과 같다. Resumability는 멈춘 지점의 타임스탬프를 함께 전달하는 것이다.

```
전통적 하이드레이션:
서버: HTML 생성 → [FCP] → JS 다운로드 → 컴포넌트 재실행 → VDOM 생성 → DOM 비교 → 이벤트 연결 → [TTI]
                            └────────── 서버가 이미 한 작업의 반복 ──────────┘

Resumability:
서버: HTML + 직렬화 상태 + 핸들러 위치 → [FCP] → 상태 복원(JSON 파싱) → [TTI ≈ FCP]
                                                    이벤트 발생 시 → 그때 핸들러 로드
```

### 4.2 Qwik의 구현

**`$` 표시 = 지연 로딩 경계.** `component$`, `onClick$`처럼 `$`가 붙은 곳을 기준으로 컴파일러가 코드를 별도 청크로 분리한다. `onClick$` 안의 함수는 **실제 클릭이 발생하기 전까지 다운로드되지 않는다.** 상태 직렬화만으로는 부족하다 - 핸들러 코드를 초기에 로드하지 않아야 진짜 "즉시 상호작용"이 된다.

서버 렌더링 결과:

```html
<button on:click="q-abc123.js#onClick_1">Increment</button>
<script type="qwik/json">{"ctx": {"count": 0}, "refs": [...]}</script>
```

- `on:click` 속성의 **QRL(Qwik Resource Locator)**: "q-abc123.js 파일의 onClick_1 함수" - 핸들러의 위치 기록.
- `<script type="qwik/json">`: 직렬화된 상태.

클라이언트 흐름: HTML 렌더링 → **Qwikloader(약 1KB)** 로드 → 상태 복원 → **이 시점에 이미 TTI**(≈FCP). 클릭이 일어나면 QRL을 읽어 청크를 다운로드(첫 클릭 시에만)하고 실행한다. 리액트는 하이드레이션에서 모든 컴포넌트를 실행해야 하지만, Qwik은 이벤트가 발생한 핸들러만 로드·실행한다.

### 4.3 트레이드오프와 선택 기준

1. **첫 인터랙션 지연(Cold Start)**: 클릭 시점에 핸들러를 다운로드하므로 네트워크에 따라 첫 클릭에 수백 ms 지연 가능. speculative prefetching으로 완화하지만 완벽하지 않다.
2. **직렬화 제약**: 함수·클로저·DOM 참조·WeakMap은 상태에 넣을 수 없다(리액트는 무엇이든 가능).
3. **생태계 부족**: MUI·Chakra·Radix 같은 리액트 라이브러리를 못 쓴다. npm trends 기준 주간 다운로드가 리액트의 0.05% 수준.
4. **학습 곡선**: `$`·QRL·직렬화 경계 등 새 패러다임 - 팀 전체 도입 비용이 높다.
5. **디버깅 복잡성**: 코드가 수십 개 청크로 분산되어 스택 트레이스 추적이 어렵다.

Qwik이 유리: 콘텐츠 위주 사이트, 초기 로딩이 극도로 중요, 모바일 주 타깃. 불리: 복잡한 상태 관리, 실시간 인터랙션, 리액트/뷰 생태계 의존.

> **핵심 통찰**: 현실적 판단 - 대부분의 프로젝트는 **Next.js + 서버 컴포넌트 + 스트리밍으로 충분한 성능**을 얻는다. Qwik은 "초기 로딩이 극도로 중요하고 리액트 생태계 없이 개발 가능한" 특수한 경우의 선택지다.

## 측정과 검증

- **Performance 패널**: FCP 마커 이후 `Evaluate Script`·하이드레이션 호출·긴 작업(50ms+, 빨간 삼각형) 확인. FCP~TTI 간격이 1초 이상이면 개선 여지.
- **TTI 실무 판단**: 마지막 하이드레이션 관련 작업이 끝난 시점(공식 기준: FCP 후 5초 quiet window, GET 2개 이하, 긴 작업 없음).
- **리액트 Profiler Flamegraph**: 컴포넌트별 하이드레이션 시간 - 느린 컴포넌트를 lazy/서버 컴포넌트 후보로.
- **Performance API**: `PerformanceObserver`(paint, buffered)로 FCP 대비 하이드레이션 시간을 계산해 애널리틱스 전송.
- **RUM**: web-vitals(onINP 포함) 또는 Vercel Speed Insights - 실사용자 기기·네트워크에서의 INP 분포 확인(TTI는 미제공).
- **스트리밍 검증**: Network 탭에서 HTML 응답이 청크로 도착하는지, 스켈레톤→콘텐츠 교체 시점 확인.
- **번들 검증**: 서버 컴포넌트 전환 후 클라이언트 번들에서 해당 코드·라이브러리가 빠졌는지 빌드 결과물로 확인.

## 요약

- SSR의 함정: FCP는 빠른데 TTI가 늦다. 하이드레이션 = 컴포넌트 재실행 + 가상 DOM 생성 + DOM 비교 + 이벤트 연결 + 상태 초기화 - HTML이 핸들러·상태를 표현할 수 없어 생기는 **전통적 SSR의 근본 한계**이며, 시간은 컴포넌트 수에 비례한다.
- **불쾌한 골짜기**: 완성돼 보이는데 무반응인 상태. 하이드레이션 전 클릭은 무시되거나(INP에도 안 잡힘) 큐에 쌓였다 한꺼번에 처리된다(장바구니 4개 시나리오 - `isAdding` 플래그 무력). 핵심 액션은 `<form>` + 서버 액션으로 방어한다.
- 측정: Performance 패널(노란 블록·강제 동기 레이아웃·긴 작업 3대 신호), 리액트 Profiler(컴포넌트별), Performance API(프로그래매틱), web-vitals RUM(실사용자). DOM 읽기/쓰기 분리만으로 실측 346배 차이.
- 최적화의 세 축: ① **스트리밍 SSR**(시간 분산) - 서스펜스 경계로 준비된 부분부터 전송, 독립 위젯별 경계 + above-the-fold 제외 + SEO 콘텐츠는 경계 밖. ② **부분 하이드레이션**(공간 축소) - 아스트로(정적 기본 + `client:*`로 섬 추가) vs 넉스트(하이드레이션 기본 + `.server.vue`로 정적 제외), Next.js 서버 컴포넌트(정적=서버, 인터랙티브=클라이언트). ③ **Resumability**(제거) - 상태 직렬화 + 핸들러 위치 기록으로 재실행 없이 재개, TTI≈FCP.
- 서버 컴포넌트 5대 트레이드오프: 서버 부하 / 네트워크 워터폴(`Promise.all`로 병렬화) / 캐싱 전략(**Next.js 15부터 fetch 기본 no-store**) / 직렬화 제약 / 서버 로그 디버깅.
- Qwik: `$` 지연 로딩 경계 + QRL + qwik/json 직렬화 + 1KB Qwikloader. 대가는 첫 클릭 Cold Start·직렬화 제약·작은 생태계(리액트의 0.05%)·학습 곡선. 대부분의 프로젝트는 Next.js + 서버 컴포넌트 + 스트리밍으로 충분하다.
- 공통 원칙: **"클라이언트에서 꼭 해야 하는 일만 클라이언트에서 하라."** 실무 첫걸음은 측정 → 정적 컴포넌트의 `'use client'` 제거 → 느린 페칭을 서스펜스로 감싸기다.

## 다른 챕터와의 관계

- **Ch10(코드 스플리팅)**: 서스펜스의 기본 동작(lazy 로딩)을 전제로 SSR 스트리밍과의 결합을 다뤘다. 코드 스플리팅은 하이드레이션 최적화의 보완재다.
- **Ch11(서버로 로직 이동)**: 서버 컴포넌트가 번들을 줄인다는 관점(Ch11)에 이어, 이 장은 **하이드레이션 제거**라는 두 번째 효익을 밝힌다. 번들 축소는 필요조건일 뿐 - TTI는 하이드레이션 전략이 결정한다.
- **Ch15(CSS 최소화)**: Runtime CSS-in-JS의 SSR 하이드레이션 이중 작업(FOUC)이 이 장의 하이드레이션 비용 논의와 직결된다.
- **Ch17(데이터 캐싱)**: 서버 컴포넌트의 캐싱 전략 필수 트레이드오프(Next.js 15 기본 변경)가 다음 장의 본 주제로 확장된다.
- **Ch18(자바스크립트 실행)**: 하이드레이션 이후에도 남는 문제 - 긴 작업 분할, 메인 스레드 효율 - 를 다음 장이 다룬다. 강제 동기 레이아웃 패턴도 Ch18·Ch21의 렌더링 파이프라인 논의로 이어진다.
- **Ch20(CLS)·Ch21(애니메이션)**: 하이드레이션 중 스타일 교체가 만드는 레이아웃 시프트, 메인 스레드 차단이 만드는 프레임 드롭과 연결된다.
