# Chapter 12: 이미지는 화질이 아니라 전달 방식이 성능을 좌우한다

## 핵심 질문

이미지는 모바일 페이지 용량의 50% 이상(중앙값 약 1.1MB)을 차지한다. 품질 슬라이더를 90에서 80으로 내리는 것 말고, **어떻게 전달하는가** — 포맷, 크기, 로딩 타이밍, 우선순위 — 를 바꾸면 무엇이 달라지는가?

## 1. 이미지 포맷 선택이 용량을 좌우한다

같은 이미지라도 포맷에 따라 파일 크기가 2배 이상 차이 난다. JPEG 100KB가 WebP로는 70KB, AVIF로는 50KB가 될 수 있다.

### 1.1 네 가지 포맷의 특징

- **JPEG(1992)**: DCT 기반 손실 압축. 인간 눈이 덜 민감한 고주파 성분을 제거하고 크로마 서브샘플링으로 색상 정보를 압축한다. 70~85% 품질이면 시각적 차이 없이 용량을 크게 줄인다. 투명도 미지원, 높은 압축률에서 8×8 블록 아티팩트 발생.
- **PNG(1996)**: GIF 특허 분쟁에서 탄생한 무손실 포맷(DEFLATE). 알파 채널 투명도 지원. 사진 같은 복잡한 이미지는 JPEG의 2~5배 크기라 전통적으로 로고·아이콘 전용이었다.
- **WebP(2010, 구글)**: VP8 비디오 코덱의 인트라 프레임 기술을 적용. 손실·무손실·투명도·애니메이션을 모두 지원하는 만능 포맷. **손실 압축은 JPEG 대비 25~34%, 무손실은 PNG 대비 26% 작다.** 인코딩·디코딩 속도도 JPEG 수준. 지원율 94% 이상.
- **AVIF(2019)**: AV1 코덱 기반. 최대 128×128 블록과 인루프 필터링으로 **JPEG 대비 40~50%, WebP 대비 20% 작다.** 10/12비트 색 깊이·HDR 지원. 단점은 **인코딩 시간이 WebP의 5~10배**이고 디코딩 연산이 무거워 저사양 기기에서 렌더링이 느릴 수 있다. 지원율 93% 이상(2024년 1월 Baseline Newly Available)이지만 폴백 필수.

이미지 특성에 따라 절감 폭이 크게 다르다. 실측 기준 **사진은 JPEG 대비 WebP/AVIF 약 20~25% 절감**이지만, **텍스트·선명한 경계가 많은 UI 스크린샷은 AVIF가 JPEG 대비 66% 절감**된다. 실제 이미지로 테스트하는 것이 중요하다.

### 1.2 `<picture>` 태그로 점진적 도입

브라우저는 `<source>`를 위에서부터 확인해 지원하는 첫 번째 포맷을 선택한다. 자바스크립트나 UA 감지가 필요 없다.

```html
<picture>
  <source srcset="hero.avif" type="image/avif" />  <!-- AVIF 지원 브라우저 -->
  <source srcset="hero.webp" type="image/webp" />  <!-- 사파리 16.4 미만 등 -->
  <img src="hero.jpg" alt="Hero Image" width="1920" height="1080" />  <!-- 폴백 -->
</picture>
```

> **실무 팁**: `<picture>` 안의 `<img>`에 **반드시 `width`/`height`를 지정**해야 CLS를 막는다. `alt`는 `<img>`에만 쓴다. 여러 포맷 생성은 수동 관리 대신 Sharp 빌드 스크립트나 프레임워크 컴포넌트로 자동화한다.

### 1.3 `<picture>`와 프리로드 결합

LCP 이미지를 프리로드할 때 JPEG만 프리로드하면 AVIF 지원 브라우저에서 **두 번 다운로드**된다. `type` 속성으로 브라우저가 지원하는 포맷만 프리로드하게 한다.

```html
<!-- ✅ 브라우저가 지원하는 포맷만 프리로드 -->
<link rel="preload" as="image" href="hero.avif" type="image/avif" />
```

**반응형 이미지 프리로드에는 `imagesrcset`·`imagesizes`가 필수다.** 없으면 프리로드와 실제 렌더링이 서로 다른 버전을 선택해 중복 다운로드가 발생한다.

```html
<link
  rel="preload" as="image"
  href="hero-1280.webp"
  imagesrcset="hero-640.webp 640w, hero-1280.webp 1280w, hero-1920.webp 1920w"
  imagesizes="(max-width: 768px) 100vw, 1280px"
/>
```

`href`는 `imagesrcset` 미지원 구형 브라우저용 폴백으로 유지한다. 프리로드는 **LCP 이미지에만** 쓴다.

### 1.4 포맷별 최적 사용 케이스

| 이미지 유형 | 1순위 | 2순위 | 3순위(폴백) |
|---|---|---|---|
| 사진, 복잡한 이미지 | AVIF | WebP | JPEG |
| 로고, 아이콘, 단순 그래픽 | SVG | WebP | PNG |
| 투명 배경 필요 | AVIF | WebP | PNG |
| 애니메이션 | WebM | MP4 | GIF |
| 스크린샷, 텍스트 많음 | PNG | WebP | JPEG |

- **SVG는 벡터 포맷**이다. 도형을 수학 공식(XML)으로 저장하므로 확대해도 깨지지 않고 용량도 작다. 반면 JPEG·PNG·WebP·AVIF는 **래스터 포맷**으로 픽셀 격자를 저장한다 — 확대하면 계단 현상이 생기지만 사진의 미묘한 그러데이션 표현에 유리하다. 복잡한 사진을 SVG로 만들면 오히려 커진다.
- 투명 이미지는 WebP가 PNG 대비 50~70%, AVIF가 70~90% 절감한다. JPEG는 투명도가 없으므로 PNG 폴백이 필수다.
- **애니메이션 GIF는 비디오로 교체한다.** WebM/MP4는 GIF보다 90% 이상 작고 품질도 좋다(`<video autoplay loop muted playsinline>`).

> **핵심 통찰**: 모든 이미지를 한 번에 바꾸지 않는다. **LCP 이미지와 주요 이미지부터** 차세대 포맷을 적용하고 효과를 측정하며 확대한다. 모든 이미지를 AVIF로 변환하면 빌드 시간이 10배 이상 늘 수 있고, 3~4개 포맷 제공은 스토리지도 3~4배 필요하다.

## 2. 반응형 이미지로 불필요한 전송 막기

Web Almanac 2024 기준 **모바일 페이지의 50%가 필요 이상으로 큰 이미지를 전송**한다. CSS `max-width: 100%`는 렌더링만 줄일 뿐 네트워크 전송은 이미 끝난 뒤라 성능 효과가 없다.

### 2.1 srcset과 sizes 속성

**`w` 디스크립터**는 이미지의 실제 픽셀 너비를 선언한다. 브라우저는 `유효 픽셀 밀도 = 이미지 실제 너비 ÷ 표시될 크기` 공식과 DPR을 고려해 최적 이미지를 선택한다.

**`sizes`는 "이 이미지가 레이아웃에서 차지할 크기"를 알려주는 힌트**다.

```html
<img
  srcset="product-400.jpg 400w, product-800.jpg 800w, product-1200.jpg 1200w"
  sizes="(max-width: 768px) 100vw,
         (max-width: 1200px) 50vw,
         33vw"
  src="product-800.jpg"
  alt="상품 이미지"
/>
```

선택 과정 예시:

```
375px 모바일(DPR 2): sizes → 375px 필요 → ×2 = 750px → 800w 선택
1920px 데스크톱(DPR 1): sizes 33vw → 634px 필요 → ×1 = 634px → 800w 선택
```

**주의사항 세 가지**

1. **`sizes`는 실제 CSS 레이아웃과 정확히 일치해야 한다.** `sizes="100vw"`인데 CSS가 `max-width: 800px`라면 큰 화면에서 불필요하게 큰 이미지를 받는다 → `sizes="(min-width: 800px) 800px, 100vw"`.
2. **브레이크포인트마다 이미지를 만들 필요는 없다.** 모바일(400~640px)·태블릿(768~1024px)·데스크톱(1200~1600px)의 3~4개면 충분하며, 실사용자 화면 크기 분포(애널리틱스)를 보고 결정한다.
3. **`src` 폴백은 항상 제공한다**(800w 정도의 중간 크기).

### 2.2 고밀도 디스플레이 대응 (1x, 2x, 3x)

고정 크기 이미지(로고·아이콘)는 `x` 디스크립터로 DPR별 이미지를 지정한다. `w` 디스크립터를 쓰면 **브라우저가 DPR을 자동으로 고려**하므로 별도 지정이 필요 없다.

> **핵심 통찰 — 3x 이미지는 대부분 불필요하다.** X(구 트위터) 연구 기준 DPR 3 기기에 2x 이미지를 표시해도 사용자는 차이를 거의 인지하지 못한다. X는 모든 플랫폼에서 이미지를 2x로 제한해 **데이터 전송량 38% 감소, 로딩 시간 32% 개선**을 달성했다. 2x → 3x는 픽셀 수가 2.25배(전체로는 1x의 9배) 늘어난다. 실무 절충안: **히어로 이미지만 3x, 나머지는 2x까지.**

### 2.3 Art Direction과 미디어 쿼리

`srcset`은 같은 이미지의 크기만 바꾼다. **화면 크기에 따라 완전히 다른 이미지**(크롭·구도)가 필요하면 `<picture>`의 `media` 속성을 쓴다.

```html
<picture>
  <!-- 모바일: 세로 크롭 + DPR 대응 -->
  <source media="(max-width: 768px)"
          srcset="hero-mobile-400.jpg 400w, hero-mobile-800.jpg 800w" sizes="100vw" />
  <!-- 데스크톱: 와이드 이미지 + DPR 대응 -->
  <source srcset="hero-desktop-1200.jpg 1200w, hero-desktop-2400.jpg 2400w" sizes="100vw" />
  <img src="hero-desktop-1200.jpg" alt="히어로 이미지" width="1200" height="600" />
</picture>
```

Art Direction이 필요한 순간은 세 가지다. ① **중요한 요소가 잘려 보일 때**(와이드 배너 중앙의 작은 제품 → 모바일용 제품 크롭), ② **텍스트 가독성이 중요할 때**(레이아웃 변경으로 텍스트가 밝은 영역 위로 이동), ③ **화면 비율이 크게 다를 때**(16:9 풍경 → 모바일 세로 구도). 그 외 대부분은 `srcset`/`sizes`로 충분하다 — Art Direction은 화면마다 다른 이미지를 준비해야 해 관리 부담이 크다.

## 3. 압축과 품질 최적화의 실전 기준

### 3.1 품질 70~85%가 표준인 이유

주요 서비스의 기본값: Cloudflare Images 85%, Next.js Image 75%, Cloudinary 80%. 실측(3008×2000 사진) 기준:

- 품질 100%: 7.5MB (기준)
- **품질 85%: 2.7MB (63.4% 감소, 시각적 차이 거의 없음)**
- 품질 75%: 2.4MB (섬세한 영역에서 약간의 노이즈)
- 품질 60%: 2.0MB (명확한 압축 아티팩트)

JPEG는 이미지를 블록으로 나눠 '큰 변화'(하늘의 그러데이션 — 눈이 민감)와 '작은 변화'(머리카락 텍스처 — 눈이 둔감)로 분류하고 작은 변화부터 버린다. **품질 100%는 눈에 안 보이는 정보까지 보존하는 것이라 실무적으로는 대역폭 낭비에 가깝다.**

**이미지 유형별 권장 품질**: 히어로·제품 사진 80~85% / 본문·배경 70~75% / 섬네일·프로필 65~70%. **WebP는 JPEG보다 10~15% 낮은 수치로 동일한 시각 품질**을 얻는다(JPEG 85% ≈ WebP 75~80% ≈ AVIF 70~75%).

### 3.2 프로그레시브 JPEG

베이스라인 JPEG는 위에서 아래로 순차 로드되지만, 프로그레시브 JPEG는 **전체 이미지를 흐릿하게 먼저 보여주고 점진적으로 선명해진다.** 여러 스캔으로 나눠 저장하고 첫 스캔(저해상도 전체)을 받는 즉시 윤곽을 표시한다.

3MB 히어로 이미지를 Slow 4G에서 로드할 때: 베이스라인은 8초 동안 빈 공간, 프로그레시브는 **1초부터 내용 파악 가능**(완성은 동일하게 8초). 실제 로딩 시간은 같지만 체감이 다르다. 파일 크기는 대부분 비슷하거나 오히려 작아진다. 디코딩 CPU를 조금 더 쓰지만 체감할 수준은 아니다. **10KB 이상의 JPEG, 특히 LCP 이미지는 프로그레시브로 인코딩한다**(`sharp().jpeg({ progressive: true })`).

### 3.3 압축 도구: Sharp와 Squoosh

- **Sharp**: Node.js에서 가장 빠른 이미지 처리 라이브러리(libvips 기반, ImageMagick 대비 4~5배). 빌드 프로세스·CI/CD 대량 처리·서버 동적 생성에 사용한다. 용도별 품질 설정(`hero: 85, content: 75, thumbnail: 70`)과 크기별 JPEG/WebP/AVIF 생성을 스크립트로 자동화하면, 이미지 하나가 9개 파일로 변환돼도 사용자는 자신의 환경에 맞는 1개만 받는다(모바일 크롬 = 640 AVIF 35KB, 구형 사파리 데스크톱 = 1920 JPEG 300KB).
- **Squoosh**: 구글의 브라우저 기반 압축 도구. 슬라이더로 원본/압축본을 비교하며 **최적 품질 설정을 찾는 실험**에 적합하다. 로컬 처리라 프라이버시도 보호된다. CLI 버전으로 자동화도 가능하다.

실무 흐름: **Squoosh로 최적 설정 탐색 → 그 설정을 Sharp 스크립트로 자동화.**

## 4. 이미지 로딩 전략: 지연 로딩과 디코딩 최적화

### 4.1 loading="lazy"

브라우저는 기본적으로 모든 `<img>`를 즉시 다운로드한다. `loading="lazy"`는 이미지가 뷰포트 근처(보통 1~2화면 전, 브라우저가 결정)에 올 때까지 다운로드를 미룬다. 사용자가 스크롤하기 전에 미리 시작되므로 체감에 부정적 영향이 없다.

- `eager`(기본값): 즉시 다운로드 — LCP 후보 이미지에
- `lazy`: 뷰포트 근처까지 대기 — 오프스크린 이미지에

**주의 세 가지**: ① **LCP 이미지에 절대 쓰지 않는다**(LCP 지연), ② 첫 화면에 보이는 이미지(보통 상위 3~5개)는 제외, ③ 지연 로딩을 써도 **`width`/`height`는 필수**(CLS 방지).

### 4.2 decoding="async"

다운로드 후에도 **디코딩**(압축 포맷 → 픽셀 데이터 변환)이 남아 있다. 4K 복잡한 JPEG는 디코딩에 수백 ms가 걸릴 수 있고 이 동안 페이지가 멈춘 것처럼 느껴진다. `decoding="async"`는 디코딩을 메인 스레드 밖에서 처리하도록 요청하는 힌트다.

- `sync`: 이미지와 주변 콘텐츠를 함께 표시하기 위해 디코딩을 기다릴 수 있음
- `async`: 디코딩 때문에 나머지 화면 표시가 늦어지는 것을 줄임
- `auto`(기본값): 브라우저가 결정

**조합 전략**

| 이미지 유형 | loading | decoding | 이유 |
|---|---|---|---|
| LCP 후보(히어로, 주요 제품) | `eager`(또는 생략) | `sync`(또는 생략) | 최대한 빨리 표시 |
| 첫 화면 내 보조 이미지 | `eager` | `async` | 로드는 빠르게, 디코딩은 비차단 |
| 스크롤해야 보이는 이미지 | `lazy` | `async` | 다운로드·디코딩 모두 지연/비차단 |
| 매우 작은 아이콘·로고 | 생략 | 생략 | 기본 동작으로 충분 |

> **실무 팁**: `loading="lazy"`는 **언제 다운로드할지**, `decoding="async"`는 **어떻게 디코딩할지**를 제어한다. 함께 쓰면 이미지가 많은 페이지의 스크롤 성능과 INP가 개선된다. 검증은 Performance 패널의 `Decode Image` 이벤트로 한다.

## 5. 이미지 로딩 UX 개선

### 5.1 스켈레톤과 대표 색상 플레이스홀더

가장 단순한 방법은 CSS `background-color`(+ 시머 애니메이션)로 회색 박스를 미리 표시하는 것이다. 추가 요청이 없고 모든 브라우저에서 작동하지만 어떤 이미지가 올지 예상할 수 없다.

한 단계 나은 방법은 **이미지의 대표 색상을 배경으로** 쓰는 것이다(구글 이미지·핀터레스트 방식). Sharp의 `stats()`로 평균 색상을 추출하거나 color-thief로 dominant color를 뽑아, 빌드 시점에 JSON으로 저장해두고 `background-color`로 사용한다.

### 5.2 블러-업과 LQIP

블러-업(Blur-up)은 **작고 흐릿한 이미지를 먼저 보여주고 고해상도가 로드되면 페이드 인으로 전환**하는 기법이다(미디엄이 대중화). 작동 원리:

1. 원본을 **20×15px, 품질 20~30%**로 리사이즈 → 1~2KB(보통 500~1,000바이트)
2. Base64로 인코딩해 HTML에 인라인
3. CSS `filter: blur(10px)` + `transform: scale(1.1)`(블러 테두리 제거)로 표시
4. 고해상도 로드 완료(`load` 이벤트) 시 `opacity` 전환

```css
.image-placeholder {
  position: absolute;
  inset: 0;
  width: 100%;
  height: 100%;
  object-fit: cover;
  filter: blur(10px);
  transform: scale(1.1); /* blur 테두리 제거 */
}
.image-full {
  opacity: 0;
  transition: opacity 0.3s ease-in;
}
.image-full.loaded {
  opacity: 1;
}
```

### 5.3 프로덕션 이미지 컴포넌트의 요건

직접 구현할 때 갖춰야 할 요소: ① Base64 프리뷰 우선 표시, ② 부드러운 전환(0.3~0.5초 페이드 인), ③ `loading="lazy"` + `decoding="async"` 조합, ④ **`aspect-ratio`로 CLS 방지**(빌드 시점에 이미지 크기를 JSON으로 저장해 다운로드 전에 비율을 앎), ⑤ `onError` 폴백 UI, ⑥ **캐시 최적화** — `img.complete && img.naturalHeight !== 0`으로 캐시된 이미지를 감지해 프리뷰 단계를 건너뛴다.

> **핵심 통찰**: LCP 후보 이미지에는 `loading="eager"` + `decoding="sync"`(또는 생략)를 쓴다. 블러-업 컴포넌트라도 히어로에는 `loading="eager"`를 전달해야 한다. 프레임워크 도구(Next.js Image 등)는 편리하지만, 직접 구현하면 전환 타이밍·카테고리별 품질·네트워크 조건별 프리뷰 크기 같은 세밀한 제어가 가능하고 프레임워크 종속이 없다.

## 6. 자동화 도구로 최적화 간소화하기

모든 이미지를 수동으로 최적화하는 것은 비현실적이다. 세 가지 접근이 있다.

### 6.1 프로젝트 특성별 도구 선택

| 상황 | 선택 | 이유 |
|---|---|---|
| 정적 이미지만(블로그·마케팅·포트폴리오) | 빌드 시점 최적화(SvelteKit Enhanced Image, Astro Image, Sharp 스크립트) | 런타임 오버헤드 0, 가장 빠름. 단 이미지 변경 시 재빌드 |
| 동적 이미지(CMS·SNS·커머스) | 이미지 CDN(Cloudinary, imgix) | URL 파라미터로 실시간 변환, 원본 하나만 저장 |
| Next.js/넉스트 프로젝트 | 프레임워크 내장 컴포넌트 | 통합 간편, 팀 일관성, 정적+동적 모두 처리 |
| 레거시 마이그레이션 | 이미지 CDN부터 | URL만 바꾸면 되어 코드 변경 최소 → 점진 확대 |

### 6.2 프레임워크 이미지 컴포넌트

- **Next.js `next/image`**: WebP/AVIF 자동 변환, 반응형 생성, 블러-업(`placeholder="blur"`), 지연 로딩을 기본 제공. 요청 시점 최적화 + 캐싱. AVIF는 `formats` 설정으로 켤 수 있지만 **공식 문서는 대부분 WebP를 권장** — AVIF는 20% 더 작지만 인코딩이 50% 더 걸려 요청 시점 변환 서버에 부하가 크다. Next.js 16에서 `quality={85}`를 쓰려면 `images.qualities`에 85를 포함해야 한다.
- **넉스트 `@nuxt/image`**: `<NuxtImg>`로 유사 기능 + 다양한 이미지 프로바이더(Cloudinary·imgix·Vercel) 연동. 컴포넌트 코드는 그대로 두고 소스만 교체 가능.
- **SvelteKit `@sveltejs/enhanced-img`**: 빌드 시점에 AVIF/WebP 변환 + `<picture>` 생성 + `width`/`height` 자동 추가 + EXIF 제거. 캐싱으로 재빌드는 빠르다. **정적 파일만 지원.**

### 6.3 이미지 CDN

Cloudinary(`w_400,q_80,f_webp` 경로 파라미터), imgix(`?w=400&fm=webp&q=80` 쿼리)는 **원본 하나만 저장하고 필요한 변형을 요청 시점에 생성**한다. `f_auto`/`auto=format`은 브라우저 지원에 따라 AVIF/WebP/JPEG를 자동 선택한다. AI 얼굴 인식 크롭·배경 제거 같은 고급 기능도 있다. 단점은 사용량 기반 비용과 외부 서비스 종속(장애 시 전체 이미지 다운).

### 6.4 네트워크 힌트 + CDN 자동 변환 결합

CDN이 포맷·크기를 최적화해도 **브라우저에 우선순위 신호를 주지 않으면 LCP가 지연된다.** 이미지는 기본 Medium/Low 우선순위이기 때문이다.

```html
<link
  rel="preload" as="image"
  href="https://res.cloudinary.com/demo/image/upload/w_1920,f_auto,q_auto/v1730/hero.jpg"
  imagesrcset="…768w, …1280w, …1920w"
  imagesizes="(max-width: 768px) 100vw, 1280px"
  fetchpriority="high"
/>
<img src="…" srcset="…" sizes="…" fetchpriority="high" width="1920" height="1080" alt="Hero" />
```

기본 전략: **LCP 이미지는 `preload` + `fetchpriority="high"`로 앞당기고, 섬네일은 `loading="lazy"` + `fetchpriority="low"` + CDN `dpr` 파라미터로 뒤로 미룬다.** `fetchpriority`는 크롬/엣지 101+, 사파리 17.2+, 파이어폭스 132+ 지원이며 미지원 브라우저에서는 무시된다 — High는 LCP 후보 1~2개에만 쓴다.

> **핵심 통찰**: Priority Hint를 추가했다고 항상 LCP가 개선되는 것은 아니다. 캐시 상태·CDN 엣지 위치·네트워크 품질에 따라 우선순위 큐가 매번 다르게 동작한다. **WebPageTest·라이트하우스 CI로 "측정→개선→재측정" 루프**를 돌려 LCP 이미지가 실제로 High로 처리되는지, 프리로드가 중복 다운로드를 줄였는지 워터폴로 확인한다.

## 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|---|---|---|
| CSS `max-width: 100%`로 반응형을 해결했다고 믿음 | 렌더링만 축소될 뿐 큰 파일 전송은 이미 끝남 | `srcset`/`sizes`로 전송 자체를 줄임 |
| LCP 이미지에 `loading="lazy"` | 뷰포트 판정 후에야 다운로드가 시작되어 LCP 악화 | `eager`(생략) + `preload` + `fetchpriority="high"` |
| `<picture>` 쓰면서 JPEG만 프리로드 | AVIF 지원 브라우저에서 2회 다운로드 | `<link rel="preload" type="image/avif">`로 포맷 지정 |
| 반응형 이미지 프리로드에 `imagesrcset` 누락 | 프리로드와 실제 선택 버전이 달라 중복 다운로드 | `imagesrcset`/`imagesizes` 지정 |
| `sizes`와 실제 CSS 레이아웃 불일치 | 필요보다 큰 이미지를 다운로드 | `sizes`에 `max-width` 등 실제 레이아웃 반영 |
| 모든 이미지에 3x 제공 | 픽셀 수 9배 — 시각적 차이는 거의 없음 | 2x 상한, 히어로만 선택적 3x |
| 품질 100%로 내보내기 | 눈에 안 보이는 정보에 3배 용량 소모 | 75~85%(WebP는 10~15% 더 낮게) |
| `width`/`height` 미지정 | 이미지 로드 시 레이아웃이 밀려 CLS 발생 | 항상 지정 또는 `aspect-ratio` 확보 |
| 애니메이션을 GIF로 제공 | 256색 + 낮은 압축률로 비디오 대비 10배 크기 | WebM/MP4 `<video>` 태그로 교체 |
| 투명 이미지를 PNG로만 제공 | WebP/AVIF 투명도로 50~90% 절감 기회 상실 | `<picture>`로 AVIF→WebP→PNG |
| 모든 이미지를 한 번에 AVIF 전환 | 빌드 시간 10배 + 스토리지 3~4배 | LCP·주요 이미지부터 점진 도입 |
| `fetchpriority="high"` 남발 | High가 많으면 우선순위 구분 자체가 희석됨 | LCP 후보 1~2개만 |

## 측정과 검증

- **Network 탭 + Device Toolbar**: 화면 크기·DPR을 바꿔가며 어떤 이미지가 선택되는지 확인한다(같은 400px 화면도 DPR 1은 400w 21.8KB, DPR 3은 1200w 162KB). `sizes` 효과도 검증한다 — 800px 화면에서 33vw 그리드는 400w를 선택해 71% 절감.
- **Performance 패널**: `Decode Image` 이벤트로 디코딩이 메인 스레드를 얼마나 차단하는지 확인한다. LCP 요소를 식별해 그 이미지에만 프리로드를 적용한다.
- **라이트하우스**: "Properly size images", "Serve images in next-gen formats", "Preload Largest Contentful Paint image" 경고를 확인한다.
- **목표 지표**: LCP 이미지 2.5초 이내 로드, 페이지 총 이미지 용량 1MB 이하(HTTP Archive 중앙값 기준), CLS 0.1 이하.
- **WebPageTest 워터폴**: 프리로드가 중복 다운로드를 만들지 않는지, LCP 이미지가 High 우선순위로 처리되는지 확인한다.

## 요약

- 이미지 최적화의 본질은 화질 조정이 아니라 **전달 방식**이다. 포맷 전환만으로 25~50%, 반응형으로 50% 이상, 품질 85% 설정으로 눈에 안 띄게 절반 이상을 줄인다.
- 포맷 우선순위: 사진은 **AVIF → WebP → JPEG**, 단순 그래픽은 **SVG**, 애니메이션은 **WebM/MP4**. `<picture>`가 브라우저별 자동 선택을 처리한다.
- `<picture>` + 프리로드 결합 시 `type` 지정, 반응형 + 프리로드 결합 시 **`imagesrcset`/`imagesizes`** — 없으면 중복 다운로드가 발생한다.
- `srcset`의 `w` 디스크립터 + `sizes`가 화면 크기와 DPR을 모두 자동 처리한다. **`sizes`는 실제 CSS 레이아웃과 일치**해야 하고, 이미지 크기는 3~4개면 충분하다.
- **3x는 대부분 낭비다.** X의 실측: 2x 상한으로 데이터 38% 절감·로딩 32% 개선, 시각 차이는 인지 불가 수준.
- 품질 100%는 대역폭 낭비다. **75~85%가 업계 표준**이며 JPEG 압축이 버리는 것은 눈이 감지 못하는 고주파 디테일이다. 프로그레시브 JPEG는 같은 크기로 체감 속도를 크게 올린다.
- `loading="lazy"`(다운로드 시점) + `decoding="async"`(디코딩 방식)는 오프스크린 이미지의 표준 조합이고, **LCP 이미지에는 둘 다 쓰지 않는다.**
- 로딩 UX는 스켈레톤 → 대표 색상 → 블러-업(LQIP) 순으로 정교해진다. 블러-업은 1KB 프리뷰로 체감 성능을 크게 바꾸며, `aspect-ratio`가 CLS를 막는다.
- 자동화가 지속 가능성의 핵심이다. 정적은 빌드 시점(Sharp·Enhanced Image), 동적은 이미지 CDN, 프레임워크 프로젝트는 내장 컴포넌트.
- 최종 전달 전략: **CDN 자동 변환(`f_auto,q_auto`) + 브라우저 힌트(`preload`·`fetchpriority`) + 지연 로딩**이 맞물릴 때 최대 효과. LCP 후보 1~2개만 High로, 나머지는 lazy + low로.
- 우선순위: LCP 이미지 먼저 → 반복 이미지(섬네일) 자동화 → 나머지. 그리고 **측정→개선→재측정.**

## 다른 챕터와의 관계

- **Ch4(리소스 우선순위)**: 이미지의 기본 우선순위(Medium/Low)와 `fetchpriority`·`preload`의 원리를 다뤘고, 이 장은 그것을 이미지 도메인에 구체화한다. `imagesrcset` 프리로드가 그 연장선이다.
- **Ch5(프리로드 스캐너)**: `<picture>`·`srcset`이 HTML에 선언되어야 프리로드 스캐너가 발견한다는 원칙이 이 장의 전제다.
- **Ch2(네트워크 압축)**: JPEG·PNG·WebP가 "재압축하면 안 되는 포맷"인 이유(자체 압축)가 이 장의 포맷 이야기와 연결된다.
- **Ch10(코드 스플리팅)**: 블러-업 전환·스켈레톤의 레이아웃 일치 원칙이 청크 로딩 폴백 UX와 같은 문법을 공유한다.
- **Ch13(동영상 최적화)**: 애니메이션 GIF → 비디오 전환에서 시작된 논의가 코덱·비트레이트·스트리밍으로 확장된다.
- **Ch20(CLS)**: `width`/`height`·`aspect-ratio`로 이미지 공간을 예약하는 기법이 CLS 장의 핵심 도구다.
