# Chapter 22: 컴포넌트 최적화는 상태 범위를 줄이는 것에서 시작한다

## 핵심 질문

이름 하나 입력했는데 내비게이션·사이드바·푸터까지 전부 리렌더링된다 — 네트워크와 번들을 다 최적화했는데도 입력이 버벅이는 이유다. 가장 흔한 원인은 **상태를 최상위에 두는 습관**("나중에 필요할 수도 있으니까"). `React.memo`·`useMemo`는 증상 완화일 뿐 — 근본 원인은 **상태의 범위가 필요 이상으로 넓다**는 것이다. 메모이제이션에 의존하지 않고도 빠른 앱을 만들려면 무엇부터 해야 하는가? (이 장은 CSR 최적화에 집중 — RSC·아일랜드는 Ch16 참조.)

## 1. 프레임워크별 렌더링 모델 — 최적화의 전제

리렌더링 조건이 프레임워크마다 근본적으로 다르므로, 모델을 모르면 최적화가 엉뚱한 방향으로 간다.

### 1.1 리액트 — 불변성과 얕은 비교

상태 변경 → 컴포넌트 함수 재실행 → 이전/새 가상 DOM 비교(재조정) → 실제 DOM에 차이만 반영. 변경 감지는 **얕은 비교(참조)** — 그래서 두 가지 규칙이 나온다:

1. **불변성 필수**: `todo.completed = !todo.completed` 후 `setTodos(todos)`는 참조가 같아 **리렌더링되지 않는다.** `map` + 스프레드로 새 배열·새 객체를 만들어야 감지된다.
2. **부모 리렌더링은 자식 전체로 전파**: 프롭이 없거나 안 바뀐 자식도 함께 재실행된다. 막으려면 `React.memo`(프롭 얕은 비교) — 단 객체·함수 프롭은 렌더마다 새 참조라 memo가 무효화되므로 `useMemo`/`useCallback` 병행이 필요하다.

### 1.2 뷰 — 반응형 프락시의 자동 추적

`ref`/`reactive`(Proxy)가 접근·수정을 추적한다. **직접 수정해도**(`todo.completed = !todo.completed`, `todos.push(...)`) 자동 감지되고, **변경된 부분만** 정확히 업데이트한다 — 불변성 요구가 없다.

대가는 **깊은 반응성**: 중첩된 모든 속성이 Proxy로 래핑된다. 10,000개 사용자 × 중첩 프로필이면 초기화·메모리 비용이 크다 → `shallowReactive`/`shallowRef`로 최상위만 반응형으로. `computed`는 의존성을 **자동 추적**하는 캐싱(리액트 useMemo의 의존성 배열이 필요 없다).

### 1.3 스벨트 — 컴파일 타임 + 룬

컴파일 타임에 코드를 분석해 DOM 업데이트 코드를 미리 생성한다(런타임이 없거나 작음 → 작은 번들). 스벨트 5의 룬: `$state()`(깊은 반응성 — 직접 수정·push 가능), `$derived()`(파생 상태), `$effect()`(부수 효과). 재할당 패턴(`todos = [...todos, ...]`)도 여전히 유효 — 불변성 유지가 디버깅에 유리할 때 선택.

주의: 컴포넌트마다 업데이트 로직이 생성되므로 **컴포넌트가 많아지면 리액트·뷰보다 번들이 커질 수 있다.**

### 1.4 비교 요약

| 측면 | 리액트 | 뷰 | 스벨트 |
|---|---|---|---|
| 변경 감지 | 참조 비교(불변성 필수) | Proxy 자동 추적 | 컴파일 분석 + 룬 |
| 리렌더 범위 | 부모→자식 전파(memo로 차단) | 변경된 부분만 | 변경된 DOM만 |
| 대용량 데이터 | 메모이제이션 관리 | shallowReactive 필요 | 깊은 반응성 기본 |
| 번들/메모리 | 런타임 큼 | 중간 | 작음(대규모선 역전 가능) |
| 생태계 | 압도적 | 공식 도구 충실 | 상대적으로 작음 |

어느 것을 쓰든 **"상태 범위를 최소화하라"는 원칙은 동일**하다.

## 2. 상태는 사용하는 곳 가까이에 둬라 — 상태 콜로케이션

### 2.1 원리

프레임워크는 상태를 가진 컴포넌트부터 **아래로** 리렌더링을 전파한다. 상태가 최상위면 전체 트리가, 하위면 그 서브트리만 영향받는다. `searchQuery`가 `App`에 있으면 타이핑마다 Header·Sidebar·Footer까지 재실행 — `SearchBar` 안으로 내리면 **SearchBar만** 리렌더링된다. 이것이 상태 콜로케이션이고, 성능 최적화의 가장 기본이자 가장 효과적인 방법이다.

### 2.2 전역 상태가 꼭 필요한지 먼저 의심하라

전역이 진짜 필요한 경우는 생각보다 적다: **인증 정보, 테마 설정, 장바구니, 전역 알림(토스트)** 정도. 모달 열림/닫힘까지 전역 스토어에 두면 관리만 복잡해진다 — 모달을 여는 컴포넌트의 로컬 상태로 충분하다.

전역으로 올리기 전 세 가지 질문: ① 진짜 여러 컴포넌트에서 필요한가? ② 프롭 드릴링이 귀찮아서는 아닌가? ③ 이 상태의 생명주기가 앱 전체와 같은가, 특정 컴포넌트에 국한되는가?

### 2.3 상태를 트리 아래로 내리기

Dashboard가 userInfo·notifications·sidebarOpen·chartData·filterOptions를 전부 쥐고 있다면 — notifications는 Header로, chartData는 MainChart로, filterOptions는 FilterPanel로 내린다. 진짜 공유되는 userInfo만 남긴다. 효과: 리렌더링 범위 축소 + 컴포넌트 독립성(재사용 용이) + 가독성.

> **핵심 통찰**: 내릴지 말지의 판단 기준은 "몇 개 컴포넌트에서 쓰이는가"가 아니라 **"이 상태의 생명주기와 책임이 어디에 있는가"** 다. 검색창 입력값은 검색 컴포넌트의 책임 → 안에. 검색 결과는 여러 곳에 보여야 함 → 위에. 모달 열림 상태는 모달의 생명주기와 같음 → 모달 안에.

### 2.4 컴포넌트 합성 — "상태를 올리지 말고, 컴포넌트를 내려라"

상태를 위로 올리는(Lifting State Up) 대신, **상태를 가진 컴포넌트를 children으로 전달**한다:

```tsx
// ✅ Layout은 children을 렌더링만 — Counter의 상태 변경에 영향받지 않음
function App() {
  return (
    <Layout>
      <Counter /> {/* 상태는 Counter 안에 */}
    </Layout>
  );
}
```

`count`가 `App`에 있으면 클릭마다 `Layout`도 리렌더링되지만(children이 매번 새 요소로 생성), 상태를 `Counter`에 두면 `children`은 App에서 한 번 생성된 참조라 Layout이 재실행되지 않는다. 탭 UI도 같은 원리 — `activeTab`은 `Tabs`에 있지만 각 탭 콘텐츠의 내부 상태는 독립적으로 유지된다.

## 3. 전역 상태 공유는 구독 범위를 최소화해야 한다

### 3.1 공유 메커니즘별 리렌더링 특성

- **리액트 컨텍스트**: 값이 바뀌면 **구독하는 모든 컴포넌트가 리렌더링** — 일부 필드만 써도 전체를 구독한다(선택적 구독 불가). 게다가 Provider의 value 객체를 렌더마다 새로 만들면 참조가 항상 바뀐다 — `useMemo`로 감싸도 "불필요한 객체 생성 방지"일 뿐, 값이 바뀌면 여전히 전 구독자가 리렌더링된다.
- **뷰 provide/inject**: 반응형 덕분에 **속성 단위 추적**이 된다(user.name 변경 → name 사용 컴포넌트만). 단 객체 자체 교체나 깊은 중첩은 여전히 문제 — 상태별로 분리해 provide하는 것이 정석.
- **스벨트 스토어**: `$user` 구독은 객체 전체 구독 — name만 바뀌어도 theme 사용 컴포넌트가 리렌더링.

### 3.2 해법 1 — 컨텍스트 분리

변경 빈도가 다른 상태를 한 컨텍스트에 두지 않는다. `UserContext`/`ThemeContext`/`NotificationContext`로 나누고 각각 독립적으로 `useMemo`하면 theme 변경 시 ThemeToggle만 리렌더링된다. Provider 중첩이 지저분하면 `AppProviders` 커스텀 컴포넌트로 감싼다.

### 3.3 해법 2 — 상태와 액션 분리

상태는 자주 바뀌지만 액션 함수는 안 바뀐다. `UserStateContext`와 `UserActionsContext`(액션 객체는 의존성 없는 useMemo로 고정)로 나누면 — **쓰기 전용 컴포넌트**(폼)는 상태가 바뀌어도 리렌더링되지 않는다.

### 3.4 해법 3 — 원자적 상태 관리

- **주스탄트**: 셀렉터로 선택적 구독 — `useStore((state) => state.theme)`. 반환값을 `Object.is`로 비교하므로 단일 값 선택이면 그 값이 바뀔 때만 리렌더링. 여러 값을 객체로 묶어 반환하려면 `useShallow` 필요.
- **조타이**: atom 단위 — 컴포넌트는 필요한 atom만 구독. **파생 atom**(`atom((get) => get(userAtom).name)`)으로 name만 구독하면 age 변경에 반응하지 않는다. (리코일은 유지보수 중단 — 새 프로젝트는 Jotai/Zustand.)
- **피니아**(뷰): 스토어를 모듈로 분리 — useUserStore 사용자는 user 변경에만 반응.

원리는 컨텍스트 분리와 같다 — **상태를 작은 단위로 나누고 필요한 조각만 구독** — 라이브러리가 그 로직을 대신해 줄 뿐이다.

## 4. 메모이제이션은 최후의 수단이다

### 4.1 리액트 3종 도구의 관계

- `React.memo` = **컴포넌트** 메모이제이션(프롭 얕은 비교로 리렌더링 스킵)
- `useMemo` = **값** 메모이제이션(의존성 불변 시 같은 참조 반환)
- `useCallback` = **함수** 메모이제이션

핵심: **memo만으로는 부족하다.** 부모가 렌더마다 `data = [...]`를 새로 만들면 참조가 바뀌어 memo가 뚫린다 — `useMemo`로 data 참조를 고정해야 한다. 콜백 프롭도 마찬가지 — `useCallback` + **함수형 업데이트**(`setItems((prev) => [...prev, item])`)로 의존성 배열까지 비우면 함수가 한 번만 생성된다.

### 4.2 뷰의 메모이제이션 기법

뷰는 자동 추적 덕에 명시적 메모이제이션이 훨씬 덜 필요하다. 도구들:

- **computed 체이닝**: 검색→카테고리 필터→정렬을 별도 computed로 나누면 sortBy만 바뀔 때 정렬만 재계산된다(하나에 다 넣으면 뭐가 바뀌든 전체 재계산).
- **shallowRef/shallowReactive**: 대용량 데이터의 최상위만 반응형. 내부 수정 후엔 `triggerRef`로 수동 트리거. 테이블 전체 교체 패턴에 적합.
- **markRaw**: 반응성이 아예 불필요한 객체(차트 인스턴스, 수천 건 정적 데이터)를 프락시에서 제외.
- **v-memo**: 템플릿 블록 메모이제이션 — `v-memo="[item.selected]"`면 selected 변경 시에만 그 블록 재렌더링(큰 리스트에 유효). 정적 콘텐츠는 `v-once`.

### 4.3 메모이제이션이 오히려 느려지는 경우

메모이제이션은 공짜가 아니다 — 의존성 비교 + 캐시 저장 + 참조 유지 비용이 든다.

1. **단순 계산**: `useMemo(() => a + b, [a, b])` — 덧셈보다 비교·캐시 관리가 더 느리다.
2. **의존성이 자주 변경**: query·filters·sortBy·page가 수시로 바뀌면 캐시 무효화만 반복 — 비교 비용만 추가.
3. **메모리**: 10만 항목을 가공해 메모이제이션하면 원본+가공본 2배 메모리 — 차라리 가상 스크롤·페이지네이션.
4. **React.memo 비교 비용**: 프롭 6개면 매번 6회 비교 — 컴포넌트 렌더링 자체가 싸면 비교가 더 비싸다.

### 4.4 적용 기준 — 측정이 먼저

메모이제이션을 쓰는 경우는 넷뿐: ① **비용이 큰 계산**(정렬+그룹핑+집계 50ms급) ② **참조 동등성이 필요**(자식이 React.memo이고 객체/함수 프롭 전달) ③ **무거운 리스트 항목**(항목 컴포넌트 memo + 콜백 useCallback) ④ **Profiler 측정으로 병목이 확인된 경우**. "느릴 것 같다"는 추측으로 남발하면 오히려 나빠진다. 리액트 18+에서는 `useTransition`/`useDeferredValue`로 렌더링 우선순위를 조정하는 선택지도 있다.

## 5. 리스트 렌더링에서 키는 성능의 핵심이다

### 5.1 키가 없으면 — 위치 기반 비교

키가 없으면 프레임워크는 **위치(인덱스)로** 이전/새 리스트를 비교한다. 맨 앞에 1개를 추가하면 모든 위치의 내용이 "바뀐 것"이 되어 **전체가 업데이트**된다. 더 나쁜 건 DOM 상태 어긋남 — 첫 입력 필드에 타이핑한 내용(비제어 입력 상태)이 새로 추가된 항목에 붙어 보인다. 위치 0의 DOM이 재사용되기 때문이다. 리액트·뷰·스벨트(`{#each todos as todo (todo.id)}`) 모두 동일하다.

### 5.2 인덱스 키가 안 되는 이유

`key={index}`는 경고만 없앨 뿐 키의 목적("**항목의 정체성**")을 놓친다. 가격순 정렬을 하면 인덱스 0은 여전히 키 0 — 리액트는 "같은 항목의 내용이 바뀌었다"고 판단해 **3개 전부 업데이트**하고, 사용자가 수정한 입력값이 **엉뚱한 상품에 옮겨 붙는다**(노트북 가격이 마우스에 표시되는 버그). 중간 삽입도 같은 문제.

예외: **정적 리스트**(재정렬·추가·삭제가 절대 없는 내비게이션 메뉴 등)만 인덱스 허용. 확신이 없으면 항상 고유 ID.

### 5.3 좋은 키의 조건과 전략

좋은 키 = **고유** + **안정적**(리렌더마다 불변) + **예측 가능**(같은 항목 = 같은 키).

- **최선: DB ID** — 서버가 준 고유 식별자 그대로.
- ID가 없으면 **nanoid** — 단, **데이터 추가 시점에 생성해 저장**한다. `key={nanoid()}`처럼 렌더링 시점 생성은 매번 다른 키가 되어 무의미하다.
- **복합 키**: `` `${event.date}-${event.title}` `` — 조합의 고유성과 두 필드의 불변이 전제.
- 원시 값 배열은 값 자체를 키로(중복 없을 때만).
- **금지**: `Math.random()`/`Date.now()`(매번 바뀜), 객체(참조 비교 불가), 중복 가능 값.

### 5.4 가상 스크롤 — 수천 개 이상일 때

키를 완벽히 써도 DOM 노드 수만 개면 느리다. 가상 스크롤은 **화면에 보이는 항목만 렌더링**하고 스크롤에 따라 교체한다 — 10,000개 데이터라도 DOM엔 8~10개.

- 리액트: **TanStack Virtual**(`useVirtualizer` — count·estimateSize, `getVirtualItems()`를 absolute + translateY로 배치) 또는 react-window.
- 뷰: vue-virtual-scroller(`RecycleScroller`, key-field 지정). 스벨트: svelte-virtual-list.

주의 4가지: ① 고정/예상 높이 필요(가변 높이는 성능 저하) ② 키 여전히 필수 ③ 스크롤 위치 복원은 별도 처리 ④ **접근성** — 스크린 리더가 미렌더링 항목을 인식 못할 수 있다.

> **실무 팁**: 가상 스크롤은 **1,000개 이상**부터 고려. 수백 개면 일반 렌더링으로 충분하고, 그보다 먼저 **페이지네이션·무한 스크롤로 항목 수 자체를 제한**하는 것이 더 간단하고 효과적일 수 있다.

## 6. 렌더링 성능을 측정하고 디버깅하라

### 6.1 리액트 개발자 도구 Profiler

녹화 → 문제 동작 수행 → 중지 → Flame Chart(트리+시간 색상)/Ranked Chart(느린 순). 컴포넌트 클릭 시 **"Why did this render?"** — 프롭 변경/상태 변경/부모 리렌더링 중 원인을 정확히 알려준다. 활용: ① 값은 같은데 참조만 바뀐 리렌더링 찾기 ② 부모→자식 전파 확인(memo로 차단 후보) ③ Ranked에서 최대 병목부터.

코드로는 `<Profiler id onRender={callback}>` — `actualDuration > 16ms`(60fps 기준)이면 경고, 프로덕션 수집도 가능.

### 6.2 뷰 개발자 도구

Performance 패널로 컴포넌트 렌더·이벤트 핸들러·생명주기 시간을 타임라인으로. `app.config.performance = true`(개발 모드)를 켜면 User Timing으로 마킹되어 **크롬 Performance 탭에도 뷰 컴포넌트 타이밍이 표시**된다. computed/watch에 로그를 심어 재계산 빈도 확인, 컴포넌트 업데이트 시 초록 깜빡임으로 시각 확인.

### 6.3 why-did-you-render

불필요한 리렌더링을 **자동 감지**해 콘솔 경고하는 리액트 라이브러리. 대표 경고: *"different objects that are equal by value"* — 내용은 같은데 참조만 바뀐 프롭 → 부모에서 useMemo로 안정화하라는 신호. 설정: 진입점 최상단에서 `whyDidYouRender(React, { trackAllPureComponents: true })`, 개별 컴포넌트는 `Component.whyDidYouRender = true`. 주의: **개발 전용**(오버헤드), 거짓 양성 존재, 중요 컴포넌트부터 점진 적용.

### 6.4 Performance API — 정밀 측정과 프로덕션 모니터링

`performance.mark()`/`measure()`로 구간 측정. 리액트에서는 **렌더 함수에서 start 마킹 + `useLayoutEffect`에서 end 마킹** — DOM 커밋까지를 정확히 잡는다(`useEffect`는 페인트 이후라 대기 시간이 섞임). `useRenderTime(componentName)` 커스텀 훅으로 재사용하고, `PerformanceObserver`(entryTypes: measure)로 16ms 초과 렌더를 자동 수집해 모니터링 서비스로 전송한다.

- 임곗값 감각: 16ms(60fps) / 100ms(즉각 반응 한계) / 1000ms(사고 흐름 한계).
- 측정 후 `clearMarks`/`clearMeasures`로 정리(메모리).
- 크롬 Performance 탭의 User Timing 절에서 커스텀 마크를 시각 확인.

| 리액트에서 객체 직접 수정 후 setState | 참조가 같아 변경 감지 실패 — 리렌더링 안 됨 | map + 스프레드로 새 객체/배열 |
| 하나의 컨텍스트에 모든 상태 | 일부만 써도 전체 구독 — theme 변경에 유저 프로필 리렌더 | 컨텍스트 분리 + 상태/액션 분리, 또는 원자적 상태 관리 |

| 수만 행을 그대로 렌더링 | DOM 폭증 — 초기 렌더·메모리·스크롤 모두 저하 | 페이지네이션 → 가상 스크롤(1,000+) |
| 뷰에서 대용량 중첩 데이터를 reactive로 | 모든 중첩 속성 Proxy 래핑 — 초기화·메모리 비용 | shallowReactive/shallowRef/markRaw |

## 측정과 검증

- **리액트 Profiler**: Flame/Ranked Chart + "Why did this render?" — 최적화 전후 녹화 비교로 개선을 숫자로 증명.
- **뷰**: 개발자 도구 Performance + `app.config.performance = true`로 크롬 타임라인 통합.
- **why-did-you-render**: 개발 중 실시간으로 참조 불안정 프롭 감지.
- **Performance API + useLayoutEffect**: 렌더→커밋 시간 정밀 측정, PerformanceObserver로 16ms 초과 자동 리포트.
- **최종 지표**: INP(실사용자), 저사양 모바일 테스트, 크롬 Performance 탭의 긴 작업 확인.

## 요약

- 컴포넌트 성능의 출발점은 메모이제이션이 아니라 **상태 범위 축소**다. 상태를 사용하는 곳 가까이 두면(콜로케이션) 리렌더링 범위가 구조적으로 줄어든다 — 전역은 인증·테마·장바구니·알림 정도만.
- 프레임워크 모델을 알아야 최적화가 맞는다: 리액트 = 참조 비교(불변성 필수 + 부모→자식 전파), 뷰 = Proxy 자동 추적(깊은 반응성 비용 — shallow*), 스벨트 = 컴파일 + 룬(깊은 반응성 지원, 대규모선 번들 역전).
- 상태 내리기의 판단 기준은 **생명주기와 책임**. 내릴 수 없으면 **컴포넌트 합성**("상태를 올리지 말고 컴포넌트를 내려라") — children 참조 고정으로 중간 컴포넌트 리렌더링을 차단한다.
- 전역 상태는 **구독 범위 최소화**: 컨텍스트 분리(변경 빈도별) + 상태/액션 분리, 또는 원자적 상태 관리(주스탄트 셀렉터·조타이 atom·피니아 모듈)로 필요한 조각만 구독.
- **메모이제이션은 최후의 수단**: memo/useMemo/useCallback은 세트로 써야 효과가 있고(참조 안정화), 단순 계산·잦은 의존성 변경·대용량 캐시에는 오히려 손해다. 50ms급 계산·참조 동등성·측정 확인 — 이 세 경우에만.
- **리스트 키 = 항목의 정체성**: 키 없음/인덱스 키는 위치 기반 비교로 전체 업데이트 + 입력 상태 어긋남 버그를 만든다. DB ID 최선, nanoid는 데이터 생성 시점에. 수천 개는 가상 스크롤(그 전에 항목 수 제한 먼저).
- 측정 없이 최적화 없다: Profiler("Why did this render?"), why-did-you-render, Performance API(useLayoutEffect 마킹). 원칙 한 줄 — **"상태는 가능한 한 좁게, 변경은 명확하게, 측정은 빈번하게, 최적화는 신중하게."**

## 다른 챕터와의 관계

- **Ch16(하이드레이션)**: 이 장이 다루지 않는 서버 중심 렌더링(RSC·아일랜드)의 짝 — 클라이언트 리렌더링 최적화(이 장)와 하이드레이션 제거(Ch16)가 프레임워크 성능의 양 축이다.
- **Ch17(데이터 캐싱)**: 서버 상태는 리액트 쿼리로, UI 상태는 이 장의 콜로케이션 원칙으로 — 상태의 종류별 관리 전략이 완성된다.
- **Ch18(자바스크립트 실행)**: 16ms 프레임 예산, 10,000개 리스트의 긴 작업(가상 스크롤 해법)이 이 장의 리스트·측정 논의와 직결된다.
- **Ch19(메모리 누수)**: useCallback 의존성·클로저 캡처 설계가 두 장에 걸쳐 있다. 메모이제이션 캐시도 메모리 비용이다.
- **Ch21(애니메이션)**: Profiler로 찾은 리렌더링 병목이 프레임 드롭의 원인일 때 — 상태 갱신 대신 ref+직접 스타일 업데이트 같은 결합 지점.
- **Ch23(서드파티)**: 프레임워크 코드(통제 가능)를 최적화한 다음 남는 것 — 통제 밖처럼 보이는 서드파티를 다음 장에서 다룬다.
