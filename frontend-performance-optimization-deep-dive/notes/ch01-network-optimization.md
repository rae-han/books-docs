# Chapter 1: 네트워크 최적화는 가장 손쉬운 성능 개선이다

## 핵심 질문

성능 최적화 책의 첫 장을 왜 자바스크립트나 렌더링이 아닌 네트워크로 시작하는가? 코드를 한 줄도 바꾸지 않고 설정만으로 수백 밀리초를 단축할 수 있다면, 그것이 가장 먼저 손대야 할 영역이 아닐까? 그리고 인프라 팀의 영역처럼 보이는 CDN·HTTP 프로토콜에 프런트엔드 개발자가 관여해야 하는 이유는 무엇인가?

## 1. 프런트엔드 개발자가 네트워크를 봐야 하는 이유

프런트엔드 개발자는 웹 성능을 논할 때 리액트 컴포넌트의 불필요한 리렌더링을 제거하거나 알고리즘을 개선하는 일을 먼저 떠올린다. 분명 중요한 작업이다. 그러나 사용자가 체감하는 가장 큰 병목은 네트워크 레이어에서 발생하는 경우가 많다. 아무리 효율적인 코드를 작성해도 그 코드가 사용자에게 도달하는 과정이 느리면 결국 느린 웹사이트가 된다.

### 1.1 사용자가 체감하는 속도의 대부분은 네트워크 시간이다

웹 페이지 로딩 시간을 분석하면 자바스크립트 실행이나 렌더링보다 네트워크 전송 시간이 훨씬 긴 경우가 대부분이다. Slow 4G 환경(크롬 개발자 도구 기준 1.44Mbps)에서 1MB 자바스크립트 번들을 다운로드하는 데 약 5.7초가 걸린다. 반면 그 번들을 파싱하고 실행하는 데는 보통 수백 밀리초면 충분하다.

다운로드 시간 계산에서 자주 틀리는 지점이 단위다. 네트워크 속도는 Mbps(*megabits per second - 초당 메가비트*), 파일 크기는 MB(*megabyte - 메가바이트*)로 표시되는데 둘은 다른 단위다. 1바이트는 8비트이므로 1MB = 8Mb다. 소문자 `b`는 비트, 대문자 `B`는 바이트를 의미한다.

```
다운로드 시간 = (파일 크기 × 8) ÷ 네트워크 속도

(1MB × 8) ÷ 1.44Mbps = 8 ÷ 1.44 ≈ 5.56초 ≈ 5.7초
```

이는 이론적 최대 속도 기준이며, 실제로는 TCP 오버헤드·패킷 손실·네트워크 혼잡으로 더 오래 걸린다.

HTTP Archive의 2025년 9월 데이터에 따르면 모바일 웹사이트의 중앙값 기준 총 페이지 무게는 약 2,604KB이고, 그중 자바스크립트가 약 677KB를 차지한다. 4G LTE 환경(실효 속도 약 8~10Mbps)에서도 이 정도 리소스를 받는 데 2~3초가 걸리며, 여기에 TTFB(*Time to First Byte - 첫 바이트 응답까지의 시간*)까지 더하면 사용자가 의미 있는 콘텐츠를 보기까지는 더 오래 걸린다.

더 중요한 것은 **네트워크 속도의 편차**다. 개발자가 일하는 사무실 와이파이는 보통 50~100Mbps의 안정적인 속도를 제공하지만, 실제 사용자는 지하철·버스·카페에서 접속한다. 4G 모바일 환경의 실효 속도는 10~30Mbps로 낮고 지연 시간과 패킷 손실률도 높다. 신호가 약한 지하철이나 건물 내부에서는 이 차이가 더 커진다.

> **핵심 통찰**: 개발자의 고사양 기기와 안정적인 네트워크에서 재현되지 않는 성능 문제가 실제 사용자에게는 일상이다. 성능 측정은 항상 사용자 환경을 흉내 낸 조건(스로틀링, 저사양 디바이스)에서 해야 한다.

### 1.2 투자 대비 효과가 가장 크다

네트워크 최적화가 매력적인 이유는 적은 노력으로 큰 효과를 내기 때문이다. 자바스크립트 리팩터링이나 렌더링 로직 개선은 시간이 오래 걸리고 기능 변경을 동반하기도 한다. 반면 네트워크 최적화는 대부분 설정 변경이나 간단한 코드 추가로 끝난다.

- **브로틀리 압축 활성화**: 엔진엑스 구성 파일에 몇 줄 추가하는 것만으로 자바스크립트 번들 전송 크기를 Gzip 대비 추가로 줄인다.
- **HTTP/1.1 → HTTP/2 전환**: 멀티플렉싱으로 병렬 전송 효율이 높아진다.
- **이미지 CDN 도입 또는 WebP 전환**: 이미지 전송량을 절반 이상 줄일 수 있다.

또 하나의 장점은 **사이드 이펙트가 거의 없다**는 점이다. 자바스크립트 코드를 최적화하다 보면 가독성이 떨어지거나 유지보수가 어려워지는 경우가 있다. 하지만 압축을 활성화하거나 HTTP/2를 사용한다고 해서 코드가 복잡해지지는 않는다. 기존 코드는 그대로 두고 인프라 레이어에서 성능을 개선하므로 개발 워크플로에 미치는 영향이 최소화된다.

### 1.3 프런트엔드 개발자가 적극적으로 의견을 내야 한다

HTTP 프로토콜 버전, 압축 알고리즘, CDN 설정은 대부분 서버나 인프라 레벨에서 결정된다. 그렇다고 프런트엔드 개발자가 방관해도 된다는 뜻은 아니다. 오히려 네트워크 성능의 영향을 가장 직접적으로 받는 것이 프런트엔드이므로 적극적으로 의견을 내야 한다.

프런트엔드 개발자는 실제 사용자 경험에 가장 가까운 위치에 있다. 크롬 개발자 도구의 Network 탭을 열면 리소스가 얼마나 느리게 로드되는지, TTFB가 얼마나 긴지, 압축이 적용됐는지 바로 확인할 수 있다. 이런 정보는 인프라 팀보다 프런트엔드 개발자가 먼저 발견하는 경우가 많다.

핵심은 **구체적인 요구사항을 전달하는 것**이다.

| 나쁜 요청 | 좋은 요청 |
|---|---|
| "사이트가 느려요" | "HTTP/1.1을 사용 중인데 HTTP/2로 전환하면 멀티플렉싱으로 병렬 전송이 가능합니다" |
| "CDN을 도입해주세요" | "정적 리소스에 `Cache-Control: public, max-age=31536000, immutable` 헤더를 설정하면 재방문 시 네트워크 요청을 줄일 수 있습니다" |

네트워크 최적화가 누락되는 이유가 항상 기술적 어려움 때문만은 아니다. 인프라 팀은 서버 안정성·보안·배포 자동화에 집중하고 있어 성능 최적화의 우선순위가 낮을 수 있다. 이럴 때 "이 최적화가 사용자 경험에 직접적인 영향을 미친다"는 것을 데이터와 함께 전달하면 도움이 된다.

물론 프런트엔드 개발자가 직접 할 수 있는 것도 많다. 번들러 설정으로 파일명에 해시를 포함시키면 브라우저가 리소스를 오래 캐싱할 수 있고, Next.js나 버셀 같은 플랫폼을 쓰면 HTTP/2·브로틀리 압축·CDN이 이미 기본 적용돼 있다. 버셀·클라우드플레어 페이지·AWS 앰플리파이 같은 플랫폼은 글로벌 CDN, HTTP/3, 브로틀리 압축, 자동 SSL을 기본 제공하므로 코드를 푸시하기만 하면 최적화된 상태로 배포된다.

> **실무 팁**: 클라우드플레어는 무료 플랜에서도 HTTP/3와 브로틀리를 지원하며 대시보드에서 클릭 몇 번으로 설정을 바꿀 수 있다. 레거시 자체 서버를 운영한다면 인프라 팀과의 협업이 필수지만, 그 출발점은 프런트엔드 개발자의 문제 인식이다.

### 1.4 네트워크 최적화는 다른 최적화의 전제 조건이다

자바스크립트 실행 시간을 100ms 줄여도 그 자바스크립트를 다운로드하는 데 5초가 걸린다면 사용자는 여전히 5.1초를 기다린다. 반면 네트워크 최적화로 다운로드 시간을 2초로 줄이면 실행 시간이 그대로여도 전체는 2.2초로 단축된다.

핵심 웹 지표 관점에서도 네트워크는 모든 지표에 영향을 미친다.

- **LCP(*Largest Contentful Paint - 가장 큰 콘텐츠 요소의 렌더링 시점*)**: 해당 요소가 이미지라면 네트워크 속도가 LCP를 직접 결정한다.
- **CLS(*Cumulative Layout Shift - 누적 레이아웃 이동*)**: 이미지 크기를 명시하지 않거나 웹폰트 로딩이 늦어지면 증가한다.
- **INP(*Interaction to Next Paint - 상호작용 후 다음 페인트까지의 시간*)**: 메인 스레드가 자바스크립트 파싱·실행으로 바쁘면 입력에 반응하지 못하는데, 큰 번들을 빠르게 전송하는 것이 첫 단계다.

> **핵심 통찰**: 아무리 효율적인 코드를 작성해도 그 코드가 사용자에게 빠르게 도달하지 못하면 의미가 없다. 반대로 네트워크를 최적화하면 코드를 바꾸지 않아도 성능이 개선되는 경우가 많다.

## 2. CDN과 엣지 캐싱의 작동 원리

### 2.1 물리적 거리가 성능에 미치는 영향

네트워크 지연은 크게 두 가지로 나뉜다.

- **전송 지연(*transmission delay*)**: 데이터를 네트워크 링크에 올리는 데 걸리는 시간. 데이터 크기와 대역폭이 결정한다.
- **전파 지연(*propagation delay*)**: 데이터가 물리적 매체를 통해 이동하는 데 걸리는 시간. 순전히 거리의 문제다.

빛은 진공에서 초당 약 30만 km를 이동하지만 광섬유에서는 약 20만 km로 느려진다. 지구 규모의 거리에서는 무시할 수 없는 지연이 된다.

| 출발지 → 도착지 | 거리 | 이론적 RTT | 실제 RTT | 비고 |
|---|---|---|---|---|
| 서울 → 도쿄 | ~1,160km | ~12ms | 30~50ms | 해저 케이블 |
| 서울 → 미국 서부 | ~9,600km | ~96ms | 150~200ms | 태평양 횡단 |
| 서울 → 미국 동부 | ~11,000km | ~110ms | 200~250ms | 더 많은 라우팅 |
| 서울 → 유럽(런던) | ~8,800km | ~88ms | 300ms+ | 복잡한 라우팅 경로 |

RTT(*Round Trip Time - 요청과 응답의 왕복 시간*)가 250ms라면, 페이지 로딩에 필요한 리소스가 10개만 되어도 순수하게 왕복 시간만으로 2.5초가 소모된다. HTTP/2의 멀티플렉싱으로 병렬 전송이 가능하지만 초기 연결 수립과 중요 리소스 체인은 여전히 RTT의 영향을 받는다.

여기에 네트워크 불안정성이 더해진다. 국제 해저 케이블은 여러 국가를 거치고 구간마다 다른 ISP를 통과하므로 라우팅 지연·혼잡·패킷 손실이 발생한다. WebPageTest로 서울에서 미국 오리진 서버에 접속하면 같은 리소스도 시간대에 따라 TTFB가 150ms에서 500ms까지 변동한다.

> **핵심 통찰**: 물리적 거리는 어떤 최적화로도 극복할 수 없는 절대적 제약이다. 빛의 속도를 넘을 수 없으므로 유일한 해결책은 콘텐츠를 사용자와 가까운 곳에 미리 배치하는 것이다.

### 2.2 CDN의 계층적 캐싱 구조

CDN(*Content Delivery Network - 콘텐츠 전송 네트워크*)은 전 세계에 분산된 서버 네트워크로 콘텐츠를 제공하는 시스템이다. 원본 서버는 한 곳에만 있지만 CDN은 콘텐츠를 여러 서버에 복제해 배치하므로, 사용자는 가장 가까운 CDN 서버에서 응답을 받는다.

대부분의 CDN은 3계층 캐싱 구조를 사용한다.

```
      사용자 (서울)
           │ 요청
           ▼
  ┌─────────────────────┐
  │  엣지 캐시 (서울 POP) │  ── Cache Hit ──▶ 응답: 10ms 이하
  └─────────┬───────────┘
            │ Cache Miss
            ▼
  ┌─────────────────────┐
  │ 리전 캐시 (한국/아시아)│  ── Cache Hit ──▶ 응답: 20~30ms
  └─────────┬───────────┘
            │ Cache Miss
            ▼
  ┌─────────────────────┐
  │  오리진 서버 (미국)   │  ─────────────▶ 응답: 200ms+
  └─────────────────────┘
```

- **오리진 서버**: 원본 콘텐츠가 저장된 서버. 보통 단일 지역에 위치한다.
- **리전 캐시**: 대륙이나 국가 단위로 배치된 중간 계층 캐시.
- **엣지 캐시**: 사용자와 가장 가까운 POP(*Point of Presence - 접속 거점*)에 위치하며 주요 도시마다 여러 개가 배치된다.

첫 번째 사용자의 요청은 오리진까지 올라가므로 느리지만, 이후 사용자들은 엣지나 리전 캐시에서 즉시 응답을 받는다.

CDN이 콘텐츠를 얼마나 오래 캐싱할지는 오리진 서버가 HTTP 응답 헤더로 제어한다.

- `Cache-Control: public, max-age=31536000`: CDN이 1년간 캐싱
- `Cache-Control: no-cache`: CDN이 매번 오리진에 재검증 요청
- `Cache-Control: private`: CDN 캐싱을 완전히 차단

해시가 포함된 파일명처럼 변하지 않는 리소스는 긴 `max-age`를, 자주 변경되는 HTML은 짧은 `max-age`나 `no-cache`를 쓰는 것이 일반적이다.

### 2.3 엣지에서 할 수 있는 최적화

엣지 서버는 단순 캐싱을 넘어 다양한 최적화를 수행할 수 있다. 가장 기본은 정적 리소스 캐싱이다. 자바스크립트·CSS·이미지·폰트처럼 변경이 드문 리소스를 엣지에 캐싱하면 오리진 부하를 줄이고 응답 속도를 개선한다. 빌드 시 파일명에 해시를 포함시키면(예: `app.a3f2c1d.js`) 캐시 무효화도 자동으로 처리된다.

최근에는 엣지 컴퓨팅(*edge computing*)으로 엣지에서 간단한 로직을 실행하는 것도 가능해졌다. 지역별 콘텐츠 분기, 간단한 A/B 테스트, 이미지 리사이징·포맷 변환 등이 여기에 해당한다.

CDN 도입 시에는 캐시 무효화 전략, 원본 서버와의 일관성 유지, 비용 관리를 함께 고려해야 한다. `Cache-Control` 헤더를 잘못 설정하면 오래된 콘텐츠가 계속 제공되거나, 반대로 캐시 히트율이 낮아져 CDN 효과가 반감된다.

### 2.4 프런트엔드 개발자가 해야 할 CDN 설정

**첫째, 정적 리소스에 적절한 캐시 헤더 설정하기**

웹팩이나 비트는 기본적으로 빌드 파일명에 해시를 포함한다(`main.js` → `main.a1b2c3d4.js`). 내용이 바뀌지 않는 한 파일명이 동일하므로 긴 캐시 시간을 설정해도 안전하다.

```nginx
# 엔진엑스 예시
location ~* \.(js|css|png|jpg|jpeg|gif|svg|woff|woff2)$ {
    expires 1y;
    add_header Cache-Control "public, immutable";
}

location = /index.html {
    expires -1;
    add_header Cache-Control "no-cache";
}
```

파일 내용이 바뀌면 해시값이 변경되어 파일명도 바뀌므로 캐시 무효화가 자동으로 처리된다. 반면 HTML은 `no-cache`로 설정해 매번 최신 버전을 확인하도록 한다.

**둘째, CDN 서비스 선택하고 연결하기**

버셀·넷리파이·클라우드플레어 페이지 같은 정적 호스팅 서비스는 CDN이 기본 탑재돼 있어 배포하면 자동으로 전 세계에 배포된다. Next.js·Nuxt·SvelteKit은 이러한 플랫폼과 통합이 잘 돼 있다. 기존 서버가 있다면 클라우드플레어나 AWS 클라우드프런트를 오리진 앞에 두면 된다.

프레임워크에 따라 추가 설정이 필요하다. Next.js에서 정적 리소스를 CDN으로 서빙하려면 `assetPrefix`를 설정한다.

```ts
// next.config.ts
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  // 정적 리소스를 CDN에서 로드
  assetPrefix: process.env.NODE_ENV === 'production' ? 'https://cdn.example.com' : '',
  // 이미지 최적화 CDN 설정
  images: {
    loader: 'custom',
    loaderFile: './cdn-loader.ts',
  },
};

export default nextConfig;
```

Next.js `Image` 컴포넌트는 별도의 이미지 최적화 서버를 거치므로 CDN을 쓰려면 커스텀 로더가 필요하다.

```ts
// cdn-loader.ts
import type { ImageLoaderProps } from 'next/image';

export default function cdnLoader({ src, width, quality }: ImageLoaderProps): string {
  const params = [`w=${width}`];
  if (quality) {
    params.push(`q=${quality}`);
  }
  const paramsString = params.join('&');
  return `https://cdn.example.com/_next/image?url=${encodeURIComponent(src)}&${paramsString}`;
}
```

Nuxt는 `nuxt.config.ts`의 `app.cdnURL`, 리믹스(Remix)는 `remix.config.js`의 `publicPath` 옵션을 사용한다. 버셀이나 넷리파이를 쓴다면 CDN이 자동 설정되므로 별도 작업이 필요 없다.

**셋째, 캐시 무효화 전략 수립하기**

CDN은 콘텐츠를 오래 캐싱하므로 배포해도 즉시 반영되지 않을 수 있다. 파일명 해싱을 쓰면 이 문제가 자동으로 해결된다. 코드가 바뀌면 파일명도 바뀌므로 CDN은 새로운 파일로 인식해 오리진에서 가져온다. HTML만 `no-cache`로 설정하면 사용자는 항상 최신 HTML을 받고, HTML이 참조하는 리소스도 올바른 버전을 받게 된다.

## 3. HTTP/2와 HTTP/3의 기술적 개선

### 3.1 HTTP 프로토콜의 기본 개념

HTTP(*HyperText Transfer Protocol*)는 웹에서 클라이언트와 서버가 데이터를 주고받는 통신 규약이다. 1991년 팀 버너스리가 월드와이드웹을 만들면서 함께 설계했고 지금도 웹의 근간이다.

HTTP는 요청-응답 구조로 동작한다. 요청은 HTTP 메서드(GET, POST, PUT, DELETE 등), URL, 헤더, 본문으로 구성되고, 서버는 상태 코드(200 OK, 404 Not Found 등)와 함께 응답한다.

HTTP는 계층적 프로토콜 스택 위에서 동작한다. 가장 하위는 TCP(*Transmission Control Protocol*)로, 데이터가 손실 없이 순서대로 전달되도록 보장하는 전송 계층 프로토콜이다. 암호화가 필요하면 TCP와 HTTP 사이에 TLS(*Transport Layer Security*) 계층이 추가된다. 주소창의 `https://`에서 `S`가 바로 TLS를 사용한다는 의미다.

HTTP의 핵심 특징 중 하나는 **무상태성(*stateless*)**이다. 각 요청은 완전히 독립적이며 서버는 이전 요청을 기억하지 않는다. 불편해 보이지만 확장성을 위한 설계다. 어떤 서버든 요청을 처리할 수 있으므로 서버를 쉽게 추가하거나 제거할 수 있다. 상태가 필요하면 쿠키·세션·JWT 토큰 같은 별도 메커니즘으로 해결한다.

버전별 발전 과정은 다음과 같다.

| 버전 | 연도 | 핵심 변화 |
|---|---|---|
| HTTP/1.0 | 1996 | 요청마다 새 TCP 연결 수립 |
| HTTP/1.1 | 1997 | 지속 연결(Keep-Alive), 청크 전송 인코딩, 파이프라이닝, Host 헤더 필수 |
| HTTP/2 | 2015 | 바이너리 프로토콜, 멀티플렉싱, HPACK 헤더 압축 |
| HTTP/3 | 2022 | TCP 대신 UDP 기반 QUIC 채택 |

### 3.2 HTTP/1.1의 근본적 한계

HTTP/1.1의 가장 큰 문제는 **HOL(*Head-of-Line*) 블로킹**이다. 하나의 TCP 커넥션에서 한 번에 하나의 요청만 처리할 수 있고, 파이프라이닝으로 여러 요청을 연속으로 보내더라도 응답은 요청 순서대로 받아야 한다. 첫 요청의 응답이 느리면 그 뒤의 모든 응답이 대기한다.

```
브라우저                              서버
   │ ① GET /slow.html (느린 요청)  ──▶ │
   │ ② GET /fast.js   (빠른 요청)  ──▶ │  slow.html 처리 중... (3초)
   │ ③ GET /quick.css (빠른 요청)  ──▶ │  ②③ 응답 대기 중 (블로킹)
   │                                   │
   │ ◀── ① slow.html (3초 후)          │
   │ ◀── ② fast.js   (즉시)            │  ②③은 준비됐어도
   │ ◀── ③ quick.css (즉시)            │  ①을 기다려야 함
   │
   └─ 전체 소요: 3초+
```

이를 우회하기 위해 브라우저는 도메인당 6~8개의 병렬 커넥션을 열었다. 하지만 커넥션마다 TCP 핸드셰이크와 TLS 협상을 거쳐야 하므로 오버헤드가 크고, 여러 커넥션이 동시에 대역폭을 쓰면서 혼잡 제어가 제대로 작동하지 않는 문제도 있었다.

개발자들은 다음과 같은 우회 기법을 사용했다.

- **도메인 샤딩(*domain sharding*)**: `static1.example.com`, `static2.example.com`처럼 여러 도메인으로 리소스를 분산해 브라우저가 더 많은 커넥션을 열도록 유도
- **CSS 스프라이트 이미지**: 작은 아이콘을 하나의 이미지로 합쳐 요청 수 감소
- **자바스크립트 번들링**: 작은 파일 100개보다 큰 파일 하나가 HOL 블로킹의 영향을 덜 받음

이러한 최적화는 캐싱 효율을 떨어뜨리고 필요 없는 리소스까지 다운로드하게 만드는 사이드 이펙트가 있었다. 또한 HTTP/1.1은 텍스트 기반이라 헤더 압축이 없어 요청마다 중복된 헤더(`Cookie`, `User-Agent` 등)를 반복 전송했다.

### 3.3 HTTP/2의 멀티플렉싱

HTTP/2의 가장 중요한 개선은 **멀티플렉싱(*multiplexing*)**이다. 하나의 TCP 커넥션에서 여러 스트림을 동시에 전송하며, 각 스트림은 독립적으로 처리되므로 한 스트림의 지연이 다른 스트림에 영향을 주지 않는다. 애플리케이션 레벨의 HOL 블로킹이 해결된 셈이다.

12개 리소스를 받는 상황을 비교해 보자.

- **HTTP/1.1(6개 병렬 커넥션)**: 처음에 6개 커넥션이 HTML·CSS·JS·IMG1~3을 동시에 받고, 400ms에 CSS·JS·IMG1~3이 완료되면 빈 커넥션에서 IMG4~8이 시작된다. 하지만 HTML은 800ms까지 커넥션을 점유하므로 IMG9는 800ms 시점에야 시작해 전체 완료까지 **1200ms**가 걸린다.
- **HTTP/2(단일 커넥션 멀티플렉싱)**: 12개 리소스를 모두 동시에 전송하므로 가장 큰 HTML 파일 기준 **800ms** 만에 완료된다.

HTTP/2의 다른 특징도 살펴보자.

- **바이너리 프로토콜**: 텍스트 메시지 대신 프레임(frame) 단위로 전송한다. HEADERS 프레임은 헤더를, DATA 프레임은 본문을 담는다. 파싱이 빠르고 오류 처리가 명확하다.
- **HPACK 헤더 압축**: 첫 요청에서 보낸 헤더는 압축 사전에 저장되고 이후 요청에서는 변경된 부분만 전송한다.
- **스트림 우선순위**: 클라이언트가 각 스트림에 우선순위와 가중치를 지정하고 서버가 이를 참고한다.

문제는 스트림 우선순위가 브라우저·서버 구현에 따라 일관되지 않았다는 점이다.

- **크롬(크로미움 계열)**: 리소스를 리스트 형태로 순차 처리. 렌더링 블로킹 리소스에는 효과적이지만 이미지는 하나씩 100% 완료될 때까지 기다려야 한다.
- **파이어폭스**: 가중치 기반 우선순위 트리를 구축하지만 실제로는 많은 리소스에 동일 우선순위를 할당해 라운드로빈으로 처리하는 경우가 많다.
- **사파리**: SPDY 시절의 단순한 방식을 유지하며 5단계 우선순위를 정적으로 가중치에 매핑한다.
- **구형 엣지(18 이하)·인터넷 익스플로러**: 우선순위 지원이 아예 없어 모든 요청이 대역폭을 균등하게 나눠 썼다. 2020년 크로미움 기반으로 전환한 엣지 79 이상은 크롬과 동일하다.

서버 측도 마찬가지다. 기술적으로는 지원하지만 서버 내부·TCP 스택·네트워크 경로의 버퍼링 문제로 실제로는 효과적으로 작동하지 않았다. 이러한 일관성 부족으로 HTTP/2의 스트림 우선순위는 **RFC 9113에서 공식 폐기(deprecated)**됐고, 2022년 6월 표준화된 **RFC 9218 "Extensible Prioritization Scheme for HTTP"**가 이를 대체한다.

> **참고 — RFC 9218의 `Priority` 헤더**<br><br>복잡한 스트림 의존성 트리 대신 간단한 키-값 쌍으로 우선순위를 지정한다. `Priority: u=1, i`는 긴급도(*urgency*) 1단계(가장 높음)이며 증분(*incremental*) 처리가 가능함을 의미한다. 긴급도는 0(가장 높음)부터 7(가장 낮음)까지 8단계이며, 증분 플래그는 이미지처럼 부분적으로 받아도 렌더링할 수 있는 리소스에 사용한다. HTTP/2와 HTTP/3 모두에서 동작한다. 크롬과 파이어폭스는 HTTP/3에서는 RFC 9218을 지원하지만 HTTP/2에서는 여전히 레거시 방식을 쓰는 경우가 많다.

HTTP/2에는 **서버 푸시(*Server Push*)** 기능도 있다. 서버가 클라이언트의 요청 없이 미리 리소스를 보내는 기능인데, 실전에서는 오히려 성능을 해치는 경우가 많았다. 클라이언트가 이미 캐시에 리소스를 가지고 있어도 서버가 이를 알 수 없어 불필요한 전송이 발생하기 때문이다. 최근에는 서버 푸시보다 `<link rel="preload">`를 선호한다.

### 3.4 HTTP/3와 QUIC 프로토콜

HTTP/2는 애플리케이션 레벨 HOL 블로킹을 해결했지만 **TCP 레벨의 HOL 블로킹**은 남아 있었다. TCP는 패킷 순서를 보장하므로 중간에 한 패킷이 손실되면 그 뒤의 모든 패킷이 재전송을 기다려야 한다. HTTP/2의 여러 스트림이 하나의 TCP 커넥션을 공유하므로 한 스트림의 패킷 손실이 다른 모든 스트림을 막는다. 패킷 손실률이 높은 모바일 네트워크에서는 HTTP/2가 HTTP/1.1보다 느린 경우도 있었다.

구글은 2013년 QUIC(*Quick UDP Internet Connections*)라는 전송 프로토콜을 개발했고, 2021년 IETF 표준(RFC 9000)으로 채택됐다. HTTP/3는 이 QUIC 위에서 동작하는 HTTP의 최신 버전이다.

QUIC는 UDP 기반이지만 그 위에 신뢰성·혼잡 제어·흐름 제어를 직접 구현한다. UDP를 택한 이유는 두 가지다. 첫째, 신뢰성·혼잡 제어·암호화 로직을 유저스페이스에서 자유롭게 설계·갱신할 수 있다. 둘째, 기존 NAT·방화벽 같은 중간 네트워크 장비를 통과하기 쉽다.

핵심은 **스트림 독립성**이다. QUIC의 각 스트림은 독립적인 순서 보장을 받으므로 한 스트림에서 패킷이 손실돼도 다른 스트림은 영향 없이 계속 데이터를 받는다.

```
HTTP/2 (TCP) - HOL 블로킹 발생        HTTP/3 (QUIC) - 독립 스트림
─────────────────────────────        ─────────────────────────────
Stream A: P1 ✓  P2 ✓  P3 ✗(손실)     Stream A: P1 ✓  P2 ✓  P3 ✗(손실)
          P4 (대기)                            P4 (대기) → P3만 재전송
Stream B: P5 (블로킹)                Stream B: P5 ✓ (정상)
          P6 (블로킹)                          P6 ✓ (정상)
          P7 (블로킹)                          P7 ✓ (정상)

→ P3 재전송까지 모든 스트림 대기      → 다른 스트림 영향 없음
```

QUIC의 또 다른 장점은 **연결 수립 속도**다.

| 조합 | 핸드셰이크 | RTT 200ms 환경에서 첫 요청까지 |
|---|---|---|
| HTTP/1.1 + TLS 1.2 | TCP(1 RTT) + TLS(2 RTT) = 3 RTT | 600ms |
| HTTP/2 + TLS 1.3 | TCP(1 RTT) + TLS(1 RTT) = 2 RTT | 400ms |
| HTTP/3 + QUIC | 연결·암호화 통합 = 1 RTT | 200ms |
| HTTP/3 + QUIC 재방문 | 0-RTT 재개 | 0ms(첫 패킷에 데이터 포함) |

0-RTT 재개(*0-RTT Resumption*)는 클라이언트가 이전 세션의 암호화 정보를 캐싱하고 있으면 첫 패킷부터 암호화된 데이터를 보낼 수 있는 기능이다. 또한 사용자가 네트워크를 전환할 때(Wi-Fi ↔ LTE) TCP는 커넥션이 끊기지만 QUIC는 연결 ID로 세션을 유지한다.

> **핵심 통찰**: 실제 서비스에서는 HTTP/1.1과 HTTP/2도 대부분 TLS 1.3을 쓰므로 이미 1 RTT로 핸드셰이크가 이뤄진다. 따라서 HTTP/3의 진짜 장점은 "TLS 왕복 수를 줄인다"가 아니라 **패킷 손실이 있는 환경에서 HOL 블로킹을 제거하고, 네트워크 전환 시에도 연결을 유지한다**는 점이다.

### 3.5 프로토콜 변화에 따른 최적화 전략 변경

HTTP/1.1 시대에 효과적이었던 기법들이 이제는 불필요하거나 오히려 역효과를 낸다.

| HTTP/1.1 시대의 기법 | HTTP/2 이후의 판단 |
|---|---|
| 도메인 샤딩 | **제거해야 한다.** 단일 커넥션으로 병렬 수신이 가능하므로 도메인을 나누면 추가 DNS 조회와 커넥션 수립 비용만 늘어난다 |
| CSS 스프라이트 | **재고 대상.** 필요한 아이콘만 개별 파일로 로드하는 편이 캐싱 효율이 높다. 단, 수백 개의 1KB 미만 파일로 쪼개는 것은 오버헤드 |
| 인라인 데이터 URI | **재고 대상.** 요청 수 절감 효과보다 캐싱 손실이 클 수 있다 |
| 단일 거대 번들 | **코드 스플리팅으로 전환.** 초기 로딩에 불필요한 코드는 별도 청크로 분리하고, 공통 라이브러리는 별도 청크로 캐싱 효율을 높인다 |

> **핵심 통찰**: 프로토콜 개선은 전송 효율을 높이는 것이고, 전송할 데이터 자체를 줄이는 것은 여전히 개발자의 몫이다. 프로토콜 업그레이드는 좋은 코드를 더 빠르게 전달하는 수단이지, 나쁜 코드를 보완하는 마법이 아니다.

### 3.6 HTTP/3를 활성화하는 방법

**CDN 서비스에서 활성화하기**

- **클라우드플레어 페이지**: HTTP/3가 기본 활성화. `*.pages.dev` 도메인에 자동 적용된다. DNS/CDN으로 사용하는 경우 대시보드의 Network 섹션에서 HTTP/3 토글을 켠다.
- **AWS 클라우드프런트**: 2022년 8월부터 지원. Distribution 설정의 "Supported HTTP Versions"에서 HTTP/3를 체크한다.
- **버셀·넷리파이**: HTTP/2까지만 지원한다. HTTP/3의 이점을 얻으려면 앞에 클라우드플레어를 두어 "사용자 ↔ 클라우드플레어" 구간만 HTTP/3를 쓰는 하이브리드 구조를 만든다.

> **실무 팁**: 각 서비스의 HTTP/3 지원 여부는 수시로 바뀐다. 적용 전에 공식 문서나 대시보드에서 현재 상태를 직접 확인하고, 크롬 개발자 도구의 Network 탭 Protocol 칼럼으로 실제 사용 프로토콜을 검증하는 것이 가장 확실하다.

**직접 서버를 운영하는 경우 엔진엑스 설정하기**

엔진엑스 1.25.0 이상이 필요하며(2023년 5월부터 정식 지원), OpenSSL 3.0 이상과 함께 컴파일해야 한다.

```nginx
server {
    listen 443 ssl;
    listen 443 quic reuseport;   # HTTP/3용 UDP 리스너
    http2 on;                    # HTTP/2도 함께 활성화
    http3 on;                    # HTTP/3 활성화

    ssl_certificate     /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;

    # Alt-Svc 헤더로 HTTP/3 지원 알림
    add_header Alt-Svc 'h3=":443"; ma=86400';

    # QUIC 관련 설정
    quic_retry on;
    ssl_early_data on;

    location / {
        root /var/www/html;
        index index.html;
    }
}
```

핵심은 `listen 443 quic` 지시어와 `http3 on` 설정이다. HTTP/3는 UDP를 사용하므로 방화벽에서 **UDP 443 포트**를 열어야 한다. `Alt-Svc` 헤더는 브라우저에게 "이 서버는 HTTP/3를 지원한다"고 알리는 역할을 하며, 브라우저는 이 헤더를 보고 다음 요청부터 HTTP/3를 시도한다.

**폴백 전략 이해하기**

HTTP/3는 UDP 기반이라 기업 방화벽이나 일부 ISP가 UDP 443 포트를 막는 경우가 있다. 다행히 브라우저가 자동으로 폴백을 처리한다. HTTP/3 → HTTP/2 → HTTP/1.1 순으로 자동 전환되며 개발자가 코드에서 처리할 필요는 없다. 다만 초기 연결 시도 시간이 추가될 수 있으므로 서버는 HTTP/2와 HTTP/3를 모두 활성화하는 것이 권장된다.

### 3.7 HTTP/3 도입의 현실적 제약과 HTTP/2의 충분함

브라우저 지원율은 95% 이상이고 클라우드플레어로 오는 요청 중 32%가 HTTP/3를 쓰지만, 정작 개발자가 사용하는 도구의 지원은 제한적이다.

- **서버 구현**: 엔진엑스는 2024년 초에야 HTTP/3를 메인라인에 병합했다. 아파치는 2025년 현재도 공식 지원하지 않으며 `mod_http3`는 실험적이고 직접 컴파일해야 한다. Node.js의 네이티브 HTTP/3 지원은 아직 프로덕션 준비가 되지 않아 엔진엑스나 Caddy를 앞에 둬야 한다. 파이썬의 Django·Flask도 직접 지원하지 않는다.
- **클라이언트 라이브러리 부족**: 서버보다 더 심각하다. 파이썬 `requests`와 Node.js `axios`는 기본적으로 HTTP/1.1만, 자바 `HttpClient`는 HTTP/2까지만 지원한다. 마이크로서비스 간 통신이나 외부 API 호출에 HTTP/3가 필요하면 별도 QUIC 라이브러리를 통합해야 하는데 복잡도와 유지보수 부담이 크다.
- **OpenSSL의 QUIC 분열**: OpenSSL은 QUIC API 제공을 계속 미루다 2021년 "BoringSSL 방식의 API는 제공하지 않겠다"고 선언했다. 2025년 4월 OpenSSL 3.5에서 QUIC API를 제공했지만 BoringSSL·quiche와는 다른 방식이다. OpenSSL은 "데이터가 필요할 때 요청해서 가져가라"는 pull 방식을, BoringSSL은 "데이터가 준비되면 알려줄게"라는 push 방식을 쓴다. 이 차이 때문에 코드 이식에 상당한 수정이 필요하며, 많은 프로젝트가 BoringSSL(구글)·quiche(클라우드플레어)·ngtcp2 같은 대안을 쓰게 됐다.

**HTTP/2가 충분한 이유**

HTTP/3의 핵심 개선(HOL 블로킹 제거, 0-RTT, 연결 마이그레이션)이 실질적 효과를 내는 환경은 제한적이다.

1. **HOL 블로킹은 안정적인 네트워크에서 거의 문제가 되지 않는다**: 유선이나 안정적인 와이파이는 패킷 손실률이 1% 미만이며, 이 정도에서는 영향이 거의 없다. 문제가 되는 것은 신호가 약하거나 이동 중인 모바일 환경인데 이는 전체 트래픽의 일부다.
2. **0-RTT 재연결의 활용 기회가 제한적이다**: SPA가 지배적인 현대 웹에서는 페이지 새로고침 자체가 드물다. 사이트 내 이동은 자바스크립트로 처리되므로 재연결이 필요 없다. HTTP/2 + TLS 1.3의 1-RTT와 비교해도 차이는 200ms 정도다.
3. **연결 마이그레이션의 효과가 미미하다**: 실제로 네트워크 전환이 일어나는 순간은 드물고, 브라우저는 전환 시 자동으로 재연결을 시도한다. 장시간 웹소켓이나 대용량 다운로드에서는 유용하지만 일반 브라우징에서는 체감하기 어렵다.
4. **HTTP/2가 이미 대부분의 요구사항을 충족한다**: HTTP/1.1 → HTTP/2 전환은 극적인 개선(6개 리소스 제한 제거, 커넥션 오버헤드 감소)이었지만, HTTP/2 → HTTP/3는 점진적 개선으로 대부분 환경에서 5~10% 향상에 그친다.

**현실적인 도입 가이드라인**

- **도입해야 하는 경우**: CDN을 사용해 클릭 한 번으로 활성화할 수 있다면 도입하지 않을 이유가 없다. 글로벌 서비스이고 개발도상국 사용자 비율이 높다면 HOL 블로킹 개선이 의미 있다. 실시간 통신(WebRTC, 웹소켓)이 핵심이라면 연결 마이그레이션이 도움이 된다.
- **HTTP/2로 충분한 경우**: 자체 서버 운영 + 안정적인 유선 네트워크 사용자가 주를 이룬다면 복잡도가 개선 효과를 상회한다. 내부 마이크로서비스 통신도 마찬가지다. 팀의 네트워킹 전문성이 제한적이라면 그 리소스를 이미지 최적화·코드 스플리팅·캐싱 전략에 투자하는 편이 ROI가 높다.

> **핵심 통찰**: HTTP/3는 "반드시 해야 하는" 최적화가 아니라 "할 수 있다면 좋은" 선택적 최적화다. 다만 HTTP/1.1만 사용하는 것은 어떤 경우에도 피해야 한다.

## 자주 하는 실수

| 실수 | 왜 문제인가 | 해결 |
|---|---|---|
| 네트워크는 인프라 팀의 영역이라고 여기고 방치 | 성능 영향을 가장 직접 받는 것이 프런트엔드다. 문제를 먼저 발견할 수 있는 위치에 있다 | Network 탭으로 상태를 측정하고 구체적인 설정값과 함께 개선을 요청한다 |
| HTTP/2 환경에서도 도메인 샤딩 유지 | 단일 커넥션 멀티플렉싱의 이점을 없애고 DNS 조회·커넥션 수립 비용만 추가된다 | 도메인을 하나로 통합한다 |
| HTML에 긴 `max-age` 설정 | 배포해도 사용자가 계속 옛 HTML을 받아 새 리소스를 참조하지 못한다 | HTML은 `no-cache`, 해시 파일명 리소스만 `max-age=31536000, immutable` |
| CDN 도입 후 파일명 해싱 없이 배포 | 캐시 무효화를 수동으로 해야 하고 누락 시 옛 리소스가 계속 제공된다 | 번들러의 `[contenthash]` 설정을 확인한다 |
| HTTP/2 서버 푸시로 리소스 선전송 | 클라이언트 캐시 상태를 서버가 알 수 없어 불필요한 전송이 발생한다 | `<link rel="preload">`를 사용한다 |
| 프로토콜만 업그레이드하고 리소스 크기는 방치 | 전송 효율이 올라가도 보낼 데이터가 많으면 여전히 느리다 | 압축·번들 최적화·이미지 최적화를 함께 적용한다 |

## 측정과 검증

**크롬 개발자 도구 Network 탭**

가장 기본이면서 강력한 도구다. Protocol 칼럼이 보이지 않으면 칼럼 헤더를 우클릭해 Protocol 항목을 체크한다.

- **Protocol 칼럼**: `h3`(HTTP/3), `h2`(HTTP/2), `http/1.1`로 실제 사용 프로토콜을 확인한다.
- **Size 칼럼**: 실제 네트워크로 전송된 크기를 보여준다.
- **워터폴 차트**: 각 리소스가 언제 요청되고 다운로드됐는지 시각적으로 확인한다.

**커맨드라인으로 HTTP/3 지원 확인**

HTTP/3 지원 `curl`이 없어도 HTTP/2로 접속해 `alt-svc` 헤더를 확인하면 된다.

```bash
# HTTP/2로 접속해서 alt-svc 헤더를 확인
curl -I --http2 https://www.cloudflare.com/

# 또는 grep으로 필터링
curl -I --http2 https://www.cloudflare.com/ | grep -i alt-svc
```

서버가 HTTP/3를 지원하면 응답에 다음 헤더가 포함된다.

```http
HTTP/2 200
server: cloudflare
alt-svc: h3=":443"; ma=86400
```

다만 이 방법은 **서버가 HTTP/3를 지원하는지만** 확인할 수 있다. 실제로 HTTP/3로 접속하는 것이 아니라 서버가 "나는 HTTP/3도 지원한다"고 알려주는 헤더를 보는 것이므로, 실제 사용자 환경에서의 동작은 크롬 개발자 도구로 확인해야 한다.

**온라인 도구**

HTTP/3 Check(`https://http3check.net/`) 같은 도구에 도메인을 입력하면 지원 여부를 알 수 있다. 다만 테스트 환경 기준이므로 실제 사용자 환경과 다를 수 있어 참고용으로만 쓴다.

**WebPageTest**

전 세계 여러 지역에서 실제 디바이스로 측정해 CDN 효과를 검증한다. Connection View는 DNS 조회, 초기 연결, SSL 협상, 리소스 타입별 다운로드 시간을 단계별로 시각화한다. 여러 도메인 연결이 어떻게 병렬 처리되는지, CPU 사용률과 대역폭이 시간에 따라 어떻게 변하는지, 메인 스레드가 언제 바쁜지를 한눈에 볼 수 있다. Long Tasks 영역에서 메인 스레드를 오래 블로킹하는 작업도 찾을 수 있다.

**라이트하우스**

HTTP/2 사용 여부를 체크해 개선 제안을 제공한다.

## 체크리스트

**CDN 설정**

- [ ] 정적 리소스에 해시 기반 파일명 사용(웹팩/비트 기본 설정)
- [ ] 해시 파일은 `Cache-Control: public, max-age=31536000, immutable` 설정
- [ ] HTML 파일은 `Cache-Control: no-cache` 설정
- [ ] CDN 서비스 연결(버셀, 넷리파이, 클라우드플레어 페이지 또는 AWS 클라우드프런트)
- [ ] 프레임워크별 CDN 설정 확인(Next.js `assetPrefix`, Nuxt `app.cdnURL`, Remix `publicPath` 등)
- [ ] Next.js `Image` 컴포넌트를 CDN으로 서빙하려면 커스텀 로더 설정

**HTTP/3 활성화(또는 최소한 HTTP/2)**

- [ ] CDN 사용 시: 설정 페이지에서 HTTP/3 활성화 확인(클라우드플레어는 기본 활성화)
- [ ] 직접 서버 시: 엔진엑스에서 `listen 443 quic` 및 `http3 on` 설정
- [ ] 방화벽에서 UDP 443 포트 개방 확인
- [ ] 크롬 개발자 도구 Network 탭에서 Protocol 칼럼이 `h3`로 표시되는지 확인
- [ ] HTTP/3가 어렵다면 최소한 HTTP/2는 반드시 활성화(엔진엑스는 `listen 443 ssl` + `http2 on`)

## 요약

- 사용자가 체감하는 로딩 시간의 대부분은 네트워크 전송 시간이다. Slow 4G에서 1MB 번들 다운로드에 5.7초가 걸리지만 파싱·실행은 수백 밀리초면 끝난다.
- 네트워크 최적화는 **설정 변경만으로 적용되고 사이드 이펙트가 거의 없어** 투자 대비 효과가 가장 크다.
- 물리적 거리는 어떤 최적화로도 넘을 수 없는 제약이다. CDN은 콘텐츠를 사용자 가까이 배치해 이 제약을 우회하며, 엣지 → 리전 → 오리진 3계층 구조로 동작한다.
- CDN 도입의 핵심 3단계는 **해시 파일명 + 긴 `max-age`**, **CDN 서비스 연결**, **HTML은 `no-cache`로 두는 캐시 무효화 전략**이다.
- HTTP/1.1의 HOL 블로킹을 우회하려고 만든 도메인 샤딩·스프라이트·거대 번들은 HTTP/2 환경에서 오히려 역효과다.
- HTTP/2는 멀티플렉싱·바이너리 프레임·HPACK으로 애플리케이션 레벨 HOL 블로킹을 해결했다. 스트림 우선순위는 구현 불일치로 RFC 9113에서 폐기되고 RFC 9218의 `Priority` 헤더로 대체됐다.
- HTTP/3는 QUIC 기반으로 TCP 레벨 HOL 블로킹까지 제거하고 1-RTT(재방문 시 0-RTT) 연결을 제공한다. 진짜 가치는 왕복 수 감소가 아니라 **패킷 손실 환경에서의 스트림 독립성과 연결 마이그레이션**이다.
- CDN을 쓴다면 HTTP/3를 켜지 않을 이유가 없지만, 자체 인프라라면 오픈소스 생태계 지원 부족을 감안해 HTTP/2로 충분한 경우가 많다. 단, HTTP/1.1 유지는 피해야 한다.
- 프로토콜 개선은 전송 효율을 높일 뿐이다. 전송할 데이터 자체를 줄이는 것은 여전히 개발자의 몫이다.

## 다른 챕터와의 관계

- **Ch2(네트워크 압축)**: 이 장이 "빠른 경로"를 만들었다면 다음 장은 "가벼운 짐"을 만든다. CDN·HTTP/3와 압축을 함께 적용해야 네트워크 레이어 최적화가 완성된다.
- **Ch3(브라우저 캐시)**: 이 장에서 다룬 `Cache-Control` 지시어(`public`, `private`, `no-cache`, `no-store`, `max-age`, `s-maxage`, `immutable`)의 정확한 동작과 리소스별 캐시 전략을 본격적으로 설계한다.
- **Ch4~5(리소스 우선순위·프리로드 스캐너)**: HTTP/2 스트림 우선순위의 한계를 보완하는 브라우저 레벨 제어 수단(`preload`, `preconnect`, `fetchpriority`)을 다룬다.
- **Ch9~10(번들 최적화·코드 스플리팅)**: "프로토콜은 전송 효율만 높인다"는 이 장의 결론을 이어받아 전송할 데이터 자체를 줄이는 방법을 다룬다. HTTP/2 환경에서 코드 스플리팅이 유리해진 이유도 여기서 확장된다.
- **Ch11(서버로 로직 이동)**: CDN 엣지 컴퓨팅으로 언급만 하고 넘어간 "서버가 할 수 있는 일" 주제를 본격적으로 다룬다.
