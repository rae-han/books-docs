# Chapter 7: API Authentication and Authorization (API의 인증과 인가)

## 핵심 질문

호출자가 누구인지 어떻게 확인하고, 그가 무엇을 할 수 있는지 어떻게 정하는가? 서드파티 시스템이 사용자를 대신해 우리 API를 부를 때, **사용자의 자격증명을 넘겨주지 않고** 어떻게 허가를 표현하는가?

## 1. 인증과 인가

- **인증(*authentication*)**: 호출자가 **누구인지** 확인하는 것
- **인가(*authorization*)**: 그 호출자에게 **어떤 동작을 허용할지** 확인하는 것

사용자 인증의 가장 전통적인 방법은 사용자 이름과 비밀번호이며, 요즘은 **다중 인증**(*Multi-Factor Authentication - MFA*)을 표준 로그인 흐름에 넣는 것이 보편화되고 있다. 머신 간 인증에서는 자격증명이 **키나 인증서** 형태다.

참석자 API는 이름·이메일 같은 **PII**를 보관한다. 이 정보를 지키는 첫 단계가 **호출자가 누구인지 알아내는 것(인증)** 이고, 그다음이 **무엇에 접근할 수 있는지 확인하는 것(인가)** 이다.

```
┌──────────┐    ┌──────────────────┐  API 호출  ┌──────────────────┐   생성·조회   ┌──────────────┐
│  참석자   │ ──▶│     모바일 앱      │  [HTTP]   │                  │ ───────────▶ │  참석자 서비스  │
│ [사람]    │    │ [소프트웨어 시스템] │ ────────▶ │  API 게이트웨이    │              │ [리소스 서버]  │
└──────────┘    └──────────────────┘           │ [인프라스트럭처]   │              └──────────────┘
┌──────────┐    ┌──────────────────┐  API 호출  │                  │
│  발표자   │ ──▶│   CFP [서드파티]   │  [HTTP]   │                  │
│ [사람]    │    │ 발표 자료를 제출    │ ────────▶ │                  │
└──────────┘    └──────────────────┘           └──────────────────┘
```

두 종류의 상호작용이 있다 — 모바일 앱(우리 것)과 **CFP 시스템(서드파티 소유)** 이다. 이 차이가 이 장 전체의 문제의식이다.

### 토큰을 이용한 최종 사용자 인증

토큰 기반 인증에서는 사용자가 입력한 이름·비밀번호를 **토큰으로 교환**한다. 가장 단순한 형태는 알아보기 힘든 문자열이며, REST 요청의 **베어러 인증 헤더**로 전달한다. 토큰은 민감 정보이므로 **HTTPS로 전송**해야 한다.

```
1) POST /login              Authorization: Basic am9lOnBhc3N3b3Jk
   인증 서버 ──▶ 데이터 스토어에 토큰 저장(XYZ) ──▶ 토큰 리턴(XYZ)

2) GET /attendees           Authorization: Bearer XYZ
   참석자 API ──▶ 데이터 스토어에서 토큰 조회(XYZ) ──▶ 응답
```

토큰의 수명은 **제한적**(예: 1시간)이어야 하고 만료되면 새로 받아야 한다. 장점은 **비밀번호 같은 장기 자격 데이터를 매 요청마다 네트워크로 보내지 않아도 된다**는 것이다.

그런데 이 방식에는 큰 단점이 둘 있다.

1. 사용자가 입력한 **이름과 비밀번호가 데이터를 조회하는 API로 전달된다**
2. 토큰을 저장소에 만들면 **매번 조회해 검증**해야 하므로 성능 문제가 생긴다

그래서 더 나은 방법은 **인 프로세스에서 무결성을 검증할 수 있는 토큰**을 쓰는 것이다.

> **참고**: HTTP 기본 인증으로 API에 접근할 수도 있다. 하지만 **서드파티 애플리케이션이 나를 대신해 API에 접근해야 한다면 내 이름과 비밀번호를 그 서드파티와 공유해야 한다.** 그러니 기본 인증으로 API를 보호하려 하지 말자.

### 시스템 간 인증과 API 키

사용자가 관여하지 않고 시스템끼리 통신할 때는 **API 키**를 쓸 수 있다(표준으로 볼 수는 없다). 키는 반드시 안전해야 한다 — **암호학적으로 안전한 난수 생성기**로 예측할 수 없는 값을 만들며, 보통 32문자(256비트)를 쓴다. **짧고 결정적이어서 예측 가능하면 그 자체가 취약점**이 된다.

```http
POST /attendees/12345/papers
X-API-KEY: My_super_secret_APIkey

{ "title": "mastering-apis-a-discussion",
  "description": "A guide to API Architecture" }

---

201 Created
Location: /papers/12345
```

### 키와 사용자를 혼합하면 안 되는 이유

발표자가 서드파티 CFP 시스템을 쓰는데, CFP가 **발표자의 이메일 주소를 업데이트**하려 한다고 하자. API 키로는 **요청을 보낸 시스템**은 알 수 있어도 **그 시스템의 어떤 사용자를 대신하는지**는 알 수 없다.

떠오르는 해법은 CFP가 사용자의 이름·비밀번호를 API 키와 함께 보내는 것이다. 그런데 그건 **사용자가 CFP를 통해 참석자 서비스에 자기 비밀번호를 넘겨주는 것**이라 권장할 수 없다.

> **핵심 통찰**: 필요한 것은 **CFP가 사용자를 대신해 보내는 요청이, 자격증명을 공유하지 않고도 사용자의 허가를 거쳐 처리되는 것**이다. 이 문제의 답이 OAuth2다.

## 2. OAuth2

OAuth2는 2012년경 발표된 **토큰 기반 인가 프레임워크**로, **사용자가 서드파티 애플리케이션이 자기를 대신해 데이터에 접근하는 것에 동의**하도록 설계되었다. 그 동의가 곧 인가다. 핵심은 **리소스를 제어하는 본인의 자격증명을 서드파티와 공유할 필요가 없다**는 것이다.

명세가 정의하는 네 역할이다.

- **리소스 소유자(*resource owner*)**: 보호된 리소스에 대한 접근을 승인할 능력을 가진 엔티티. 사람이면 최종 사용자다
- **인가 서버(*authorization server*)**: 리소스 소유자를 인증하고 인가를 얻은 뒤 클라이언트에 **액세스 토큰을 발급**하는 서버. 구글이나 Auth0 같은 신원 제공자 대부분이 여기 해당한다
- **클라이언트(*client*)**: 인가 정보를 이용해 리소스 소유자를 대신해 보호된 리소스에 요청을 보내는 애플리케이션
- **리소스 서버(*resource server*)**: 보호된 리소스를 호스팅하고, 액세스 토큰으로 요청을 받아 응답하는 서버

인가 서버는 엔드포인트 두 개를 제공한다 — 리소스 소유자가 접근을 인가받는 **인가 엔드포인트**, 클라이언트가 토큰을 얻는 **토큰 엔드포인트**.

> **핵심 통찰**: 리소스 서버는 개별 애플리케이션일 필요가 없다. 흔한 패턴은 **API 게이트웨이를 리소스 서버로 두는 것**이다. 뒤에 서비스가 여럿 있어도 클라이언트 입장에서 보호된 리소스를 호스팅하는 것은 게이트웨이다. 우리 사례에서 리소스 소유자는 **모바일 앱을 쓰는 참석자**와 **CFP를 쓰는 발표자**다.

### JSON 웹 토큰(JWT)

**JWT**는 RFC 표준 토큰 형식으로 OAuth2에서 사실상 표준이다. **클레임**(*claim*)들로 구성되며, 표준 방식으로 인코딩되어 **수정이 불가능하고** 암호화할 수도 있다. `Authorization` 헤더처럼 **공간 제약이 있는 환경**에서 정보를 나르기에 특히 좋다.

```json
{
  "iss": "http://mastering-api/",
  "sub": "18f91361-7a9d-476f-a062-5381d1e21ffa",
  "aud": "Attendee-Service",
  "exp": 1618146900,
  "nbf": 1618144280,
  "iat": 1618144200,
  "jti": "4d13ba71-54e4-4583-9458-562cbf0ba4e4"
}
```

JWT RFC의 **예약된 클레임**들이다. 토큰에 반드시 있어야 하는 것은 아니지만 최소한의 출발점이 된다.

- **`iss`(issuer)**: 이 토큰을 발급한 기관 (보통 신원 제공자 이름)
- **`sub`(subject)**: JWT 자격증명을 구분하는 **고유 식별자**. 사용자를 대변할 때는 참석자를, 서버 간 연결에서는 애플리케이션을 나타낸다. 형식이 정해져 있지 않으므로 **유일한 값(UUID 등)** 을 쓴다
- **`aud`(audience)**: 토큰의 발급 대상
- **`exp`(expiration time)**: 만료 시점
- **`nbf`(not before)**: 이 시각 이전에는 써서는 안 된다
- **`iat`(issued at)**: 발급 시간
- **`jti`(JWT ID)**: JWT의 고유 식별자

> **실무 팁**: `sub`에 **이메일이나 사용자 이름처럼 나중에 바뀔 수 있는 값**을 쓰는 것은 좋지 않다. 일관된 식별자가 관리하기 쉽다. 그 밖에 선호 이름·이메일·요청한 애플리케이션 등도 담을 수 있고, 고보안 API에서는 **인가 서버의 인증 방식**(리소스 소유자가 MFA를 썼는지 등)을 담기도 한다.

**인코딩과 검증** — 두 방식이 있다.

- **JWS**(*JSON Web Signatures*): **무결성**을 제공한다. 내용은 누구나 볼 수 있지만 **디지털 서명**되어 있어 내용이 바뀌면 즉시 무효가 된다
- **JWE**(*JSON Web Encryption*): 무결성에 더해 **암호화**되어 내용을 볼 수 없다

보통 "JWT를 쓴다"는 것은 **JWS 기반 JWT**를 뜻한다. 비공개 키로 서명하고, 수신자는 공개 키로 **특정 발급자가 서명했는지** 확인한다.

> **핵심 통찰**: **JWS 기반 JWT의 클레임에 중요한 정보를 담아서는 안 된다.** JWS는 무결성만 보장하며 **토큰을 가진 누구나 클레임을 읽을 수 있다.** 읽을 수 없게 하려면 JWE를 써야 한다.

JWT가 좋은 이유는 **API 서비스가 서명만 검증하면 되고 데이터베이스에서 토큰을 조회할 필요가 없다**는 점이다. 수신 시 검증할 것은 ① 원하는 발급자가 발급했고 수정되지 않았는지(서명) ② 만료되지 않았는지(`exp`) ③ 허용 시각 전에 쓰이고 있지 않은지(`nbf`)다.

> 토큰의 장기 사용은 탈취 또는 재사용의 위험이 크다. 토큰을 단기적으로 사용하면 이 위험을 완화할 수 있다.<br>— NIST 디지털 가이드라인

만료 시간에 공식 표준은 없다. 보통 **단기 토큰 1~60분**, 장기 토큰 1~10년을 권하며, **가능한 한 짧게** 유지하는 것이 원칙이다.

### ADR 가이드라인: OAuth2를 고려해야 할까

- **결정사항**: OAuth2를 쓸 것인가, 아니면 우리 환경에 더 맞는 다른 표준이 있는가?
- **논의사항**: 현재 보안 요구와 **변화 가능성**을 확인한다 — API를 제어 부분 안에서만 쓰는가, 아니면 외부나 서드파티도 쓰는가? 어떤 보안 모델을 지원하려 하며, **특정 모델을 요구하는 외부 통합 상대**가 있는가? **여러 인증·인가 모델을 동시에 지원**해야 하는가(기존 모델에서 마이그레이션할 때 특히 중요하다)?
- **권장사항**: OAuth2를 쓰면 **다른 API 사용자와의 호환성이 극대화**된다. 업계 표준이라 문서와 클라이언트 라이브러리가 잘 갖춰져 있어 통합이 쉽고, **최종 사용자와 시스템 간 사용 사례를 모두** 지원한다

## 3. OAuth2 승인(grant)

OAuth2는 확장을 염두에 두고 설계되었다. 2012년 명세에 네 가지 승인이 정의됐고 이후 계속 추가됐다. 모든 승인이 공유하는 **추상 프로토콜**은 이렇다.

```
   ┌──────────────┐   (A) 인가 요청       ┌──────────────────┐
   │              │ ────────────────────▶│   리소스 소유자    │
   │              │   (B) 인가 승인       │                  │
   │              │◀──────────────────── └──────────────────┘
   │  클라이언트   │   (C) 인가 승인       ┌──────────────────┐
   │              │ ────────────────────▶│    인가 서버       │
   │              │   (D) 액세스 토큰     │                  │
   │              │◀──────────────────── └──────────────────┘
   │              │   (E) 액세스 토큰     ┌──────────────────┐
   │              │ ────────────────────▶│   리소스 서버      │
   │              │   (F) 보호된 리소스   │      (= API)      │
   └──────────────┘◀──────────────────── └──────────────────┘
```

> **핵심 통찰**: 이 흐름의 요점은 **리소스 소유자가 자기 리소스를 제어한다**는 것이다. 인가가 주어지는 **방식은 중요하지 않다** — 중요한 건 소유자가 **승인하거나 거부할 기회를 갖는다**는 점이다. 또 리소스 서버 입장에서는 **토큰을 어떻게 얻었는지 상관없이** 유효하기만 하면 리소스를 준다. 각 단계가 독립적이기 때문에 **시나리오마다 다른 승인 방식**이 존재할 수 있다.

### 인가 코드 승인

가장 잘 알려진 방식이며, 자신도 모르게 써봤을 가능성이 크다(링크드인이 지메일 연락처 접근을 요청하는 흐름이 그렇다). 기밀 정보를 보호할 수 있는 클라이언트를 **신뢰할 수 있는 클라이언트**(*confidential client*)라고 한다.

```
   리소스 소유자 ◀──(B) 사용자 인증·동의──▶ 인가 서버
        ▲                                      ▲
        │ 유저 에이전트(브라우저)                 │
        ▼                                      │
   ┌──────────────┐  (A) 클라이언트 식별자 + 리다이렉션 URI
   │  클라이언트    │ ───────────────────────────┤
   │              │  (C) 인가 코드              │
   │              │◀───────────────────────────┤
   │              │  (D) 인가 코드 + 리다이렉션 URI + 클라이언트 암호
   │              │ ───────────────────────────▶
   │              │  (E) 액세스 토큰 (+ 리프레시 토큰)
   └──────────────┘◀───────────────────────────
```

A에서 브라우저를 인가 서버로 보내고(클라이언트 ID와 사용할 승인 종류 포함), B에서 인가 서버가 리소스 소유자를 인증하고 **동의를 받는다**. C에서 인가 코드가 클라이언트에 전달되고, D에서 클라이언트는 **인가 서버와 공유하는 암호로 스스로를 인증**하며 코드를 토큰으로 교환한다.

### 인가 코드 승인 + PKCE

SPA는 자바스크립트로 브라우저에서 돌기 때문에 **소스가 완전히 노출**되고 **암호를 보호할 수 없다** — 이를 **공개 클라이언트**(*public client*)라 하며, 인가 코드 승인을 그대로 쓸 수 없다.

**PKCE**(*Proof Key for Code Exchange*)는 **가로채기 공격을 완화**하려고 파라미터 두 개를 추가한다.

- **`code_verifier`**: 클라이언트가 암호학적으로 임의 생성한 문자열
- **`code_challenge`**: `code_verifier`의 **해시 값**

클라이언트는 인가 요청에 `code_challenge`를 보내고, 토큰을 요청할 때 `code_verifier`를 보낸다. 인가 서버는 받은 `code_verifier`를 해시해 앞서 받은 `code_challenge`와 **일치하는지 확인**한다. **원래 클라이언트만 `code_verifier`를 갖고 있으므로** 인가 코드를 가로채도 토큰으로 바꿀 수 없다.

```
   ┌──────────────┐  (A) 인가 요청 + t(code_verifier), t_m   ┌──────────────────┐
   │              │ ───────────────────────────────────────▶│  인가 엔드포인트    │
   │  클라이언트    │  (B) 인가 코드                            │                  │
   │  (공개)       │◀─────────────────────────────────────── └──────────────────┘
   │              │  (C) 액세스 토큰 요청 + code_verifier     ┌──────────────────┐
   │              │ ───────────────────────────────────────▶│  토큰 엔드포인트    │
   │              │  (D) 액세스 토큰                          │                  │
   └──────────────┘◀─────────────────────────────────────── └──────────────────┘
```

> **실무 팁**: **공개 클라이언트라면 PKCE는 필수**다. 비공개 클라이언트도 추가 보호를 위해 쓸 수 있다.

**사례 연구** — 참석자 API의 클라이언트는 둘이다. **외부 CFP 시스템은 비공개 클라이언트**라 암호를 관리할 수 있으므로 인가 코드 승인을 쓰고, **모바일 앱은 공개 클라이언트**라 반드시 **인가 코드 승인 + PKCE**를 써야 한다. 사용자 입장에서 흐름은 사실상 같다.

### 리프레시 토큰

토큰 유효 기간은 짧아야 하지만 **매번 로그인을 다시 요구하는 것은 나쁜 경험**이다. **리프레시 토큰**은 유효 기간이 긴 토큰으로, 액세스 토큰이 만료되면 **최종 사용자 개입 없이** 새 토큰을 받는 데 쓴다.

> **실무 팁**: 리프레시 토큰은 **별개의 자격증명이고 유효 기간이 길어** 유출되지 않게 지켜야 한다. 최신 권장 사례에서는 리프레시 시 **곧바로 새 리프레시 토큰을 만들고 이전 것을 강제 폐기**하기도 한다. 클라이언트의 접근이 거부되면 리프레시 토큰도 폐기되는데, **이미 발급된 액세스 토큰은 그 순간에도 여전히 유효하다.** 그래서 액세스 토큰의 수명을 짧게 두는 것이 중요하다.

### 클라이언트 자격증명 승인

**머신 간 통신**용이며, 클라이언트가 암호를 관리해야 하므로 **신뢰할 수 있는 클라이언트**여야 한다. 연결과 접근 권한이 **미리 설정**되어 있다.

```
   ┌──────────────┐  (A) 클라이언트 인증 (client_credentials)  ┌──────────────┐
   │  클라이언트   │ ─────────────────────────────────────────▶│  인가 서버     │
   │              │  (B) 액세스 토큰                            │              │
   └──────────────┘◀───────────────────────────────────────── └──────────────┘
```

**권한을 허용할 리소스 소유자가 없으므로** 다른 절차가 필요 없다. 클라이언트는 누구를 대신하는 것이 아니라 **자기 자신만 인증**한다.

**사례 연구** — CFP 시스템이 3개월마다 "얼마나 많은 참석자가 발표를 제출하고 발표자가 되었는지" 보고서를 만든다. 이건 **참석자를 대신하는 일이 아니라 CFP가 스스로 하는 일**이다. CFP는 인가 서버에 등록되어 있고, **참석자 정보 읽기와 발표 제출자 질의 권한이 미리 부여**되어 있다.

> **참고**: 클라이언트 자격증명 승인에는 **리프레시 토큰을 쓰지 않는다.** 대신 클라이언트가 새 액세스 토큰을 요청한다.

### 추가 승인들

- **장치 인가 승인(*Device Authorization Grant*)**: 입력이 제한적이거나 브라우저가 없는 장치용. 스마트 냉장고나 라즈베리 파이 같은 IoT에 유용하다
- **암시적 승인(*Implicit Grant*)**: SPA가 쓰던 방식이지만 **인가 코드 승인 + PKCE로 대체**되었다
- **리소스 소유자 비밀번호 자격증명 승인**: HTTP 기본 인증을 쓰던 클라이언트를 OAuth2로 옮길 때 쓰였으나 **권장하지 않는다**

### ADR 가이드라인: 지원할 OAuth2 승인의 선택

- **결정사항**: 어떤 OAuth2 승인 방식을 지원할 것인가?
- **논의사항**: API를 쓸 **클라이언트의 종류**를 정한다 — IoT와 장치 인가 승인이 필요한가? **암시적 승인만 지원하는 낡은 SPA**가 있는가? 리소스 소유자 비밀번호 자격증명 승인은 완전히 배제할 것인가? 이미 보안 모델이 있다면 OAuth2로 전환할 것인가, 클라이언트를 마이그레이션할 수 있는가(클라이언트를 다 제어하거나 서드파티가 적으면 훨씬 쉽다), 신규 클라이언트는 전부 OAuth2를 쓰게 할 것인가?
- **권장사항**: **우선 필요한 모델부터 적용하고 필요에 따라 추가**한다. 이미 보안 모델이 있고 유료 고객이 많으면 이전이 쉽지 않지만, **서드파티가 우리 전용 보안 모델 구현을 피하려고 OAuth2를 요구**할 수 있다. API 시스템에 OAuth2를 도입하는 **가장 쉬운 출발점은 클라이언트 자격증명 승인**이다

## 4. OAuth2 범위와 인가의 수행

**범위**(*scope*)는 **사용자를 대신해 클라이언트가 무엇을 할 수 있는지 제어하는** 메커니즘이다. 사용자가 처음 인증할 때 보는 동의 화면("애플리케이션이 캘린더의 일정을 읽으려고 합니다")이 바로 범위를 묻는 것이다.

**사례 연구** — 참석자 API와 레거시 컨퍼런스 API가 있고, **CFP 시스템은 참석자 API에만** 접근할 수 있어야 한다. 먼저 리소스 단위로 나눈다.

- `GET /attendees`, `GET /attendees/{id}`, `POST /attendees`, `PUT /attendees/{id}` → **Attendee**
- `GET /conferences`, `POST /conferences` → **Conference**

여기서 더 나아가 **읽기와 쓰기를 분리**할 수 있다.

- `GET /attendees`, `GET /attendees/{id}` → **AttendeeRead**
- `POST /attendees`, `PUT /attendees/{id}` → **AttendeeAccount**

> **핵심 통찰**: 범위 이름에 표준은 없지만, **최종 사용자가 동의 화면에서 읽고 이해할 이름**이어야 한다. 승인된 범위는 JWT 액세스 토큰에 ``"scope": "AttendeeRead AttendeeAccount"`` 같은 클레임으로 실린다. 범위는 OAuth2 필수 요소는 아니지만 **더 세밀한 권한 관리**를 원한다면 반드시 고려할 만하다.

### 인가의 수행

OWASP API 톱 10의 대표적인 인가 이슈 둘이다.

- **BOLA**(*Broken Object Level Authorization*): 사용자가 **접근할 수 없는 객체**의 정보를 요청할 수 있게 되는 것. 보통 **리소스 ID를 조작**하다 발견된다
- **BFLA**(*Broken Function Level Authorization*): 표준 사용자가 **관리자 전용 엔드포인트**를 실행하는 등 인가받지 않은 작업을 하는 것

인가는 보통 **역할 기반 접근 제어**(*Role Based Access Control - RBAC*) 같은 자격 기반으로 수행한다. 정확한 방식은 세부 사항이지만, **접근 제어는 어떤 형태로든 있어야 하고 모든 엔드포인트가 요청 처리 전에 인가를 확인**해야 한다.

> **핵심 통찰**: **범위와 사용자 권한은 다르다.** 범위는 "클라이언트가 나를 대신해 할 수 있는 일"의 목록이지 "사용자가 모든 데이터에 접근해도 된다"는 뜻이 아니다. 클라이언트는 참석자 정보를 **읽고 관리하는** 권한을 요청할 수 있지만, 정작 그 사용자에게는 **읽기 권한밖에 없을 수 있다.** 실제 허용 동작은 **[최종 사용자의 권한] ∩ [클라이언트가 허가받은 동작]** 의 교집합이다.

게이트웨이는 **범위 인가**를 수행해 올바른 범위가 없는 클라이언트 요청을 걸러낼 수 있다. 다만 위 교집합의 나머지 절반(사용자 권한 확인)은 **서비스가 해야 한다**.

## 5. OIDC

OAuth2는 API 접근을 다루지만 **클라이언트가 리소스 소유자의 신원을 알아야 하는** 요구는 채워주지 않는다. CFP 시스템은 발표자 데이터를 저장해야 하는데, **OAuth2 승인은 최종 사용자의 신원을 확인하는 방법을 제공하지 않는다.**

**OIDC**(*OpenID Connect*)가 그 **신원 계층**이다. OAuth2 위에 구현되며, 이를 구현한 인가 서버는 **OpenID 제공자**가 된다. 클라이언트는 `openid`라는 특별한 범위를 요청해 사용자 클레임을 담은 **ID 토큰**을 받는다.

`openid`만 쓰면 ID 토큰에는 **`sub` 클레임(사용자 고유 ID, 절대 바뀌면 안 된다)** 정도만 담긴다. 그래서 OIDC는 추가 범위를 정의한다.

- **`profile`**: `name`·`family_name`·`given_name`·`middle_name`·`nickname`·`preferred_username`·`profile`·`picture`·`website`·`gender`·`birthdate`·`zoneinfo`·`locale`·`updated_at`
- **`email`**: `email`, `email_verified`
- **`address`**: `address`
- **`phone`**: `phone_number`, `phone_number_verified`

이 범위들은 **ID 토큰에서만** 쓰이며 액세스 토큰에는 나타나지 않는다. OIDC는 인가 코드 흐름·암시적 흐름·하이브리드 흐름 셋을 정의하는데, 인가 코드 승인과 같은 이유로 **인가 코드 흐름이 가장 안전하다**.

> **핵심 통찰**: 많은 사람이 OAuth2와 OIDC를 같은 것으로 여기지만 **다른 것이다.** OIDC는 **클라이언트에 사용자 신원을 제공**하는 역할이지 **API 접근을 제공하지 않는다.** OIDC가 필요하면 신원 제공자가 지원하는지 확인하고, **신원 계층을 직접 구현하려 하지 말자.**

> **참고**: **절대 ID 토큰으로 액세스 토큰을 대체하면 안 된다.** ID 토큰은 유효 기간이 길고 **클라이언트에 사용자 정보를 주는 것**이 목적이지 리소스 접근을 제어하는 것이 아니다.

## 6. SAML 2.0

**SAML**(*Security Assertion Markup Language*)은 **어설션**(*assertion*)을 전달하는 개방 표준으로, 주로 **싱글 사인온**에 쓰이며 이때 전달하는 어설션은 사용자의 신원이다. 임직원이 외부 애플리케이션에 로그인하게 해주므로 엔터프라이즈에서 매우 보편적이다.

SAML은 원래 API용이 아니다. 다만 **OAuth 2.0 클라이언트 인증 및 인가 승인을 위한 SAML 2.0 프로파일 확장**이 있어, 인가 서버가 그 기능을 구현했다면 **클라이언트가 SAML로 액세스 토큰을 요청**할 수 있다. OAuth2 마이그레이션에 SAML이 필요하다면 알아둬야 할 지점이다.

## 요약

- **인증**은 리소스 소유자의 신원 확인이고 — 최종 사용자일 수도, 시스템 간 통신을 하는 애플리케이션일 수도 있다 — **인가**는 그가 무엇을 할 수 있는지 확인하는 것이다
- 서드파티가 사용자를 대신할 때 **API 키 + 사용자 자격증명을 섞는 방식은 답이 아니다.** 자격증명을 공유하지 않고 허가를 표현하는 것이 OAuth2의 존재 이유다
- **OAuth2는 베어러 헤더의 JWT로 API를 보호하는 사실상의 표준**이다. JWT는 서명되어 조작이 불가능하며, 서비스는 DB 조회 없이 **인 프로세스로 검증**한다. 다만 **JWS는 무결성만 보장하므로 클레임은 누구나 읽을 수 있다**
- 승인 방식 중 가장 흔한 것은 **인가 코드 승인 + PKCE**(사용자 대신)와 **클라이언트 자격증명 승인**(머신 간)이다. 공개 클라이언트에는 PKCE가 필수다
- **리프레시 토큰**은 사용자 경험을 지키되 별개의 자격증명이므로 안전하게 다뤄야 하고, **액세스 토큰의 수명은 짧게** 유지한다
- **범위**는 클라이언트의 접근을 사용자가 제어하게 해준다. 실제 허용 동작은 **사용자 권한과 클라이언트 허가의 교집합**이며, BOLA·BFLA를 막으려면 **모든 엔드포인트가 요청 처리 전에 인가를 확인**해야 한다
- **OIDC**는 클라이언트가 최종 사용자 정보를 필요로 할 때 쓰는 신원 계층이다. API 접근 제어와는 별개이며 ID 토큰을 액세스 토큰 대신 쓰면 안 된다

## 다른 챕터와의 관계

- **3장**: API 게이트웨이를 **리소스 서버**로 두는 패턴, 게이트웨이에서 범위 인가를 수행하는 이야기가 여기서 구체화된다
- **4장**: 메시의 mTLS가 **서비스 신원**을 다룬다면, 이 장은 **사용자 신원**을 다룬다. 둘은 대체 관계가 아니라 층이 다르다
- **5장**: 인증 헤더를 그대로 포워딩하면 위장이 가능하다는 경고, OAuth2 베어러 토큰은 전송 계층이 안전하면 전달 가능하다는 이야기가 이 장의 토큰 개념과 맞물린다
- **6장**: 스트라이드의 **위장**은 인증으로, **권한 상승**은 인가(BOLA·BFLA)로 대응된다. 이 장은 6장이 남긴 두 위협의 해법이다
- **9장**: 제로 트러스트로 옮겨가며 **모든 요청을 계속 재인증**하는 흐름으로 이어진다
