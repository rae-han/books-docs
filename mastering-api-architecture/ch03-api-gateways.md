# Chapter 3: API Gateways: Ingress Traffic Management (API 게이트웨이: 인그레스 트래픽 관리)

## 핵심 질문

인그레스 트래픽을 내부로 전달하는 데 API 게이트웨이가 유일한 답인가? 게이트웨이는 무엇을 해결해주고 그 대가로 무엇을 요구하는가? 그리고 모든 요청이 지나가는 이 지점이 무너질 때를 어떻게 대비하는가?

## 1. API 게이트웨이가 유일한 해결책일까

저자들이 가장 자주 받는 질문이다. 짧은 답은 **아니다**. 다만 숨은 의미가 있다.

인그레스(*ingress*) 기능을 제공하는 솔루션은 URI에서 백엔드로 트래픽을 전달하는 메커니즘뿐 아니라 안정성·관측용이성·보안까지 제공해야 한다. 이런 요구는 단순한 **프록시**나 **로드밸런서**로도 어느 정도 채울 수 있다. 다만 API 게이트웨이는 **소비자와 제공자의 수가 늘어날 때** 더 확장 가능하고 유지보수하기 쉬우며 안전한 선택지다.

| 기능 | 리버스 프록시 | 로드밸런서 | API 게이트웨이 |
|------|--------------|-----------|---------------|
| 단일 백엔드 | ✓ | ✓ | ✓ |
| TLS/SSL | ✓ | ✓ | ✓ |
| 다중 백엔드 | | ✓ | ✓ |
| 서비스 발견 | | ✓ | ✓ |
| API 조합 | | | ✓ |
| 인가 | | | ✓ |
| 재시도 로직 | | | ✓ |
| 호출률 제한 | | | ✓ |
| 로깅과 추적 | | | ✓ |
| 서킷브레이커 | | | ✓ |

### ADR 가이드라인: 프록시, 로드밸런서 또는 API 게이트웨이의 선택

- **결정사항**: 인그레스 트래픽 전달에 프록시·로드밸런서·API 게이트웨이 중 무엇을 쓸 것인가?
- **논의사항**: 엔드포인트 하나에서 백엔드 하나로 가는 **단순 라우팅**만 필요한가? 인증·인가·호출률 제한 같은 **고급 교차 기능 요구사항**이 있는가? API 키/토큰, 수익화·입금 취소 같은 **API 관리 기능**이 필요한가? 이미 적용된 솔루션이 있거나, 모든 트래픽을 특정 에지 컴포넌트로 보내라는 조직 차원의 요구가 있는가?
- **권장사항**: **가까운 미래와 현재 요구를 함께 보되, 그 요구를 만족시키는 가장 단순한 솔루션**을 고른다. 고수준 교차 기능 요구가 있다면 대개 API 게이트웨이가 최선이고, 엔터프라이즈 조직이라면 API 관리 기능을 지원하는 게이트웨이를 권한다. 기존 권한·솔루션·컴포넌트에 대한 조직 내 실사를 항상 먼저 한다

## 2. 사례 연구: 참석자 서비스를 소비자에게 노출하기

컨퍼런스 시스템 소유자가 **모바일 애플리케이션**에서 참석자 상세 정보를 볼 수 있게 해달라고 한다. 그러려면 참석자 서비스 API를 외부에 공개해야 한다. 참석자 서비스는 **PII를 저장**하므로 API는 안정적이고 관측이 용이하며 안전하게 호출될 수 있어야 한다.

프록시나 로드밸런서로 노출하고 나머지를 언어·프레임워크 기능으로 구현할 수도 있다. 하지만 그 솔루션이 확장 가능한지, 재사용 가능한지(다른 언어·프레임워크로 만든 API도 지원하는지), 이미 그 요구를 해결하는 제품이 있는지 따져봐야 한다. 이 사례에서는 **앞으로 다른 언어·프레임워크로 만든 API를 더 노출할 계획**이라는 사실을 알고 있으므로, API 게이트웨이 기반 솔루션이 타당하다.

```
┌────────┐  UI 요청이 새      ┌──────────────────────────┐  세션 리뷰·예약   ┌────────────────────┐
│  고객   │  게이트웨이로 유입   │      API 게이트웨이        │ ──────────────▶ │ 레거시 컨퍼런스 시스템 │
│ [사람]  │ ─────────────────▶│ [소프트웨어 인프라스트럭처]  │                  └─────────┬──────────┘
└────────┘                    │ 요청을 적절한 시스템으로 라우팅│                            │ API 호출로
                              └────────────┬─────────────┘                            │ 참석자 상세 조회
                                           │ 참석자를 생성·조회                          ▼
                                           └──────────────────────────────▶ ┌────────────────────┐
                                                                            │   참석자 [서비스]     │
                                                                            └────────────────────┘
```

## 3. API 게이트웨이의 정의

API 게이트웨이는 소비자와 백엔드 서비스 사이의 **시스템 에지에 위치하는 관리 도구**로, 사전에 정의한 여러 API로의 **진입점** 역할을 한다. 소비자는 단일 페이지 웹 앱, 모바일 앱, 다른 내부 시스템, 서드파티 시스템 등 무엇이든 될 수 있다.

구현은 두 컴포넌트로 나뉜다. 한 패키지로 묶을 수도, 따로 배포할 수도 있다.

- **제어 부분(*control plane*)**: 작업자가 라우트·정책·텔레메트리를 **정의**하는 영역
- **데이터 부분(*data plane*)**: 제어 부분에서 정의된 것을 실제로 수행하는 영역 — 네트워크 패킷 라우팅, 정책 반영, 텔레메트리 송출

기능적으로 게이트웨이는 네트워크 수준에서 모든 API 요청을 받는 **리버스 프록시**로 동작하며, 애플리케이션 수준의 여러 백엔드(필요하면 외부 서비스까지)를 호출하고 결과를 종합해 돌려준다.

> **참고 — 프록시·포워드 프록시·리버스 프록시**: **포워드 프록시**는 여러 클라이언트의 요청을 인터넷의 다른 서버로 전달하는 중간 서버이며 **클라이언트를 보호**한다(기업이 직원의 인터넷 접근 트래픽을 라우팅·필터링하는 경우). **리버스 프록시**는 보통 비공개 네트워크의 방화벽 뒤에 있으며 클라이언트 요청을 적절한 백엔드로 라우팅하고 **서버를 보호**한다.

### 배포 위치

게이트웨이는 시스템의 에지에 배포하는데, 여기서 "시스템"의 범위는 조직 규모에 따라 유연하다.

- **스타트업·소규모 기업**: 데이터센터나 클라우드의 에지에 **단일 게이트웨이**(고가용성을 위해 여러 인스턴스)를 두고, 이 하나가 전체 백엔드의 진입점이자 에지 기능 전부를 담당한다

```
클라이언트 ──┐                                        ┌──▶ REST 백엔드
             ├── 인터넷 ──▶ [ API 게이트웨이 ] ────────┼──▶ gRPC 백엔드
서드파티 ────┘                                        └──▶ REST 백엔드
```

- **대규모 조직·엔터프라이즈**: 데이터센터 주변 에지 스택에 여러 곳으로 배포하고, **제품·사업부·조직 부서별로 별개의 게이트웨이**를 두기도 한다. 거버넌스 요구나 지리적 위치, 인프라 수용량(예: 저전력 에지 컴퓨트)에 따라 게이트웨이마다 다른 기능을 제공한다

```
클라이언트 ──┐                      ┌── A 부서 게이트웨이 ──▶ SOAP·gRPC 서비스
             ├── 인터넷 ── DMZ ────┤
서드파티 ────┘                      └── B 부서 게이트웨이 ──▶ REST 서비스
```

### 에지 스택에서의 위치

API 기반 시스템의 에지에는 컴포넌트가 여럿 배포된다. 소비자가 백엔드와 처음 마주하는 지점이라 공통 이슈를 여기서 처리하기 때문이다.

```
        ┌─────────────────────────────────────────┐
        │  콘텐츠 전달 네트워크(CDN) · DNS 외부 제공자 │
        ├─────────────────────────────────────────┤
  에지  │  계층 4 로드밸런서 · 앱 전달 컨트롤러(ADC)  │
  스택  ├─────────────────────────────────────────┤
        │        웹 애플리케이션 방화벽(WAF)         │
        ├─────────────────────────────────────────┤
        │             API 게이트웨이                │
        └────────────────────┬────────────────────┘
                             ▼
                 백엔드 시스템 · 앱과 서비스
```

> **핵심 통찰**: 이 계층을 **모놀리식 덩어리로 취급하면 안 된다.** 보통 각 계층은 따로 배포되고 서로 다른 팀이나 서드파티가 소유·운영한다. 에지 스택 전체 기능을 제공하는 게이트웨이도 있고, 게이트웨이·API 관리 기능만 제공하는 것도 있다.

## 4. API 게이트웨이를 사용해야 하는 이유

### 프론트엔드와 백엔드의 낮은 결합도: 어댑터/퍼사드 패턴

결합도·응집도·정보 은닉은 아키텍트가 일찍 배우는 기본 개념이다. 결합도가 낮으면 구현체를 교체하기 쉽고 테스트에서 모조 객체·스텁으로 바꾸기도 쉽다. 응집도가 높으면 이해용이성·신뢰성·재사용성이 올라간다. 정보 은닉은 **바뀔 가능성이 높은 결정을 분리**하는 원리다.

> **핵심 통찰**: API는 **아키텍처 이론이 현실과 만나는 지점**에 있다. 말 그대로 다른 엔지니어와 통합하는 인터페이스이기 때문이다.

API 게이트웨이는 단일 진입점으로서 **퍼사드**나 **어댑터**처럼 동작한다. 퍼사드는 시스템을 위한 **간결한 새 인터페이스**를 제공하고, 어댑터는 두 인터페이스 사이의 **상호운용성**을 위해 기존 인터페이스를 재사용한다. 잘 합의된 계약을 게이트웨이로 노출하면 **백엔드의 위치·아키텍처·구현(언어, 프레임워크)을 최소한의 노력으로 바꿀 수 있다.**

### 사용법의 간소화: 종합과 해석

프론트엔드에 주고 싶은 API가 백엔드들이 제공하는 인터페이스와 다른 경우가 자주 생긴다. 프론트엔드 엔지니어의 멘탈 모델을 단순화하려고, 데이터 관리를 간소화하려고, 혹은 백엔드 아키텍처를 감추려고 **여러 백엔드의 API를 종합해 단일 API로** 제공하고 싶어진다. GraphQL을 쓰는 흔한 이유이기도 하다. 다만 트레이드오프가 있다 — **백엔드의 비즈니스 로직과 게이트웨이가 구현한 로직이 강하게 결합되기 아주 쉽다.**

> **참고 — 동시적 API 호출의 조율**: 대부분의 게이트웨이는 여러 독립 백엔드 API를 **병렬로** 호출해 결과를 모아준다. 소비자가 각자 구현할 필요가 없어진다. 대신 비즈니스 로직이 게이트웨이와 백엔드로 분산되고, **운영 결합**도 생긴다 — 게이트웨이 구현이 바뀌어 호출 순서가 달라지면, 특히 백엔드가 멱등성을 지원하지 않을 때 결과가 달라질 수 있다.

엔터프라이즈에서는 **프로토콜 해석**도 자주 필요하다. SOAP만 지원하는 유물 시스템이 여럿인데 소비자에게는 REST만 노출하고 싶은 경우다. 게이트웨이의 종합·해석 기능을 쓸 수 있지만, 해석을 제대로 설계·구현·테스트하는 비용과 **요청이 많을 때의 컴퓨팅 비용**이 추가된다.

### 남용과 오용으로부터 API 보호

에지는 사용자가 애플리케이션을 처음 만나는 지점이고, 그렇기에 **악의적 사용자와 공격자가 처음 만나는 지점**이기도 하다. 대기업은 CDN·WAF·DMZ 등 보안 계층을 여럿 두지만, 소규모 조직에는 **API 게이트웨이가 최초의 방어선**이다. 그래서 많은 게이트웨이가 TLS 종료, 인증/인가, IP 허용/거부 목록, WAF(내장 또는 외부 통합), 호출률 제한과 부하 분산, **API 계약 검증**을 제공한다.

```
해커 ──┐                    ┌─ 허용/거부 목록: 128.0.0.x 허용 / 129.0.0.x 거부
       ├──▶ API 게이트웨이 ─┤
정상 ──┘                    └─ 호출률 제한: 사용자 1 = 초당 200회 / 사용자 2 = 초당 10회
```

이 기능의 핵심은 **오용을 탐지하는 것**이고, 그러려면 포괄적인 관측용이성 전략이 필요하다.

### API 활용 방식에 대한 이해: 관측용이성

비즈니스 목표는 고객 전환율·시간별 수익·초당 스트림 시작 같은 **KPI**로 측정하고, 인프라와 플랫폼은 레이턴시·에러·대기 지연 같은 **SLI**로 관측한다.

**대부분의 사용자 요청이 시스템 에지를 지나므로 여기가 관측용이성에서 가장 중요한 지점이다.** 에러 횟수·처리량·레이턴시 같은 주요 인그레스 지표를 확보하기 이상적이고, 업스트림으로 흘러가는 요청을 확인·표시하기도 좋다. 보통 게이트웨이가 요청에 **연관 식별자**(*correlation identifier*)를 붙여 각 업스트림 서비스로 전파하고, 이 식별자를 로그에 남겨 분산된 요청을 추적한다.

> **핵심 통찰**: 데이터를 수집하는 것과 **그 데이터를 실행 가능한 정보로 해석하는 것**은 다른 문제다. 대시보드와 경고를 설계하는 일이 관측용이성 전략의 절반이다.

### API를 제품으로 관리하기: API 수명주기 관리

모던 API는 내부 시스템은 물론 서드파티도 쓰는 **제품**으로 설계·운영되므로 제품처럼 관리해야 한다. 완전한 **API 수명주기 관리**(*API Management - APIM*)는 계획 단계에서 시작해 운영 종료까지 이어지며, 여러 단계가 게이트웨이 구현과 **강하게 결합**되어 있다. 그래서 APIM을 지원하려면 게이트웨이 선택이 중요하다.

Axway 팀이 정리한 10단계는 다음과 같다.

1. **구현**: API를 설계하고 구현한다
2. **테스트**: 기능·성능·보안 요구사항을 검증한다
3. **발행**: API를 개발자에게 공개한다
4. **보안**: 보안 위험과 우려를 완화한다
5. **관리**: 정상 동작·업데이트·비즈니스 요구 충족을 유지한다
6. **온보딩**: 개발자가 빠르게 학습하도록 돕는다 (OpenAPI/AsyncAPI 문서, 포털, 샌드박스)
7. **분석**: 관측용이성을 확보하고 모니터링 데이터로 활용도를 이해하며 문제를 탐지한다
8. **홍보**: API 마켓플레이스 등록 등으로 개발자에게 알린다
9. **수익화**: 사용에 비용을 청구하고 수익을 만든다
10. **운영 중단**: 비즈니스 우선순위·기술 변화·보안 등의 이유로 일어나는 퇴출과 제거를 지원한다

### API의 수익화

고객에게 노출되는 API는 제품으로 설계되어 개발자 포털로 제공되므로 **계정 관리와 결제 옵션**이 필요하다. 대부분의 엔터프라이즈 게이트웨이가 수익화 기능을 포함하며, 결제 포털은 페이팔·스트라이프 같은 솔루션과 통합되어 개발자가 제품 기능·호출률 제한·사용 옵션을 설정하게 한다.

## 5. 모던 API 게이트웨이의 역사

> 역사는 되풀이되지 않는다. 다만 비슷하게 반복될 뿐이다.<br>— 마크 트웨인(Mark Twain)

아키텍처 스타일과 패턴은 소프트웨어 개발사에서 주기별로 반복된다. 역사를 이해해야 더 견고한 기반을 만들고 **같은 실수를 반복하지 않는다**.

- **1990년대 — 하드웨어 로드밸런서**: 웹 1.0 시기에 브라우저(넷스케이프 1994), 웹 서버(아파치 1995), 하드웨어 로드밸런서(F5 설립 1996)가 함께 등장했다. 동적 페이지는 펄·C 스크립트와 **CGI**(*Common Gateway Interface*)로 만들었는데, 이것이 오늘날 **FaaS의 시초**다. 방문자가 늘자 부하 분산과 내고장성이 필요해졌고, 인프라 엔지니어들이 데이터센터 에지에 하드웨어 로드밸런서를 배포해 요청을 여러 웹 서버로 나눴다. 기본적인 **헬스체크** 로직을 갖춰 서버에 문제가 생기면 다른 서버로 넘겼다. 하드웨어 로드밸런서는 지금도 쓰이며 주요 기능은 변하지 않았다
- **2000년대 초반 — 소프트웨어 로드밸런서**: 고가용성·확장성 요구가 커지는데 하드웨어 로드밸런서는 비싸고 유연하지 않았다. 하프록시(2001)·엔진엑스(2002)가 등장하며 시스템 관리자에게 필요한 기술이 **하드웨어 문제 처리에서 소프트웨어 설정**으로 옮겨갔다. 같은 시기 CDN과 WAF도 하드웨어에서 소프트웨어로 전환됐고, 오픈소스 ModSecurity와 아파치의 통합이 WAF 대중화를 이끌었다
- **2000년대 중반 — 애플리케이션 전달 컨트롤러(ADC)**: 브라우저에 `XMLHttpRequest`가 실리고 **Ajax**가 퍼지며 웹 2.0이 열렸다. API가 본질적으로 비동기가 되면서 페이지 전체를 매번 다시 받지 않아도 됐고, 데이터 교환 계층과 표현 계층이 분리됐다. 그 결과 웹 서버와 로드밸런서는 더 많은 부하, 더 안전한(SSL) 트래픽, 더 큰 페이로드, 요청별 우선순위를 감당해야 했다. **ADC**는 로드밸런싱에 압축·캐싱·연결 멀티플렉싱·트래픽 가공·SSL 오프로드를 더한 개념이다. 이 시기 에지 스택 컴포넌트 대부분이 업계에 자리 잡았지만 **팀 간 격리**도 깊어졌다 — 새 애플리케이션 하나를 공개하려면 CDN 벤더·로드밸런싱 팀·정보보안/WAF 팀·웹 서버 팀과 회의를 거쳐야 했다. **데브옵스 운동이 시작된 계기 중 하나가 바로 이 격리의 갈등이었다**
- **2010년대 초 — 1세대 API 게이트웨이**: API 경제가 열렸다. 트윌리오 창업자 제프 로슨은 "우리는 전화의 지저분하고 복잡한 체계를 5개의 API 호출로 정리했다"고 했다. 구글 애드 API는 콘텐츠 생산자에게 수익화 길을 열었고 스트라이프는 비용 청구를 쉽게 만들었다. 마셰이프(2007)는 API 마켓플레이스를 시도했고, 그 부산물로 오픈레스티와 **콩**이 나왔다. WSO2, Apigee, 3Scale도 등장했다. 이들은 **플랫폼 팀과 시스템 관리자뿐 아니라 개발자를 겨냥한 최초의 에지 기술**이었고, 핵심은 API의 **SDLC 관리**와 프로토콜 커넥터·해석 모듈 같은 통합 기능이었다. 동시에 관심이 OSI **4계층(IP·포트)에서 7계층(HTTP)** 으로 옮겨가, 경로나 헤더 같은 HTTP 메타데이터 기반 라우팅이 가능해졌다
- **2015년 이후 — 2세대 API 게이트웨이**: 마이크로서비스 개념이 굳어지고 도커(2013)·쿠버네티스 1.0(2015)이 나오며 에지에 새 요구가 생겼다. 넷플릭스는 2013년 JVM 기반 **줄(Zuul)** 을 공개했다 — 동적 백엔드를 위한 **서비스 발견**, 런타임에 그루비 스크립트로 동작을 바꾸는 기능, 그리고 인증·카나리 릴리스·요청률 제한·부하 분산·관측용이성을 **하나의 에지 컴포넌트로 통합**했다. 스프링 클라우드 게이트웨이도 여기서 나왔다. 2016년 리프트가 **엔보이 프록시**를 오픈소스로 공개하자 엠버서더 에지 스택·콘투어·글루 에지 등이 그 위에 만들어졌다

> **참고 — 클라우드상의 혼선**: **API 게이트웨이**는 애플리케이션 계층(OSI 7)에서 어댑터 스타일의 공통 기능부터 완전한 API 수명주기 관리까지 **API에 대한 관리 기능**을 제공한다. **에지 프록시**는 네트워크(3)·전송(4) 계층에서 동작하는 범용 트래픽 프록시로 공통 기능은 주되 API 특화 기능은 없다. **인그레스 컨트롤러**는 쿠버네티스 전용 용어로, 클러스터로 들어오는 트래픽과 그 처리 방식을 제어한다.

## 6. 현재의 API 게이트웨이 분류

- **전통적인 엔터프라이즈 게이트웨이**: 비즈니스 중심 API의 제공·관리가 목적이며 **API 수명주기 관리 솔루션과 통합**되는 경우가 많다. 대개 오픈 코어/상용 버전을 쓴다. 데이터 스토어 같은 **종속 서비스의 배포·운영이 필요**하고, 그 외부 의존성도 고가용성을 지원해야 하므로 운영 비용과 DR/BC 계획에 반영해야 한다
- **마이크로서비스/마이크로 게이트웨이**: 주 목적은 인그레스 트래픽을 백엔드로 전달하는 것이고 수명주기 관리 기능은 적다. 단독 컴포넌트로 배포하며 쿠버네티스 같은 기반 플랫폼에 내부 상태를 맡기기도 한다. 엔보이 같은 현대 프록시로 구현되어 **(같은 프록시 기술로 만든) 서비스 메시와의 통합이 좋다**
- **서비스 메시 게이트웨이**: 외부 트래픽을 메시로 전달하는 한 가지 기능만 하도록 설계된 경우가 많다. 인증·계정 관리 통합이나 WAF 같은 엔터프라이즈 기능은 없다. 관련 서비스 메시(및 그 운영 요구)와 **암묵적으로 결합**되므로, **서비스 메시 도입 계획이 없다면 첫 번째 선택지로 삼지 않는 편이 좋다**

| 관점 | 전통적 엔터프라이즈 | 마이크로서비스 | 서비스 메시 게이트웨이 |
|------|------------------|--------------|---------------------|
| 주목적 | 내부 비즈니스 API와 서비스의 노출·조합·관리 | 내부 비즈니스 서비스의 노출·조합·관리 | 메시 내부 서비스 노출 |
| 발행 방식 | API 관리 팀이 관리용 API로 등록/수정 | 서비스 팀이 배포 과정에서 **선언적 코드**로 등록/수정 | 서비스 팀이 배포 과정에서 선언적 코드로 등록/수정 |
| 모니터링 | 관리·운영 중심 (소비자별 호출 수, 5xx 에러) | 개발자 중심 (레이턴시·트래픽·에러·포화도) | 플랫폼 중심 (활용도·포화도·에러) |
| 디버깅 | L7 에러 처리, 스테이징 로그로 디버깅 | L7 에러 처리 + 상세 모니터링·트래픽 복사·카나리로 재현 | L7 에러 처리 + 트래픽 '태핑'으로 서비스 간 통신 확인 |
| 테스트 | 자동 통합 테스트, semver 기반 버저닝 | 카나리 라우팅·다크 론칭으로 동적 테스트, 계약 테스트 | 카나리 라우팅으로 동적 테스트 |
| 로컬 개발 | 설치 스크립트·베이그란트·도커로 로컬 설치 | 컨테이너·쿠버네티스로 로컬 배포 | 쿠버네티스로 로컬 배포 |
| 사용자 경험 | 웹 관리 UI·개발자 포털·서비스 카탈로그 | IaC/CLI + 간단한 개발자 포털 | IaC/CLI + 제한된 서비스 카탈로그 |

## 7. 사례 연구: 게이트웨이로 컨퍼런스 시스템 개선하기

모놀리스에서 분리한 참석자 서비스로 트래픽을 **직접** 라우팅하도록 게이트웨이를 설정한다. 이것이 8장의 **교살자 무화과나무 패턴**(*strangler fig pattern*)을 실행하는 방법이다 — 기존 시스템에서 기능을 조금씩 떼어내 독립 배포 가능한 서비스로 옮기는 패턴이다.

> **핵심 통찰**: 많은 조직이 서비스를 분리하면서도 **라우팅은 기존 모놀리스가 계속 담당하게** 한다. 모놀리스가 이미 그 기능을 갖고 있으니 쉬운 선택이다. 하지만 그러면 ① 모든 트래픽이 모놀리스로 유입되고 ② **설정 반영 시점이 모놀리스의 배포 빈도에 묶여** 강결합이 생기며 ③ 모놀리스의 부하와 장애 영향 반경이 커진다. **모놀리스로 트래픽을 라우팅하지 말 것**, 특히 짧은 시간에 여러 서비스를 분리할 계획이라면 절대 채택하지 말 것.

### 쿠버네티스에 게이트웨이 설치하기

컨퍼런스 시스템이 쿠버네티스에 배포돼 있으면 YAML 적용이나 헬름 같은 표준 방식으로 게이트웨이를 설치할 수 있다. 게이트웨이를 배포·설정하고 나면 렛츠인크립트로 TLS 인증서를 받는 것도 어렵지 않다.

게이트웨이가 HTTPS 연결을 담당하면 **애플리케이션은 TLS 종료나 다중 포트 리스닝을 더 이상 신경 쓰지 않아도 된다.** 인증이나 호출률 제한도 **애플리케이션 설정 변경이나 재배포 없이** 켤 수 있다.

### URL 경로와 백엔드 서비스 매핑

`legacy` 네임스페이스의 8080 포트에서 도는 `conferencesystem` 서비스를 도메인 루트에 매핑한다.

```yaml
---
apiVersion: getambassador.io/v3alpha1
kind: Mapping
metadata:
  name: legacy-conference
spec:
  hostname: "*"
  prefix: /
  rewrite: /
  service: conferencesystem.legacy:8080
```

이제 `/attendees`로 오는 트래픽만 분리해낸 참석자 마이크로서비스(`nextgen` 네임스페이스)로 보낸다. `rewrite` 키를 쓰면 대상 서비스를 호출하기 전에 경로 접두어를 **재작성**할 수 있어, 참석자 서비스 입장에서는 `/`로 들어온 요청처럼 보인다.

```yaml
---
apiVersion: getambassador.io/v3alpha1
kind: Mapping
metadata:
  name: attendees
spec:
  hostname: "*"
  prefix: /attendees
  rewrite: /
  service: attendees.nextgen:8080
```

레거시에서 서비스를 분리할 때마다 같은 패턴의 매핑을 더하면 된다. 접두어는 중첩(`/attendees/affiliation`)하거나 정규표현식(`/attendees/^[a-z].*`)으로 정의할 수도 있다. **결국 레거시는 몇 가지 기능만 남고 나머지는 각자 매핑을 가진 마이크로서비스가 처리하게 된다.**

### 호스트 기반 라우팅

새 서비스에 신규 도메인이나 서브도메인이 필요할 때 쓴다.

```yaml
---
apiVersion: getambassador.io/v3alpha1
kind: Mapping
metadata:
  name: attendees-host
spec:
  hostname: "attendees.conferencesystem.com"
  prefix: /
  service: attendees.nextgen:8080
```

> **실무 팁 — 요청 페이로드 기반 라우팅은 피하자.** 이유는 둘이다. ① 특정 도메인과 강하게 결합된 정보가 게이트웨이 설정으로 새어 나온다(페이로드에는 애플리케이션에서 바뀔 수 있는 스키마/계약이 들어 있어 게이트웨이가 그 변경을 계속 따라가야 한다). ② 라우팅 정보를 뽑으려고 페이로드를 **역직렬화하고 파싱하는 연산 비용**이 높고 느리다.

## 8. 배포: 장애에 대한 이해와 관리

게이트웨이는 배포 방식과 무관하게 **대부분의 사용자 요청이 지나는 결정적 지점**에 있다. 에지 게이트웨이가 죽으면 시스템 전체를 못 쓰고, 업스트림 게이트웨이가 죽으면 핵심 서브시스템을 못 쓴다.

### API 게이트웨이도 단일 실패 지점이다

표준 웹 시스템에서 가장 분명한 단일 실패 지점은 **DNS**다(대개 외부 시스템이고 장애 시 탈출구가 없다). 그다음이 전역·지역 4계층 로드밸런서이고, 설정에 따라 방화벽이나 WAF도 그렇다. **핵심 에지 컴포넌트 다음 계층이 보통 API 게이트웨이다.** 게이트웨이 기능에 더 많이 의존할수록 장애의 위험과 영향도가 커지며, 게이트웨이는 소프트웨어 릴리스에 포함되어 **설정이 계속 바뀐다**는 점도 위험을 더한다.

> **참고 — 보안 컴포넌트의 장애 시 대처**: 제품·배포·설정에 따라 일부 보안 컴포넌트는 **"장애에 개방적"**(*fail open*)일 수 있다. 컴포넌트가 죽으면 트래픽이 백엔드로 그냥 흘러간다는 뜻이다. 가용성이 최우선인 시나리오에서는 괜찮지만 **금융·정부 시스템에서는 그러면 안 된다.** 현재 설정이 어느 쪽인지 반드시 확인하자.

### 문제의 탐지·해결과 위험 완화

탐지의 첫 단계는 모니터링 시스템에서 **적절한 신호**(지표·로그·추적)를 수집·확인할 수 있게 하는 것이다. 중요한 시스템에는 문제를 책임질 전담 팀이 있어야 하고, 팀은 SLA의 기반이 되는 **SLO**로 소통해야 한다.

각 게이트웨이에는 **문제가 생겼을 때 책임질 소유자**가 필요하다. 소규모 조직에서는 기반 시스템을 맡은 개발자나 SRE가, 대규모 조직에서는 전담 인프라 팀이 맡고 그중 일부는 24/365 긴급 대응을 한다. 장애가 해결되면 **비난 없는 건설적인 회고**로 모든 것을 문서화한다 — 재발 방지뿐 아니라 학습 중인 엔지니어와 비슷한 문제를 겪는 다른 팀에게도 자산이 된다.

고가용성은 대개 **여러 인스턴스를 실행하는 것**에서 시작한다. 온프레미스라면 이중화 장비를 여러 지역에, 클라우드라면 다중 가용성 존·지역에 분산한다. 앞단에 전역 로드밸런서가 있다면 헬스체크를 제대로 설정하고 **장애 조치 절차를 정기적으로 테스트**해야 한다(액티브/패시브나 리더/노드 모드라면 더욱).

장애 조치 시 흔한 문제는 다음과 같다.

- 백엔드 상태가 제대로 옮겨가지 않아 **스티키 세션**이 깨지는 클라이언트 상태 관리 문제
- 클라이언트의 **지리적 위치를 무시한 리다이렉트**(미국 동부가 살아 있는데 유럽 사용자를 미국 서부로 보내는 식)
- 리더 선출 컴포넌트 장애로 데드락이 생겨 **모든 백엔드로 번지는 연속적 장애**

## 9. 흔한 위험과 안티패턴

**망치를 들면 모든 것이 못으로 보인다.** 게이트웨이를 망치로 볼 때 나오는 세 가지 안티패턴이 있다.

**① API 게이트웨이 루프백** — 서비스가 몇 개 안 될 때 서비스 메시까지 설치할 필요는 없지만 **서비스 발견** 같은 기능은 필요하다. 가장 쉬운 방법은 모든 서비스의 위치를 아는 게이트웨이로 **모든 트래픽을 라우팅**하는 것이고, 그림은 '허브 앤 스포크'가 된다. 문제는 둘이다. ① 서비스 간 트래픽이 **네트워크를 벗어났다가 다시 들어오면서** 성능·보안·비용 문제를 만든다(클라우드는 이그레스와 가용성 존 간 트래픽에 과금한다). ② 서비스 수가 늘면 게이트웨이가 병목이 되어 **진짜 단일 실패 지점**이 된다. 주기가 맞물려 각 호출에서 무슨 일이 일어나는지 이해하기도 어려워진다.

지금 우리 컨퍼런스 시스템이 딱 그 문제에 걸린다. 외부 트래픽은 게이트웨이가 잘 라우팅하는데, **레거시 애플리케이션은 참석자 서비스의 위치를 어떻게 찾는가?** 가장 먼저 떠오르는 방법이 공개 주소(`www.conferencesystem.com/attendees`)로 다시 호출하는 것인데, 그러지 말고 **내부 서비스 발견 메커니즘으로 내부 네트워크 안에서 해결해야 한다**(4장).

**② API 게이트웨이를 ESB처럼 활용** — 대부분의 게이트웨이는 플러그인·모듈로 기능을 확장한다(엔진엑스의 루아 모듈, 엔보이의 C·웹어셈블리 필터, 줄의 그루비 스크립트). 인증·필터링·로깅 같은 쓸모가 분명한 사용처가 많다. 그런데 여기에 **비즈니스 로직을 넣고 싶은 충동**이 생긴다. 그러면 게이트웨이와 서비스가 강하게 결합되어, 플러그인 하나만 바꿔도 조직 전체가 영향을 받거나 **대상 서비스와 플러그인을 딱 맞춰 배포해야 해서** 릴리스가 어려워진다.

**③ 모두가 거북이(게이트웨이)가 되는 현상** — 게이트웨이 하나가 좋으면 더 많이 두면 좋지 않을까? 대규모 조직은 계층·네트워크·부서별로 게이트웨이를 여럿 배포한다. 관심사 분리라는 좋은 의도로 시작하지만, **간단한 서비스 업그레이드에도 여러 게이트웨이 팀과 조율**해야 하고("추적 기능은 누가 담당했지?") 네트워크 홉마다 비용이 붙어 성능이 나빠진다.

## 10. API 게이트웨이의 선택

**요구사항 파악**이 첫 단계다. 당연해 보이지만 새로운 기술과 화려한 마케팅에 휘말리기가 너무 쉽다. "API 게이트웨이를 사용해야 하는 이유" 절로 돌아가 **현재의 문제점과 향후 로드맵 양쪽에 초점을 맞춘 질문**을 스스로 던져야 한다.

**구현할 것인가, 구입할 것인가.** 어떤 엔지니어는 벤더보다 나은 것을 만들 수 있다거나 우리 조직은 특별하다고 판단한다. 하지만 게이트웨이 컴포넌트는 이미 충분히 성숙했으므로 **오픈소스 구현체나 상용 솔루션을 쓰는 편을 권한다.** 직접 만들 때 흔히 빠지는 함정은 셋이다.

- **총 소유 비용(*TCO*) 과소평가**: 구현 비용, 지속적 유지보수 비용, 운영 비용을 모두 낮게 잡는다
- **기회 비용 무시**: 클라우드나 플랫폼 벤더가 아닌 이상 게이트웨이를 직접 만들어 경쟁 우위를 얻을 가능성은 거의 없다
- **현재 기술 솔루션에 대한 인지 부족**: 오픈소스와 상용 플랫폼 모두 빠르게 변하므로 따라가기 어렵지만, **그것을 따라가는 것이 기술 리더 역할의 핵심**이다

### ADR 가이드라인: API 게이트웨이의 선택

- **결정사항**: 조직에 적합한 API 게이트웨이를 어떻게 선택할 것인가?
- **논의사항**: 모든 요구사항을 분석하고 **우선순위**를 매겼는가? 조직이 이미 배포해 쓰는 기술 솔루션을 파악했는가? 팀·조직의 제약을 파악했는가? 관련 로드맵을 확인했는가? '구현 대 구매' 비용을 정확히 계산했는가? 현재 기술 동향과 가용 솔루션을 이해하는가? 모든 이해당사자와 상의했는가?
- **권장사항**: **낮은 결합도 유지·사용법 간소화·남용 방지·활용도 이해·제품으로서 관리와 수익화**라는 목적에 요구사항을 정렬한다. 이미 쓰는 게이트웨이가 있는지, 여러 기술을 조합해 유사 기능을 낼 수 있는지, 현재 에지 스택이 몇 개 컴포넌트로 되어 있는지 확인한다. 팀의 숙련도·투입 인력·예산을 본다. 현재와 미래 솔루션의 **TCO**를 계산한다. **개발자·QA·아키텍처 리뷰 보드·플랫폼 팀·정보보안 팀 모두와 상의한다**

## 요약

- API 게이트웨이는 인그레스 트래픽 관리의 **유일한** 답이 아니다. 요구가 단순 라우팅뿐이면 프록시나 로드밸런서로 충분하고, 고급 교차 기능 요구가 있을 때 게이트웨이가 값을 한다
- 게이트웨이는 시스템 에지에서 **퍼사드/어댑터**로 동작해 프론트엔드와 백엔드를 떼어놓고, 종합·해석·보안·관측용이성·수명주기 관리·수익화를 제공한다. 다만 종합과 해석은 **비즈니스 로직이 게이트웨이로 새어 나가는** 결합 위험을 함께 가져온다
- 기술의 계보는 하드웨어 로드밸런서 → 소프트웨어 로드밸런서 → ADC → 1세대 API 게이트웨이 → 2세대(마이크로서비스·컨테이너 시대)로 이어진다. 관심의 초점이 **OSI 4계층에서 7계층으로** 옮겨간 것이 API 게이트웨이 등장의 조건이었다
- 게이트웨이는 **엔터프라이즈·마이크로서비스·서비스 메시** 세 유형으로 갈리며, 발행 방식(관리 UI vs 선언적 코드)과 모니터링 관점(운영 vs 개발자 vs 플랫폼)이 다르다
- 사례 연구에서는 게이트웨이 매핑으로 `/attendees`를 새 서비스로 보내며 **교살자 무화과나무 패턴**을 시작했다. 라우팅을 모놀리스에 맡기면 강결합이 생기므로 피한다
- 게이트웨이는 **단일 실패 지점**이다. 다중 인스턴스·헬스체크·장애 조치 테스트·전담 소유자·비난 없는 회고가 위험 완화의 기본이다
- 안티패턴 셋 — **루프백**(서비스 간 트래픽을 게이트웨이로 되돌리기), **ESB처럼 사용**(플러그인에 비즈니스 로직 넣기), **게이트웨이 남발**(조율 비용과 홉 비용 증가)
- 게이트웨이 선택에 정답은 없지만 **피해야 할 나쁜 솔루션은 분명히 있다**

## 다른 챕터와의 관계

- **0장**: 수직(north-south) 트래픽을 관리하는 컴포넌트가 바로 이 장의 주제다. 그림 0-3의 **API 컨트롤러를 프로세스 밖으로 꺼낸 것**이 API 게이트웨이다
- **1장**: 게이트웨이 뒤에서 여러 API를 같은 기반 URL로 노출하는 이야기, 그리고 **API 계약 검증**을 인프라 계층에서 수행하는 이야기가 이어진다
- **2장**: 테스트를 마친 API를 프로덕션에 노출하는 다음 단계다. 카나리 라우팅·트래픽 복사가 게이트웨이 유형 비교표에 등장한다
- **4장**: 루프백 안티패턴이 남긴 질문 — **내부 서비스는 서로를 어떻게 찾는가** — 에 서비스 메시가 답한다
- **5장**: 게이트웨이의 트래픽 제어 기능이 카나리·블루-그린 릴리스의 토대가 된다
- **6·7장**: 에지가 최초의 방어선이라는 관점이 위협 모델링과 인증·인가로 확장된다
- **8장**: 여기서 시작한 교살자 무화과나무 패턴을 아키텍처 진화의 관점에서 정리한다
