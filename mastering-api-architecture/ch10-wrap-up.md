# Chapter 10: Wrap-up (지속적인 아키텍처 진화를 위해)

## 핵심 질문

컨퍼런스 시스템은 0장에서 여기까지 무엇이 어떻게 바뀌었는가? 그 변화를 조직은 어떻게 뒷받침해야 하는가? 그리고 이 책이 끝난 뒤에도 계속 배우려면 무엇을 해야 하는가?

## 1. 사례 연구: 지금까지의 변화

### 출발점 (0장)

```
┌────────┐  사용  ┌──────────────┐  HTTP로   ┌────────────────────┐  기록·조회  ┌──────────────┐
│  고객   │ ─────▶│ 웹 애플리케이션 │ API 호출  │ 컨퍼런스 애플리케이션 │ ─────────▶ │  데이터베이스  │
│ [사람]  │        │  [컨테이너]    │ ────────▶ │     [컨테이너]      │            │  단일 스토어   │
└────────┘        └──────────────┘           └────────────────────┘            └──────────────┘
                              컨퍼런스 시스템 [소프트웨어 시스템]
```

**단일 UI + 서버 애플리케이션 + 데이터베이스 하나.** 여기서 시작했다.

### 0장 — 참석자 서비스 분리

컨퍼런스 관계자의 요구(모바일 앱·CFP 통합·클라우드 이전)에 따라 참석자 컴포넌트를 **독립 프로세스로 도는 API 기반 서비스**로 떼어냈다. 이때 트래픽이 **수직(고객→레거시)** 과 **수평(레거시→참석자)** 으로 갈렸다.

### 1·2장 — 아키텍처 변화 없음

참석자 API를 **설계·명세하고(1장) 테스트하는(2장)** 동안 아키텍처 자체는 그대로였다. **구조가 아니라 계약과 신뢰를 만드는 단계**였다.

### 3장 — API 게이트웨이 추가

```
┌────────┐   UI 요청  ┌──────────────────┐  세션 리뷰·예약  ┌────────────────────┐
│  고객   │ ─────────▶│  API 게이트웨이    │ ──────────────▶│ 레거시 컨퍼런스 시스템 │
└────────┘            │ [인프라스트럭처]   │                 └──────────┬─────────┘
                      │  단일 진입 지점    │  참석자 생성·조회            │ API 호출
                      └────────┬─────────┘ ──────────────┐             ▼
                                                          └──▶ ┌────────────────┐
                                                               │  참석자 서비스    │
                                                               └────────────────┘
```

게이트웨이가 **추상화이자 단일 진입점**이 되었고, **언제 레거시를 부르고 언제 새 서비스를 부를지 제어하는 퍼사드 패턴**이 도입됐다.

### 4장 — 세션 서비스 분리 + 서비스 메시

세션 기능을 레거시에서 떼어내고, **서비스 간 API 트래픽을 조율하는 메시**를 추가했다. 이제 레거시·참석자·세션이 서로를 호출한다.

### 5장 — 기능 플래그로 점진적 릴리스

참석자 서비스의 **내부 버전과 외부 버전을 나란히 두고**, 기능 플래그로 요청을 어디로 보낼지 정했다. **배포와 릴리스가 분리된** 시점이다.

### 6장 — 모바일 앱 등장 (위협 모델링)

아키텍처 자체는 바뀌지 않았지만, 위협 모델링에 현실적인 시나리오를 주기 위해 **컨퍼런스 시스템을 호출하는 모바일 앱**이 등장했다.

### 7장 — 외부 CFP 시스템 등장 (인증·인가)

**외부 인증과 인가가 필요한 서드파티 CFP 시스템**이 아키텍처에 추가됐다. 발표자(리소스 소유자)가 CFP를 통해 참석자 정보를 갱신하는 흐름이 생겼다.

### 9장 — 클라우드 이전, 그리고 제로 트러스트

참석자 서비스와 게이트웨이를 **클라우드로 플랫폼 교체**했고, 마지막으로 배포·라우팅·보안에 **균일한 방식을 적용하는 제로 트러스트 하이브리드 아키텍처**로 넘어갔다.

```
┌──────────── 클라우드 ─────────────┐
│  API 게이트웨이 [메시 인프라]        │
│         │ mTLS                    │
│    참석자 서비스 ──▶ 데이터 스토어    │
└─────────┬────────────────────────┘
          │ 멀티클러스터 서비스 메시 (mTLS 라우팅)
┌─────────▼──────── 온프레미스 ─────┐
│  레거시 컨퍼런스 ──▶ 세션 ──▶ 스토어  │
└──────────────────────────────────┘
```

> **핵심 통찰**: 온프레미스의 단일 서비스+데이터베이스에서 시작해 **클라우드와 온프레미스에 걸친 멀티서비스 시스템**이 되었다. 최종 아키텍처는 **유연성이 훨씬 커졌지만, 그 대가로 아키텍처와 인프라의 복잡도가 늘었다.** 이 트레이드오프가 사례 연구 전체의 요약이다.

## 2. API, 콘웨이의 법칙, 그리고 조직

> 조직의 (넓은 범위의) 시스템 설계는 조직의 의사소통 구조를 반영하는 시스템을 설계하게 된다.<br>— 멜빈 콘웨이(Melvin Conway), 「위원회는 어떻게 발명하는가(How Do Committees Invent?)」

간단히 말하면 **"4개의 그룹이 컴파일러를 만들면 4단계 컴파일러가 나온다"** 는 것이다. API 세계에서도 같은 일이 벌어져서, 저자들은 **"4개의 그룹이 마이크로서비스 시스템을 만들면 4개의 계층을 가진 API가 나온다"** 는 농담을 하곤 했다.

> **핵심 통찰**: API 기반 시스템은 본질적으로 **사회기술적(socio-technical) 시스템**이다. '기술적' 관점만큼 **'사회적' 관점도 중요하게** 다뤄야 한다. 대규모 조직 전환이나 '디지털 트랜스포메이션'을 맡게 된다면 사전 작업에 대해 철저히 상담을 받자.

관련해 읽어볼 책으로 『팀 토폴로지』, 『팀 애자일 조직 혁명』, 『The Art of Scalability』를 권한다.

## 3. 의사결정 종류의 이해

제프 베조스(Jeff Bezos)가 나눈 두 종류의 의사결정이다.

- **타입 1**: 쉽게 되돌릴 수 없는 결정. **주의해서** 결정해야 한다
- **타입 2**: 문으로 걸어 들어가는 것처럼 **쉽게 바꿀 수 있는** 결정. 마음에 안 들면 되돌리면 된다

> **핵심 통찰**: 문제는 둘을 혼동해 **타입 2 결정에 타입 1의 절차를 쓰는 것**이다. 그러면 느리고 지나치게 조심스러운 위험 회피가 되어 **실험이 줄고 결국 혁신이 줄어든다.** 다만 대규모 엔터프라이즈에서 **API 게이트웨이나 서비스 메시 도입은 대체로 타입 1 결정**이다 — 조직이 그 결정 방식에 맞게 움직이도록 해야 한다.

## 4. 미래를 위한 준비

### 비동기 통신

비동기 API는 **클라이언트-서버**(gRPC 같은 기술)와 **클라이언트-브로커**(카프카 같은 중간 기술)로 나뉜다. **AsyncAPI**는 비동기 API 명세를 제공하는 흥미롭지만 **아직 개발 중인 표준**이다. 비동기 API의 어려움은 **프로토콜 형식과 기술이 다양하다는 것**이며, 이벤트 주도 아키텍처가 퍼지고 데이터 교환 방식의 정의가 빠르게 바뀌고 있어 주시할 분야다.

### HTTP/3

HTTP의 **의미(동사·상태 코드·메시지 필드)는 버전과 무관하게 같다.** 다른 것은 **그 의미를 기반 전송 프로토콜에 매핑하는 방식**이다. HTTP/1.1과 HTTP/2는 TCP를 쓰지만 **HTTP/3는 UDP 기반 전송 프로토콜인 QUIC**을 쓴다. 이 전환은 HTTP/2의 큰 문제인 **HOL 차단**(*head-of-line blocking*)을 해결한다 — 로드할 리소스가 많은 사이트에서 특히 두드러지던 문제다.

이론적으로 훨씬 빠르지만 **전송 프로토콜이 바뀌었으므로 인그레스 프록시와 네트워킹 컴포넌트를 업그레이드해야 한다.** 다행히 웹 브라우저의 70% 이상이 이미 HTTP/3를 지원한다.

### 플랫폼 기반 메시

4장에서 언급했듯 **서비스 메시는 모던 플랫폼 서비스에 통합되어 갈 것이다.** 대부분의 조직이 클라우드 벤더의 쿠버네티스 스택을 쓰면서 컨테이너(OCI)나 네트워킹(CNI) 구현을 바꾸지 않듯, **서비스 간 통신도 그렇게 될 것이다.** **서비스 메시 인터페이스(SMI)** 같은 표준을 주시하자 — 견고한 인터페이스의 등장과 도입은 **이 통신 계층이 균일해진다는 뜻**이다.

## 5. API 아키텍처를 계속 학습하는 방법

### 기반 기술을 계속 연마한다

> **핵심 통찰**: 마스터하려는 기술이 무엇이든 **그 기반을 계속 재검토하는 것**이 중요하다. 소프트웨어처럼 **유행에 민감한 업계에서는 특히** 그렇다. 응집도와 결합도 같은 주제를 다루는 컨퍼런스 세션에서 배운 개념을 **다음 날 바로 적용**하곤 했다.

**"옛것이 새것"** 이라는 말은 이 업계에서 진부한 표현이지만, 기반을 끊임없이 재검토하는 아키텍트는 **조금씩 다른 형태로 반복되는 기술의 순환**을 훨씬 잘 따라간다.

### 업계의 최신 정보를 얻는다

아키텍처·API 분야의 뉴스 사이트 목록을 모으고 **주 1회 정도 훑어보며** 트렌드 감각을 유지한다 — InfoQ, DZone, The New Stack, Software Architecture Reddit. RSS 리더로 블로그를 모아 주간·월간으로 리뷰하고, **관심사가 비슷하고 오픈소스에 기여하는 사람들을 팔로우**하면 새 기능을 일찍 알 수 있다.

### 레이더·쿼드런트·트렌드 리포트

**개념 증명과 실험은 항상 직접** 해야 하지만, 분석 자료로 트렌드를 추적하면 **어려운 문제에 부딪혔거나 해법은 찾았는데 벤더 기술을 특정해야 할 때** 유용하다 — 쏘트웍스 테크놀로지 레이더, 가트너 매직 쿼드런트(API 전체 수명주기 관리), CNCF 테크 레이더, InfoQ 트렌드 리포트.

> **실무 팁**: 기술 비교 스프레드시트는 '서류상의 평가'에 유용하지만 **벤더가 후원하는 경우가 많으므로 편향을 확인**하고 **발행 일자가 최근인지** 봐야 한다.

### 권장 기법과 사용 사례를 학습한다

기업들이 자기 방식을 공유하는 동기는 **이타심·자랑·매출·채용이 섞인 것**이므로 그 동기를 이해해야 한다. 특히 **초기의 실패나 지금도 잘못된 부분은 대개 언급되지 않는다.** 그래도 사용 사례는 우리 팀의 문제와 해법을 비춰보게 해준다 — 선택이 옳았음을 확인시켜 주기도 하고, **다시 생각할 기회**가 되기도 한다.

문서와 발표 둘 다 보되, **컨퍼런스 발표는 끝나고 발표자와 이야기할 수 있다**는 장점이 있다(QCon, CraftConf, APIDays, KubeCon, Devoxx 등).

### 실전을 통해 학습한다

> **핵심 통찰**: **아키텍트는 실용적인 소프트웨어 엔지니어로 남아 있어야 한다.** 매일 프로덕션에 코드를 넣지는 않더라도 **정기적으로 팀 엔지니어와 짝 프로그래밍을 하거나 최신 기술을 실험할 시간**을 마련하자. 그러지 않으면 **개발자에 대한 공감을 잃기 쉽다.**

예를 들어 많은 아키텍트가 **컨테이너 기술이 개발자 도구에 미치는 영향을 초기에 잘못 이해했다.** 이미지를 만들고 원격 레지스트리에 발행해본 적이 없으면, 그 작업이 API를 만들고 유지하는 일상 업무에 어떤 영향을 주는지 **무시하기 쉽다.**

### 가르치면서 학습한다

**어떤 개념을 가르치려고 정보를 모으는 경험**을 능가하는 학습은 없다. 그 과정에서 자기가 개념을 제대로 이해하지 못했음을 깨닫거나, 학생의 질문에서 **내 이해와의 차이**를 갑자기 발견하게 된다.

> **핵심 통찰**: **아키텍트의 또 다른 역할은 가르치는 것이다.** 기본을 가르치든 새 기법을 공유하든, 가르치는 행위는 **팀 안에서 내 기술을 강화하고 신뢰를 확립**한다.

## 요약

- 컨퍼런스 시스템은 **단일 UI+애플리케이션+DB**에서 시작해 **참석자·세션 분리 → 게이트웨이 → 서비스 메시 → 기능 플래그 릴리스 → 외부 소비자(모바일·CFP) → 클라우드 이전 → 제로 트러스트 하이브리드**로 진화했다. 유연성을 얻은 만큼 **복잡도라는 대가**를 치렀다
- **콘웨이의 법칙** — 시스템 설계는 조직의 의사소통 구조를 닮는다. API 시스템은 **사회기술적 시스템**이므로 조직 설계를 함께 봐야 한다
- **타입 1(되돌리기 어려운)과 타입 2(쉽게 되돌리는) 의사결정**을 구분하자. 둘을 혼동하면 실험과 혁신이 줄어든다. 게이트웨이·메시 도입은 대체로 타입 1이다
- 주시할 흐름은 **비동기 통신(AsyncAPI)**, **HTTP/3(QUIC, HOL 차단 해결)**, **플랫폼에 통합되는 서비스 메시(SMI)** 다
- 계속 배우는 방법은 다섯이다 — **기반 기술 연마, 업계 소식 수집, 레이더·트렌드 리포트 추적, 권장 기법과 사용 사례 학습, 실전(짝 프로그래밍·실험), 그리고 가르치기**

## 다른 챕터와의 관계

- **0장**: 여기서 그린 첫 C4 다이어그램과 이 장의 최종 아키텍처를 나란히 놓으면 책 전체가 한 장의 그림이 된다
- **1장**: OpenAPI가 REST를 서술했듯 **AsyncAPI**가 비동기를 서술하려 한다. HTTP/2의 성능 이점 논의가 **HTTP/3**로 이어진다
- **4장**: 메시가 플랫폼 서비스로 흡수되리라는 전망이 여기서 다시 확인된다
- **8·9장**: 아키텍처와 인프라의 진화를 각각 다뤘고, 이 장은 그 결과를 조직·의사결정·학습의 관점에서 마무리한다
