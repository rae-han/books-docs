# 모던 API 아키텍처 설계 전략 (Mastering API Architecture)

> 제임스 고프(James Gough)·대니얼 브라이언트(Daniel Bryant)·매튜 어번(Matthew Auburn) 지음, 장현희 옮김, 책만, 2026<br>원서: *Mastering API Architecture: Design, Operate, and Evolve API-Based Systems* (O'Reilly, 2023)

API를 "설계 대상"이 아니라 **시스템의 아키텍처 그 자체**로 다루는 책이다. REST/gRPC 명세를 어떻게 쓰느냐에서 끝나지 않고, API 트래픽이 시스템 경계를 어떻게 드나드는지(API 게이트웨이·서비스 메시), 어떻게 배포·릴리스되고 관측되는지, 어떻게 인증·인가되고 위협 모델링되는지, 그리고 모놀리스를 API 주도 아키텍처와 클라우드 플랫폼으로 어떻게 **진화**시키는지까지를 한 줄기로 잇는다. 참석자가 세션을 예약하는 **컨퍼런스 시스템** 사례가 0장부터 10장까지 전 장을 관통하며, 장마다 **ADR 가이드라인**으로 "무엇을 결정해야 하는가"를 남긴다.

## 개요

이 책의 출발점은 "API는 코드가 아니라 **경계**"라는 관점이다. 한 프로세스 안에서 클래스가 메서드를 부르던 호출을 네트워크 너머로 옮기는 순간, 그것은 함수 시그니처 문제가 아니라 **트래픽·신뢰성·보안·배포·조직의 문제**가 된다. 그래서 책은 명세 작성(1장)에서 시작해 테스트(2장) → 인그레스 트래픽(3장) → 서비스 간 트래픽(4장) → 배포와 릴리스(5장) → 위협 모델링(6장) → 인증·인가(7장) → 아키텍처 진화(8장) → 인프라 진화(9장)로, **하나의 API가 살아가는 전 구간**을 따라간다.

서술 방식의 특징은 두 가지다. 첫째, **하나의 사례가 책 전체를 관통한다.** 3계층 모놀리스인 컨퍼런스 시스템에서 참석자 서비스를 떼어내는 것으로 시작해, 게이트웨이를 세우고, 세션 서비스를 분리하고, 기능 플래그로 릴리스를 나누고, 모바일 앱과 외부 CFP 시스템이라는 소비자를 맞이하고, 결국 클라우드와 온프레미스에 걸친 제로 트러스트 하이브리드가 된다. 매 장의 결정이 **다음 장의 문제로 되돌아오기 때문에**, 각 기술이 왜 그 자리에 필요한지가 드러난다.

둘째, **"경우에 따라 다르다"를 그대로 두지 않는다.** 책은 주제마다 **ADR 가이드라인**(결정사항·논의사항·권장사항)을 두어, 무엇이 상황을 가르는 변수인지와 저자들이 어느 쪽을 권하는지를 명시한다. 게이트웨이를 쓸지 프록시로 충분한지, 메시를 쓸지 라이브러리로 갈지, 계약 테스트를 도입할지, OAuth2의 어떤 승인을 지원할지 - 답 대신 **판단의 축**을 남기는 것이 이 책의 방식이다.

## 학습 가이드

**기본은 순차 읽기다.** 사례 연구가 장을 넘어가며 누적되므로, 앞 장의 결정이 뒤 장의 문제로 되돌아오는 구조를 따라가는 것이 가장 효율적이다. 특히 **0장은 건너뛰지 말 것** - 수직/수평 트래픽 구분과 ADR 형식이 여기서 정의되고, 이후 모든 장이 그 어휘로 쓰였다.

```
        ┌──────────────────────────── 0장: 사례·C4·ADR·트래픽 패턴 ────────────────────────────┐
        │                                                                                      │
        ▼                                                                                      ▼
   [1장 설계·명세] ──▶ [2장 테스트]                                          [8장 아키텍처 진화]
        │  (명세는 형태만 서술)   │                                                  │
        │                        ▼                                                  ▼
        └────────────▶ 계약 테스트                                            [9장 인프라 진화]
                                                                                    │
   수직 트래픽 ──▶ [3장 API 게이트웨이] ──┐                                          ▼
                                          ├──▶ [5장 배포와 릴리스] ──▶ [10장 마무리]
   수평 트래픽 ──▶ [4장 서비스 메시] ─────┘         │
                        │                          │
                        └──────▶ [6장 위협 모델링] ─┴──▶ [7장 인증과 인가]
```

**역할별 진입점** - 시간이 없다면 이렇게 잘라 읽어도 된다.

- **API를 만드는 개발자**: 1장 → 2장 → 5장. 명세·계약·릴리스가 하나의 흐름이다
- **플랫폼/인프라 엔지니어**: 3장 → 4장 → 9장. 게이트웨이·메시·클라우드 전환이 한 축이다
- **보안 담당**: 6장 → 7장. 6장이 위협의 지도이고 7장이 그중 위장·권한 상승의 해법이다
- **아키텍트**: 0장 → 8장 → 10장. 진화의 원리(응집도·결합도·적합성 함수)와 조직·의사결정 이야기가 여기 모여 있다
- **"게이트웨이를 쓸까 메시를 쓸까"가 궁금하면**: 3장의 표 3-1(프록시/로드밸런서/게이트웨이 비교)과 4장의 인그레스↔서비스 간 트래픽 속성 비교표만 봐도 판단 축이 잡힌다

## 핵심 개념 맵

- **수직(north-south) / 수평(east-west) 트래픽**이 책 전체의 척추다. 0장에서 이 축이 정의되고, 3장(게이트웨이)과 4장(메시)이 각 축을 하나씩 맡으며, 9장에서 클라우드로 옮겨 가며 **그 경계가 흐려지는 것**으로 되돌아온다
- **명세 → 계약 → 릴리스**는 하나의 사슬이다. OpenAPI 명세는 API의 **형태만** 서술하므로(1장), 의미를 지키려면 계약 테스트가 필요하고(2장), 그 계약이 지켜지는지 확인하며 **버전을 나눠 릴리스**한다(5장). 사슬의 어느 고리가 없으면 단절적 변경이 프로덕션에서 발견된다
- **배포 ≠ 릴리스.** 이 구분이 트래픽 관리 기술(게이트웨이·메시의 분할·미러링)과 만나 카나리·다크 론치·블루-그린이 된다. 5장은 3·4장의 기능이 **왜 값을 하는지**를 보여주는 장이다
- **위협 모델링(6장)이 지도, 인증·인가(7장)가 해법.** 스트라이드의 여섯 위협 중 **위장은 인증**으로, **권한 상승은 인가(BOLA·BFLA)** 로 대응된다. 게이트웨이는 계약 검증·호출률 제한·TLS로 많은 것을 막지만 **대량 할당과 과도한 데이터 노출은 서비스가 막아야 한다**
- **응집도와 결합도가 진화의 판단 기준**이다(8장). 낮은 결합도는 설계 미덕이자 **테스트 가능성의 전제**(2장의 모킹)이고, 정보 은닉은 **데이터 모델을 노출하지 않는다**는 1장·6장의 조언과 같은 원리다
- **ADR과 C4는 결정을 남기는 두 도구**다. C4는 구조를(0장), DFD는 데이터 흐름과 신뢰 경계를(6장) 그리며, ADR 가이드라인은 매 장의 선택을 **논점과 권고로** 남긴다. 그래서 이 책은 "무엇을 쓸까"가 아니라 **"무엇을 결정해야 하는가"** 의 목록이기도 하다
- 마지막으로 **아키텍처는 조직을 닮는다**(10장 콘웨이의 법칙). API 시스템은 사회기술적 시스템이므로, 기술 선택만으로 원하는 경계가 생기지는 않는다

## 시그니처 요소와 표기 규칙

- **`### ADR 가이드라인: 제목`** - 이 책의 시그니처. **결정사항 / 논의사항 / 권장사항** 세 항목의 불릿으로 적는다(원서의 표 형식을 리스트로 옮김). 각 장 끝의 선택지 정리 역할
- **`### ADR-00N: 제목`** - 사례 연구에서 실제로 작성한 ADR. **상태 / 컨텍스트 / 결정사항 / 결론** 불릿. 0장(참석자 분리)·4장(세션 분리)에 등장
- **`## N. 사례 연구: ...`** - 컨퍼런스 시스템의 진행 상황. 매 장에서 아키텍처가 어떻게 바뀌는지를 이 절에서 추적한다
- **다이어그램은 ASCII/유니코드로 재구성** - C4 컨텍스트·컨테이너·컴포넌트 다이어그램(0장), 데이터 흐름 다이어그램(6장), 에지 스택·메시 토폴로지·구역화 아키텍처 등. 원서 그림 번호는 본문에 병기
- **콜아웃 세 종류**: `> **핵심 통찰**:` (그 절의 요점), `> **실무 팁**:` (운영에서 지켜야 할 것), `> **참고**:` (원서의 박스·각주에서 온 보조 설명)
- **레이블 없는 `>` 인용** - 외부 인용과 저자 경험담. `> 인용문<br>- 화자` 형식으로 병합
- **코드 병기**: 원서의 **Java 코드는 `<details>`로 접고 TypeScript를 펼침**으로 병기한다(사용자가 TS 개발자이므로). **HTTP·YAML·proto·CLI 예제는 언어 중립이므로 원문 그대로** 둔다
- **표는 3열 이상 대조일 때만** 사용한다(게이트웨이 유형 비교, 메시 구현 방식 비교, 인그레스↔서비스 간 트래픽 속성, 적합성 함수 분류 등). 항목-설명 2열은 불릿 리스트로 작성

## 인용문

> 아키텍처는 미래를 위해 전략적으로 계획할 수 있을 것 같지만, 소프트웨어 개발 생태계는 지속적으로 변화하기 때문에 계획을 세우기가 어렵다. 변화를 피해갈 수는 없고 오히려 이용해야 한다.<br>- 닐 포드 외, "진화적 아키텍처" (Ch0, 저자가 재인용)

> 프로젝트가 살아있는 동안 추적하기 가장 어려운 것 중 하나는 어떤 의사결정이 내려진 동기다. 프로젝트에 새로 참여한 사람은 과거의 어떤 의사결정으로 인해 당황하거나, 이해를 못 하거나, 기뻐하거나, 혹은 짜증을 낼 수도 있다.<br>- 마이클 나이가드(Michael Nygard), ADR 개념의 창시자 (Ch0)

> API는 아키텍처적 이론이 현실과 만나는 시스템에 위치한다. 즉 API는 말 그대로 다른 엔지니어와 통합하는 인터페이스다.<br>- 제임스 고프·대니얼 브라이언트·매튜 어번 (Ch3)

> 역사는 되풀이되지 않는다. 다만 비슷하게 반복될 뿐이다.<br>- 마크 트웨인(Mark Twain) (Ch3, 저자가 API 게이트웨이의 역사를 여는 데 재인용)

> 이 오류들은 장시간에 걸쳐 모두 잘못된 것으로 검증되었으며 큰 문제와 고통스러운 학습 경험을 유발한다.<br>- 피터 도이치(Peter Deutsch) 외, "분산 컴퓨팅의 8가지 오류" (Ch4)

> TCP/IP 스택과 일반 네트워킹 모델은 수십 년 전에 개발되었고 여전히 컴퓨터 간의 통신에 있어 강력한 도구이지만, 좀 더 정교한 마이크로서비스 기반 아키텍처는 이런 아키텍처를 구현하는 엔지니어가 준수해야 하는 또 다른 요구사항 계층을 만들어냈다.<br>- 필 칼샤도(Phil Calçado), "패턴: 서비스 메시"(2017) (Ch4)

> 우리는 배포(deployment)라는 용어를 애플리케이션 컴포넌트나 인프라스트럭처의 변화를 배포하는 행위만을 의미하는 용어로 사용하길 권한다. 릴리스(release)라는 용어는 어떤 기능 변경이 최종 사용자에게 릴리스되어 비즈니스에 영향을 주게 되는 경우에만 사용해야 한다.<br>- 쏘트웍스 테크놀로지 레이더(2016) (Ch5)

> 설정에 오류가 있는 보안 장치는 보안 장치가 아예 없는 것보다 더 나쁜 결과를 낳을 수도 있다. 사용자는 자신의 동작과 데이터가 안전하지 않다고 생각하면 완전히 다르게 행동하기 때문이다.<br>- 제임스 고프·대니얼 브라이언트·매튜 어번 (Ch6)

> 토큰의 장기 사용은 탈취 또는 재사용의 위험이 크다. 토큰을 단기적으로 사용하면 이 위험을 완화할 수 있다.<br>- NIST 디지털 가이드라인 (Ch7)

> "여기서 어디로 가야 하는지 알려주실래요?" 그러자 고양이가 말했다. "그건 어디로 가고 싶은지에 따라 다르겠죠."<br>- 루이스 캐럴, "이상한 나라의 앨리스" (Ch8, 저자가 목표 없는 진화를 경계하며 재인용)

> 나는 개인적으로 모듈(또는 마이크로서비스) 경계에서 최대한 적은 내용을 노출하는 방식을 선호한다. 일단 뭔가가 모듈 인터페이스의 일부가 되었다면 이를 되돌리기란 어렵다. 하지만 지금 숨기고 있다면 언제든지 공유하기로 결정할 수 있다.<br>- 샘 뉴먼(Sam Newman) (Ch8)

> 되돌릴 수 없는 의사결정이 꼭 나쁜 것은 아니다. 하지만 충분히 주의 깊게 생각하고 고려하지 않은 상태로 결정을 내리면 그 결정은 나쁜 결정이다.<br>- 제임스 고프·대니얼 브라이언트·매튜 어번 (Ch8)

> 조직의 (넓은 범위의) 시스템 설계는 조직의 의사소통 구조를 반영하는 시스템을 설계하게 된다.<br>- 멜빈 콘웨이(Melvin Conway), "위원회는 어떻게 발명하는가(How Do Committees Invent?)" (Ch10)

> 우리는 아키텍트라면 실용적인 소프트웨어 엔지니어로 머물러 있어야 한다고 믿는다. (…) 이런 작업을 정기적으로 하지 않으면 아키텍트로서 개발자에 대한 공감을 잃기가 쉽다.<br>- 제임스 고프·대니얼 브라이언트·매튜 어번 (Ch10)
