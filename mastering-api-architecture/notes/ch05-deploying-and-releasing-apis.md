# Chapter 5: Deploying and Releasing APIs (API의 배포와 릴리스)

## 핵심 질문

새 기능을 프로덕션에 올리는 일과 그 기능을 사용자에게 여는 일을 어떻게 분리하는가? 그 분리를 API 버저닝·수명주기와 어떻게 맞물리게 하는가? 그리고 릴리스가 성공했는지 실패했는지 무엇을 보고 판단하는가?

## 1. 배포와 릴리스의 분리

레거시 컨퍼런스 시스템은 UI 하나와 서버 애플리케이션 하나로 되어 있다. 그래서 업그레이드를 배포한다는 것은 **어느 정도의 다운타임**을 뜻하고, 배포와 릴리스가 강하게 결합되어 분리할 수 없으며, 문제가 생겨 롤백하는 데도 시간이 걸린다.

- **배포(*deployment*)**: 실행 중인 시스템에 **새 기능을 올려두는 행위**다. 배포되었어도 그 기능은 아직 활성화되지 않았거나 아무 동작도 하지 않는다
- **릴리스(*release*)**: 그 **기능의 활성화를 제어하는 행위**다. 새 기능을 여는 데 따르는 위험을 통제하기 위한 것이다

> 우리는 배포(deployment)라는 용어를 애플리케이션 컴포넌트나 인프라스트럭처의 변화를 배포하는 행위만을 의미하는 용어로 쓰길 권한다. 릴리스(release)라는 용어는 어떤 기능 변경이 최종 사용자에게 릴리스되어 비즈니스에 영향을 주게 되는 경우에만 써야 한다. 기능 토글과 다크 론치 같은 기법을 활용하면 프로덕션 시스템에 기능을 릴리스하지 않고도 더 자주 배포할 수 있다. 배포 빈도가 높아지면 변경과 관련된 위험은 줄이면서도 비즈니스 이해당사자들은 최종 사용자에게 기능을 릴리스할 시점을 제어할 수 있다.<br>- 쏘트웍스 테크놀로지 레이더(2016)

> **핵심 통찰**: API 기반 아키텍처의 장점 중 하나가 **본질적인 분리 덕분에 팀이 빠르게 릴리스할 수 있다**는 것이다. 그런데 배포와 릴리스를 구분하지 않은 채 API 아키텍처로 넘어가면 그 장점이 사라진다. 서비스 결합도가 높을 때는 그럭저럭 굴러가지만, **여러 팀이 릴리스에 관여하는 순간 부담과 다운타임이 빠르게 커진다.**

### 사례 연구: 기능 플래그

레거시 시스템과 데이터베이스가 API 기반 서비스와 **나란히** 도는 상태에서 시작한다. 컨트롤러는 **기능 플래그**로 어디에 쿼리할지 코드 수준에서 고른다.

```
                       ┌──────────────────────────────────────────────┐
                       │        컨퍼런스 애플리케이션 [컨테이너]           │
   API 호출            │  ┌────────────────┐   내부 라우팅 [인 프로세스] │
 ─────────────────────▶│  │  API 컨트롤러    │ ──────────────────────┐  │
                       │  └───────┬────────┘                       ▼  │
                       │          │ 외부 라우팅 [아웃 오브 프로세스] ┌──────────────┐
                       │          │                              │ 참석자 [모듈]  │─── SQL ──▶ 데이터 스토어
                       │  ┌───────▼────────┐                     └──────────────┘
                       │  │  기능 플래그      │ ← 플래그로 실행 경로 결정            │
                       │  └────────────────┘                                     │
                       └──────────┼──────────────────────────────────────────────┘
                                  ▼
                       ┌────────────────────┐
                       │ 리팩터링한 참석자 서비스 │─── SQL ──▶ 데이터 스토어
                       └────────────────────┘
```

기능 플래그는 보통 **애플리케이션 외부에 설정을 저장**하므로 기능을 끈 상태로 코드를 배포할 수 있다. 팀이나 제품 소유자가 준비되면 켜서 다른 경로를 타게 한다. 세분화 단위는 **사용자 단위**까지 내려갈 수도 있다.

<details>
<summary>원서 예제 (Java, LaunchDarkly)</summary>

```java
LDUser user = new LDUser("jim@masteringapi.com");
boolean newAttendeesService =
    launchDarklyClient.boolVariation("user.enabled.modern", user, false);

if (newAttendeesService) {
    // 신형 스토어에서 참석자 조회
} else {
    // 레거시 스토어에서 참석자 조회
}
```

</details>

```typescript
const context = { kind: 'user', key: 'jim@masteringapi.com' };
// 세 번째 인자는 플래그 서비스 장애 시 쓰이는 기본값이다
const newAttendeesService = await ldClient.variation('user.enabled.modern', context, false);

if (newAttendeesService) {
  return await modernAttendeeStore.findAll();
}
return await legacyAttendeeStore.findAll();
```

이 방식이면 **사용자 일부만 새 시스템으로 옮겨** 동작을 확인할 수 있다. 잘못되면 플래그만 끄고, 잘되면 100%까지 계속 롤아웃한다.

> **실무 팁**: 기능 플래그 서비스도 관리를 못 하면 **단일 실패 지점**이 된다. 마지막 값을 캐시에 두거나 기본값을 주면 영향을 줄일 수 있다. 그리고 플래그는 **반드시 정리**해야 하고 **항상 유일한 이름**으로 만들어야 한다. 마이그레이션이 끝나면 플래그 코드를 완전히 제거한다. 나이트 캐피털(Knight Capital)은 **플래그를 재사용**했다가 배포가 실패해 초당 수천 달러씩, 최종 4억 6천만 달러의 손실을 냈다.

### 트래픽 관리로 넘어가기

API 기반 아키텍처는 트래픽과 라우팅 개념을 이미 갖고 있으므로 **두 곳에서 트래픽을 조작**할 수 있다 - API 게이트웨이의 인그레스 트래픽(3장), 서비스 메시 안의 트래픽 형태 변경(4장).

쿠버네티스·메시 기반 시스템의 배포 과정은 대략 이렇다.

1. 변경사항을 담은 풀 리퀘스트를 만들고, 승인 후 머지하면 자동으로 빌드가 돈다
2. 빌드 파이프라인이 도커(또는 OCI)로 새 이미지를 만든다
3. 새 이미지를 컨테이너 레지스트리에 등록한다
4. 대상 환경으로 배포한다

쿠버네티스는 기본적으로 실행 중인 배포본을 새 것으로 **교체**한다. 여기까지가 "배포"이고, **새 파드의 릴리스를 단계화하는 것**이 별도의 릴리스 과정이다.

## 2. 사례 연구: 컨퍼런스 시스템의 릴리스 모델링

릴리스를 모델링할 때는 **시맨틱 버저닝(1장)과 API 수명주기를 조합**하는 것이 좋다.

### API 수명주기

페이팔 API 표준에서 유래한, 지금은 고전이 된 모델이다.

1. **계획(Planned)**: API를 만들고 있음을 알리고 **설계와 형태에 대한 피드백**을 모으는 단계다. 초기 설계 결정을 여기서 반영한다
2. **베타(Beta)**: 사용자가 통합해볼 버전을 릴리스하되 목적은 **피드백 수집**이다. 아직 버전이 확정되지 않았으므로 **생산자가 호환성을 유지할 의무가 없다.** 덕분에 구조를 굳히기 전에 빠른 피드백을 받고, **처음부터 여러 메이저 버전을 떠안는 부담**을 줄인다
3. **라이브(Live)**: 버전이 확정되어 프로덕션에서 활성화된 상태다. 이후 모든 변경에는 버전이 할당된다. 라이브 API는 유일하며 가장 최근 메이저/마이너 조합으로 표시한다
4. **사용하지 않음(Deprecated)**: 여전히 쓸 수는 있지만 신규 개발은 대부분 적용되지 않는다. **마이너 업그레이드**라면 새 버전이 검증되는 잠깐만 이 상태에 머물다 퇴출된다(하위호환되므로). **메이저 업그레이드**라면 소비자가 마이그레이션해야 하므로 **몇 주에서 몇 달**을 이 상태로 있는다. 이 기간에도 소비자와의 의사소통·마이그레이션 가이드·사용량 추적이 필요하다
5. **퇴출(Retired)**: 프로덕션에서 내려가 더 이상 쓸 수 없다

> **핵심 통찰**: 시맨틱 버저닝과 수명주기를 조합하면 **소비자는 메이저 버전 변경만 신경 쓰면 된다.** 마이너와 패치는 소비자 측 업데이트가 필요 없고 호환성도 깨지 않는다.

### 수명주기에 릴리스 전략을 결합하기

**메이저 버전 변경**이 소비자에게 가장 큰 영향을 준다. 소비자가 자기 소프트웨어를 고쳐야 하므로 **라이브 버전과 사용하지 않음 버전을 한동안 함께 운영**해야 한다. 방법은 둘이다.

```http
GET /v1/attendees
```

URL에 버전을 넣으면 소비자가 쉽게 확인할 수 있지만, **버전은 리소스의 일부가 아니므로** REST 원리에 어긋난다고 보는 시각도 있다. 다른 방법은 헤더에 메이저 버전을 명시하고 **클러스터 인그레스 시점에 라우팅으로 처리**하는 것이다.

```http
GET /attendees
Version: v1
```

**마이너·패치 변경**은 이런 제약에서 자유롭다. 프로덕션 트래픽이 유입되지 않는 상태로 먼저 배포한 뒤 릴리스 전략에 따라 열면 되고, 소비자는 코드를 바꾸지 않아도 된다. 다만 이런 **투명한 릴리스가 가능하려면 빌드 단계에서 단절적 변경이 실수로 섞이지 않도록 막아야 한다** - 1장의 `openapi-diff`로 하위호환성이 깨지면 **빌드를 실패시키는** 것이 그 장치다.

소비자와 생산자가 강하게 결합되어 있고 **같은 팀이 관리한다면** 늘 함께 바뀌므로 버저닝과 수명주기가 그리 중요하지 않다. 이때는 두 컴포넌트를 함께 릴리스하고 인그레스에서 트래픽을 제어하는 전략, 대개 **블루-그린**이 적합하다.

### ADR 가이드라인: 트래픽 관리와 기능 플래그를 이용한 분리

- **결정사항**: 배포와 릴리스를 어떻게 분리할 것인가?
- **논의사항**: 지금 라이브 상태인 시스템에서 **오늘 당장** 분리가 가능한가? 소비자와 생산자의 결합도는 어느 정도인가? 느슨한 결합 요구를 반영하고 **호환성을 테스트할 빌드 파이프라인**이 있는가?
- **권장사항**: **기존 소프트웨어의 배포와 릴리스를 분리하는 것부터 시작한다** - 그래야 기존 시스템이 단순해지고 진화적 아키텍처로 넘어갈 수 있다. **기능 플래그**가 좋은 출발점이지만, 조심하지 않으면 단일 실패 지점이 되므로 권장 사례와 위험을 먼저 살핀다. 아키텍처 안 API 간 **결합의 종류를 확인하고 그에 맞는 릴리스 전략**을 고른다

## 3. 릴리스 전략

분리를 마쳤다면 다음은 **점진적 릴리스를 제어하는 메커니즘**이다. 핵심은 프로덕션의 위험을 최소화하는 것 - **트래픽 일부에 먼저 릴리스해 결과를 검증하고**, 성공하면 전체로 확대한다.

### 카나리 릴리스

새 버전을 **작은 비율의 트래픽에만** 노출한다. 이름은 광부들이 유독가스를 확인하려고 먼저 광산에 들여보낸 새에서 왔다.

```
[이전]   게이트웨이 ─▶ 레거시 v1.0 ─%분할─▶ 참석자 v1.0

[배포]   게이트웨이 ─▶ 레거시 v1.0 ─%분할─▶ 참석자 v1.0
                                          참석자 v1.1  ← 배포만 됨(트래픽 0)

[릴리스] 게이트웨이 ─▶ 레거시 v1.0 ─%분할─┬▶ 참석자 v1.0  (99%)
                                        └▶ 참석자 v1.1  (1%)
```

쿠버네티스만으로 하면 **파드 수로 비율을 만든다** - 1%를 원하면 v1 파드 99개와 v2 파드 1개가 필요하니 대개 실용적이지 않다. 그래서 서비스 메시나 게이트웨이의 **트래픽 이전**(*traffic shifting*)을 쓴다. 1%로 시작해 시간이 지나며 전체를 옮기고, 그동안 **기술적 문제(레이턴시 증가, 에러율)와 비즈니스 영향(전환율, 평균 구매 비용)** 을 함께 본다. 트래픽 분할을 50:50으로 두면 **A/B 테스트나 다변량 테스트**도 된다.

모든 서비스 간 통신에 메시가 관여하므로 이 기법은 **어떤 내부 서비스에도** 쓸 수 있다. 세션 일정을 내부 캐싱하는 새 세션 서비스를 카나리 릴리스하면서, 세션 일정 확인 빈도 같은 **비즈니스 KPI**와 CPU 사용량 감소 같은 **운영 SLI**를 함께 모니터링하는 식이다.

- **장점**: 카나리에 노출되는 트래픽을 **정교하게 제어**한다. 블루-그린과 달리 **두 번째 스택 전체가 필요 없어** 비용과 운영 복잡도가 낮다
- **트레이드오프**: 이슈를 빨리 감지하고 롤백할 수 있도록 **좋은 모니터링이 반드시 있어야 한다**(자동화 가능)

### 트래픽 미러링

트래픽을 **복사해 다른 곳으로도 보내는** 방식이다. 복제된 요청의 응답은 대개 호출자에게 돌려주지 않는다. 대신 기존 서비스와 리팩터링한 서비스의 **응답을 비교**하거나, 레이턴시·CPU 사용량 같은 **운영 속성을 관측**하는 데 쓴다.

```
[릴리스/실험] 게이트웨이 ─▶ 레거시 v1.0 ──▶ 참석자 v1.0  (응답은 여기서만 돌아감)
                                        ┊
                                        ┊ 요청 복제(미러링)
                                        ▼
                                        참석자 v1.1  (응답은 버려지고 관측만)
```

이것이 **다크 론치**(*dark launch*)다 - 사용자는 새 릴리스를 모르지만 내부적으로는 원하는 효과가 나는지 관측한다. 캐싱을 넣은 새 참석자 서비스를 다크 론칭하면 **비즈니스 영향이 아니라 운영 성능**을 평가할 수 있다.

### 블루-그린

라우터·게이트웨이·로드밸런서 뒤에 **완전한 두 환경**을 둔다. **블루**는 현재 라이브, **그린**은 다음 버전이다. 실제 트래픽을 옮기기 전에 그린을 검사하고, 문제없으면 전체 트래픽을 한 번에 넘긴다. 블루는 '꺼진' 상태가 되지만 문제가 나면 **빠르게 롤백**할 수 있다. 다음 변경은 그린→블루로, 이후 둘 사이를 오간다.

```
[배포]   게이트웨이 ─▶ [블루] 레거시 v1.0 + 참석자 v1.0   ← 라이브
                       [그린] 레거시 v1.1 + 참석자 v1.1   ← 검사 중

[릴리스] 게이트웨이 ─▶ [그린] 레거시 v1.1 + 참석자 v1.1   ← 라이브
                       [블루] 레거시 v1.0 + 참석자 v1.0   ← 롤백 대기
```

간결하고 잘 동작하며 **결합도가 높은 서비스에 특히 좋은 선택**이다. 서비스의 영속성을 관리하기도 쉽다(롤백 시에는 주의가 필요하다). 대신 **리소스가 두 배** 든다.

### 사례 연구: 아르고 롤아웃으로 롤아웃 수행하기

롤아웃 자체를 손으로 관리하고 싶지는 않다. **아르고 롤아웃**은 쿠버네티스 API를 CRD로 확장해 롤아웃 동작을 지원한다. `Rollout` CRD는 표준 배포 CRD에 **롤아웃 전략**을 결합한 것이다.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: attendees
spec:
  replicas: 5
  strategy:
    canary:
      steps:
        - setWeight: 20
        - pause: {}                 # 빈 중괄호 = 사람이 확인할 때까지 무기한 대기
        - setWeight: 40
        - pause: { duration: 10 }
        - setWeight: 60
        - pause: { duration: 10 }
        - setWeight: 80
        - pause: { duration: 10 }
  revisionHistoryLimit: 2
  selector:
    matchLabels:
      app: attendees-api
  template:
    metadata:
      labels:
        app: attendees-api
    spec:
      containers:
        - name: attendees
          image: jpgough/attendees:v1
```

`pause: {}`는 아르고가 다음 단계로 가기 전에 **사람의 확인을 받도록** 한다. 새 카나리는 이렇게 시작한다.

```console
$ kubectl argo rollouts set image attendees attendees=jpgough/attendees:v1.2
```

그러면 첫 단계로 **20%의 부하가 v1.2로 이전**되고 일시 정지 상태가 된다. 아르고 대시보드는 현재 롤아웃 상태(전략·단계·설정 가중치·실제 가중치·리비전)를 시각화하며, 문제가 있으면 **빠르게 롤백**할 수 있다.

수동 확인 대신 **지표를 분석해 자동으로 진행**하게 할 수도 있다.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: success-rate
spec:
  args:
    - name: service-name
    - name: prometheus-port
      value: 9090
  metrics:
    - name: success-rate
      successCondition: result[0] >= 0.95
      provider:
        prometheus:
          address: "http://prometheus.example.com:{{args.prometheus-port}}"
```

성공률은 꽤 단순한 지표다. **인프라가 아니라 API가 클라이언트 요청 처리에 실패하는 상황**도 있으므로, 무엇을 볼지 더 생각해야 한다.

## 4. 성공에 대한 모니터링과 장애의 인지

레거시 시스템은 애플리케이션 하나에 로그 파일 하나였다. 참석자 서비스처럼 분리해내면 **홉이 늘어 장애 지점이 늘고**, 문제를 직접 찾아내기가 금세 어려워진다.

### 관측용이성을 지탱하는 3가지 요소

- **지표(*metrics*)**: 플랫폼 상태에 중요한 요소를 **정기적으로 수집·측정**한 값이다. 구조가 자유로워서 무엇을 모을지 플랫폼이 정한다(자바라면 CPU 사용률, 힙 크기, 가비지 컬렉션 정지 시간)
- **로그(*logs*)**: 컴포넌트 처리에 대한 **세분화된 정보**다. 품질은 이를 출력하는 애플리케이션에 달렸고, **구조화된 로깅**이 검색·조회에 유리하다. 분산 시스템에서는 **로그만으로 부족하며** 추적·지표의 컨텍스트와 결합될 때 의미가 커진다
- **추적(*traces*)**: 분산 아키텍처로 옮기면 **반드시 필요하다**. 요청이 지나는 모든 컴포넌트를 따라갈 수 있어 실패 시 어디서 문제가 났는지 빠르게 안다. 요청 근원지에 최대한 가까운 곳에서 **유일한 헤더**를 붙이고 이후 처리에 계속 전파하며, 큐 같은 다른 인프라로 넘어가면 **메시지 헤더에도 그 값을 기록**한다

세 요소를 갖추는 데는 **오픈텔레메트리**가 가장 적합하다. CNCF의 공개 표준이라 벤더 종속을 피할 수 있다. 지표와 추적은 표준이 안정화되었고, **로깅은 방식이 워낙 다양해 더 어려운 문제**다.

### API에서 중요한 지표

**RED 지표**(*rate, error, duration* - 비율·에러·지속 시간)가 트래픽 기반 서비스 아키텍처를 재는 방법으로 자주 거론된다. 특정 시점에 무슨 일이 벌어지는지 좋은 개요를 준다. SRE 분야에서는 레이턴시·트래픽·에러·포화도로 구성된 **4가지 황금 신호**가 이에 해당한다.

> **핵심 통찰**: RED·황금 신호의 가장 큰 약점은 **시스템의 더 넓은 컨텍스트를 놓치기 쉽다**는 것이다. API의 모든 에러가 요청 체인의 한 서비스에서 나온 것인가? 5xx는 인프라나 서비스가 원인이라 중요하다. 4xx는 클라이언트 문제라지만 그냥 무시해도 되는가 - **403 Forbidden은 악의적 사용자가 허용되지 않은 데이터에 접근하려 했다는 뜻일 수 있다.** 무엇을 재야 하는지 조사하는 시간은 RED로 API를 훑는 시간보다 더 든다.

컨퍼런스 시스템에서 모을 지표는 이렇다.

- 참석자 서비스의 **분당 요청 수**
- 참석자 서비스의 **SLO = 응답 평균 레이턴시** (심하게 늘면 문제 신호다)
- CFP 시스템의 **401 에러 수** (벤더가 공격당했거나 토큰이 도용됐다는 암시일 수 있다)
- 참석자 서비스의 **가용성과 업타임**
- 애플리케이션의 **메모리·CPU 사용량**
- 시스템의 **총 참석자 수**

> **실무 팁**: 중요한 지표에는 반드시 알람을 건다. 다만 **위양성**(*false positive*)에 주의해야 한다. 활동 수치가 낮을 때 울리는 알람은 공휴일이나 주말에 터진다. **업무 시간에만 울리게** 하거나 **현재 로그인 사용자 수를 함께 고려**하는 편이 낫다.

### 신호 읽어내기

가비지 컬렉션 시간이 늘어나는 것은 **장애의 조기 신호**일 수 있다. GC는 애플리케이션을 멈추므로 요청이 지연되고 레이턴시에 영향을 준다. 이것을 일찍 알아채는 것은 **자동차 엔진이 이상한 소리를 내는 것을 감지하는 것**과 같다 - 아직 돌아가지만 뭔가 문제가 있다.

신호를 제대로 읽으려면 **기준치와 기댓값을 설정**하고 그 범위를 벗어날 때 알람을 내야 한다. 그다음 단계는 **API 레이턴시가 실제로 영향을 받을 때의 지표를 관찰**하는 것으로, 계기반에 엔진 검사등이 켜지는 것에 해당한다. **둘 다 무시하면 결국 장애가 나고 팀이 복구에 매달리게 된다.**

분산 아키텍처에서 장애는 불가피하며, 장애가 나면 **추적이 근본 원인을 찾는 첫 단계**다. 추적 도구가 없으면 개발자가 형사처럼 로그를 뒤지며 "누가 무엇을 했는지" 단서를 찾느라 몇 시간을 쓴다.

## 5. 효율적인 릴리스를 위한 애플리케이션의 대응

- **응답 캐싱**: 참석자 서비스를 카나리 릴리스했고 문제가 없어 보여 전체 롤아웃을 했다. 그런데 `GET /attendees`를 호출하는 쪽이 프록시를 쓰고 있었고, 그 프록시가 바운스되며 사방에 500초 지연이 생겼다. **캐싱된 결과 때문에 새 소프트웨어의 문제가 드러나지 않았던 것**이다. GET을 보내는 클라이언트에 `Cache-Control: no-cache, no-store` 같은 헤더를 붙여 캐싱되지 않게 하는 것이 중요하다
- **애플리케이션 수준 헤더 전파**: 요청을 받아 다른 서비스로 새 요청을 만드는 API는 **원 요청의 헤더를 새 요청에 복사**해야 한다. 추적·관측 관련 헤더가 전파되어야 분산 추적이 유지된다. 다만 인증·인가 헤더는 **무엇을 내려보낼지 신중히 정해야 한다** - 인증 헤더를 그대로 포워딩하면 **서비스가 다른 서비스나 사용자로 위장**할 수 있다. OAuth2 베어러 토큰은 전송 계층이 안전하다는 전제하에 안전하게 전달할 수 있다
- **디버깅을 돕는 로깅**: 로그를 두 종류로 나누면 좋다. **저널**(*journal*)은 시스템의 중요한 트랜잭션·이벤트를 수집하고(새 메시지 수신과 그 처리 결과), **진단**(*diagnostics*)은 처리 실패와 예상 못 한 에러에 집중한다. 구조화된 로그에 **종류를 나타내는 필드**를 넣으면 둘에 빠르게 접근할 수 있다

### 규약형 플랫폼 고려하기

이 장에서 다룬 결정들을 팀마다 따로 내리면 작업이 반복되고 방식이 제각각이 된다. 해법 중 하나가 **플랫폼 팀을 만들어 규약형 플랫폼**(*opinionated platform* - 설계 방향성·규칙이 명확한 플랫폼)을 만드는 것이다. 핵심 의사결정을 플랫폼에 기술적으로 녹여 넣어 **모든 개발자가 같은 기능을 각자 구현하지 않아도 되게** 한다.

성공하려면 데브옵스와 플랫폼 운영을 고려해 **프로덕션으로 가는 경로**를 확장해야 하며, 이를 **포장 도로**(*paved path*) 또는 **황금 경로**(*golden path*)라고 부른다. 개발 팀이 쓰고 싶어 하고 문제를 쉽게 풀어주는 플랫폼일수록 채택률이 높다. 다만 **개발자의 자유와 조직이 요구하는 동작 사이에 트레이드오프**가 있다는 점을 기억해야 한다.

### ADR 가이드라인: 규약형 플랫폼

- **결정사항**: 배포와 릴리스를 분리하기 위해 규약형 플랫폼을 도입할 것인가?
- **논의사항**: 조직이 쓰는 언어는 무엇이며, 플랫폼이 **그중 몇 가지만 지원해도 괜찮은가**? 개발자를 고객처럼 대하고 플랫폼을 **내부 제품으로 운영**할 수 있게 조직이 구성되어 있는가? 플랫폼이 주는 이점과 제약은 무엇인가(모니터링과 관측용이성을 즉시 제공해야 하는가)? 권장사항을 갱신하고 **이미 쓰는 팀에 변경을 어떻게 전달**할 것인가?
- **권장사항**: 개발자를 **플랫폼 제품의 고객처럼** 대우하고 의견을 받을 메커니즘을 만든다. 주요 기능은 개발자에게 **최대한 투명하게** 제공한다(예: 오픈텔레메트리를 구현한 라이브러리를 기본 제공). 새 애플리케이션은 항상 최신 기능을 쓰게 되는데, **기존 사용자를 최신으로 끌어올릴 방법**을 함께 설계한다

## 요약

- 출발점은 **배포와 릴리스의 분리**다. 기존 애플리케이션이라면 코드 수준의 **기능 플래그**가 좋은 시작이며, 플래그는 반드시 정리하고 유일한 이름을 써야 한다
- **트래픽 관리**는 라우팅으로 릴리스를 모델링할 기회를 준다. 게이트웨이(인그레스)와 서비스 메시(서비스 간) 두 곳에서 조작할 수 있다
- **메이저·마이너·패치**의 구분이 릴리스 옵션을 가른다. 메이저는 두 버전 병행과 소비자 마이그레이션이 필요하고, 마이너·패치는 투명한 릴리스가 가능하되 **빌드에서 단절적 변경을 막는 장치**가 전제다. API와 강하게 결합된 애플리케이션은 블루-그린 같은 다른 전략이 맞다
- 릴리스 전략은 **카나리**(정교한 트래픽 제어, 모니터링 필수), **트래픽 미러링/다크 론치**(운영 특성 평가), **블루-그린**(단순·빠른 롤백, 리소스 2배)으로 나뉘며, **아르고 롤아웃** 같은 도구로 단계와 자동 분석을 선언할 수 있다
- 관측용이성의 세 요소는 **지표·로그·추적**이고, 오픈텔레메트리가 표준의 축이다. RED/황금 신호는 좋은 출발점이지만 **컨텍스트를 놓치기 쉽다**
- 애플리케이션도 대응해야 한다 - **캐싱 제어, 헤더 전파(특히 인증 헤더의 위험), 저널/진단 로그 분리**
- 이 결정들을 조직 전체가 반복하지 않도록 **규약형 플랫폼(포장 도로)** 을 고려한다

## 다른 챕터와의 관계

- **1장**: 시맨틱 버저닝과 `openapi-diff`가 여기서 API 수명주기·릴리스 전략과 연결된다
- **2장**: "프로덕션에서 동작을 확인하는 것보다 나은 테스트는 없다"는 2장의 결론이 이 장의 카나리·다크 론치로 이어진다. SLI·SLO의 정의도 여기서 다뤘다
- **3·4장**: 게이트웨이의 인그레스 제어와 메시의 트래픽 분할·미러링이 릴리스 전략의 실행 수단이다
- **6·7장**: 401·403 에러를 지표로 읽는 관점이 위협 모델링과 인증·인가로 이어진다. 헤더 전파의 위험도 7장에서 다시 다룬다
- **9장**: 점진적 전달과 카나리가 클라우드 마이그레이션 전략에서 다시 등장한다
