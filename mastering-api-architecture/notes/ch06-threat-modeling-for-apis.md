# Chapter 6: Operational Security: Threat Modeling for APIs (운영 보안: API의 위협 모델링)

## 핵심 질문

보안 전문가가 아닌 아키텍트가 시스템의 취약점을 어떻게 체계적으로 찾아내는가? 발견한 위협 중 무엇을 먼저 고칠지는 어떻게 정하는가? 그리고 API 게이트웨이는 어디까지 막아줄 수 있는가?

## 1. 왜 지금 보안인가

지금까지 설계·테스트·배포·릴리스까지 API의 수명주기를 훑었다. 참석자 API는 외부에 노출될 준비가 된 것처럼 보인다. 그런데 **API는 구현이 빠르고, 미래 호환성을 고려해 설계하기가 까다로우며, 안전하게 구현하기는 더 어렵다.** 현실에서 개발자와 아키텍트는 기능 구현에 집중하고 보안은 프로젝트 막바지에 생각하는 경우가 많다.

> **핵심 통찰**: 모든 위협을 알아낼 수는 없다(공격자도 다양하고 위협 자체가 계속 진화한다). 아키텍트에게 중요한 기술은 **최대한 일찍 보안을 고려해 설계하고 구현하는 것**이다. 개발 주기에서 보안을 일찍 다룰수록 진화하는 위협에 더 쉽고 비용 효율적으로 대응할 수 있다.

4장에서 mTLS로 제어 부분 안의 안전한 통신을 구현했다. 하지만 **제어 부분이 미치지 않는 '외부' 시스템**이 등장하면 새로운 방법이 필요하다.

### 외부 API가 안전하지 않을 때의 위험

대부분의 소프트웨어 전문가는 보안을 최우선으로 두지 않는다. 개발자는 비즈니스 솔루션, SRE는 시스템 운영, 제품 소유자는 새 기능 계획에 집중한다. 보안은 늘 뒷전이고 운이 좋아 보안 팀이 있으면 그쪽에 맡겨버린다. 고객도 대개 **보안 장치가 있는지보다 어떤 서비스를 제공하는지에 관심이 있다**.

그런데 유출의 영향은 재앙에 가깝다 — 주식 공개 회사의 사이버 유출 평균 비용은 **1억 1600만 달러**, 2021년 조직의 데이터 유출 평균 비용은 전년 대비 10% 늘어난 **424만 달러**다. 실제 사건의 제목들만 훑어도 규모가 보인다.

- 4억 1900만 명의 사용자 데이터가 데이터베이스에서 유출
- 데이터 유출로 1억 4300만 명의 미국 사용자가 영향
- 보안 문제로 4700만 명의 개인 정보 유출
- 1억 600만 명의 고객 기록 유출에 **8000만 달러의 벌금**
- 사이버 공격 대응 실패에 **1640만 파운드의 벌금**

마지막 둘은 규제 당국이 **규칙 위반이나 부적절한 대응**에 벌금을 매긴 사례다. GDPR 위반 최대 벌금은 아마존의 6억 3600만 파운드, 왓츠앱의 2억 2500만 유로다. **사용자는 자신의 데이터가 보호될 것이라 믿으며, 그렇지 않으면 그 책임은 조직의 것이다.**

> **참고**: 책임 범위는 **내가 만든 API보다 훨씬 넓다.** 벤더 제품과 오픈소스도 관리하지 않으면 큰 문제가 된다. 벤더 제품이 우리 개발 표준과 같은 수준인지 확인해야 하고, 조직이 **CVE**(*Common Vulnerabilities and Exposures* - 공개적으로 알려진 보안 결함 목록)를 추적해 영향받는 소프트웨어를 다시 손봐야 한다.

## 2. 사례 연구: 참석자 API에 OWASP 적용하기

**OWASP**(*Open Web Application Security Project*)는 소프트웨어 보안 개선에 힘쓰는 비영리 재단이고, 가장 잘 알려진 프로젝트가 **OWASP 톱 10**이다. 2019년에는 **API 보안 톱 10**이 따로 나왔다. 보안 유출과 버그 바운티를 조사한 보안 전문가들의 의견에 침입 테스터의 조언까지 더해 만든 목록이며, **정기적으로 갱신되므로 계속 확인해야 한다.**

```
┌──────────┐        ┌──────────────────┐  API 호출  ┌──────────────────┐   참석자 생성·조회   ┌──────────────┐  CRUD  ┌────────────┐
│  참석자   │ ─────▶ │    모바일 앱       │  [HTTP]   │  API 게이트웨이    │ ────────────────▶ │ 참석자 서비스  │ [SQL] │ 데이터 스토어 │
│ [사람]    │        │ [소프트웨어 시스템] │ ────────▶ │ [인프라스트럭처]   │                    └──────────────┘ ─────▶└────────────┘
└──────────┘        └──────────────────┘           └──────────────────┘
```

## 3. 위협 모델링의 기초

위협 모델링(*threat modeling*)은 **"위협·공격·취약점을 식별하고 애플리케이션이 받게 될 영향도를 측정하는 데 도움이 되는 기법"** 이다.

집에 대해 위협 모델링을 해본다면 문과 창문 같은 입구를 인식하고, 이웃에게 현관 열쇠를 준 적이 있는지 떠올리게 된다. **위협을 명확히 인지했을 때만 위험을 완화할 수 있다.** 그리고 의미 없는 노력도 피할 수 있다 — 큰돈을 들여 현관문을 강철문으로 바꾸고는 **열쇠를 문 앞 발판 밑에 숨겨둔다면** 아무 소용이 없다.

위협 모델링은 소프트웨어 개발 수명주기 **전체에 통합**해야 한다. 이상적으로는 프로젝트 시작 시점에 하고, 시스템이 진화하면 **계속 다시** 한다. 이 책은 마이크로소프트의 프레리트 가르그(Praerit Garg)와 로렌 콘펠더(Loren Kohnfelder)가 설계한 **스트라이드(STRIDE)** 방법론을 쓴다.

### 데이터 흐름 다이어그램(DFD)

위협 모델링은 전통적으로 **데이터 흐름 다이어그램**(*Data Flow Diagram - DFD*)을 쓴다. **C4 모델이 시스템의 정적인 측면(구조)** 을 다룬다면 **DFD는 동적인 측면(데이터의 흐름)** 을 다룬다. 구성 요소는 다섯이다.

- **외부 엔티티(*external entity*)**: 내 시스템이 아닌 애플리케이션/서비스 — 여기서는 모바일 앱
- **프로세스(*process*)**: 내 도메인 안의 애플리케이션/태스크 — API 게이트웨이
- **데이터 스토어(*datastore*)**: 데이터가 저장되는 곳 — 데이터베이스
- **데이터 흐름(*data flow*)**: 모바일 앱 → API 게이트웨이 같은 연결
- **경계(*boundary*)**: 신뢰 수준이 바뀌는 **신뢰 경계** — 모바일 앱과 게이트웨이 사이의 인터넷 경계

```
┌──────────────────────┐                    ╎                 ┌──────────────────────────────────────┐
│     모바일 앱          │      HTTPS         ╎                 │            서비스 메시 (mTLS)          │
│  (클라이언트 앱)       │ ══════════════════▶╎════════════════▶│  API 게이트웨이 ──▶ 참석자 API ──▶ DB   │
│   [외부 엔티티]        │                    ╎                 │  [프로세스]        [프로세스]  [스토어] │
└──────────────────────┘                    ╎                 └──────────────────────────────────────┘
                                    인터넷 경계(신뢰 경계)
```

### 공격자 입장에서 생각하기

아키텍트와 개발 팀은 보안이 전담 팀 업무라고 여겨 직접 다루기를 꺼린다. 하지만 **시스템의 핵심 컴포넌트를 설계하고 구현한 사람들이 아니면 누가 잠재적 약점을 이해하겠는가?**

다행히 위협 모델링을 하려고 보안 전문가가 될 필요는 없다. **"공격자라면 어떻게 할까?"** 를 계속 물으면 된다. 밤에 차를 주차할 때 열쇠를 어떻게 하는가? 길가라면 차에 두지 않겠지만 차고라면 그럴 수도 있다. 현관에 걸어두면 누군가 **우편함 구멍으로 옷걸이를 넣어** 가져갈 수 있고, 스마트키라면 **신호 증폭**으로 열쇠 없이 문을 열 수 있다. 그럼 2층으로 가져갈까, 패러데이 케이지에 넣을까? — **이미 상황을 주시하고 위협을 평가해 위험을 저울질하고 있는 것이다.**

## 4. 위협 모델링 실습 6단계

1. **목표를 정의한다**: 비즈니스·보안 목표 목록을 만든다. **최대한 단순하게**(예: 인증 없는 접근은 허용하지 않는다)
2. **올바른 정보를 수집한다**: 고수준 설계를 완성하고, 여러 시스템이 어떻게 얽혀 도는지 이해할 수 있도록 **적절한 사람들을 대화에 참여**시킨다
3. **시스템을 분할한다**: 고수준 설계를 쪼갠다. 모델과 다이어그램이 여러 개 필요할 수 있다
4. **위협을 정의한다**: 시스템에 대한 위협을 **체계적으로** 확인한다
5. **위협의 위험도를 평가한다**: 가능성이 높은 것부터 우선순위를 매기고 완화 방법을 찾는다
6. **검증한다**: 변경이 위협을 실제로 완화했는지 팀 전체가 평가하고, 또 다른 리뷰가 필요한지 판단한다

### 1단계: 목표를 정의한다

목표가 위협 모델링의 수행 방식을 결정한다. 이 목표는 **내 팀이나 정보보안 팀이 아니라 조직 전체가 원하는 것**이어야 하며, 대부분 법적 문제 회피나 GDPR 준수 같은 비즈니스 목표에서 나온다. **내가 직접 연관된 분야에서만 목표를 정하면 조직이 마주할 가장 중요한 이슈를 놓친다.**

참석자 서비스의 목표는 **OWASP 톱 10을 참고해 서드파티가 외부에서 쓸 API를 준비하는 것**이다.

### 2단계: 올바른 정보를 수집한다

각 영역의 기반 코드·제품 전문가를 동원해야 시스템 전체 동작을 이해하고 모호함을 없앨 수 있다. 참석자 API라면 **모바일·게이트웨이·데이터베이스·참석자 서비스를 담당한 팀 구성원 전부**가 필요하다.

### 3단계: 시스템을 분할한다

수집한 정보로 DFD를 만든다. 시간이 많이 드는 작업이라 **전용 도구**(마이크로소프트 위협 모델링 도구, OWASP Threat Dragon 등)를 권한다.

### 4단계: 위협을 정의한다 — 스트라이드

마이크로소프트 도구는 스트라이드 기반의 **부분 자동 분석**을 해준다. 참석자 API 시스템에서는 27개의 잠재적 위협이 나왔다(완벽하진 않지만 출발점이 된다). **스트라이드**는 여섯 위협의 머리글자다.

- **위장(*Spoofing*)**: 사용자 인증 정보의 유출. 해커가 유효한 사용자나 시스템으로 **가장**해 접근을 확보하고 보안을 손상시킨다
- **변조(*Tampering*)**: 탐지되든 아니든 **시스템이나 사용자 데이터를 변경**하는 것. 저장·전송 중인 정보 변경, 탐지 불가능한 네트워크 패킷 추가, 민감한 파일의 몰래 수정
- **부인(*Repudiation*)**: 신뢰할 수 없는 사용자가 **추적 불가능한 불법 작업**을 하는 것. 잘못을 했음을 부인하는데 **증명할 방법이 없는** 상황
- **정보 공개(*Information Disclosure*)**: 봐서는 안 되는 사람에게 정보를 **노출**하는 것. 가해자가 사용자로 위장하는 대신 **직접 정보에 접근**한다는 점에서 위장과 다르다
- **서비스 거부(*Denial of Service*)**: 시스템 리소스를 **일시적으로 사용 불가능**하게 만드는 것
- **권한 상승(*Elevation of Privilege*)**: 권한 없는 사용자가 **전체 시스템을 손상시킬 수 있을 만큼의 접근 권한**을 얻는 것. 감지되지 않는 방식으로 신뢰받는 시스템의 일부가 되어버리기에 특히 위험하다

각 프로세스와 연결에 스트라이드를 적용하는 것을 **요소별 스트라이드**라고 한다. 아래는 스트라이드 항목별로 OWASP API 톱 10 이슈와 완화책을 묶어본 것이다.

### 위장 → 손상된 사용자 인증

**모든 요청을 인증하고 적법한지 확인**해야 한다. OWASP의 **손상된 사용자 인증**(*Broken User Authentication*)이 여기 해당하며, 인증 흐름이 망가지지 않게 하는 것이 핵심이다(7장).

### 변조 → 페이로드 주입, 대량 할당

**페이로드 주입**(*payload injection*)은 요청에 악의적인 페이로드를 넣는 공격이다. SQL 주입뿐 아니라 **모든 사용자 입력**이 대상이다. 우리 사례에서는 API 게이트웨이가 요청이 **계약이나 스키마를 준수하는지 검증**해 초기에 막고, 준수하지 않는 요청은 거부하거나 버린다(1장의 OpenAPI 검증이 여기서 방어 수단이 된다).

```http
POST /attendees
{
  "name": "Danny B",
  "age": 35,
  "profile": "Hax'; DROP ALL TABLES; --"
}
```

명세상 `name`은 글자만, `age`는 양의 정수만, `profile`은 문자·숫자·특수문자를 받는다. 게이트웨이는 검증에 성공한 요청만 백엔드로 넘긴다.

> **실무 팁**: 게이트웨이에서 입력을 검증한다고 **백엔드가 검증과 무결화를 생략해도 되는 것은 아니다.** API를 신뢰하되 검증은 필수다. 참석자 서비스도 DB 작업 시 SQL 주입을 고려해야 한다 — **방어 장치를 여러 겹 두어야 하나가 뚫려도 버틴다.**

**대량 할당**(*mass assignment*)은 수정되면 안 되는 속성이 클라이언트 입력으로 바뀌는 취약점이다. 액티브 레코드 패턴이나 자동 직렬화/역직렬화를 제공하는 ORM에서 특히 조심해야 한다. `devices`가 애플리케이션 코드만 바꿀 수 있는 읽기 전용 속성이라고 하자.

```http
GET /attendees/123456
{ "name": "Danny B", "age": 35, "devices": ["iPhone", "Firefox"] }
```

```http
PUT /attendees/123456
{ "name": "Danny B", "age": 36, "devices": ["vulnerableDevice"] }   ← age만 고치는 척하며 devices까지
```

저장 시 `devices`에 담긴 데이터는 **전부 무시해야 한다**. 대량 할당은 클라이언트 입력이 아무 생각 없이 내부 객체에 연결되어 **데이터베이스 API가 웹 API처럼 노출되는** 결과다. 1장에서 기반 데이터 모델 노출을 사용성 관점에서 경계했는데, **이것이 노출하지 말아야 할 또 다른 이유**다. 그리고 **이 취약점은 게이트웨이 수준에서 처리할 수 없으므로** API 구현에서 막아야 한다.

### 부인 → 불충분한 로깅·모니터링

애플리케이션이 사용자 동작을 제대로 추적·기록하지 않으면 공격자가 **자기가 한 일을 부인**할 수 있다. 규제에 따라 주고받은 데이터를 임의로 조사할 수 있어야 하는 경우도 있다. **불충분한 로깅과 모니터링**은 OWASP API 톱 10 항목이다.

모든 요청이 게이트웨이를 지나므로 **거기가 트래픽을 모니터링하고 요청·응답을 기록할 지점**이다. 다만 그 정보를 어떻게 **저장하고 시간이 지나도 검색·추출**할지 이해해야 하고, DR/BC 역량처럼 **로깅과 모니터링이 원하는 것을 제대로 모으는지 주기적으로 검증**해야 한다.

### 정보 공개 → 과도한 데이터 노출, 부적절한 자산 관리

**과도한 데이터 노출** — 참석자 서비스가 여권 번호 같은 PII를 갖고 있다면 그것이 새어 나가지 않게 해야 한다. 특히 시스템이 오래 진화하면 **내부용으로 만든 API가 나중에 공개되거나**, 신뢰할 수 있는 클라이언트만 호출하던 API가 공개용으로 바뀌기 쉽다. 웹 애플리케이션이 호출한다면 **브라우저 개발자 도구로 응답을 그대로 볼 수 있다.**

```json
{
  "values": [
    { "id": "0", "name": "Danny B", "age": 65,
      "email": "danny.b@masteringapis.com", "passport": "Abc12408NJUILM" },
    { "id": "1", "name": "Jimmy G", "age": 93,
      "email": "jimmy.g@masteringapis.com", "passport": "ZYx123ASJJ0072m" }
  ]
}
```

> **핵심 통찰**: 게이트웨이에서 응답을 검증할 수도 있지만, **어떤 데이터를 노출하는지 확인할 책임은 API를 구현하는 사람에게 있다.** 게이트웨이의 검증은 **마지막 수단**이어야 한다. 웹 서버 버전이나 스택 추적처럼 민감한 정보를 클라이언트에 돌려주지 않는 것도 마찬가지다.

**부적절한 자산 관리** — 조직이 **어떤 API의 어떤 버전이 공개되어 있는지** 추적하지 못할 때 생긴다. 옛 버전이 참석자의 모든 속성을 노출하고 있는데, 데이터 모델이 진화하며 PII 필드가 추가됐다면 **옛 버전으로 추가 정보를 빼낼 수 있다.** 테스트하려고 열어둔 `/beta/attendees`를 잊어버린 경우도 마찬가지다. 게이트웨이로 모든 트래픽을 관리한다면 **알고 있는 엔드포인트를 전부 등록**하거나, 요청을 살펴 **의도치 않은 엔드포인트를 부르는 이상 요청**을 찾아야 한다. 근본 대응은 **API 관리·개발자 포털로 프로덕션의 모든 API를 분류·추적**하는 것이다.

### 서비스 거부 → 리소스 부족과 호출률 제한 결여

방화벽이 기본적으로 모든 트래픽을 허용하도록 설정되어 있으면 막혔어야 할 악의적 호출이 들어와 부하가 는다. 혹은 공격자가 그저 **투표 사이트 같은 중요한 서비스의 가용성을 떨어뜨리려** 할 수도 있다.

> **참고**: 서비스 거부는 **우리 시스템이 스스로 트래픽을 너무 많이 만들 때도** 벌어진다. 실수로 **순환 의존성**이 생기면 내부 서비스가 서로의 API를 무한히 호출한다. 내부 호출에도 **호출률 제한과 에러 모니터링**이 필요한 이유다.

**호출률 제한**은 일정 시간 안의 호출 횟수를 제한하며, 주로 **개별 요청의 속성**(사용자·클라이언트 앱·위치)에 따라 거부한다. **부하 분산**은 **시스템 전반의 상태**(DB가 한계에 다다르거나 워커 스레드가 없는 경우)에 따라 거부한다. 기본적으로 애플리케이션·웹 서버·게이트웨이는 이 둘을 구현하고 있지 않으며 **장애 모드도 갖춰져 있지 않은 경우가 많다** — 부하 테스트로 한계와 실제 동작을 확인해야 한다.

제한 전략은 네 가지가 흔하다.

- **고정 기간(*fixed window*)**: 특정 기간에 고정된 제한 (하루 2,400개)
- **변동 기간(*sliding window*)**: 마지막 기간 기준 제한 (최근 1시간에 100개)
- **토큰 버킷(*token bucket*)**: 총 요청 수만큼 토큰을 두고 요청마다 하나씩 소모, 버킷은 주기적으로 채워진다
- **누수 버킷(*leaky bucket*)**: 토큰 버킷과 유사하되 **처리 비율이 고정**이고 나머지는 새어 나간다

```
모바일 앱 ──▶ API 게이트웨이 ──X──▶ 참석자 서비스
                    │
                    └──▶ 429 Too Many Requests   (호출률 제한 / 부하 분산)
```

> **참고 — 장애에 개방적인가, 폐쇄적인가**: **장애에 개방적**(*fail open*)이면 장애 상황에서도 접근이 된다 — 긴급 의료 서비스라면 요청을 인증하는 것보다 **환자 기록을 제공하는 것**이 더 중요하다. **장애에 폐쇄적**(*fail closed*)이면 장애 시 연결을 막는다. 무엇이 옳다기보다 **요구사항에 맞아야 한다** — 금융 API는 대개 폐쇄적, 공개 날씨 서비스는 개방적을 택한다.

### 권한 상승 → 객체·기능 수준 인가의 실패

사용자나 애플리케이션이 **현재 보안 컨텍스트의 범위를 벗어난 작업**을 실행하는 경우다. OWASP에는 두 항목이 있다 — **객체 수준 인가의 실패**, **기능 수준 인가의 실패**. 둘 다 요청이 그 작업을 할 권한을 실제로 갖도록 하는 문제이며 7장에서 다룬다.

### 보안 설정 오류 — 스트라이드 전체에 걸치는 문제

**보안 설정 오류**(*misconfiguration*)는 스트라이드 한 항목에 속하지 않는다. 권한이 잘못 할당되면 정보 공개가 되고, 호출률 제한이 장애에 개방적으로 잘못 설정되면 서비스 거부가 된다.

> **핵심 통찰**: **설정이 잘못된 보안 장치는 보안 장치가 아예 없는 것보다 더 나쁠 수 있다.** 사용자는 자신의 동작과 데이터가 안전하지 않다고 생각하면 완전히 다르게 행동하기 때문이다.

게이트웨이는 '진입 지점'이라 설정 오류의 파장이 가장 크다. 특히 셋을 봐야 한다.

- **TLS 종료**: TLS는 받은 트래픽이 가로채여 수정되지 않았음을 보장하고, 인증서는 도메인 소유자 정보를 준다. 게이트웨이에서 켜면 **외부 인증서를 한 곳에서 관리**할 수 있다(각 웹 서버·프록시·애플리케이션에 따로 붙이는 것보다 관리가 쉽고 에러에 덜 취약하다). **TLS 1.2 이상**을 쓸 것 — 이전 버전에는 알려진 이슈가 있다
- **교차 출처 리소스 공유(*CORS*)**: 다른 출처(도메인·스키마·포트)의 리소스를 브라우저가 로딩하게 해주는 HTTP 헤더 기반 메커니즘이다. 브라우저는 보안상 스크립트가 만든 교차 출처 요청을 제한하며, **프리플라이트 요청**(개발자 도구에서 보이는 `OPTIONS` 요청)으로 호출 가능 여부를 먼저 확인한다
- **보안 지시 강화**: 요청에는 임의의 헤더가 붙을 수 있다. 공격자는 `X-Assert-Role=Admin`이나 `X-Impersonate=Admin` 같은 헤더를 보내며 **그것이 제거되지 않고 내부에서 쓰이기를** 기대한다. 게이트웨이에 **HTTP 헤더 허용 목록**을 두고 유효하지 않은 헤더를 전부 제거해야 한다

## 5. 5단계: 위협의 위험도를 평가한다

위협 목록을 얻었으면 **고칠 순서**를 정해야 한다. 마이크로소프트가 만든 **드레드(DREAD)** 는 단순한 점수 시스템이다.

- **피해(*Damage*)**: 이 공격이 얼마나 큰 피해를 주는가?
- **재현용이성(*Reproducibility*)**: 공격을 쉽게 재현할 수 있는가?
- **이용용이성(*Exploitability*)**: 공격을 성공시키기가 얼마나 쉬운가?
- **영향을 받는 사용자(*Affected users*)**: 얼마나 많은 사용자가 영향을 받는가?
- **발견용이성(*Discoverability*)**: 위협이 발견될 가능성은 얼마나 높은가?

각 항목에 1~10점을 주고 **다섯 값의 평균**을 위험값으로 쓴다. 우리 사례에서 **호출률 제한이 없는 게이트웨이에 대한 DDoS 위협**을 평가하면 이렇다.

- **피해 8**: 제한이 없으니 누구든 원하는 만큼 요청을 보내 과부하를 일으켜 시스템을 못 쓰게 만들 수 있다
- **재현용이성 8**: 매초 수많은 요청을 반복하면 결국 게이트웨이가 멈춘다
- **이용용이성 5**: 게이트웨이가 먼저 인증·인가를 수행하므로 **시스템과 통합된 클라이언트에서 나온 요청**이어야 한다
- **영향을 받는 사용자 10**: 게이트웨이가 죽으면 **모든 사용자**가 영향을 받는다
- **발견용이성 10**: 악용하려는 사람이 쉽게 발견할 수 있다

총점은 (8+8+5+10+10)/5 = **8.2**다.

> **핵심 통찰**: 위험값은 **주관적이다.** 일관성을 얻으려면 **카테고리마다 값의 의미를 미리 정해야 한다** — 예를 들어 모든 사용자가 영향받으면 10점, 내부 또는 외부 사용자 전체면 7점, 그룹의 절반이면 3점, 아무도 영향받지 않으면 0점.

> **참고 — 다른 평가 도구**: **드레드 마이너스 D**는 발견용이성을 뺀 변형이다. 발견용이성은 경우에 따라 **"은폐에 의존한 보안"**(*security through obscurity*)을 뜻할 수 있는데 이는 데이터를 지키는 매우 부적절한 방법이기 때문이다. **CVSS**(*Common Vulnerability Scoring System*)는 취약점의 심각도를 재는 체계로, NIST가 CVE를 평가할 때 쓴다.

## 6. 6단계: 검증한다

보안 목표가 **완전히 달성되었는지**, 다시 볼 부분은 없는지 확인한다. 발견한 모든 위협을 평가하고 완화 행동을 취했는지, 처음에 세운 목표를 다 이뤘는지 본다. 몰랐던 이슈를 발견하면 **위협 모델링을 다시 반복**한다. 새 기능을 추가할 때뿐 아니라 **외부 위협 환경 자체가 계속 진화하므로 절차를 정기적으로 반복해야 한다.**

위협 모델링은 하나의 기술이고 절차를 익히는 데 시간이 든다. 다만 다른 기술과 마찬가지로 **업무 흐름에 통합할수록 쉬워진다.**

## 요약

- API를 안전하게 구현하지 못하면 **경제적 타격과 평판 손상**이 함께 온다. 규제 위반은 별도의 벌금으로 이어진다
- 위협 모델링은 보통 **DFD 작성**에서 시작한다. C4가 구조를 본다면 DFD는 **데이터의 흐름과 신뢰 경계**를 본다
- **보안 전문가가 아니어도 할 수 있다.** 가장 중요한 기술은 **공격자 입장에서 생각하는 것**이다
- 절차는 **목표 정의 → 정보 수집 → 시스템 분할 → 위협 정의 → 위험도 평가 → 검증** 6단계이며, 목표는 조직 전체 관점에서 정해야 한다
- **스트라이드**는 위장·변조·부인·정보 공개·서비스 거부·권한 상승을 체계적으로 훑게 해주고, **OWASP API 보안 톱 10**은 그 각각에 대응하는 실제 취약점 목록을 준다
- **드레드**는 무엇을 먼저 고칠지 점수로 정하게 해준다. 값이 주관적이므로 **점수의 의미를 팀이 미리 합의**해야 한다
- **API 게이트웨이는 위협을 완화하기 좋은 지점**(계약 검증·호출률 제한·TLS·헤더 허용 목록)이지만 만능이 아니다. **대량 할당과 과도한 데이터 노출은 서비스 구현이 막아야 하고**, 시스템이 분산될수록 개별 서비스와 서비스 간 통신도 함께 봐야 한다

## 다른 챕터와의 관계

- **1장**: OpenAPI 명세 검증이 **페이로드 주입 방어**로, 데이터 모델을 그대로 노출하지 말라는 조언이 **대량 할당 방어**로 이어진다
- **3장**: 게이트웨이가 최초 방어선이라는 관점, TLS 종료·호출률 제한·계약 검증이 여기서 위협별 완화책으로 재배치된다. '장애에 개방적/폐쇄적' 논의도 3장에서 시작됐다
- **4장**: mTLS로 지킬 수 있는 범위(제어 부분 내부)와 그 바깥을 구분하는 데서 이 장이 출발한다
- **5장**: 401·403 에러를 지표로 읽는 이야기, 로깅과 모니터링이 **부인 위협**의 완화책으로 다시 등장한다
- **7장**: 위장(인증)과 권한 상승(인가)에 대한 구체적 해법이 다음 장이다
- **9장**: 구역화 아키텍처에서 **제로 트러스트**로 옮겨가는 흐름을 다룬다
