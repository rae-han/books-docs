# Chapter 4: Service Mesh: Service-to-Service Traffic Management (서비스 메시: 서비스 간 트래픽 관리)

## 핵심 질문

서비스 간 통신의 라우팅·신뢰성·관측·보안을 어디에 구현할 것인가 - 애플리케이션 코드(라이브러리)인가, 인프라(메시)인가? 서비스 메시는 그 대가로 무엇을 요구하는가?

## 1. 서비스 메시가 유일한 해결책인가

거의 모든 웹 애플리케이션은, 데이터베이스와 통신하는 단순 모놀리스라 해도 **서비스 간 호출과 유사한 호출**을 한다. 그래서 이 통신을 관리하는 솔루션은 오래전부터 있었다. 가장 보편적인 것은 SDK나 데이터베이스 드라이버 같은 **언어 전용 라이브러리**로, 애플리케이션 호출을 서비스 API 요청에 매핑하고 HTTP·TCP/IP 트래픽을 관리한다.

서비스 지향 아키텍처를 쓰면 이 문제가 커진다. 한 서비스가 사용자 요청을 처리하려고 다른 서비스의 API를 호출하는 일이 잦아지고, 라우팅뿐 아니라 **신뢰성·관측용이성·보안**까지 필요해진다.

> **핵심 통찰**: 라이브러리 기반과 메시 기반 **둘 다** 서비스 간 통신 요구를 만족시킬 수 있다. 다만 소비자와 제공자의 수가 늘어날수록 서비스 메시가 더 확장 가능하고 유지보수하기 쉬우며 안전한 선택이 된다.

### ADR 가이드라인: 서비스 메시와 라이브러리의 선택

- **결정사항**: 서비스 트래픽 라우팅에 서비스 메시를 쓸 것인가, 라이브러리를 쓸 것인가?
- **논의사항**: 조직이 **하나의 프로그래밍 언어**만 쓰는가? REST·RPC 수준의 단순한 서비스 간 라우팅만 필요한가? 인증·인가·호출률 제한 같은 **고급 공통 기능** 요구가 있는가? 이미 도입한 솔루션이 있거나, 모든 트래픽이 특정 네트워크 컴포넌트를 지나야 한다는 조직 규칙이 있는가?
- **권장사항**: 조직이 **단일 언어·프레임워크를 강제한다면 언어 전용 라이브러리**가 낫다. 곧 마주할 요구를 주시하되 **항상 가장 단순한 솔루션**을 고른다. 서로 다른 언어·기술 스택의 여러 서비스에 **공통 기능을 일관되게 적용해야 한다면 서비스 메시가 최선**이다

## 2. 사례 연구: 세션 기능을 서비스로 분리하기

컨퍼런스 주최자가 새 기능을 요청했다. 참석자가 **모바일 앱으로 관심 세션을 확인하고 관리**하는 기능이다. 마케팅 팀은 이것이 참여율을 높인다고 보며, 각 세션에 관심 있는 참석자 수도 알고 싶어 한다.

**ADR-002: 레거시 컨퍼런스 시스템에서 세션 기능을 분리**

- **상태**: 제안
- **컨텍스트**: 참석자가 모바일 앱으로 관심 세션을 보고 상세를 확인할 수 있어야 하며, 각 세션에 관심 있는 참석자 수도 집계되어야 한다
- **결정사항**: 세션 컴포넌트를 **독립 서비스**로 옮긴다. 레거시 컨퍼런스 시스템이 호출할 수 있도록 API 우선으로 개발하며, 참석자 서비스도 세션 서비스의 API를 직접 호출해 모바일 앱용 세션 정보를 제공한다
- **결론**: 레거시는 세션 쿼리 시 새 세션 서비스를 호출한다. 사용자가 관심 세션을 확인·추가·삭제하면 참석자 서비스도 세션 서비스를 호출한다. 관리자가 세션별 참석자 명단을 보려 하면 **세션 서비스가 참석자 서비스를 호출**한다(양방향 호출이 생긴다). 세션 서비스는 **단일 실패 지점**이 될 수 있으므로 완화 단계가 필요하다. 그리고 **컨퍼런스 이벤트 중 트래픽이 급증**할 수 있어 과부하와 성능 저하에 대비해야 한다

```
┌──────────┐        ┌────────────────┐   세션 리뷰·예약   ┌────────────────────────┐
│  참석자   │ ─────▶ │  API 게이트웨이  │ ───────────────▶ │  레거시 컨퍼런스 시스템   │
│ [사람]    │        └────────────────┘                  └──────┬──────────┬──────┘
└──────────┘                                                    │          │ API 호출로 세션 생성·조회
                                                                │          ▼
                                       API 호출로 참석자 상세 조회 │   ┌────────────────┐
                                                                │   │   세션 서비스    │
                                                                ▼   │ [소프트웨어 시스템]│
                                                    ┌────────────────┐ └───────┬────────┘
                                                    │  참석자 서비스   │◀────────┘
                                                    │ [소프트웨어 시스템]│  세션별 참석자 조회
                                                    └────────┬───────┘
                                                             └──────────▶ 세션 서비스 API 호출
```

새 세션 서비스는 **외부에 노출할 필요가 없다**. API 게이트웨이로 노출하고 레거시와 참석자 서비스가 게이트웨이의 외부 주소로 호출하게 하면 라우팅·안정성 요구는 쉽게 채워진다. 하지만 그건 3장에서 본 **API 게이트웨이 루프백 안티패턴**이다 - 내부에서 끝나야 할 트래픽이 네트워크를 떠나 성능·보안·비용에 영향을 준다.

## 3. 서비스 메시란

**서비스 메시**는 분산 시스템에서 **모든 서비스 간(또는 애플리케이션 간) 통신을 관리하는 패턴**이다. API 게이트웨이 패턴과 유사한 점이 많지만 두 가지가 다르다.

1. 클러스터나 데이터센터 **안**의 서비스 간(수평) 트래픽 처리에 최적화되어 있다
2. 요청의 시작이 사용자 장치나 외부 서비스가 아니라 **잘 알려진 내부 서비스**인 경우가 대부분이다

> **참고**: 서비스 메시는 **메시 네트워킹과 다르다.** 메시 네트워킹은 IoT나 재해 복구 같은 시나리오에서 쓰이는 저수준 네트워킹 토폴로지다. 서비스 메시는 기존 네트워킹 프로토콜과 토폴로지 **위에** 구현된다.

이 패턴은 부얀트(Buoyant) 팀이 **링커드**의 기능을 설명하려고 채택한 용어이며 **2016년에야** 등장했다. 구글이 지원하는 **이스티오**가 뒤따르며 용어가 빠르게 자리 잡았다.

게이트웨이처럼 **제어 부분**과 **데이터 부분**으로 구현되는데, 서비스 메시에서는 이 둘을 **항상 따로 배포한다**. 쿠버네티스라면 운영자가 커스텀 리소스로 라우팅·정책을 정의하고 `kubectl`이나 CD 파이프라인으로 적용하면, 클러스터 안의 **메시 컨트롤러(제어 부분)** 가 이를 파싱해 **각 서비스 옆의 사이드카 프록시(데이터 부분)** 에 반영한다.

```
                        ┌───────────── 이스티오 메시 ─────────────┐
   인그레스 트래픽 ───▶  │  ┌───────────┐   메시 트래픽  ┌───────────┐│──▶ 이그레스 트래픽
                        │  │ 서비스 A    │◀────────────▶│ 서비스 B   ││
                        │  │ [프록시]    │              │ [프록시]   ││   ← 데이터 부분
                        │  └─────┬─────┘              └─────┬─────┘│
                        └────────┼──────────────────────────┼──────┘
                                 │  발견 · 설정 · 인증서       │
                        ┌────────▼──────────────────────────▼──────┐
                        │      제어 부분 (Istiod: Pilot·Citadel…)   │
                        └──────────────────────────────────────────┘
```

> **참고 - 사이드카와 프록시**: 둘을 같은 뜻으로 쓰는 경우가 있지만 정확하지 않다. **사이드카**는 메시 안에서 프록시로 구현되는 **범용 패턴**이므로 "사이드카 프록시"라고 부르는 게 맞다. 이름은 오토바이 옆 좌석에서 왔고, 애플리케이션의 기능을 **같은 네트워크·프로세스 네임스페이스에서 도는 별도 프로세스**로 분리하는 패턴이다. 언어 전용 라이브러리 없이 능력을 덧붙일 수 있다는 것이 핵심이다.

### 제공하는 기능

네트워크 수준에서 메시 프록시는 **완전 프록시**(*full proxy*)로 동작한다. 유입 트래픽을 모두 받고 유출 요청도 모두 낸다. 게이트웨이와 달리 **데이터 부분과 서비스의 매핑은 1:1** 이며, 따라서 **여러 서비스 호출을 종합하지 않는다**. 사용자 검증·호출률 제한·타임아웃/재시도 같은 공통 기능과 지표·로그·추적을 제공한다.

> **참고 - 완전 프록시 vs 반 프록시**: 반 프록시와 달리 완전 프록시는 클라이언트와 서버 **양쪽을 위한 독립적인 네트워크 스택 2개**를 갖고 모든 통신을 처리한다. 그래서 양방향으로 관측·조작할 수 있지만, **리소스 소비와 오버헤드·레이턴시**라는 트레이드오프가 따른다.

### 배포 위치와 다른 네트워크 계층과의 관계

메시는 내부 네트워크나 클러스터 안에 배포한다. 대규모 시스템은 **여러 메시 인스턴스**를 두고 하나가 네트워크 세그먼트나 비즈니스 도메인을 담당하게 한다.

> **참고 - 에지에도 메시를 배포할까?**: 메시가 DMZ나 외부 시스템, 다른 클러스터로 엔드포인트를 노출하기도 한다. 보통 **메시 게이트웨이·종점(terminating) 게이트웨이·환승(transit) 게이트웨이**라 부르는 프록시로 구현하는데, 외부용 API 게이트웨이만큼의 기능은 없다.

메시는 OSI **3계층과 7계층 사이**에서 동작한다. 쿠버네티스라면 기본적으로 서비스 이름-IP 매핑과 `NetworkPolicies`(3/4계층), CNI 플러그인이 트래픽을 제어한다. 메시는 그 위에서 **CNI의 서비스-IP 해석과 라우팅을 오버라이드**하고, 클러스터 간 투명 라우팅, 3/4계층과 7계층 보안, **7계층 로드밸런싱**(gRPC·HTTP/2 같은 멀티플렉스 킵얼라이브 프로토콜에서 특히 유용), 서비스 간 관측용이성을 더한다.

## 4. 서비스 메시를 사용해야 하는 이유

### 라우팅·신뢰성·트래픽 관리의 세분화된 제어

분산 시스템의 라우팅은 생각보다 어렵다. 성능(로드밸런싱)과 신뢰성(이중화)을 위해 **서비스 인스턴스가 여러 개** 떠 있고, 현대 인프라는 순간적 컴퓨팅 리소스를 쓰므로 **서비스 위치가 매일(심지어 매분) 바뀐다**.

3장의 게이트웨이 기법을 쓸 수도 있다. 하지만 **내부 서비스는 외부 API보다 수가 훨씬 많고 변경 속도도 훨씬 빠르다.** 모든 내부 서비스 앞에 게이트웨이를 두면 컴퓨팅 리소스와 사람의 유지보수 비용이 급증한다.

**투명한 라우팅과 이름 정규화** - 클라우드 이전에는 내부 서비스 IP가 거의 고정이었고 오래된 애플리케이션은 IP를 하드코딩했다. 그래서 서비스 위치를 바꾸면 호출하는 모든 서비스를 재배포해야 했다. 클라우드로 인프라 수명이 짧아지자 IP가 주기적으로 바뀌었고, 마이크로서비스로 서비스 수까지 늘자 초기 도입자들은 **서비스 발견 레지스트리**를 외부 서비스로 만들어 해결했다.

메시는 이 탐색을 **코드 수정·재배포·재시작 없이 서비스 외부에서 투명하게** 수행한다. 게다가 **환경 인식**(*environment awareness*)과 외부 설정을 조합해 이름을 정규화한다 - 코드의 `sessions-service`라는 이름이 프로덕션 메시에서는 `AWS-us-east-1a/prod/sessions/v2`로, 스테이징에서는 `internal-staging-server-a/stage/sessions/v3`로 투명하게 매핑된다.

**신뢰성** - 서비스는 협업 대상의 연결 끊김·일시적 사용 불가·느려짐을 제대로 처리해야 한다. 재시도·타임아웃·서킷 브레이커·벌크헤드·폴백 같은 패턴은 코드로도 구현할 수 있지만, **여러 언어·플랫폼을 쓰면 동작의 일관성이 깨진다.**

메시는 모든 서비스 간 통신에 관여하므로 이 패턴들을 구현해 **장애 내성과 우아한 퇴보를 일관되게** 만들 완벽한 위치에 있다. 우리 사례를 보자. 수천 명이 아침 키노트를 보며 그날의 세션 일정을 확인하면 세션 서비스 성능이 떨어질 수 있다. 대개는 타임아웃과 재시도 정책으로 충분하지만, 참석자 서비스의 세션 API 호출이 반복 실패하면 **서킷 브레이커**를 열어 더 빨리 실패하게 만들 수 있다(그래야 세션 서비스가 더 빨리 복구된다). 모바일 앱은 그동안 개인 일정 대신 **전체 세션 일정을 렌더링하는 폴백**을 실행하면 된다.

**고급 트래픽 라우팅** - 두 개념을 구분해야 한다.

- **트래픽 형태 변경**(*traffic shaping*): 트래픽을 원하는 프로파일에 맞추기 위해 **대역폭을 관리**하는 기법이다. 성능 보장이나 레이턴시 개선을 위해, 혹은 특정 트래픽의 대역폭을 확보하려고 다른 트래픽에 지연을 준다. 수평 트래픽에서는 서비스 ID나 요청 헤더의 메타데이터(예: 무료 사용자인지 유료 사용자인지)로 핑거프린트를 만든다
- **트래픽 정책 반영**(*traffic policing*): 트래픽을 정책·계약에 비춰 모니터링하고 **위반 트래픽을 즉시 거부**하거나 표시하는 것이다. DoS로 인한 내부 서비스 오동작이나, 트래픽이 데이터 스토어 같은 취약한 내부 리소스를 잠식하는 것을 막는다

메시는 여기에 **트래픽 분할과 미러링**을 더해, 특정 버전으로 향하는 트래픽을 점진적으로 옮길 수 있게 한다. 5장의 **트래픽 기반 릴리스 전략**이 이 기능 위에 선다.

### 투명한 관측용이성

역사적으로 시스템 전반의 모니터링을 도입하려면 애플리케이션에 **강하게 결합된 런타임 에이전트나 라이브러리**를 넣어야 했고, 최초 롤아웃은 물론 이후 업그레이드마다 모든 애플리케이션을 재배포해야 했다.

메시는 애플리케이션(L7)과 네트워크(L4) 지표를 **투명하게** 제공한다. 즉 **애플리케이션 재배포 없이** 텔레메트리 컴포넌트나 메시 자체를 업데이트할 수 있다. 물론 한계가 있어서 비즈니스 지표나 API 호출 KPI는 여전히 애플리케이션이 남겨야 한다.

### 보안: 전송 암호화, 인증, 인가

서비스 간 통신 보안도 언어 전용 라이브러리로 구현해 왔고 같은 단점을 안고 있다. 내부 전송 계층 암호화는 흔한 요구인데 **언어마다 인증서를 조금씩 다르게 관리**해서 배포와 회전의 운영 부담이 커진다. 서비스(머신)와 사용자(사람)의 신원을 다루는 인증·인가도 여러 언어에서 똑같이 구현하기 어렵고, **라이브러리를 실수로 또는 의도적으로 빼면 보안 체계를 우회할 수 있다.**

메시의 데이터 부분은 모든 트래픽 경로에 있으므로 서비스 신원(SPIFFE 등), 암호화 인증서, **mTLS 활성화**, 서비스 수준 인증·인가를 제공하기 쉽다. 우리 사례에서도 **코드 변경 없이 mTLS를 켤 수 있다**.

### 여러 언어의 교차 기능적 통신 지원

인 프로세스 통신을 아웃 오브 프로세스로 바꾸면 라우팅·신뢰성·관측용이성·보안을 다시 생각해야 한다. 이를 라이브러리로 구현하면 **쓰는 언어마다 라이브러리를 만들어야 한다**(폴리글랏은 마이크로서비스에서 보편적이다). 메시는 사이드카 패턴으로 이 기능을 **프록시 안에 한 번만 구현하고 모든 서비스가 재사용**하게 한다.

> **핵심 통찰**: 이것을 **"인프라스트럭처 의존성 주입"** 이라고 생각하면 된다. 덕분에 교차 기능적 부분을 일관되게 유지하면서도, 성능 요구를 맞추려고 참석자 서비스를 **다른 언어로 다시 구현**하는 자유를 얻는다.

### 인그레스와 서비스 간 트래픽 관리의 분리

| 속성 | 인그레스(수직) 트래픽 | 서비스 간(수평) 트래픽 |
|------|---------------------|---------------------|
| 트래픽 근원지 | 외부 (사용자·서드파티·인터넷) | 신뢰 경계 내의 내부 |
| 트래픽 목적지 | 공개 또는 비즈니스 API·웹사이트 | 서비스 또는 도메인 API |
| 인증 | '사용자'(실세계 엔티티) 위주 | '서비스'(머신)와 '사용자' 양쪽 |
| 인가 | '사용자' 역할·역량 수준 | '서비스' 신원 또는 네트워크 세그먼트 + 사용자 역할 |
| TLS | 단방향, 대부분 강제(프로토콜 업그레이드) | 상호적이며 필수일 수 있음(엄격한 mTLS) |
| 주요 구현체 | API 게이트웨이, 리버스 프록시 | 서비스 메시, 애플리케이션 라이브러리 |
| 주 소유자 | 게이트웨이/네트워킹/운영 팀 | 플랫폼/클러스터/운영 팀 |
| 조직 사용자 | 아키텍트, API 관리자, 개발자 | 개발자 |

우리 사례로 옮기면, **세션 서비스 팀은 레거시와 참석자 서비스만 자기를 호출하게 하고 싶고**, 참석자 서비스 팀은 외부 호출 가능 여부를 자기가 명시하지 않고 게이트웨이·네트워킹 팀 책임으로 남기고 싶어 한다. 요구가 이렇게 다르므로 두 제어 부분이 제공해야 할 역량도 다르다.

## 5. 서비스 메시의 진화

용어는 2016년에 생겼지만, 트위터·넷플릭스·구글·아마존은 2000년대 후반부터 내부 플랫폼에서 관련 기술을 만들어 썼다. 트위터는 스칼라 기반 RPC 프레임워크 **피나글**을 2011년 오픈소스화했고, 넷플릭스는 2012년 **리본·유레카·히스트릭스** 같은 자바 공유 라이브러리를 냈다. 이후 비JVM 서비스도 그 라이브러리를 쓰게 해주는 **프라나 사이드카**를 냈다. 이 흐름이 최초의 사이드카 기반 메시인 **링커드**와 CNCF 첫 프로젝트로 이어졌고, 구글은 리프트의 엔보이를 기반으로 **이스티오**를 냈다.

```
   공유 라이브러리 모델              사이드카 모델                  커널 모델
 ┌──────────────────┐        ┌──────────────────┐        ┌──────────────────┐
 │  앱 + 메시 라이브러리 │        │  앱 │ 메시 사이드카  │        │      앱 │ 앱       │
 ├──────────────────┤        ├──────────────────┤        ├──────────────────┤
 │  커널 TCP/IP      │        │  커널 TCP/IP      │        │ 커널 (서비스 메시) │
 └──────────────────┘        └──────────────────┘        │      TCP/IP       │
                                                          └──────────────────┘
```

### 왜 이 계층이 필요해졌는가 - 분산 컴퓨팅의 8가지 오류

90년대 썬 마이크로시스템즈의 피터 도이치(Peter Deutsch) 등이 정리한, 엔지니어가 분산 시스템을 만들 때 **잘못 가정하는 것들**의 목록이다.

1. 네트워크는 신뢰할 수 있다
2. 레이턴시가 없다
3. 대역폭은 무한하다
4. 네트워크는 안전하다
5. 토폴로지는 변화하지 않는다
6. 관리자는 한 명이다
7. 전송 비용은 없다
8. 네트워크는 모두 동종이다

> 이 오류들은 장시간에 걸쳐 모두 잘못된 것으로 검증되었으며 큰 문제와 고통스러운 학습 경험을 유발한다.<br>- 피터 도이치 외, 「분산 컴퓨팅의 8가지 오류」

> **핵심 통찰**: 90년대 목록이라고 유물 취급하면 안 된다. 기술이 바뀌어도 이 이슈들은 그대로 남는다. **아키텍트는 이 오류들이 오늘도 유효하다는 사실을 팀에 주지시키고 그에 맞춰 설계해야 한다.**

2010년대에 필 칼샤도(Phil Calçado)는 "**표준화된 RPC**"를 마이크로서비스의 핵심 전제 조건으로 꼽으며 이렇게 정리했다.

> TCP/IP 스택과 일반 네트워킹 모델은 수십 년 전에 개발되었고 여전히 컴퓨터 간 통신의 강력한 도구이지만, 좀 더 정교한 마이크로서비스 기반 아키텍처는 이런 아키텍처를 구현하는 엔지니어가 준수해야 하는 또 다른 요구사항 계층을 만들어냈다.<br>- 필 칼샤도(2017)

### 구현 패턴

**① 라이브러리** - 서비스 발견이나 서킷 브레이킹 같은 핵심 기능조차 제대로 만들기 어렵다는 인식에서 피나글, 넷플릭스 OSS 같은 정교한 라이브러리가 나왔다. 모든 서비스가 같은 로직을 다시 만들 필요가 없어 빠르게 퍼졌지만, **도구·런타임·언어에 제약**을 건다. 라이브러리가 지원하지 않는 플랫폼이면 직접 포팅해야 하고 **언어 수에 비례해 비용이 는다.**

> **참고 - 라이브러리와 폴리글랏의 가격**: 오래 도는 비즈니스 서비스는 자바로, 인프라 서비스는 Go로, 데이터 과학은 파이썬으로 하는 식의 폴리글랏에서 라이브러리 기반 메시를 택하면 **모든 라이브러리를 동시에 구현·유지·업그레이드**하거나 일부 언어에 차선의 경험을 줄 수밖에 없다. 게다가 언어마다 구현 차이나 **특정 런타임에서만 나는 버그**를 만나게 된다.

**② 사이드카** - 필요한 네트워킹 추상화를 **서비스 밖의 독립 프로세스**로 빼는 방식이다. 2013년 에어비앤비의 '시냅스와 신경', 이듬해 넷플릭스의 프라나가 그 예다. 이후 링커드와 엔보이가 나오며 프록시의 물결이 일었다. 각 서비스는 옆에서 도는 프록시 프로세스를 갖고, 보통 **같은 프로세스·파일·네트워킹 네임스페이스**와 보안 보장을 공유한다.

2010년대 중반 메소스·도커 스웜·쿠버네티스로 옮겨가며 **독립 프록시에서 중앙 제어 부분을 갖춘 형태**로 바뀌었다. 트래픽은 여전히 프록시에서 프록시로 직접 흐르지만 제어 부분이 그것을 인지하고 각 인스턴스에 영향을 준다. 덕분에 **여러 서비스에 걸친 협업이 필요한 접근 제어와 지표 수집**이 가능해졌다.

> **핵심 통찰**: 사이드카 프록시의 가장 강력한 장점은 프록시를 **격리된 컴포넌트로 보는 시각에서 벗어나, 프록시들이 형성하는 네트워크 자체를 가치로 인정하게 된다**는 점이다.

> **참고 - 대규모 사이드카 운영 비용**: 3개 노드에서 각 5개 파드를 도는 20개 서비스라는 작은 환경도 **프록시 컨테이너 100개**를 뜻한다. 프록시 메모리는 통신해야 하는 서비스 수에 비례해 는다. 1GB 쓰던 프록시를 60~70MB로 줄인 사례가 있지만, 그렇게 최적화해도 이 작은 환경에서 **노드당 2GB가량**이 필요하다.

**③ 프록시 없는 gRPC 라이브러리** - 2021년 구글 클라우드가 밀기 시작한 방식으로, 네트워크 추상화를 다시 **언어 전용 라이브러리**로 옮긴다. gRPC 라이브러리가 서비스에 포함되어 데이터 부분처럼 동작하고, 구글 트래픽 디렉터 같은 **외부 제어 부분**이 오픈소스 xDS API로 이를 직접 설정한다. 사이드카 방식과 프록시 없는 방식을 함께 쓰는 **하이브리드** 모드도 지원한다. 구글이 제안하는 적합 상황은 다음과 같다.

- **대규모 메시에서의 리소스 효율성** - 사이드카 프로세스를 추가로 돌리지 않는다
- **고성능 gRPC 애플리케이션** - 네트워크 홉과 레이턴시를 줄인다
- **사이드카를 배포할 수 없는 환경** - 두 번째 프로세스를 못 돌리거나 네트워크 스택을 조작할 수 없는 경우
- **프록시 기반 메시에서 프록시 없는 메시로 마이그레이션**하는 경우

우리 컨퍼런스 시스템은 REST와 gRPC를 함께 쓰므로 지금은 이 방식을 택하지 않는다.

**④ 사이드카 없는 OS 커널(eBPF) 구현** - 네트워킹 추상화를 **커널 자체**에 넣는 방식으로, 커널 샌드박스에서 커스텀 프로그램을 돌리는 **eBPF** 덕분에 가능해졌다. eBPF 프로그램은 함수 진입/탈출, 추적 지점, **네트워크 패킷 도착** 같은 수천 개의 OS 이벤트에 반응한다. 커널은 노드당 하나이고 모든 컨테이너가 그것을 공유하므로, 어떤 프로세스가 이벤트를 냈든 프로그램이 호출된다 - **메시를 우회하려는 시도를 원천적으로 막을 수 있다.** eBPF 기반 **실리엄**은 특정 기능을 사이드카까지 가지 않고 커널이 처리하게 해 레이턴시를 줄이고, **노드당 엔보이 하나**로 데이터 부분을 돌려 리소스 사용을 낮춘다.

| 관점 | 라이브러리 기반(프록시 없는) | 사이드카·프록시 기반 | OS/커널 기반 |
|------|--------------------------|-------------------|-------------|
| 언어/플랫폼 | 단일 언어 라이브러리, 플랫폼 중립 | 언어 중립, 폭넓은 플랫폼 지원 | 언어 중립, OS 수준 지원 |
| 런타임 | 애플리케이션 안에 패키지로 포함 | 애플리케이션과 별개 프로세스 | OS 커널의 일부로 실행 |
| 업그레이드 | 전체 애플리케이션 재빌드·재배포 | 사이드카 재배포 (대부분 다운타임 없음) | 커널 프로그램 업데이트/패치 |
| 관측용이성 | 애플리케이션과 트래픽 완전 통찰, 컨텍스트 전파 쉬움 | 트래픽만 통찰, 컨텍스트 전파는 언어/심 지원 필요 | 트래픽만 통찰, 컨텍스트 전파는 언어/심 지원 필요 |
| 보안 위협 모델 | 라이브러리 코드가 애플리케이션의 일부로 실행 | 사이드카가 애플리케이션과 프로세스·네트워크 네임스페이스 공유 | 애플리케이션이 시스템 콜로 OS와 직접 소통 |

## 6. 사례 연구: 라우팅·관측·보안 구현하기

세 가지 메시로 각각 하나씩 보여준다. **실제로는 기술 스택에 하나만 골라 쓸 것을 권한다** - 여기서는 학습 목적으로 셋을 나눠 보인다.

### 이스티오를 이용한 라우팅

핵심 전제 조건은 **사이드카 프록시 자동 주입**이다.

```console
$ kubectl label namespace default istio-injection=enabled
```

주요 커스텀 리소스 둘을 쓴다. **`VirtualService`** 는 호스트 주소에 대한 **라우팅 규칙**을 정의하고, **`DestinationRule`** 은 라우팅 후 서비스로 향하는 트래픽에 반영할 **정책**(로드밸런싱 설정, 연결 풀 크기, 이상치 탐지)을 정의한다.

```yaml
---
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: sessions
spec:
  hosts:
    - sessions
  http:
    - route:
        - destination:
            host: sessions
            subset: v1
---
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: attendees
spec:
  hosts:
    - attendees
  http:
    - route:
        - destination:
            host: attendees
            subset: v1
```

`DestinationRule`에서 **참석자 서비스만 두 버전을 지정**한 점에 주목하자. v2로의 **카나리 라우팅**을 위한 준비다.

```yaml
---
apiVersion: networking.istio.io/v1alpha3
kind: DestinationRule
metadata:
  name: sessions
spec:
  host: sessions
  subsets:
    - name: v1
      labels:
        version: v1
---
apiVersion: networking.istio.io/v1alpha3
kind: DestinationRule
metadata:
  name: attendees
spec:
  host: attendees
  subsets:
    - name: v1
      labels:
        version: v1
    - name: v2
      labels:
        version: v2
```

### 링커드를 이용한 트래픽 관측

링커드는 **텔레메트리와 모니터링이 자동으로 켜지므로** 기본 설치 후 설정을 바꿀 필요가 없다.

- HTTP·HTTP/2·gRPC의 주요 지표(요청 볼륨, 성공률, 레이턴시 분산) 기록
- 그 밖 TCP 트래픽의 TCP 수준 지표(입출력 바이트) 기록
- **서비스별·호출자/피호출자별·라우트별** 지표 보고
- 서비스 간 런타임 관계를 보여주는 **토폴로지 그래프** 생성
- 라이브·온디맨드 요청 샘플링

```console
$ linkerd viz install | kubectl apply -f -
$ linkerd viz dashboard
```

대시보드에서 서비스 그래프로 트래픽 흐름(성공률 SR, 초당 요청 RPS, p99 레이턴시)을 보고, 내장 프로메테우스와 그라파나 대시보드로 지표를 확인한다. `linkerd viz stat`·`linkerd viz routes` 같은 CLI도 있다.

> **실무 팁**: 프로덕션에서는 **비정상 트래픽을 자동으로 탐지**해야 한다. 메시의 관측 도구는 내부 API나 서비스가 **비정상적으로 호출되는 경우**를 찾아내는 데 특히 유용하다.

### 콘설을 이용한 네트워크 분할

마이크로서비스 이전에는 서비스 간 인가를 방화벽 규칙과 라우팅 테이블로 했다. 콘설은 **의도**(*intention*)로 이를 단순화한다 - 서비스 **이름**을 기준으로 통신 권한을 정의하고, 사이드카 프록시의 인바운드 연결에 반영한다. 인바운드 서비스의 신원은 **TLS 클라이언트 인증서**로 검증하며(콘설이 각 서비스 신원을 인증서에 인코딩한다), 허용하는 의도가 없으면 연결을 끊는다.

의도는 네 부분이다.

- **출발지 서비스**: 통신을 시작하는 서비스. 전체 이름 또는 `*`
- **목적지 서비스**: 통신 대상('업스트림') 서비스. 전체 이름 또는 `*`
- **권한**: 허용(allow)할지 금지(deny)할지
- **설명**: 선택적 메타데이터

가장 먼저 할 일은 기본값을 **'모두 금지'** 로 바꾸는 것이다.

```yaml
apiVersion: consul.hashicorp.com/v1alpha1
kind: ServiceIntentions
metadata:
  name: deny-all
spec:
  destination:
    name: '*'
  sources:
    - name: '*'
      action: deny
```

그다음 필요한 통신만 열어준다.

```yaml
apiVersion: consul.hashicorp.com/v1alpha1
kind: ServiceIntentions
metadata:
  name: legacy-app-to-attendee
spec:
  destination:
    name: attendee
  sources:
    - name: legacy-conf-app
      action: allow
---
apiVersion: consul.hashicorp.com/v1alpha1
kind: ServiceIntentions
metadata:
  name: legacy-app-to-sessions
spec:
  destination:
    name: sessions
  sources:
    - name: legacy-conf-app
      action: allow
---
apiVersion: consul.hashicorp.com/v1alpha1
kind: ServiceIntentions
metadata:
  name: attendee-to-sessions
spec:
  destination:
    name: sessions
  sources:
    - name: attendee
      action: allow
---
apiVersion: consul.hashicorp.com/v1alpha1
kind: ServiceIntentions
metadata:
  name: sessions-to-attendee
spec:
  destination:
    name: attendee
  sources:
    - name: sessions
      action: allow
```

이렇게 하면 **명시한 네 경로만 열리고 나머지 서비스 간 호출은 전부 차단**된다. ADR-002가 예상한 호출 관계(레거시→참석자, 레거시→세션, 참석자↔세션)가 그대로 정책이 된 셈이다. 비슷한 목적으로 **OPA**(*Open Policy Agent*)를 이스티오와 함께 쓰기도 한다.

## 7. 배포: 장애의 이해와 관리, 그리고 안티패턴

메시도 **대부분의 사용자 요청이 지나는 결정적 지점**이다. 클러스터 안에서 메시 인스턴스에 장애가 나면 대개 그 네트워크 반경의 전체 시스템을 못 쓴다. 메시는 애플리케이션 릴리스를 조율하는 데도 쓰이므로 **설정이 계속 바뀐다**는 점에서 게이트웨이와 위험 구조가 같다(3장의 논의가 그대로 적용된다). 특히 **가장 불안한 컴포넌트는 제어 부분**이며, 반드시 보호·모니터링하고 고가용성으로 운영해야 한다.

메시는 게이트웨이보다 새로운 기술이라 안티패턴이 아직 다 드러나지 않았지만, 피해야 할 것 셋은 분명하다.

- **ESB로 사용하기**: 플러그인·트래픽 필터·웹어셈블리가 생기면서 페이로드 변환·해석 같은 ESB식 기능을 넣으려는 경우가 는다. **비즈니스 기능을 더하거나 인프라에 너무 많은 '스마트'를 결합하지 말 것**
- **게이트웨이로 사용하기**: 대부분의 메시가 인그레스 게이트웨이를 제공하다 보니, API 게이트웨이가 필요한 조직이 메시를 깔고 게이트웨이 기능만 쓰는 경우가 있다. 동기는 이해되지만 **메시 게이트웨이는 완전한 API 게이트웨이만큼 기능이 풍부하지 않고**, 메시의 장점은 못 얻으면서 설치·운영 비용만 치르게 된다
- **네트워크 계층이 너무 많은 경우**: 기존 네트워크가 이미 충분한 추상화를 제공하는데 개발 팀이 그 위에 메시를 또 얹으면 **호환성 문제**(기존 기술이 헤더를 제거하는 등), **레이턴시 증가**(프록시를 여러 번 거침), **기능 중복**(서킷 브레이커가 메시와 저수준 스택 양쪽에서 도는 등)이 생긴다. 그래서 메시 도입은 **가능한 모든 팀과 조율·협업**해야 한다

## 8. 서비스 메시의 선택

요구사항 분석이 먼저다. 그리고 '구현 대 구입'에서는 게이트웨이 때와 같은 함정이 반복된다 - **TCO 과소평가**, **기회 비용 무시**, **운영 비용**(같은 문제를 푸는 여러 구현체를 온보딩·운영하는 비용), **기술 솔루션에 대한 인지 부족**. 다만 메시는 비교적 새 기술이라, 레거시가 많은 조직에서는 논의 자체가 늦게 시작되고 **구현이 조직 곳곳에 부분적으로 흩어져 있는** 경우가 많다(어떤 부서는 언어 라이브러리, 어떤 부서는 ESB, 어떤 부서는 간단한 프록시).

### ADR 가이드라인: 서비스 메시의 선택

- **결정사항**: 조직에 적합한 서비스 메시를 어떻게 선택할 것인가?
- **논의사항**: 모든 요구사항을 분석하고 우선순위를 매겼는가? 조직이 이미 쓰는 기술 솔루션을 파악했는가? 팀·조직 제약과 로드맵을 확인했는가? '구현 대 구매' 비용을 계산했는가? 현재 동향과 가용 솔루션을 이해하는가? 이해당사자와 상의했는가?
- **권장사항**: 내부 API 결합도 낮추기·사용법 간소화·남용 방지·활용 이해·제품처럼 관리라는 목적에 요구를 정렬한다. 이미 쓰는 메시가 있는지, 여러 기술을 조합해 유사 기능을 낼 수 있는지 본다. 팀 숙련도·인력·예산을 본다. **TCO**를 계산한다. **개발 팀·QA·아키텍처 리뷰 보드·플랫폼 팀·정보보안 팀 모두와 상의한다.** 도입하기로 했다면 **직접 구현보다 오픈소스나 상용 솔루션으로 표준화**하는 것이 최선이다

## 요약

- 서비스 메시는 분산 시스템의 **모든 서비스 간 통신을 관리하는 패턴**이며, 프록시는 **완전 프록시**로 동작해 인바운드·아웃바운드를 모두 다룬다. 게이트웨이와 달리 **서비스와 1:1** 이고 호출을 종합하지 않는다
- 메시는 내부 네트워크·클러스터에 배포하며, 대형 시스템은 세그먼트나 도메인별로 여러 인스턴스를 둔다. 외부 노출은 인그레스·종점·환승 게이트웨이로 한다
- 값을 하는 지점은 **투명한 라우팅과 이름 정규화, 신뢰성 패턴의 일관된 적용, 투명한 관측용이성, mTLS를 포함한 보안, 폴리글랏 지원**이다. 핵심 아이디어는 **인프라스트럭처 의존성 주입** - 교차 기능을 프록시에 한 번 구현하고 모두가 재사용한다
- 구현 방식은 **라이브러리 → 사이드카 프록시 → 프록시 없는 gRPC → 커널(eBPF)** 로 진화해 왔고, 각각 언어 지원·업그레이드 방식·관측 범위·위협 모델이 다르다
- 사이드카는 **리소스 비용**이 실재한다. 작은 클러스터도 프록시 100개와 노드당 GB 단위 메모리를 요구할 수 있다
- **분산 컴포넌트의 8가지 오류**는 지금도 유효하다. 메시는 그 오류를 인정하고 상쇄하는 계층이다
- 메시도 **단일 실패 지점**이며 특히 **제어 부분**이 취약하다. 안티패턴은 **ESB처럼 쓰기·게이트웨이처럼 쓰기·네트워크 계층 과다**다

## 다른 챕터와의 관계

- **0장**: 수평(east-west) 트래픽을 관리하는 컴포넌트가 이 장의 주제다
- **1장**: gRPC/HTTP2를 쓸 때 7계층 로드밸런싱과 프록시 없는 gRPC 선택지가 여기서 이어진다
- **3장**: 게이트웨이 루프백 안티패턴이 남긴 질문에 이 장이 답한다. 게이트웨이(수직)와 메시(수평)의 소유자·요구·구현체가 어떻게 다른지 표로 대비했다
- **5장**: 메시의 트래픽 분할·미러링 기능이 카나리·블루-그린·트래픽 미러링 릴리스 전략의 토대가 된다
- **7장**: mTLS와 서비스 신원(SPIFFE)이 인증·인가 논의로 이어진다
- **9장**: 수직/수평 구분이 흐려지는 흐름과 **제로 트러스트**에서 메시의 역할을 다룬다
- **10장**: 메시가 플랫폼 서비스로 흡수되는 미래 전망을 다룬다
