# Chapter 9: Using API Infrastructure to Evolve Toward Cloud Platforms (클라우드 플랫폼으로의 진화)

## 핵심 질문

클라우드로 옮기는 방식에는 어떤 선택지가 있고 무엇을 기준으로 고르는가? 마이그레이션 도중 여러 네트워크에 걸친 트래픽은 어떻게 다루는가? 그리고 그 과정에서 보안 모델은 어떻게 바뀌어야 하는가?

## 1. 사례 연구: 참석자 서비스를 클라우드로 이전하기

컨퍼런스 시스템 소유자가 **데이터센터를 직접 운영하는 부담을 없애고 싶어 한다.** 결국에는 새 서비스·모놀리스·미들웨어(API 게이트웨이)·데이터 스토어까지 전부 클라우드로 옮기게 될 것이다.

**참석자 서비스를 먼저 옮기는 이유**는 가장 새로운 컴포넌트이면서 **대부분의 트래픽을 감당할 서비스**이기 때문이다.

> **핵심 통찰**: 인프라의 변화에는 **독자적인 리듬**이 있다 - 하드웨어가 고장 나고, 기업과 기술이 인수·통합되고, 조직 IT 정책이 업그레이드를 요구한다. 다만 현대화와 클라우드 이전에서는 **API 프로그램이 인프라 변화를 주도하는 때도 있다.**

## 2. 클라우드 마이그레이션 전략의 선택 - 6가지 R

가트너의 2010년 기사를 바탕으로 AWS가 2016년 정리한 **"클라우드 마이그레이션의 6가지 R"** 이다. **아무것도 하지 않는 것부터 완전히 새로 만들거나 없애는 것까지** 전 범위를 담는다.

> **핵심 통찰**: API는 **사용자에게 가장 가까운 비즈니스 주도 컴포넌트**이자 대부분의 요청이 들어오는 지점이므로, 마이그레이션 방식을 정할 때 특히 신중해야 한다.

### 유지하거나 재검토(Retain / Revisit)

**(지금은) 아무것도 하지 않는** 전략이다. 접근법이라 부르기 민망해 보이지만, 많은 아키텍트는 **"싸울 곳을 직접 고르라"** 고 조언한다 - API 마이그레이션은 **들인 노력에 비해 얻는 것이 없을 수도 있다.** 다만 이 결정은 **건전한 비즈니스·기술 평가에 기반**해야 하고 조직 안팎에 제대로 전달되어야 하며, **ADR로 근거를 남겨야** 한다.

> **참고 - 변경과 퇴출에 대한 소통**: 지금 개선하지 않기로 했더라도 **반드시 완료해야 할 날짜는 알려야 한다** - 사업부 폐쇄일, 시스템의 EOL, 핵심 소프트웨어·데이터 스토어 라이선스 만료일 등. 계약과 SLA에 **이런 통지가 의무로 명시**되어 있을 수 있다.

> **실무 팁**: 진화 단계에서 **두 서비스 사이에 생기는 레이턴시**가 중요한 변수다. 트래픽이 높은 서비스라면 요청이 **네트워크 경계를 건널 때마다** 느려진다. 어떤 성능 저하가 생기고 **SLA를 위반하지는 않는지** 따져야 하며, 경우에 따라 **옮기지 않는 것이 정답**일 수 있다.

### 호스트 교체(Rehost)

**"그대로 들어서 옮기기"**(*lift-and-shift*)다. **아키텍처 변경 없이** 시스템과 부하를 클라우드로 옮긴다. 부하를 통합하거나 현재 인프라에서 떼어내는 것이 목적이면 효과적이다. 다만 **클라우드가 온프레미스 하드웨어와 똑같이 동작하지는 않으므로** 무심코 깔고 있는 가정이 없는지 확인해야 한다.

> **참고 - 전문가 시스템과 맞춤형 하드웨어를 주의하자**: 오래된 전문가 시스템은 **모든 통신이 로컬 버스나 전용 네트워크로 일어난다고 전제**하고 있을 수 있고, 어떤 데이터 스토어는 **기반 블록 스토리지 하드웨어의 특성(또는 그 보장)** 에 의존한다. 의심스러우면 확인하자.

### 플랫폼 교체(Replatform)

**"들어서 고치고 옮기기"**(*lift-tinker-and-shift*)다. 호스트 교체와 비슷하되 **최소한의 재작업으로 클라우드 서비스의 이점을 취한다.** 예를 들어 자체 운영하던 MySQL을 **호환되는 관리형 서비스**(AWS RDS, Azure Database, GCP Cloud SQL)로 바꾸거나, 언어별 애플리케이션 서버를 컨테이너로 교체하는 식이다.

**컨퍼런스 사례는 이 방식을 택한다.**

### 재구매(Repurchase)

**다른 제품으로 갈아타는 것**이다. 이메일 서버를 직접 운영하는 대신 SaaS 이메일 전송 서비스를 구독하는 식이다. 컨퍼런스 시스템은 맞춤형 애플리케이션과 표준 데이터 스토어라 해당하지 않는다.

### 리팩터링/아키텍처 재설계(Refactor / Re-architecture)

**클라우드 네이티브 기능을 이용해 아키텍처와 개발 방식을 재해석**하는 것이다. **외부에서 보이는 핵심 기능은 그대로 두되 내부 구현이 확실히 바뀐다.** 보통 기존 환경에서는 얻기 어려운 신기능·확장성·성능에 대한 강한 요구가 있을 때 진행한다. 노력이 가장 많이 들지만, **제품이 시장에 맞는데 과거 기술 선택에 발목이 잡혀 있다면** 최선의 선택이 된다.

> **핵심 통찰**: 컨퍼런스 시스템은 이 책 전체가 이미 아키텍처 재설계였다. 다만 **API 인프라와 설계를 클라우드 네이티브 방식으로 진행하는 것**이 중요하다 - 1장 방식으로 API를 정의·모델링해두면 재설계 과정에서 **서비스를 표현할 더 깔끔한 메커니즘**을 갖게 되고, **여러 클라우드 서비스와 연동 자체가 API 기반**이므로 API 전략은 어떤 클라우드 서비스를 쓸지만큼 중요하다.

### 퇴출(Retire)

시스템을 **제거**하는 것이다. 대규모 마이그레이션에서는 **더 이상 쓰이지 않는데 잊힌 시스템**이 하나쯤 나오기 마련이다. 컨퍼런스 시스템의 전체 목표 중 하나도 **레거시 컨퍼런스 시스템의 퇴출**이며, 그 시점은 플랫폼 교체와 리팩터링이 완전히 끝났을 때다.

### 사례 연구: 참석자 서비스의 플랫폼 교체

- **유지/퇴출**: 요구사항 자체가 클라우드 이전이므로 부적절
- **재구매**: 지금 상황에 맞지 않음
- **리팩터링/재설계**: 이미 앞서 진행함
- **호스트 교체**: 괜찮은 전략이지만, **기존 MySQL 인스턴스를 그대로 옮기기보다 관리형 데이터베이스의 이점을 얻고 싶다**
- **→ 플랫폼 교체 + API 게이트웨이도 함께 클라우드로**

```
┌─────────────────────── 클라우드에 배포 ────────────────────────┐
│  API 호출 [HTTP]        ┌────────────────┐                    │
│  ─────────────────────▶ │  API 게이트웨이  │                    │
│                         └────────┬───────┘                    │
│                                  │ [아웃 오브 프로세스]           │
│                         ┌────────▼───────┐   CRUD [SQL]        │
│                         │  참석자 서비스   │ ─────────▶ 데이터 스토어│
│                         └────────────────┘                    │
└───────────────────────────────┬───────────────────────────────┘
                                │ [아웃 오브 프로세스이자 교차 네트워크]
┌───────────────────────────────▼─────────────── 온프레미스 ─────┐
│  ┌────────────────────┐        ┌────────────────┐             │
│  │ 레거시 컨퍼런스 시스템 │ ─────▶ │   세션 서비스    │ ──▶ 데이터 스토어│
│  └────────────────────┘        └────────────────┘             │
└───────────────────────────────────────────────────────────────┘
```

> **핵심 통찰**: **게이트웨이를 먼저 클라우드로 옮기면** 온프레미스에서 클라우드로 트래픽을 **점진적으로 끌어올 수 있다.** 게이트웨이가 위치 투명성을 제공하므로 사용자 영향을 최소화하면서 서비스를 옮길 수 있다.

## 3. API 관리의 역할

어떤 전략을 택하든 **API 관리**는 마이그레이션의 중요한 부분이며, 조직 안팎에 **API의 가치를 전달하는 역할**을 한다. API 관리자는 기본적으로 강력한 게이트웨이에 발행·제어 기능을 더한 것으로, OAuth2·콘텐츠 검증·호출률 제한·스로틀링 같은 에지 정책과 **개발자 포털(마켓플레이스)** 을 제공하고 **내외부 고객 대상 수익화**를 가능하게 한다.

> **핵심 통찰**: API 관리의 가장 중요한 역할은 **API의 변경을 방해하지 않으면서 API를 발견할 중심점을 제공하는 것**이다. **API 계약이 바뀌지 않는다면 API 관리 계층 아래에서 서비스를 얼마든지 개선할 수 있다.**

새로 분리한 참석자 API를 제공하면서 동시에 레거시 시스템에도 API를 구성할 수 있고, 그러면 컨퍼런스 운영자는 다른 컨퍼런스가 쓰거나 외부 CFP를 제어하는 인터페이스로 그 API를 활용해 **"서비스로서의 컨퍼런스 관리"** 를 만들 수도 있다.

조직에서 자주 말하는 **'API 우선'** 은 시스템의 모든 통신을 API로 설계·모델링한다는 뜻이다(1장). 좋은 설계 원리를 따르고 API 우선에 집중하면 **API 관리 같은 도구로 외부 고객뿐 아니라 조직 내부에도 가치를 전달**할 수 있다.

## 4. 수직·수평 트래픽: 관리 경계가 흐려진다

서비스를 한 번에 옮기지 않고 점진적으로 옮기기로 했으므로, 마이그레이션 도중에는 **여러 클라우드 환경과 온프레미스 데이터센터에서 동시에 서비스가 돈다.** 그러면 사용자 요청 하나를 처리하려고 **네트워크를 여러 번 갈아타야** 한다.

### 에지부터 시작해 안으로

**에지의 API 게이트웨이를 단일 서비스와 함께 먼저 옮긴다.** 그러면 마이그레이션 팀이 **기존 시스템을 멈추지 않고** 새 클라우드 환경을 세팅할 수 있다. 현재 게이트웨이를 그대로 둔 채 **복제본을 클라우드에 배포**하고, 위험을 최소화하며 점진적으로 구성한다.

> **실무 팁**: 완전한 클라우드 환경에서 **격리된 개념 증명**을 먼저 만들고, **검증된 뒤에야** 클라우드로 라우팅하는 실험을 시작하자. 클라우드 기반 아키텍처 설계는 대개 **패러다임의 전환**이다 - **새 인프라를 배우는 데 드는 시간을 과소평가하지 말자.**

### 경계 건너기: 네트워크 간 라우팅

옮기기 전에 **새 시스템과 기존 시스템이 서로 다른 네트워크를 건너 통신할 수 있는지** 확인해야 한다.

- 모놀리스 하나와 간단한 라우팅 몇 개뿐이라면 **일시적인 HTTP 리다이렉션**으로 새 게이트웨이에서 기존 게이트웨이로 보내는 것이 가장 쉽다
- 네트워크를 건너는 라우팅이 많거나 **트래픽이 유입된 네트워크를 벗어날 수 없다면**, **가상 비공개 네트워크 피어링**·엔드포인트·**멀티클러스터 서비스 메시**를 고려해야 한다

API 트래픽이 여러 네트워크를 오가면 **기존의 주변 방어와 구역화 아키텍처에 방해가 될 수 있으므로 정보보안 팀과 상의해야 한다.** 이것이 다음 절의 주제다.

## 5. 구역화 아키텍처에서 제로 트러스트로

### 구역화 아키텍처

상용 인터넷이 퍼지며 규제 산업까지 외부 접근을 허용하게 되자, **구역화**(*zoning*)가 보안 네트워크 설계의 권장 기법이 됐다. **인프라 서비스를 같은 보안 정책·요구사항을 가진 논리적 그룹으로 나눠** 네트워크가 완전히 열리는 위험을 줄이는 방법이다.

Log4Shell(CVE-2021-44228) 같은 제로데이를 생각해보자. 공격자가 이 취약점으로 네트워크의 호스트에 접근할 수 있었고 영향 범위가 상당했다. **신뢰할 수 없는 요청이 중요한 정보 접근이 제한된 구역으로만 들어온다면** 영향 반경을 최소화하고 **보안 팀이 조치할 시간을 벌 수 있다.** 구역은 연속적이어서 **안쪽으로 갈수록 보호 장치가 늘어난다.**

```
┌──────────────── 제어하지 않는 구역 ────────────────┐
│                    인터넷 (PZ)                    │
└──────────────────────┬────────────────────────────┘
                    경계 (구역 인터페이스 지점)
┌──────────────────────▼────────── 제어하는 구역 ────┐
│              공개 접근 구역 (PAZ) = DMZ             │
│  ┌────────────────────┬───────────────────────┐  │
│  │    운영 구역 (OZ)    │     제한 구역 (RZ)      │  │
│  └────────────────────┴───────────────────────┘  │
└───────────────────────────────────────────────────┘
```

- **공개 구역(PZ)**: 완전히 개방된 구역. 공개 인터넷, 공중 전화망, 이동통신사 백본
- **공개 접근 구역(PAZ)**: 운영 시스템과 공개 구역 사이의 접근을 관장하며 **DMZ를 포함**한다
- **운영 구역(OZ)**: 일반 운영을 위한 표준 환경. 민감 정보를 다룰 수는 있지만 **대규모 민감 데이터 보관이나 중요 애플리케이션에는 적합하지 않다**
- **제한 구역(RZ)**: 제어되는 네트워크 환경. **비즈니스에 중요한 서비스나 대규모 민감 정보 저장소**에 적합하다

> **핵심 통찰**: 이 설계는 **'성 주변의 해자'** 와 같다. 공격자는 유입 지점에서 가장 애를 먹지만 **일단 성벽 안으로 들어오면 비교적 쉽게 돌아다닌다.** 모든 통신이 경계 안에서 일어난다고 **가정**하기 때문이다. 그런데 **클라우드는 그 가정을 하지 않는다** - 지리적·네트워크 위치가 추상화되어 있고, 빌드 시점에 소프트웨어를 조작하는 **공급망 공격**이나 인프라 제공자 측 악의적 공격자의 위험이 남는다.

### 아무도 믿지 말고 검증하자

**제로 트러스트**(*zero trust*, 경계 없는 보안)의 핵심 개념은 **"절대 믿지 말고 항상 검증하라"** 다. 기업 LAN처럼 권한 있는 네트워크에서 접속했거나 예전에 검증된 장치라도 **기본적으로 신뢰하지 않는다.** 위치와 무관하게 **장치의 신원과 무결성을 확인하는 상호 인증**을 쓰고, 사용자 인증과 결합해 접근을 허용한다.

엔터프라이즈에서 제로 트러스트를 구현하는 8가지 원리다.

1. 사용자·장치·서비스·데이터 등 **아키텍처를 이해한다**
2. 사용자·서비스·장치의 **신원을 확인한다**
3. 사용자의 동작, 장치·서비스의 **상태를 평가한다**
4. **정책으로 요청을 인가한다**
5. **모든 곳에서** 인증과 인가를 수행한다
6. 접근과 관련된 **모든 것을 모니터링한다**
7. **보유한 네트워크를 포함해 어떤 네트워크도 신뢰하지 않는다**
8. **제로 트러스트를 위한 서비스를 선택해 설계한다**

> **핵심 통찰**: 이 원리들은 당연해 보이지만 **구역화 아키텍처에서는 지키기 매우 어렵다.** 구역화는 **에지에서 사용자를 한 번만 인증하고 경계 안의 모든 네트워크를 기본적으로 신뢰**하기 때문이다.

### 제로 트러스트에서 서비스 메시의 역할

**서비스 메시와 API 게이트웨이를 결합하면** 제로 트러스트를 구현할 좋은 플랫폼이 된다. 메시는 컴포넌트 구성과 트래픽 흐름을 **균일한 방식으로 모델링**하게 해주고, **프로세스 신원과 인증서 관리의 구체적 모델**을 세워 신원의 평가·증명을 돕는다. 추적·모니터링을 통합하면 사용자뿐 아니라 **기반 서비스와 파드의 상태까지** 분석할 수 있다. **인그레스는 OAuth2 챌린지(7장)로, 클러스터 내부는 mTLS로** 인증·인가를 강화한다.

> **참고**: "**어떤 네트워크도 신뢰하지 않는다**"는 원리는 메시에게 까다로운 주제다. 대부분의 모델에서 **사이드카는 서비스와 강하게 결합**되어 있어 배포는 간결하지만, 그만큼 **실행 중인 플랫폼 자체를 구체적으로 평가할 수 없다.** 애플리케이션과 사이드카의 **기반 구조에도 신뢰 기반 가정을 없애는 보안 장치**가 필요하다.

### 네트워크 정책으로 메시를 보강하기

**플랫폼 보안이 애플리케이션 수준의 모든 가정을 떠받친다.** 완전한 제로 트러스트를 위해서는 **가정하는 수준을 더 아래로 내려야** 한다. 쿠버네티스의 **네트워크 정책**(칼리코 같은 CNI 플러그인)이 그 수단이다.

먼저 **모든 파드를 기본적으로 완전히 격리**한다.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
spec:
  podSelector: {}
  policyTypes:
    - Egress
    - Ingress
```

메시 구현은 보통 **중앙 DNS로 서비스 이름을 조회**하므로, 잠근 상태에서도 메시가 동작하도록 DNS만 열어준다.

```yaml
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns
spec:
  podSelector:
    matchLabels:
      app: legacy-conference
  policyTypes:
    - Egress
  egress:
    - ports:
        # DNS 해석을 허용
        - port: 53
          protocol: UDP
```

이 시점에서 레거시 컨퍼런스 서비스는 사이드카로 **참석자 서비스의 위치를 찾을 수는 있지만 요청 자체는 여전히 막혀 있다.** 그래서 **메시의 모든 라우팅 규칙에 대응하는 허용 규칙**을 네트워크 정책에도 넣어야 한다.

```yaml
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-conference-egress
spec:
  podSelector:
    matchLabels:
      app: legacy-conference
  policyTypes:
    - Egress
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: attendees
```

인그레스가 동작하려면 **메시 게이트웨이에서 대상 서비스로 가는 인그레스 규칙**도 추가해야 한다.

> **실무 팁**: 이 규칙과 설정이 **일관되게, 릴리스 시점에 자동으로 반영되도록** 하는 것이 5장의 **규약형 플랫폼**을 고려할 또 하나의 이유다.

### 멀티클러스터 메시 피어링

요즘 흔한 패턴은 **메시를 서로 다른 네트워크 사이의 브리지**로 쓰는 것이다. 클러스터 간 메시를 **피어링**해 온프레미스와 클라우드의 데이터 부분을 **하나의 통합된 제어 부분**으로 관리한다.

```
┌──────────────── 클라우드에 배포 ──────────────────┐
│  API 호출 ──▶ API 게이트웨이 [서비스 메시 인프라]    │
│                     │ mTLS 라우팅                 │
│                     ▼                            │
│                참석자 서비스 ──▶ 데이터 스토어        │
└─────────────────────┬────────────────────────────┘
                      │ 클러스터 간 라우팅 [mTLS, 멀티클러스터 서비스 메시]
┌─────────────────────▼─────────── 온프레미스 ──────┐
│  레거시 컨퍼런스 시스템 ──▶ 세션 서비스 ──▶ 데이터 스토어│
└──────────────────────────────────────────────────┘
```

> **핵심 통찰**: 이 방식의 장점은 **클라우드와 구역화 환경이 섞인 하이브리드에도 일관된 보안을 적용**할 수 있다는 것이다. **온프레미스가 클라우드처럼 동작하게 만들면** 남은 서비스를 클라우드로 옮기기도 쉬워진다.

## 요약

- 클라우드로 옮기는 방식은 **6가지 R** - 유지/재검토, 호스트 교체, 플랫폼 교체, 재구매, 리팩터링/재설계, 퇴출 - 이며 **아무것도 하지 않는 것도 정당한 선택**이다(단 근거를 ADR로 남기고 관련 날짜를 소통할 것)
- 사례는 **플랫폼 교체**를 택했다. 관리형 데이터베이스의 이점은 얻되 대규모 재작업은 피하는 절충이며, **게이트웨이를 먼저 옮겨 트래픽을 점진적으로 끌어오는** 기반을 만든다
- **API 관리**는 계약이 유지되는 한 그 아래에서 서비스를 자유롭게 개선하게 해주는 **발견의 중심점**이다
- 마이그레이션 도중에는 **수직(인그레스)과 수평(서비스 간) 트래픽 관리의 경계가 흐려진다.** 에지에서 시작해 안으로 옮기고, 네트워크 간 라우팅 수단(HTTP 리다이렉션 → VPN 피어링 → 멀티클러스터 메시)을 규모에 맞게 고른다
- **API 게이트웨이는 여러 환경·네트워크에 걸친 백엔드의 퍼사드**로 동작하므로 그 자체가 마이그레이션 도구다
- 업계는 **구역화(성과 해자)에서 제로 트러스트(절대 믿지 말고 항상 검증)로** 이동 중이며, **서비스 메시 + 게이트웨이**가 그 플랫폼이 된다
- 완전한 제로 트러스트를 위해서는 **가정하는 수준을 플랫폼 아래로 내려야** 한다 - 쿠버네티스 **네트워크 정책으로 기본 차단**하고 메시의 라우팅 규칙마다 허용 규칙을 짝지어 준다
- 제로 트러스트와 구역화를 **결합**하면 마이그레이션 기간에 클라우드와 온프레미스를 **병렬로 운영**할 수 있다

## 다른 챕터와의 관계

- **1장**: 경계를 건너는 호출의 **레이턴시와 프로토콜 선택**이 마이그레이션 판단의 변수로 다시 등장한다
- **3장**: 게이트웨이가 제공하는 **위치 투명성**과 퍼사드 역할이 클라우드 이전의 핵심 수단이 된다
- **4장**: 메시의 멀티클러스터 피어링과 mTLS가 **네트워크를 건너는 제로 트러스트**의 구현체다
- **5장**: 점진적 릴리스와 **규약형 플랫폼**이 클라우드 전환에서 다시 필요해진다
- **6장**: 구역화 아키텍처와 DMZ, 그리고 **제로 트러스트로의 이전**이 위협 모델링에서 예고됐다
- **7장**: 인그레스의 OAuth2 챌린지가 제로 트러스트의 "모든 곳에서 인증하라"와 맞물린다
- **8장**: 아키텍처의 진화를 다뤘다면 이 장은 **인프라의 진화**다. 두 진화는 서로의 리듬을 존중하며 함께 간다
