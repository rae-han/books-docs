# Chapter 8: Redesigning Applications to API-Driven Architectures (API 주도 아키텍처로의 재설계)

## 핵심 질문

기존 시스템을 API 주도로 바꿔야 할 근거를 무엇으로 삼는가? 진화의 목표를 어떻게 정의하고 그 달성 여부를 어떻게 측정하는가? 그리고 실제로 어떤 패턴으로 옮겨가는가?

## 1. 시스템의 진화에 API가 필요한 이유

소프트웨어를 안전하게 바꾸는 일은 어렵다. 사용자가 많거나, 내재된 복잡도가 높거나, 다른 시스템과 단단히 통합되어 있으면 더 어려워진다. **그런데 그 특성들은 잘 쓰이고 있고 조직에서 중요한 역할을 하는 시스템이라면 거의 필연적으로 갖게 되는 것들이다.** 대부분의 레거시 시스템은 일시적 우회책, 버그 수정, 그저 쉬워서 택한 설계 변경이 쌓이며 진화해 왔다.

> **핵심 통찰**: 아키텍트에게 API는 **모듈이나 컴포넌트의 경계**다. 그래서 응집도가 높고 결합도가 낮은 시스템을 만들기 위한 자연스러운 지렛대가 된다.

### 유용한 추상화: 응집도의 향상

**응집도**(*cohesion*)는 시스템 내 요소들이 서로 함께하는 정도다. 응집도가 높으면 제공자와 소비자 모두 진화가 쉬워진다 - 제공자는 **외부 인터페이스의 하위호환성만 지키면** 알고리즘 변경·리팩터링·데이터 스토어 교체 같은 내부 구조를 바꿀 수 있고, 소비자는 통합 지점이 명확하니 수정과 확장이 쉽다.

응집력 있는 API 설계와 맞물린 것이 **추상화의 수준**이다. 자동차는 대시보드·페달·운전대로 조작하지만 우주왕복선은 제어 패널에 수많은 계기와 버튼이 있다. 그 정도의 제어 능력은 **우주왕복선에는 응집력이 있지만 자동차에는 적절하지 않다.**

> **핵심 통찰**: "향후에도 문제가 없는 API"라는 명목으로, **실제로는 자동차를 운전하는 수준의 비즈니스 서비스에 우주왕복선 제어 패널을 설계하고 싶은 충동**을 느끼게 된다. 그 유혹을 알아채는 것이 이 절의 요점이다.

응집도가 높은 API는 아키텍트가 **멘탈 모델을 만들고 동작을 유추하기 쉽고**, 시스템 내 변경이 집중되는 지점이 된다 - 응집도가 낮으면 하나의 변경에 여러 API를 고쳐야 하지만, 높으면 하나만 고치면 된다.

반례로 모든 컨퍼런스 엔티티가 공유하는 편의 함수 모음인 `utils` API를 만든다고 하자. 참석자 API 뒤의 코드를 바꾸면 **유틸리티 API도 함께 고쳐야 하는** 상황이 반복된다. 원저자가 아니거나 문서·테스트가 부실하면 그 연결을 놓쳐 일관성이 깨지고 호환성 사고가 난다.

> **참고 - 응집도의 종류는 하나가 아니다**: 흔히 하나의 척도처럼 말하지만 아키텍트가 알아야 할 종류는 여럿이다 - **기능적·순차적·소통적·절차적·일시적·논리적·우연한** 응집도.

### 도메인 경계의 정립: 낮은 결합도의 촉진

느슨하게 결합된 시스템은 두 속성을 갖는다. ① 컴포넌트들의 관계가 **약해서(쉽게 끊어져서)** 한쪽의 변경이 다른 쪽의 기능·성능에 영향을 주지 않는다. ② 각 컴포넌트가 **다른 컴포넌트의 정의를 거의 또는 전혀 모른다.** 그래서 같은 서비스를 주는 다른 컴포넌트로 쉽게 교체할 수 있고 플랫폼·언어·빌드 환경의 제약도 적다.

제공자에게는 **통합과 변경이 쉬워 조직 전체의 도입이 늘어난다**는 이점이, 소비자에게는 **런타임에도 컴포넌트를 갈아 끼울 수 있어** 테스트가 쉽고 의존성 관리 비용이 준다는 이점이 있다.

> **참고 - 결합이 느슨하면 모킹과 가상화도 쉬워진다**: 결합도가 낮으면 제공자 구현을 스텁이나 가상 서비스로 바꿔 통합·종단 간 테스트를 할 수 있다. 반대로 **결합도가 높으면 목이나 스텁으로 교체하는 것 자체가 불가능**해서 제공자를 직접 띄우거나 경량 대체 서비스를 써야 한다(2장의 논의가 여기서 설계 품질의 결과로 나타난다).

**사례 연구** - 참석자 서비스가 데이터 스토어와 강하게 결합되어 **기반 스키마 형태 그대로 데이터를 제공**한다고 하자. 스토어를 바꾸려면 선택지는 둘뿐이다. ① 기존 형식과 새 형식 **양쪽으로 데이터를 만들고 조회하는** 시스템을 만든다(복잡하고 에러가 나기 쉽다) ② 외부 API를 고치고 **모든 소비자를 바꾸게 한다**(사용자가 많을수록 어려워진다).

> **핵심 통찰 - 정보 은닉**: 응집도가 높고 결합도가 낮은 API를 설계할 때의 원리는 **변경 가능성이 높은 구현 결정을 분리하는 것**이다. API에서 정보 은닉이란 **비즈니스·도메인 중심 엔드포인트만 제공하고 내부 추상화나 구현 데이터 모델·스키마는 제공하지 않는 것**이다.

## 2. 최종적인 아키텍처의 선택

바꾼 뒤의 시스템이 어떻게 기능해야 하는지 **명확한 비전**이 있어야 한다. 그렇지 않으면 이런 상황이 된다.

> "여기서 어디로 가야 하는지 알려주실래요?" 그러자 고양이가 말했다. "그건 어디로 가고 싶은지에 따라 다르겠죠." 앨리스가 말했다. "목적지는 크게 중요하지 않아요." 그러자 고양이가 "그러면 어느 길로 가는지도 중요하지 않죠."라고 말했다.<br>- 루이스 캐럴, 『이상한 나라의 앨리스』

- **모놀리식**: 최근 평판이 나쁜데, 그건 '모놀리식'이 **'큰 진흙 덩어리'와 동의어처럼** 쓰였기 때문이다. 실제로는 모든 것이 한 조각으로 구성된 단일 프로세스 애플리케이션일 뿐이고 **본질적으로 아무 문제가 없다.** 개념 증명이나 시장 적합성을 검증하는 초기 단계에서는 **가장 빠르게 만들 수 있는 아키텍처**이며, 살펴야 할 시스템이 하나뿐이라 이해하고 고치기 쉽다. 어려움은 **의도치 않게 결합도 높은 설계를 채택하기 쉽다**는 것 - DDD와 육각형 아키텍처가 나중에 도움이 된다
- **서비스 지향 아키텍처(SOA)**: 초기의 '클래식 SOA'가 낮은 평가를 받은 이유는 SOAP·WSDL·XML 같은 무거운 기술과 ESB·메시지 큐 같은 **벤더 미들웨어** 때문이었다. 통신에 **'스마트 파이프'** 를 쓰고 비즈니스 로직을 미들웨어에 넣는 경향이 있었다. **게이트웨이나 ESB에 비즈니스 로직을 절대 넣지 말 것.** 가장 큰 난제는 **서비스의 크기와 소유권을 알맞게 정하는 것**이다
- **마이크로서비스**: 가장 최신의 SOA 구현으로, 잘 정의된 API로 통신하는 작고 독립적인 서비스들이다. **"스마트 엔드포인트와 덤(dumb) 파이프"** 를 쓰고 무거운 미들웨어를 피한다. 핵심 원리는 **낮은 결합도와 높은 응집도를 갖는 API 주도 서비스**이며, 가장 큰 난제는 **경계(와 응집도)를 올바르게 잡는 것**이다 - 옮기기 전에 **컨텍스트 매핑과 이벤트 스토밍** 같은 DDD 기법을 쓰면 큰 도움이 된다
- **함수**: 마이크로서비스의 차세대가 되리라던 약속은 실현되지 않았지만 **고도로 이벤트화된 시스템**에는 유용하다(시장 반응형 거래 시스템, 이미지 처리 파이프라인). 어려움은 **결합도**다 - 간단한 함수를 만들기가 너무 쉬워서 **비즈니스 가치를 내려면 잘 조율해야 하고 그 과정에서 결합도가 높아진다.** 재사용성과 관리용이성의 균형을 잡을 시간이 없다면 이 스타일은 고르지 않는 편이 낫다

## 3. 진화적 절차의 관리

### 목표의 결정

**변화의 동기를 명확히 하고 목록화해 팀과 조직에 전달**해야 한다. 잘못된 가정과 목표는 **코딩을 시작한 뒤보다 초기에 발견하는 편이 훨씬 싸다.**

- **기능적 목표**: 어떤 기능을 바꾸는 것. 최종 사용자나 비즈니스 이해당사자가 주도하며 보통 **코드나 통합을 더 늘리는** 방향이다
- **교차 기능적(비기능적) 목표**: 관리용이성·확장성·신뢰성 같은 **'속성'** 을 위한 것. 관리용이성 개선은 대개 **엔지니어가 시스템을 이해하고 고치는 데 드는 시간을 줄이려고** 기술 리더십이 주도하고, 신뢰성 작업은 장애의 횟수와 영향을 줄이려는 시도다

### 적합성 함수의 활용

아키텍처가 빠르게 레거시가 되지 않으려면 **성능 저하를 막는 적극적인 결정**이 필요하다. **적합성 함수**(*fitness function*)는 아키텍처와 코드 산출물을 **지속적으로 조회하는 메커니즘**이다 - **아키텍처를 위한 단위/통합 테스트**이자 아키텍처 속성을 정량적으로 재는 도구라고 생각하면 된다. 빌드 파이프라인에 넣어 목표를 지킨다.

| 분류 | 무엇을 재는가 |
|------|--------------|
| 코드 품질 | 이미 많은 팀이 쓰고 있다. 릴리스 전에 품질을 재며, **순환 복잡도** 같은 지표를 더할 수 있다 |
| 회복성 | 프리프로덕션에 배포해 샘플 트래픽을 보내고 **에러율이 한계 아래인지** 본다. 게이트웨이나 메시로 **결함을 주입**해 회복력·가용성을 시험하기도 한다 |
| 관측용이성 | 서비스가 적합한지(그리고 회귀하지 않는지) 확인하고 **여러 지표를 발행**하는지 본다(5장의 API 지표) |
| 성능 | 레이턴시·처리량 목표를 정하면 빌드 파이프라인에서 잴 수 있다. 가장 어려운 건 **프로덕션과 유사한 데이터**를 확보하는 것이다 |
| 규제 준수 | 비즈니스가 예측대로 운영된다는 증거를 지속 제공하는 **감사·데이터 요구사항** |
| 보안 | 라이브러리 의존성을 분석해 **알려진 취약점**을 확인하거나, 코드에 자동 검색을 돌려 **OWASP 스타일 취약점**이 없는지 본다 |
| 운영용이성 | 플랫폼을 운영 가능한 상태로 유지하는 최소 요구사항. **모니터링과 경고가 실제로 작동하는지** 평가하는 것부터 시작한다 |

> **실무 팁**: 도입할 적합성 함수를 중심으로 **ADR을 작성**하자. 표의 모든 것을 한 번에 구현하기는 어렵다. 그리고 **되돌리기 어려운 결정은 미리 구분**해 두어야 한다 - 되돌릴 수 없는 결정 자체가 나쁜 것이 아니라, **충분히 생각하지 않고 내린 결정**이 나쁜 것이다.

### 시스템을 모듈로 나누기

> 저자 중 한 명은 (소나큐브 기준) **24년 동안 기술 부채가 쌓인 4백만 줄짜리 기반 코드**에서 일한 적이 있다. 코드 구조는 여러 클래스와 얽혀 애플리케이션 전반에 제어 불가능한 결합도를 만들어냈다. 어느 한 곳을 리팩터링하는 것조차 어려웠고 버그 하나를 고치면 예상 못 한 다른 버그가 터졌다. **이 문제는 시스템이 모놀리식이라서가 아니라 코드의 구조와 설계 부채 때문이었다.**

모듈형 컴포넌트를 설계한다는 것은 **기능의 응집도에 따라 경계와 논리적 그룹을 분명히 정하는 것**이며, 목표는 **구현 상세를 감추는 잘 정의된 경계**다.

> 나는 개인적으로 모듈(또는 마이크로서비스) 경계에서 최대한 적은 내용을 노출하는 방식을 선호한다. 일단 뭔가가 모듈 인터페이스의 일부가 되었다면 이를 되돌리기란 어렵다. 하지만 지금 숨기고 있다면 언제든지 공유하기로 결정할 수 있다.<br>- 샘 뉴먼(Sam Newman)

컨퍼런스 시스템을 모듈로 나누면 이렇게 된다.

```
┌──────────────────────────────────────────────────────────────┐
│  컨트롤러 모듈                                                  │
│  참석자 컨트롤러 │ 예약 컨트롤러 │ 세션 컨트롤러  (RESTful 엔드포인트)│
└───────────────────────────┬──────────────────────────────────┘
                            │ 사용의 방향 (한쪽으로만 흐른다)
┌───────────────────────────▼──────────────────────────────────┐
│  서비스 모듈                                                   │
│  참석자 서비스   │ 예약 서비스   │ 세션 서비스                    │
└───────────────────────────┬──────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────┐
│  데이터 접근 객체(DAO) 모듈                                      │
│  참석자 DAO     │ 예약 DAO     │ 세션 DAO                      │
└──────────────────────────────────────────────────────────────┘
```

> **핵심 통찰**: **모듈 간 의존성이 명확하게 한쪽으로만 흐르는 시점**에 도달하면 애플리케이션이 잘 모듈화된 것이다.

저자 중 한 명은 DAO 패턴으로 모듈을 만든 뒤, **비즈니스 로직을 DAO를 활용하는 독립 서비스 3개로 분리**했다 - **모놀리식 우선 진화**의 예다. 세 모듈은 각자의 서비스로 잘 분리되었고 DAO 모듈은 라이브러리로 남았다.

### 확장의 '이음새'가 될 API 구현하기

**이음새**(*seam*)는 마이클 페더스의 『레거시 코드 활용 전략』에서 온 개념으로 **기능이 서로 연결되는 지점**이다. 보통 의존성 주입과 인터페이스로 **대체용이성**(*substitutability*)을 얻는데, 이것이 핵심이다 - **전체 시스템을 띄우지 않고도 목이나 테스트 더블로 효과적으로 테스트할 수 있게** 해주기 때문이다.

테스트가 없는 레거시 코드에서 이음새를 분리하는 순서는 이렇다.

1. 변경점(이음새)을 식별한다
2. 의존성을 분리한다
3. 테스트를 작성한다
4. 원하는 변경을 구현한다
5. 리팩터링한다

이음새가 **현재 주체 바깥에서도 쓰일 가능성**이 있다면 서비스 간 API로 만드는 것이 좋은 선택이 된다.

### 변경 유발 지점 식별하기

기반 코드에서 **특별히 어렵거나 계속 바뀌면서 이탈하는 모듈**(두 문제는 대개 연관된다)이 어디인지는 오래 일한 사람에겐 보이지만, **시스템을 물려받았다면 항상 명확하지는 않다.** 이럴 때는 **버전 관리 시스템의 이탈 감지 유틸리티**나 **복잡도 측정 도구**를 빌드 파이프라인에서 돌려 찾는다.

그리고 5장에서 본 **느슨하게 결합된 시스템의 자동화된 배포와 릴리스**, 즉 **지속적 전달과 지속적 검증**이 진화적 아키텍처의 전제다.

## 4. API로 시스템을 진화시키는 아키텍처 패턴

진화 기간의 최우선 고려사항은 **위험을 완화하면서 이점을 최대한 빨리 얻는 것**이다.

### 교살자 무화과나무

**교살자 무화과나무**(*strangler fig*)는 기존 나무 주변에 자라는 열대 무화과종이다. 숙주를 짓누르며 자라지만, **둘러싸인 나무가 열대 폭풍에서 살아남을 가능성이 더 높다는 증거**도 있어 관계가 어느 정도 상호적이다. 진화적 아키텍처의 목적이 바로 이것 - **변화하는 시스템을 지원하면서 결국 기존의 것을 완전히 대체하는 것**이다. 기존 메커니즘을 유지한 채 새 컴포넌트를 더해 가며 **점진적으로 마이그레이션**한다.

구현 방법은 둘이다.

- **기능 플래그로 분기**(5장): 레거시를 쿼리할지 새 API 기반 서비스를 부를지 코드에서 고른다. **인 프로세스 이음새가 이미 있는 경우** 잘 동작한다. 다만 **아웃 오브 프로세스로 상호작용하는 소비자가 많다면**, 그들 모두가 새 API를 쓰도록 고치고 플래그로 제어하기를 기대하는 것은 현실적이지 않다
- **프록시/게이트웨이로 라우팅**: API 앞에 프록시를 두고 레거시 또는 새 구현으로 보낸다. **프록시를 이용한 퍼사드**이며, 소비자는 **같은 API를 쓰면서 뒤에서 일어나는 마이그레이션을 알지 못한다**(3장의 게이트웨이 매핑이 이것이다)

> **실무 팁**: 뒤에서 교살자 무화과나무를 관리하는 일은 까다롭다. **새 컴포넌트가 단일 실패 지점이 될 수 있고**, **프록시에 비즈니스 로직을 넣으면 마이그레이션이 끝나도 프록시를 걷어내기 어려워진다.** 레거시와 신규를 병렬 운영하면 **두 서비스 간 데이터 일관성**을 지키기 어렵다.

### 퍼사드와 어댑터

교살자 무화과나무도 일종의 퍼사드다 - **API 호출을 가로채 뒤의 복잡도를 감춘다.**

흔한 상황은 기존 분산 애플리케이션이 이미 어떤 형태의 API(예: SOAP-RPC 같은 오래된 프로토콜)를 쓰고 있는 경우다. 여기에 **어댑터**를 두어 SOAP 요청을 RESTful 호출로 변환할 수 있다. 다만 **프로토콜 재작성은 제대로 구현하기 어렵고**, 응집도가 낮아지거나 없던 결합도가 생기지 않게 주의해야 한다. 레거시만의 이야기도 아니다 - 1장의 `grpc-gateway`는 RESTful JSON 엔드포인트를 뒤에서 gRPC로 바꿔주는 어댑터다.

> **핵심 통찰**: 퍼사드와 어댑터는 둘 다 '중간에 위치한다'는 점에서 비슷하지만, **퍼사드가 어댑터보다 복잡도가 낮다.** 전통적인 게이트웨이는 요청을 **라우팅만** 하지만 어댑터는 **대상이 이해하는 표현으로 변환할 책임**을 진다. **게이트웨이가 퍼사드에서 어댑터로 선을 넘는 순간 결합도가 즉시 올라간다** - 지금 쓰는 컴포넌트가 그 일에 맞는지 스스로 물어야 한다.

### API 계층 케이크

엔터프라이즈에서 자주 언급되는 **'계층화된 API'** 패턴이다. 2000년대 자바·닷넷 엔터프라이즈 애플리케이션에서 프레젠테이션·애플리케이션·도메인·데이터 스토어 계층으로 나누고, **각 요청이 계층을 순차적으로 내려갔다 올라오게** 하던 방식이다. 각 계층의 기능을 추상화·재사용할 수 있지만, **기능 하나를 추가하려면 여러 계층을 모두 고쳐야 한다** - 즉 **계층별 응집도가 비즈니스 기능 단위의 높은 결합도로 이어진다.**

최신판은 가트너의 **페이스 계층화 애플리케이션 전략**으로, 프레젠테이션 → **교류하는 시스템(SoE)**, 애플리케이션 → **다른 시스템(SoD)**, 데이터 스토어 → **레코드 시스템(SoR)** 으로 이름을 바꿔 부른다.

이 패턴의 평판이 나빠진 이유는 진화가 더 어려워지기 때문이다. 아키텍트와 개발자가 **다른 계층을 부르지 않으려고 같은 기능을 여러 계층에 중복 구현**하거나, **프레젠테이션 계층이 데이터 스토어와 직접 통신**하는 등 **올바른 방법 대신 쉬운 방법을 택하게** 만든다.

## 5. 어려운 부분과 기회를 식별하기

문제 있는 시스템은 피하고 싶지만, **좋은 위기를 방치해서도 안 된다.** 문제 컴포넌트를 식별해 목록화하면 추적과 개선에 도움이 된다.

**업그레이드와 유지보수 이슈** - 다음 신호들로 '조치 대상 목록'을 만든다.

- 특정 서브시스템에서 **변경 실패율이 높다**
- 시스템에 대한 **지원 이슈가 크게 늘었다**
- 특정 부분에서 **대규모 이상 현상**이 발생한다
- **복잡도가 증가한다**(정적 분석과 순환 복잡도로 식별 가능)
- 필요한 변경이 쉬운지에 대한 **개발 팀의 자신감이 낮아진다**

이런 지점들이 곧 **특정 기능을 빼내 교살자 무화과나무로 개선할 API 추상화를 제공할 기회**다.

**성능 이슈** - **SLA**는 성능을 추적·모니터링할 좋은 상한선이다. 현실에서는 문제가 터지기 전에 보호 장치를 두지 않으며, **성능 문제를 고객 피드백으로 처음 듣는 순간 팀은 이미 불리한 위치**에 선다. 성능 문제는 아키텍처 문제일 수 있다(다른 위치나 인터넷 너머의 서비스를 호출하고 있는가?). **목표를 세우고 측정하고, 개선 가설을 세워 테스트·검증**하며, **개별 컴포넌트 최적화보다 시스템을 하나로 보는 것**이 중요하다.

**의존성의 제거: 결합도가 높은 API들** - 분산 아키텍처는 **각 부분이 독립적으로 진화할 수 있을 때만** 효과가 있다. 주요 안티패턴은 **여러 부분의 릴리스를 동시에 해야 하는 상황**이며, 이는 API 결합도가 높다는 신호다.

개발자들이 자신 없어 하는 **레거시 코드에서 의존성을 분리하는 기법** 둘을 소개한다.

- **스프라우트(*sprout*)**: 새 기능을 **다른 곳에 구현하고 테스트한 뒤**, '주입점'으로 알려진 레거시 메서드에 추가한다
- **감싸기**: 기존 메서드와 **같은 이름·시그니처의 새 메서드**를 만들어 기존 기능을 감싼다. 기존 메서드는 이름을 바꾸고, 새 메서드가 **추가 로직을 수행한 뒤** 그것을 호출한다

> **실무 팁**: 서비스 대부분이 레거시라면 **레거시 코드 작업 자체가 개발해야 할 중요한 기술**이다. 복잡한 부분은 **코딩 카타나 짝 프로그래밍**으로 다루면 팀 전체의 이해도가 올라간다.

## 요약

- 대부분의 API는 자연스럽게 시스템의 추상화이자 **'이음새'** 를 제공하고, 서비스 분리와 점진적 변화를 지원하는 **퍼사드** 역할을 한다 - 그래서 진화의 강력한 무기가 된다
- **결합도와 응집도**가 언제 API로 시스템을 개선할지 판단하는 핵심 개념이다. 이 둘을 염두에 두고 설계하면 진화·테스트·배포가 쉽고 안전해진다
- 목적지 아키텍처(모놀리식·SOA·마이크로서비스·함수)는 각각 다른 난제를 준다. 모놀리식은 **결합도가 몰래 높아지는 것**, SOA는 **크기와 소유권**, 마이크로서비스는 **경계 설정**, 함수는 **조율에서 오는 결합도**다
- **목표를 명확히 정의하고 공유하지 않으면** 마이그레이션이 끝나지 않은 채 리소스만 쓰고 사기를 떨어뜨린다. **적합성 함수**로 그 목표를 빌드 파이프라인에서 계속 검증한다
- 모듈화의 판단 기준은 **의존성이 한 방향으로만 흐르는가**이며, 모듈 경계에서는 **최대한 적게 노출**한다
- **교살자 무화과나무·퍼사드·어댑터** 같은 잘 정의된 패턴을 쓰면 개선 속도와 안정성이 높아진다. 단 **프록시에 비즈니스 로직을 넣지 말고**, 퍼사드가 어댑터로 넘어가는 순간을 자각해야 한다
- **API 계층 케이크**는 계층별 응집도를 얻는 대신 기능 단위의 결합도를 키우는 패턴이라 진화를 어렵게 만든다

## 다른 챕터와의 관계

- **0장**: ADR-001에서 참석자 서비스를 분리하기로 한 결정을 **결합도·응집도·도메인 경계**의 언어로 다시 정당화한다
- **1장**: 기반 데이터 모델을 노출하지 말라는 조언이 **정보 은닉**으로, `grpc-gateway`가 **어댑터 패턴**으로 재등장한다
- **2장**: 낮은 결합도가 **모킹·가상화의 전제**라는 점에서 테스트 전략과 설계 품질이 맞물린다
- **3장**: 게이트웨이 매핑으로 시작한 교살자 무화과나무를 이 장이 패턴으로 정리한다
- **5장**: 기능 플래그와 지속적 전달이 진화의 실행 수단으로 다시 쓰인다
- **6장**: 적합성 함수의 **보안 분류**(의존성 취약점 스캔, OWASP 검색)가 위협 모델링과 이어진다
- **9장**: 같은 진화의 논의를 **클라우드 인프라 마이그레이션**으로 확장한다
- **10장**: 사례 연구가 0장부터 여기까지 어떻게 변해왔는지 전체를 되짚는다
