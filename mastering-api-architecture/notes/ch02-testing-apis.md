# Chapter 2: Testing APIs (API 테스트)

## 핵심 질문

한정된 시간과 리소스로 어떤 테스트에 투자해야 가장 큰 확신을 얻는가? 소비자를 깨뜨리지 않는다는 보장은 어느 층위의 테스트가 주는가? 그리고 외부 의존성을 넘는 경계는 무엇으로 검증하는가?

## 1. 이 장의 시나리오

참석자 API를 분리하자 새로운 상호작용이 생겼다. 참석자 API를 **외부 CFP 시스템**과 **레거시 컨퍼런스 시스템**이 함께 사용한다.

```
┌────────┐  계정 생성·세션 리뷰·   ┌────────────────────┐   호출   ┌──────────────────┐  CRUD   ┌────────────┐
│  고객   │  참석 예약             │ 레거시 컨퍼런스 시스템 │ ──────▶ │  참석자 관리 API    │ [SQL]   │ 데이터 스토어 │
│ [사람]  │ ────────────────────▶ │ [소프트웨어 시스템]   │         │ [소프트웨어 시스템] │ ──────▶ │            │
└────────┘                       └────────────────────┘         └──────────────────┘         └────────────┘
```

> **핵심 통찰**: API의 일관성이 깨지거나 릴리스 도중 실수로 단절적 변경이 들어가는 **가장 큰 원인은 테스트 부족**이다. 항상 올바른 결과를 돌려준다는 확신을 얻는 유일한 방법은 적절한 수준의 테스트에 투자하는 것뿐이다.

API는 문서화된 것과 다른 결과를 돌려줘서는 안 되고, 단절적 변경이 나서도 안 되며, 결과를 얻기까지 오래 걸려서도 안 된다. 잘못된 입력에 유용한 피드백을 주고, 안전해야 하며, **서비스 수준 지표**(*Service-Level Indicator - SLI*)를 기준으로 정해둔 **서비스 수준 목표**(*Service-Level Objective - SLO*) 안에서 응답해야 한다(SLI·SLO는 5장).

## 2. 테스트 전략

동작하는 무언가가 아니라 **올바르게 동작하는** 무언가를 만들어야 한다. 그런데 테스트를 쓸 시간과 리소스는 유한하므로, 별 소득 없는 테스트에 시간을 쓸 수는 없다. 관련 없는 테스트, 중복 테스트, 그리고 **자주 고쳐야 해서 가치 대비 비용이 큰 테스트**는 피한다. 여기 나오는 테스트를 전부 구현해야 릴리스할 수 있는 것도 아니다.

### 테스트 사분면

브라이언 매릭(Brian Marick)이 제안하고 리사 크리스핀·자넷 그레고리의 "애자일 테스팅"이 널리 알린 모델이다. 기술 관계자와 비즈니스 관계자의 서로 다른 우선순위를 한 그림에 담는다.

```
                        비즈니스 위주
        ┌──────────────────────┬──────────────────────┐
        │        Q2            │         Q3           │
  팀    │  기능 테스트           │  탐색 테스트          │  제품
  지원  │  예제·스토리 테스트     │  시나리오·사용성 테스트 │  평가
        │  프로토타입·시뮬레이션   │  UAT·알파/베타       │
        │  (자동 및 수동)        │  (수동, 점차 자동화)   │
        ├──────────────────────┼──────────────────────┤
        │        Q1            │         Q4           │
        │  단위 테스트           │  성능 및 부하 테스트   │
        │  컴포넌트 테스트        │  보안 테스트          │
        │  (자동)               │  '~성' 테스트 (도구)   │
        └──────────────────────┴──────────────────────┘
                        기술 위주
```

- **Q1**: 기술을 위한 것. 서비스가 동작하는지 검증하며 **자동화된 테스트**로 수행한다
- **Q2**: 비즈니스와 연관된다. 구현한 서비스가 **목적을 달성하는지** 확인하며 자동·수동 모두 가능하다
- **Q3**: 비즈니스와 연관된다. 기능적 요구사항 충족을 확인하며 탐색 테스트를 포함한다. 원래는 수동뿐이었지만 이제는 자동화가 가능해지고 있다
- **Q4**: 기술적 측면에서 **기존에 있던 것들이 제대로 동작하는지** 확인한다. Q1이 "만든 것이 동작하는가"라면, Q4는 "실제로 써봤을 때 의도대로 동작하는가"다. 보안 정책 적용, SLA 무결성, 오토스케일링 등이 여기 든다

축으로 읽으면 왼쪽(Q1·Q2)은 **제품을 지원하고 결함을 방지**하며, 오른쪽(Q3·Q4)은 **제품을 평가하고 결함을 찾아낸다**. 위쪽(Q2·Q3)은 사용자 기대를 만족시키는 **외적 품질**이고, 아래쪽(Q1·Q4)은 **내적 품질**이다.

> **참고**: 사분면은 **순서가 아니다**. 편의를 위한 분류일 뿐이며, 이 점이 사람들이 가장 많이 헷갈리는 부분이라고 리사 크리스핀이 직접 밝혔다. 티켓팅 시스템처럼 대규모 트래픽이 관건이라면 Q4의 성능 테스트부터 시작해도 된다.

### 테스트 피라미드

마이크 콘(Mike Cohn)의 "경험과 사례로 풀어낸 성공하는 애자일"에서 나온 모델로, 각 영역에 얼마나 시간을 쓸지, 유지보수가 얼마나 어려운지, 확신을 얼마나 더해주는지를 함께 보여준다.

```
        확신 / 범위  ▲
                    │        ┌───────────────────┐
                    │        │   UI · 종단 간 테스트 │
                    │     ┌──┴───────────────────┴──┐
                    │     │      서비스 테스트         │
                    │     │  계약 · 통합 · 컴포넌트    │
                    │  ┌──┴─────────────────────────┴──┐
                    │  │          단위 테스트            │
                    │  └───────────────────────────────┘
                    └────────────────────────────────────▶
                              속도 / 독립성 (유지보수성)
```

피라미드가 보여주는 것은 **확신·독립성·범위 사이의 트레이드오프**다. 작은 부분만 테스트하면 독립적이고 빠르지만 전체가 동작한다는 확신은 못 준다. 생태계 전체를 테스트하면 확신은 크지만 범위가 커지고 느리며 유지보수가 어렵다.

- **단위 테스트**: 코드의 작고 독립적인 단위(보통 클래스)를 검증한다. 단위 경계를 넘으면 **테스트 더블**(*test double* - 진짜 외부 엔티티처럼 보이지만 내가 제어하는 객체)을 쓴다. 피라미드의 기반이므로 가장 많아야 하고, TDD 도입을 권한다. 사분면 Q1에 해당한다. **이 책은 API의 내부가 아니라 외부 사용자 관점의 검증에 집중하므로 단위 테스트는 더 다루지 않는다**
- **서비스 테스트**: 여러 단위가 함께 동작하는지, 의도한 동작을 하는지, 애플리케이션이 회복성이 있는지 검증한다. 단위 테스트보다 확신이 크지만 범위가 넓고 독립성이 낮아 비용이 든다. 사분면 Q1·Q2·Q4에 걸친다
- **UI 테스트 = 종단 간(end-to-end) 테스트**: LAMP 스택 시절에는 프론트부터 백엔드까지 확인하는 유일한 방법이 웹 UI였다. 지금은 UI가 API 위에서 동작할 뿐이므로 **종단 간 테스트**라고 부른다. 가장 복잡하고 느리지만 전체가 함께 동작함을 검증한다. 사분면 Q2·Q3·Q4에 걸친다

어느 테스트도 다른 것보다 낫거나 못하지 않다. 피라미드는 **비율**을 안내할 뿐이다. 다만 확신이 크다는 이유로 종단 간 테스트에만 집중하면 **잘못된 안심**으로 이어지고, 피라미드가 뒤집힌 **아이스크림 콘** 형상이 만들어진다.

### ADR 가이드라인: 테스트 전략

- **결정사항**: API를 구현할 때 개발 절차에 어떤 테스트 전략을 도입할 것인가?
- **논의사항**: API와 관련된 모든 사람이 API의 동작을 **장기적으로 논의할 시간과 가용성**을 갖고 있는가?(소통이 안 되면 결정을 기다리느라 제품이 늦어진다) 그 전략을 효과적으로 쓸 기술과 경험이 있는가, 없다면 교육할 시간이 있는가? 조직이 이미 권장하는 다른 방법이 있는가?
- **권장사항**: 테스트 사분면과 테스트 피라미드를 함께 쓴다. 사분면은 **고객에게 올바른 제품을 전달하는 데** 가치가 크다. 비즈니스 부서의 도움을 못 받아 사분면을 제대로 못 쓰는 상황이라면, 최소한 피라미드만이라도 써서 **자동화 가능한 부분에 집중**한다. 어떤 경우든 제품의 방향을 정해줄 사람은 반드시 필요하다

## 3. 계약 테스트

계약 테스트(*contract test*)에는 **소비자**와 **생산자(제공자)** 두 엔티티가 있다. **계약**은 둘 사이의 상호작용을 정의한 것이다 - 소비자가 계약과 일치하는 요청을 보내면 생산자는 계약과 일치하는 응답을 돌려준다. 우리 사례에서 참석자 API가 생산자, 레거시 컨퍼런스 시스템이 소비자다.

### 왜 계약을 쓰는가

명세에 정의된 응답을 돌려주는 것이 중요하다고 1장에서 봤다. 상호작용의 정의를 **기록**해 두면 생산자가 그 정의를 따르게 되고 소비자는 그것으로 테스트를 만들 수 있다. **계약 테스트가 실패한다는 것은 생산자가 계약을 더 이상 지키지 못한다는 뜻이고, 곧 소비자 쪽이 깨진다는 신호다.**

계약에는 응답 정의가 들어 있으므로 **스텁 서버**(*stub server* - 로컬에서 실행되며 미리 정의된 응답을 돌려주는 서비스)를 생성할 수도 있다. 소비자가 생산자를 올바르게 호출하고 응답을 올바르게 해석하는지 검증할 때 쓴다. 계약 테스트는 로컬에서 실행할 수 있고(별도 서버를 띄워야 한다면 그건 서비스 테스트다), 계약이 바뀌면 양쪽이 그때마다 반영해 최신 계약을 계속 상호 준수하게 된다.

> **핵심 통찰**: 다른 테스트도 다 중요하지만 **계약 테스트가 비용 대비 효율이 가장 좋다**. 생산자가 계약을 구현하기로 동의하는 순간 소비자와 생산자를 **독립적으로** 개발할 수 있기 때문이다.

> **참고**: 계약 테스트는 **API가 스키마를 준수하는 것과 다르다**. 시스템이 OpenAPI 명세와 호환되는지 여부와 별개로, 계약은 각 당사자 사이의 상호작용에 대한 정의이며 **예시**를 제공한다.

### 계약의 구현

`/conference/{conference-id}/attendees`의 GET 요청 계약이다. 응답에 참석자 배열을 담은 `value` 속성이 정의되어 있다.

<details>
<summary>원서 예제 (Groovy, Spring Cloud Contract)</summary>

```groovy
Contract.make {
    request {
        description('Get a list of all the attendees at a conference')
        method GET()
        url '/conference/1234/attendees'
        headers {
            contentType('application/json')
        }
    }
    response {
        status OK()
        headers {
            contentType('application/json')
        }
        body(
            value: [
                $(id: 123456, givenName: 'James', familyName: 'Gough'),
                $(id: 123457, givenName: 'Matthew', familyName: 'Auburn')
            ]
        )
    }
}
```

</details>

```typescript
import { PactV3, MatchersV3 } from '@pact-foundation/pact';

const provider = new PactV3({ consumer: 'legacy-conference', provider: 'attendees-api' });

provider
  .given('컨퍼런스 1234에 참석자가 있다')
  .uponReceiving('Get a list of all the attendees at a conference')
  .withRequest({
    method: 'GET',
    path: '/conference/1234/attendees',
    headers: { Accept: 'application/json' },
  })
  .willRespondWith({
    status: 200,
    headers: { 'Content-Type': 'application/json' },
    body: {
      value: MatchersV3.eachLike({
        id: 123456,
        givenName: 'James',
        familyName: 'Gough',
      }),
    },
  });
```

이 하나의 계약에서 **생산자용 테스트**와 **소비자용 스텁 서버**가 함께 나온다.

```
┌────────────────────────┐                      ┌────────────────────────┐
│  레거시 컨퍼런스 시스템    │  API 호출로 참석자 관리 │   생성된 스텁 서버       │  ← 소비자용
│  [소프트웨어 시스템]      │ ───────────────────▶ │  [소프트웨어 시스템]     │
└────────────────────────┘                      └────────────────────────┘
              ▲
              │ 같은 계약에서 생성
              ▼
┌────────────────────────┐   테스트를 호출해     ┌────────────────────────┐
│  자동 생성한 계약 테스트   │   API를 검증         │      참석자 서비스       │  ← 생산자용
│  [소프트웨어 시스템]      │ ───────────────────▶ │  [소프트웨어 시스템]     │
└────────────────────────┘                      └────────────────────────┘
```

소비자는 개발에 쓸 스텁 서버를 갖고, 생산자는 올바른 상호작용을 구현하는지 확인할 테스트를 갖는다. 둘 다 배포됐을 때 자연스럽게 통합되므로 **통합에 드는 시간을 크게 아낀다**.

> **참고**: 계약을 시나리오 테스트에 쓰고 싶어질 수 있다(참석자를 추가한 뒤 목록을 가져와 확인하는 식). 프레임워크가 지원하긴 하지만 권장하지 않는다. **계약은 상호작용을 정의하는 것**이고, 그런 동작 검증은 컴포넌트 테스트의 몫이다.

> **참고**: 자동 생성한 테스트는 **실제로 실행 중인 API(생산자)를 대상으로** 실행하되, 그때 **외부 의존성은 테스트 더블로 바꿔야 한다.** 계약 테스트를 돌리면서 다른 서비스와의 통합까지 테스트되기를 바라지는 않을 것이다.

### 두 가지 계약 방법론

**생산자 계약**은 생산자가 직접 계약을 정의하는 방식이다. 조직 **외부**에서 API를 쓸 때 주로 쓴다. 외부용 API는 마이그레이션 계획 없이 단절적 변경을 낼 수 없으므로 무결성 유지가 최우선이고, 한 소비자가 전체 API에 영향을 주는 변경을 요청해 즉시 반영받는 일도 없어야 한다. 마이크로소프트 그래프 API가 대표적이다 - 전 세계 수천 기업이 쓰는데 개별 기업이 계약을 조정할 수는 없다(제안은 할 수 있지만, 검증과 신중한 테스트를 거치므로 빠르게 반영되지 않는다). **시작하기 쉽다는 것도 장점이다.**

**소비자 주도 계약**(*Consumer-Driven Contract - CDC*)은 소비자가 원하는 상호작용의 구현을 주도한다. 소비자가 새 기능이나 변경을 위해 계약을 제시하면, 생산자가 논의를 거쳐 반영하거나 거부한다. 상당히 **대화형이고 사교적인 절차**여서 소비자와 생산자 양쪽에 접근할 수 있어야 한다(대개 같은 조직).

### 사례 연구: CDC의 도입

CDC를 도입하면 레거시 컨퍼런스 시스템이 새 참석자 API 서비스에 **풀 리퀘스트를 제출**한다. 참석자 팀은 새 상호작용 요청을 리뷰하며 이것이 참석자 서비스가 해야 할 일인지 논의한다. 예를 들어 `PUT` 요청 계약을 제안받았는데 `PATCH`가 더 낫다고 보면 그 자리에서 결정한다.

**계약이 진짜 값어치를 하는 지점이 바로 여기다.** 이 논의는 양쪽이 문제를 파악하기 위한 것이고, 계약은 양쪽이 인정하고 동의한 바를 확인하는 수단이다. 합의되면 생산자가 계약을 프로젝트의 일부로 받아들여 이행한다.

팀마다 정확한 절차는 다르다 - 소비자가 계약을 쓸 때 그것을 수행하는 생산자 코드의 기본 구현까지 요구하기도 하고, 소비자가 TDD로 원하는 기능을 테스트한 뒤 풀 리퀘스트 전에 계약을 만들게 하기도 한다. **CDC의 핵심 개념과 패턴을 이해했다면 나머지는 구현 상세일 뿐이다.** 다만 계약 도입에는 **시간과 작성 비용이 든다**는 점을 인지해야 하며, OpenAPI 명세로부터 계약을 생성하는 도구를 찾아보는 것이 좋다.

### 프레임워크와 저장·발행

HTTP 계약 테스트에서는 **Pact**가 사실상의 기본 선택지다. 생태계가 풍부하고 여러 언어를 지원하며, **규약형 프레임워크**라 CDC를 하도록 설계되어 있다. 소비자가 쓴 테스트에서 계약을 생성하고, 그 데이터 표현이 **언어 중립적**이라는 점이 널리 쓰이는 이유다. **스프링 클라우드 계약**은 CDC와 생산자 계약을 모두 쓸 수 있지만 강제하지 않는데, 계약을 자동 생성하지 않고 손으로 쓰기 때문이다.

계약을 저장·발행하는 방법은 셋이다.

1. **생산자 코드와 함께 버전 관리 시스템에 저장** - 또는 빌드 시점에 아티팩토리 같은 산출물 저장소에 발행한다. 생산자가 어떤 계약을 수락할지 제어할 수 있지만, 대규모 조직에서는 **계약을 쓰는 API 서비스를 찾기 어렵다**
2. **한 곳(중앙 저장소)에 모아 저장** - 다른 API와의 상호작용을 쉽게 볼 수 있다. 단, 정리하지 않으면 **생산자가 이행할 의도가 없는 모듈에 계약이 쌓인다**
3. **브로커를 이용** - Pact의 브로커 제품이 중앙 저장소 역할을 한다. 생산자가 구현한 계약을 발행하므로 브로커는 **검증된 계약**을 제공하고, 네트워크 다이어그램 생성이나 CI/CD 통합으로 **누가 어떤 계약을 쓰는지**까지 보여준다. 가장 포괄적인 방법이며 호환 프레임워크를 쓴다면 이 방식을 권한다

### ADR 가이드라인: 계약 테스트

- **결정사항**: 계약 테스트를 쓸 것인가? 쓴다면 CDC인가 생산자 계약인가?
- **논의사항**: 개발자의 추가 학습이 필요한 테스트 계층을 하나 더 얹을 의사가 있는가? 계약을 중앙 관리할 것인가 프로젝트별로 나눌 것인가? 추가 도구와 훈련이 필요한가? API의 주 사용자는 누구이며, 조직 내부에서만 쓰는가? 기능 구현을 도와줄 의사가 있는 소비자가 있는가?
- **권장사항**: **계약 테스트 사용을 권한다.** 학습과 초기 설정 비용이 들지만, 상호작용을 정의하고 테스트해두면 통합 시점에 엄청난 시간을 아낀다. **대규모 외부 소비자에게 공개한다면 생산자 계약**이 중요하다. **내부용 API라면 CDC가 이상적**이며, 생산자 계약으로 시작해 나중에 CDC로 전환해도 된다. 계약 테스트를 도입하지 않기로 했다면, 생산자가 합의된 상호작용을 실제로 수행하는지 확인하고 소비자가 이를 테스트할 **대안을 반드시 마련해야 한다** - 요청과 응답이 의도대로인지 매우 주의 깊게 테스트해야 하고, 이 과정은 까다롭고 오래 걸린다

## 4. API 컴포넌트 테스트

컴포넌트 테스트는 **여러 단위가 협업해 만들어내는 동작**을 검증하며, 피라미드의 서비스 테스트에 속한다. API에 요청을 보내고 응답을 검증하는 것이 좋은 예다. 고수준에서 애플리케이션은 요청을 읽고, 인증(*authentication*)과 인가(*authorization*)를 수행하고, 본문을 해석하고, 비즈니스 로직을 돌린 뒤 응답을 구성한다. **이렇게 많은 단위가 얽히므로 버그가 정확히 어디 있는지 찾기는 어려워진다.**

계약 테스트와 다른 점은 **서비스가 올바른 동작을 수행하는지 내가 확인해야 한다**는 것이다. 새 참석자를 만드는 과정을 테스트한다면 서비스가 최종적으로 (모조) 데이터베이스를 호출하는지까지 검증한다. 컴포넌트 테스트는 **외부 의존성을 호출해서는 안 된다.**

API라면 이런 것들을 검증한다.

- 요청이 발생했을 때 **올바른 상태 코드**를 돌려주는가?
- API가 **올바른 데이터**를 돌려주는가?
- 빈 파라미터나 널 값을 전달하면 서비스가 요청을 **거부**하는가?
- XML 콘텐츠를 요청하면 **원하는 형식**으로 돌려주는가?
- **올바른 자격이 없는** 사용자가 요청하면 어떤 응답이 돌아오는가?
- **빈 데이터셋**이면 404인가, 빈 배열인가?
- 리소스를 새로 만들면 **`Location` 헤더**에 새 리소스 경로가 담기는가?

이 사례들은 사분면의 두 곳에 걸친다 - API가 응답을 돌려주는지 확인하는 **Q1**, 그 응답이 올바른지 검증하는 **Q2**다.

> **핵심 통찰**: 계약 테스트를 쓸 수 없을 때는 컴포넌트 테스트로 명세상의 동작을 검증해야 한다. 하지만 이상적이지 않다 - **초기에 오류가 나기 쉽고 작성이 지루하다.** API의 상호작용은 계약으로 표현해 테스트를 자동 생성하는 편이 낫다.

### 사례 연구: 컴포넌트 테스트로 동작 검증하기

`/conference/{conference-id}/attendees`를 검증한다. 외부 데이터베이스 의존성은 **모조 DAO**로 대체한다.

```
┌──────────────────┐   요청   ┌────────────────────┐   내부 라우팅   ┌────────────────┐
│  테스트 클라이언트  │ ──────▶ │    API 컨트롤러      │ ────────────▶ │   모조 DAO      │
│ [소프트웨어 시스템] │         │  [패키지/모듈]        │               │  [패키지/모듈]   │
└──────────────────┘         └────────────────────┘               └────────────────┘
        └──────────────────── 컴포넌트 테스트 범위 ──────────────────────────┘
```

검증 항목은 셋이다 - 성공하면 200(OK), 권한이 없으면 403(Forbidden), 참석자가 없으면 빈 배열.

## 5. API 통합 테스트

여기서 통합 테스트란 **개발 중인 모듈과 외부 의존성 사이의 경계를 넘는** 테스트다. 서비스 테스트의 일종이며, 경계를 넘는 통신이 제대로 이뤄지는지 본다.

- 상호작용이 올바른가 - REST라면 올바른 URL을 호출하는지, 응답 본문이 올바른지
- 통합된 단위가 **돌아온 응답을 올바르게 처리하는지**

우리 사례에서는 레거시 컨퍼런스 시스템이 새 참석자 API에 올바른 요청을 보내고 응답을 제대로 처리하는지 확인해야 한다.

### 스텁 서버를 쓰는 이유와 방법

계약 테스트를 쓴다면 **자동 생성된 스텁 서버**가 최선이다. 로컬에서 돌릴 수 있고 정확한 데이터를 돌려준다. 하지만 마이크로소프트 그래프 API 같은 외부 API가 상대라면 그럴 수 없으니, 가장 단순한 방법은 **스텁 서버를 직접 만드는 것**이다. 대개 어렵지 않다.

문제는 **직접 만든 스텁이 부정확하기 쉽다**는 점이다. 아래 손으로 쓴 응답에서 오류를 찾아보자.

```json
{
  "values": [
    { "id": 123456, "givenName": "James",   "familyName": "Gough" },
    { "id": 123457, "givenName": "Matthew", "familyNane": "Auburn" },
    { "id": 123456, "givenName": "Daniel",  "familyName": "Bryant" }
  ]
}
```

`id` 값이 중복되어 있고 `familyNane`에 오타가 있다. 이런 실수를 피하는 방법이 **레코더**다. 실제 엔드포인트에 대한 요청과 응답을 기록해 스텁용 매핑 파일을 만든다.

```
┌────────────────────┐   프록시   ┌──────────────┐   API 호출   ┌──────────────────┐
│ 레거시 컨퍼런스 시스템 │ ─────────▶│    레코더     │ ───────────▶│   참석자 서비스     │
└────────────────────┘           │ [프록시 레코더] │             │ [소프트웨어 시스템] │
                                 └──────┬───────┘             └──────────────────┘
                                        │ 스텁(매핑 파일)을 생성
                                        ▼
                                 ┌──────────────┐
                                 │   스텁 서버    │
                                 └──────────────┘
```

생성된 매핑 파일은 **생성 시점의 데이터를 정확히** 표현한다. 스텁 서버는 요청이 오면 매핑에서 일치하는 요청을 찾아 대응하는 응답을 돌려준다. 자바 기반이지만 언어 중립적으로 쓸 수 있는 **WireMock**이 대표적이고, 타입스크립트로 작성된 유사 도구도 있다.

> **실무 팁**: 레코딩을 쓴다면 **기록을 최신으로 유지**해야 하고, **프로덕션에서 기록했다면 매핑 파일에 PII가 들어가지 않았는지** 반드시 확인해야 한다.

### ADR 가이드라인: 통합 테스트

- **결정사항**: API 테스트에 통합 테스트를 도입할 것인가? API가 다른 서비스와 통합되어 있다면 어느 정도로 할 것인가?
- **논의사항**: 통합 테스트 없이 모조 응답만으로 충분하다는 확신이 있는가? 스텁 서버를 만든다면 요청·응답을 정확히 만들 수 있는가, 아니면 기록해야 하는가? 스텁을 최신으로 유지하고 잘못됐을 때 바로 알아챌 수 있는가?(**스텁이 낡으면 테스트는 통과하는데 프로덕션에서 실패한다**)
- **권장사항**: **계약 테스트로 자동 생성한 스텁 서버**를 쓰는 것이 최선이고, 그럴 수 없다면 **상호작용을 기록해 활용**하는 것이 차선이다. 로컬에서 실행 가능한 통합 테스트를 확보하면 특히 **리팩터링할 때** 통합이 여전히 잘 동작한다는 확신을 얻는다

통합 테스트의 근본적 한계는 **그 상호작용의 정의가 어느 한 시점의 스냅샷**이라는 점이다. 구성한 환경은 변화에 따라 저절로 갱신되지 않는다.

### 테스트 컴포넌트의 컨테이너화: Testcontainers

애플리케이션을 컨테이너 이미지로 빌드하는 것이 보편화되면서, 통합 대상 애플리케이션도 대개 컨테이너로 존재한다. 그 이미지를 **로컬에서 실행해 테스트에 쓸 수 있고, 프로덕션에서도 같은 이미지를 돌린다**. **Testcontainers**는 테스트 프레임워크와 통합되어 컨테이너의 시작·종료 수명주기를 관리해주는 라이브러리다.

### 사례 연구: Testcontainers를 이용한 통합 검증

**첫째, gRPC 스텁 서버**. 참석자 API가 REST와 gRPC를 모두 지원할 계획인데 REST를 먼저 만들기로 했다. gRPC 개발에 적극적인 개발자들을 위해 미리 정의된 응답을 돌려주는 gRPC 스텁을 만들고 **컨테이너로 패키징해 발행**했다. 이제 개발자들은 로컬에서 그 컨테이너를 띄워 경계를 넘는 테스트를 할 수 있다.

**둘째, 데이터베이스 통합**. 인메모리 DB(H2 등)로 모조 데이터베이스를 구성할 수도 있지만, 그건 **실제 DB와 구현이 같을 것이라는 가정**을 깔고 있다. 프로덕션과 같은 버전의 실제 인스턴스를 쓰면 그 가정 없이 신뢰할 수 있는 테스트가 된다.

```
┌────────────────────────────────┐
│          참석자 [소프트웨어]       │
│  ┌──────────────────────────┐  │  CRUD [SQL, 아웃 오브 프로세스]   ┌──────────────────────┐
│  │   DAO [패키지/모듈]         │──┼──────────────────────────────▶│ 데이터베이스           │
│  └──────────────────────────┘  │                                │ [컨테이너: PostgreSQL] │
└────────────────────────────────┘                                └──────────────────────┘
```

카프카·레디스·엔진엑스처럼 흔한 외부 서비스도 이 방식의 이득을 본다. 테스트 실행 시간은 길어지지만 **통합 테스트는 원래 수가 적으므로**, 늘어난 시간 대비 확신은 충분히 남는 트레이드오프다.

여기서 두 가지 의문이 생긴다.

- **이건 통합 테스트인가 종단 간 테스트인가?** - 테스트가 **통합의 경계 안에서만** 이뤄진다면 종단 간이 아니다. 컨테이너가 제대로 동작하는지 확인하는 것은 (그 이미지가 내 도메인이 아니라면) 내 일이 아니다. 카프카 브로커에 메시지를 보내는 구문은 실행하되, 토픽을 구독해 전달을 확인하지는 않는다 - 그건 카프카를 믿는 영역이고, 정말 검증해야 한다면 종단 간 테스트로 한다
- **왜 계약 대신 이걸 쓰지 않는가?** - 실제 인스턴스를 쓸 수 있다는 장점이 있지만, **계약은 스텁 서버 이상의 것**(테스트·통합·협업)을 제공하므로 대체 관계가 아니다

## 6. 종단 간 테스트

종단 간 테스트는 서비스와 그 의존성이 **함께 어우러져** 의도대로 동작하는지 본다. 요청이 목적지까지 제대로 전달되고 모든 경로를 흘러 소비자가 올바른 응답을 받는지 검증한다. 우리 사례라면 레거시 컨퍼런스 시스템·새 참석자 서비스·데이터베이스를 함께 테스트하는 것이다.

**종단 간 테스트에도 경계가 필요하다.** 조직 도메인 밖에 있고 외부 조직이 제공하는 엔티티는 스텁으로 대체해도 된다. 참석자 서비스가 AWS S3를 쓴다면 네트워크 문제나 외부 서비스 장애가 테스트를 흔들 수 있고, 테스트가 그 엔티티를 쓰지 않는다면 굳이 띄울 이유도 없다. 참석자 서비스의 종단 간 테스트에는 데이터베이스와 참석자 서비스가 필요하지만 **레거시 컨퍼런스 시스템은 필요 없다**.

```
┌──────────────────┐  API 호출  ┌──────────────┐  인 프로세스  ┌────────────┐  CRUD [SQL]  ┌──────────────────────┐
│   테스트 드라이버   │ [HTTP]    │  API 컨트롤러  │ ───────────▶ │    DAO      │ ───────────▶ │ 데이터베이스           │
│ 테스트 실행을 조율  │ ────────▶ │              │              │            │              │ [컨테이너: PostgreSQL] │
└──────────────────┘           └──────────────┘              └────────────┘              └──────────────────────┘
        └──────────────────────────── 종단 간 테스트 범위 ────────────────────────────────────────┘
```

> **실무 팁**: 종단 간 테스트에는 **실제와 유사한 페이로드**를 써야 한다. 작고 간결한 페이로드로 테스트하고 배포했더니, 소비자가 버퍼 지원 크기보다 큰 페이로드를 보내 API가 실패하는 사례를 저자들은 여러 번 목격했다. 종단 간 테스트는 **소비자가 실제로 API를 쓰는 방식**에 최대한 가까워야 한다.

> **참고**: 외부에 공개할 API에 소비자가 여럿이라면 **서드파티 UI와 그 동작을 복제하려 들지 말자.** 내 도메인 경계 바깥의 무언가를 흉내 내느라 시간만 쓰게 된다.

### 종단 간 테스트의 종류

- **시나리오 테스트(Q3)**: 전형적인 사용자 행동을 테스트하는 가장 보편적인 형태다. **BDD**(*Behavior Driven Development*)를 도입하면 테스트 작성에 도움이 되고, 비즈니스 대비 사용자 스토리를 쓰는 방법으로도 좋다. 컨퍼런스 예시로는 "참석자가 세션에 등록하면 세션 정보 조회 시 참석자 수가 증가한다"가 된다. 시나리오 테스트의 장점은 **어떤 컴포넌트가 프로덕션보다 느려도 상관없다**는 것이다 - 중요한 건 올바른 동작과 결과다
- **성능 테스트(Q4)**: 반대로 **프로덕션과 아주 유사한 환경**에서 해야 한다. 환경이 다르면 결과가 실제 동작을 의미하지 않는다. 같은 하드웨어에 배포해야 한다는 뜻이라 리소스 사정에 따라 어려울 수 있다. 초점은 **목표 SLO 안에서 요청을 서비스하는지** 검증하는 것이며, 실수로 블로킹 코드가 들어가 갑자기 지연이 생기는 일을 잡아낸다. 볼륨이 중요하다면 원하는 부하를 감당하는지 본다 - 개틀링·JMeter·Locust·k6 같은 도구가 있다
- **보안**: TLS가 적용됐는지, 적절한 인증 메커니즘이 구현됐는지도 확실히 검증한다. **테스트 과정에서 보안 기능을 꺼서는 안 된다.** 껐다가는 테스트가 사용자 행위를 제대로 표현하지 못하고 엉뚱한 지표를 얻는다

### ADR 가이드라인: 종단 간 테스트

- **결정사항**: 종단 간 테스트를 자동화할 것인가?
- **논의사항**: 종단 간 테스트를 위한 구성이 얼마나 복잡한가? 어떤 종단 간 테스트가 필요하며 그것이 충분한 가치가 있는지 이해하고 있는가? 특정 요구사항 때문에 더 고수준의 테스트를 추가해야 하는가?
- **권장사항**: **가장 중요한 사용자 행위에 대해 최소한의 종단 간 테스트**를 수행한다. 그러면 사용자에게 영향을 줄 변화를 개발 과정에서 가장 빨리 감지할 수 있다. 로컬 실행이 이상적이고, 안 되면 빌드 파이프라인에 넣는다. 자동화할 수 없다면 **수동 테스트 설명서**가 필요하며 릴리스 전 테스트 환경에서 수행해야 한다 - 다만 이런 수동 테스트는 릴리스와 가치 전달을 상당히 느리게 만든다

## 요약

- 테스트의 기본에 충실하고, API의 중요한 기능은 단위 테스트로 덮는다
- **테스트 사분면**은 기술과 비즈니스의 서로 다른 관심사를 함께 보게 해주고, **테스트 피라미드**는 각 층의 비율을 안내한다. 확신이 크다는 이유로 종단 간에만 몰리면 아이스크림 콘이 된다
- **계약 테스트는 비용 대비 효율이 가장 좋다.** 하나의 계약에서 생산자용 테스트와 소비자용 스텁 서버가 함께 나오므로 양쪽을 독립적으로 개발할 수 있다. 외부 공개 API는 생산자 계약, 내부 API는 CDC가 이상적이다
- **컴포넌트 테스트**는 여러 단위가 협업해 만드는 동작을 검증하되 외부 의존성은 호출하지 않는다
- **통합 테스트**는 경계를 넘는 통신을 검증한다. 스텁은 자동 생성 > 레코딩 > 손으로 작성 순으로 신뢰할 만하며, **Testcontainers**로 실제 인스턴스를 띄우면 인메모리 대체물의 가정을 걷어낼 수 있다
- **종단 간 테스트**는 가장 중요한 사용자 행위에 최소한으로 적용하고, 실제와 유사한 페이로드를 쓰며, 보안 기능을 끄지 않는다
- 아무리 사전 테스트를 많이 해도 **프로덕션에서 동작을 확인하는 것보다 나은 테스트는 없다** (5장)

## 다른 챕터와의 관계

- **0장**: ADR-001의 결론 "레이턴시가 생기므로 테스트가 필요하다"를 이 장이 이어받는다
- **1장**: OpenAPI 명세가 **형태만** 서술하고 의미를 담지 못한다는 한계가 계약 테스트의 존재 이유다. 명세로부터 계약을 생성하는 도구도 여기서 연결된다
- **3장**: 다음 단계는 테스트를 마친 API를 게이트웨이로 프로덕션에 노출하는 것이다
- **5장**: SLI·SLO의 정의와 **프로덕션에서의 테스트**(카나리·트래픽 미러링)가 이 장의 연장선이다
- **6장**: 종단 간 테스트에서 보안을 끄지 말라는 원칙이 위협 모델링으로 확장된다
