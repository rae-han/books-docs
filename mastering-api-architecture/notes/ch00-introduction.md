# Chapter 0: Introduction (API 아키텍처 설계 여정을 시작하며)

## 핵심 질문

API란 정확히 무엇이며, 왜 "인 프로세스"와 "아웃 오브 프로세스"를 구분해야 하는가? 3계층 아키텍처를 API 중심으로 다시 모델링하면 무엇이 보이는가? 그리고 아키텍처가 변해 가는 동안 그 변화를 어떻게 남기고 소통할 것인가?

## 1. 아키텍처는 목적지가 없는 여정이다

장거리 운전 중에 "아직도 도착 못 했어?"라는 질문을 받으면 GPS를 보고 도착 시간을 말해줄 수 있다. 그런데 API 기반 아키텍처로 가는 여정에는 그런 도착 시간이 없다. 아키텍처 GPS가 있다 한들 목적지 자체가 정해져 있지 않기 때문이다.

기술이 어떻게 바뀔지는 예측할 수 없다. 서비스 메시가 얼마나 널리 쓰이게 될지 미리 알 수는 없지만, 그 가능성을 알고 나면 기존 아키텍처를 그것으로 개선할 생각을 하게 된다. 아키텍처를 흔드는 것은 기술만이 아니다. 새로운 비즈니스 요구사항과 규제도 방향을 바꾼다.

> 아키텍처는 미래를 위해 전략적으로 계획할 수 있을 것 같지만, 소프트웨어 개발 생태계는 지속적으로 변화하기 때문에 계획을 세우기가 어렵다. 변화를 피해갈 수는 없고 오히려 이용해야 한다.<br>— 『진화적 아키텍처』(닐 포드 외, 한빛미디어, 2023)

이렇게 변화를 위험 요소가 아니라 전제로 받아들이고, 점진적으로 가치를 전달하면서 아키텍처를 개선해 나가는 방식이 **진화적 아키텍처**(*evolutionary architecture*)다.

API도 그 자체로 진화적이다. 통합하는 시스템과 서비스가 늘어날수록 API는 계속 바뀌어야 한다. 그런데 대부분의 개발자는 고객 관점에서 API의 재사용을 고민하기보다 **하나의 기능에만 집중해서** 서비스를 구현해 왔다. 그 반대편에 있는 것이 **API 우선 설계**(*API-first design*)다. 서비스의 기능을 고객 중심으로 바라보고 API를 먼저 설계하는 방법이며, 이때 소비자는 모바일 앱일 수도, 다른 서비스일 수도, 외부 고객일 수도 있다.

> **핵심 통찰**: API 주도 아키텍처는 언제든 시작할 수 있다. 기존 시스템을 운영 중이라면 아키텍처를 진화시켜 API 사용을 촉진하면 되고, 새로 시작한다면 처음부터 API 우선으로 설계하면 된다. 늦었다는 이유로 미룰 일이 아니다.

## 2. API란 무엇인가

API(*Application Programming Interface - 애플리케이션 프로그래밍 인터페이스*)는 80년대에 등장한 용어다. 오래 존재한 용어가 대개 그렇듯 남용되었고 문제 영역마다 다른 의미를 갖게 되었다. 이 책은 API를 다음과 같이 정의한다.

- **API는 기반 구현에 대한 추상화를 표현한다** — 소비자는 내부가 어떻게 만들어졌는지 몰라도 된다
- **API는 타입을 정의하는 명세로 표현한다** — 개발자가 명세를 이해할 수 있고, 도구를 이용해 여러 언어로 소비자를 구현할 수 있다
- **API는 정보 교환을 효과적으로 모델링하기 위한 의미 또는 행위로 정의한다** — 데이터 구조만이 아니라 "무엇을 할 수 있는가"를 담는다
- **효율적으로 설계된 API는 고객이나 서드파티로 확장 가능하다** — 비즈니스 통합의 통로가 된다

### 인 프로세스 API와 아웃 오브 프로세스 API

API는 호출이 같은 운영체제 프로세스 안에서 처리되는지에 따라 둘로 나뉜다.

- **인 프로세스(*in-process*) API**: 자바의 한 클래스가 다른 클래스의 메서드를 호출하는 것처럼, 호출을 유발한 프로세스 **안에서** 처리된다. 교환 조건이 코드를 작성하는 시점에 정해지므로 **컴파일 타임에 안전**하다
- **아웃 오브 프로세스(*out-of-process*) API**: .NET 애플리케이션이 HTTP 라이브러리로 외부 REST API를 호출하는 것처럼, **다른 프로세스**가 처리한다. 보통 로컬 네트워크·VPC 네트워크·인터넷 등 네트워크를 통해 데이터가 오간다

이 책이 집중하는 것은 아웃 오브 프로세스 API다. 다만 아키텍트가 실제로 자주 마주하는 요구는 **인 프로세스 API를 아웃 오브 프로세스 API로 재구성하는 것**이다. 사례 연구가 바로 그 과정을 따라간다.

## 3. 사례 연구: 컨퍼런스 시스템

컨퍼런스 시스템을 사례로 고른 이유는 도메인이 이해하기 쉬우면서도 진화적 아키텍처를 모델링하기에 충분한 복잡도를 갖기 때문이다. 외부 고객이 참석자 계정을 만들고, 컨퍼런스 세션을 살펴보고, 참석을 예약하는 시스템이다.

### C4 컨텍스트 다이어그램 (그림 0-1)

```
┌──────────────────┐                                  ┌──────────────────────┐
│      고객         │   브라우저로 컨퍼런스 세션 예약    │   컨퍼런스 시스템      │
│     [사람]        │ ───────────────────────────────▶ │  [소프트웨어 시스템]   │
│ 참석자 또는       │                                  │ 고객이 세션을 확인하고 │
│ 잠재적 참석자     │                                  │ 예약을 진행하게 한다   │
└──────────────────┘                                  └──────────────────────┘
```

### C4 컨테이너 다이어그램 (그림 0-2)

```
┌────────┐  사용   ┌──────────────┐  HTTP로   ┌────────────────────┐  SQL로  ┌──────────────┐
│  고객   │ ──────▶ │ 웹 애플리케이션 │ API 호출  │ 컨퍼런스 애플리케이션 │ 기록·조회│  데이터베이스  │
│ [사람]  │         │  [컨테이너]    │ ────────▶ │     [컨테이너]      │ ──────▶ │  [컨테이너]   │
└────────┘         │ 웹사이트 UI    │           │ 참석자·세션 관리     │         │ 단일 스토어    │
                   └──────────────┘           └────────────────────┘         └──────────────┘
```

### C4 컴포넌트 다이어그램 (그림 0-3)

```
┌──────────────┐
│ 웹 애플리케이션 │
└──────┬───────┘
       │ API 호출 [HTTP, 아웃 오브 프로세스]
       ▼
┌────────────────────────────────────────────────┐
│               API 컨트롤러                       │
│  REST 연결을 조회하고 적절한 서브시스템으로 라우팅   │
└───┬──────────────┬──────────────┬───────────────┘
    │ 인 프로세스   │ 인 프로세스   │ 인 프로세스
    ▼              ▼              ▼
┌────────┐    ┌────────┐    ┌────────┐
│ 참석자  │    │  예약   │    │  세션   │
└───┬────┘    └───┬────┘    └───┬────┘
    │ SQL         │ SQL         │ SQL  [아웃 오브 프로세스]
    └─────────────┴─────────────┘
                  ▼
           ┌──────────────┐
           │  데이터 스토어  │
           └──────────────┘
```

**API 컨트롤러**는 UI에서 들어오는 모든 트래픽을 받아 요청을 어디로 보낼지 결정한다. 네트워크로 전송되는 데이터 표현을 코드상의 객체로 **마셜링**(*marshaling*)하는 역할도 한다. 이 컴포넌트는 이음부, 즉 **프론트 컨트롤러(*front controller*) 패턴**처럼 동작하며, 3장에서 이것을 프로세스 **밖으로** 끄집어내는 것이 바로 API 게이트웨이 이야기다.

**참석자·예약·세션** 컴포넌트는 요청을 쿼리로 번역해 데이터베이스에 SQL을 실행한다. 기존 아키텍처에서 데이터베이스는 예약과 세션 사이의 제약 같은 **관계까지 정의하는** 아주 중요한 컴포넌트다.

여기서 중요한 관찰은 호출의 성격이다. 웹 애플리케이션 → API 컨트롤러는 **아웃 오브 프로세스** 호출이지만, 컨퍼런스 애플리케이션 경계 **안**의 모든 상호작용은 **인 프로세스** 호출이다.

### 시스템을 바꿔야 하는 이유

컨퍼런스 주최자가 아키텍처 변화를 요구하는 개선사항 3가지를 들고 왔다.

1. **모바일 애플리케이션**을 구현하고 싶다
2. 시스템을 **글로벌 시장**에 출시해 1년에 한 번이 아니라 수십 번의 컨퍼런스를 진행하고 싶다. 이를 위해 외부 **논문 공모(*Call for Papers - CFP*) 시스템**과 통합해 발표자와 발표 신청서를 관리해야 한다
3. 사설 데이터센터에서 **클라우드 플랫폼으로 이전**하고 싶다

목표는 기존 프로덕션 시스템에 지장을 주지 않고, 한 번에 전부 재개발하지도 않으면서 이 요구를 지원하는 것이다.

## 4. 다계층 아키텍처에서 API 모델링으로

사례의 출발점은 UI · 서버 측 처리 계층 · 데이터 스토어로 된 흔한 3계층 아키텍처다. 진화를 논의하려면 API 요청이 컴포넌트에서 어떻게 처리되는지 생각할 모델이 필요하고, 그 모델은 퍼블릭 클라우드·데이터센터 가상 머신·하이브리드에서 모두 통해야 한다.

그 도구가 **트래픽의 추상화**다. API 소비자와 API 생산자 사이의 아웃 오브 프로세스 상호작용을 트래픽으로 보면, SOA나 마이크로서비스 같은 접근법에서 결정적인 질문이 드러난다. **API 트래픽과 컴포넌트 간 통신 방식을 이해하느냐 못 하느냐에 따라 디커플링의 장점을 얻을 수도 있고, 유지보수가 악몽이 될 수도 있다.**

> **참고**: 트래픽 패턴은 원래 데이터센터 엔지니어가 데이터센터 내부와 저수준 애플리케이션 사이의 네트워크 교환을 서술할 때 쓰던 개념이다. API 수준에서는 애플리케이션 그룹 사이의 흐름을 서술하는 데 쓴다. 이 책은 애플리케이션·API 수준의 트래픽 패턴만 다룬다.

### 사례 연구: 첫 번째 진화적 단계 (그림 0-4)

참석자 컴포넌트를 레거시 컨퍼런스 시스템의 패키지/모듈이 아니라 **독립적인 서비스**로 리팩터링한다. 그러면 트래픽 흐름이 두 개로 나뉜다.

```
┌────────┐                          ┌────────────────────────┐                    ┌──────────────────┐
│  고객   │  수직(north-south) 트래픽 │  레거시 컨퍼런스 시스템   │ 수평(east-west)     │  참석자 서비스     │
│ [사람]  │ ───────────────────────▶ │  [소프트웨어 시스템]     │ ─────────────────▶ │ [소프트웨어 시스템] │
└────────┘  브라우저로 세션 예약      │                        │  API 호출로 참석자   │ 참석자를 관리하는  │
                                     └────────────────────────┘  관리              │  API 기반 서비스   │
                                                                                   └──────────────────┘
```

- **수직 트래픽(*north-south*)**: 고객 ↔ 레거시 컨퍼런스 시스템. 인터넷을 통해 **유입되는** 흐름이며, 네트워크가 외부에 노출된다는 뜻이다. 따라서 수직 트래픽을 처리하는 모든 컴포넌트는 **클라이언트의 신원을 확인하고 적절한 조치를 취한 뒤에** 내부로 트래픽을 넘겨야 한다 (7장)
- **수평 트래픽(*east-west*)**: 레거시 시스템 ↔ 참석자 서비스. 애플리케이션 그룹 **안에서** 일어나는 서비스 대 서비스 통신이다. 요청의 출발점이 우리 인프라 안이라면 어느 정도 신뢰할 수 있지만, **그렇다고 보안을 면제받는 것은 아니다**

### API 인프라스트럭처와 트래픽 패턴

트래픽을 제어하고 조율하는 일을 **트래픽 관리**(*traffic management*)라 하고, API 기반 아키텍처에는 이를 담당하는 핵심 인프라 컴포넌트가 둘 있다.

- **수직 트래픽 → API 게이트웨이** (3장)
- **수평 트래픽 → 쿠버네티스·서비스 메시** (4장). 이들은 네트워크 추상화로 요청을 서비스에 전달하므로 서비스가 관리되는 환경 안에서 실행되어야 한다. 인프라 대신 애플리케이션이 **서비스 발견**(*service discovery*)으로 직접 수평 트래픽을 처리하기도 한다

> **핵심 통찰**: 수직/수평이라는 구분은 방향을 가리키는 말이 아니라 **책임의 구분**이다. 어디서 신원을 확인하고, 어디서 라우팅하고, 어디서 장애를 격리할지가 이 축을 따라 갈린다. 3장과 4장이 각각 이 두 축을 맡는다.

## 5. 사례 연구 로드맵

책 전체에서 사례가 어떻게 바뀌어 가는지 미리 정리하면 다음과 같다.

- **1장**: 참석자 API의 설계와 명세. 버저닝과 성능을 위한 모델링
- **2장**: 참석자 서비스를 검증하는 계약 테스트·컴포넌트 테스트, Testcontainers를 이용한 통합 테스트
- **3장**: API 게이트웨이로 참석자 서비스를 소비자에게 노출. 쿠버네티스 위의 게이트웨이로 시스템 개선
- **4장**: 서비스 메시로 세션 기능을 레거시 시스템에서 분리. 라우팅·관측·보안에서 메시의 역할
- **5장**: 기능 플래그로 배포와 릴리스의 결합을 끊고, 아르고 롤아웃으로 참석자 서비스 배포
- **6장**: 참석자 서비스에 위협 모델링과 OWASP 권고 반영
- **7장**: 인증과 인가를 참석자 서비스에 구현
- **8장**: 참석자 서비스의 도메인 경계 확립과 서비스 패턴
- **9장**: 참석자 서비스를 클라우드로 이전
- **10장**: 전체 변화를 되짚고 조직·미래 기술을 정리

## 6. C4 다이어그램의 활용

C4 모델(https://c4model.com)은 아키텍처·컨텍스트·이해당사자 간 상호작용을 소통하기 위한 문서화 표준이다. 왜 UML이 아닐까? UML은 소프트웨어 아키텍처를 설명하는 요소가 풍부하지만, **그 요소들을 아키텍트와 개발자가 잘 기억하지 못한다**는 것이 문제다. 결국 사람들은 금세 박스/원/다이아몬드로 돌아가고, 기술 내용을 논하기 전에 다이어그램 자체의 구조를 이해하느라 시간을 쓴다. C4는 상세 수준이 다른 몇 장의 간소한 다이어그램을 제공한다.

- **컨텍스트 다이어그램**(그림 0-1): 기술직군과 비기술직군 **모두**를 위한 고수준 컨텍스트를 설정한다. 아키텍처 대화는 곧바로 저수준 상세로 빠지기 쉬운데, 컨텍스트를 먼저 맞춰두면 오해를 바로잡느라 쓸 수개월을 아낄 수 있다
- **컨테이너 다이어그램**(그림 0-2): 아키텍처의 주요 구성요소를 기술적으로 분리해 서술한다. C4에서 컨테이너란 "전체 시스템이 동작하는 데 필요한 어떤 것"(예: 컨퍼런스 데이터베이스)이다
- **컴포넌트 다이어그램**(그림 0-3): 각 컨테이너의 역할과 책임, 내부 상호작용을 정의한다. 새 프로젝트에 합류해 코드를 읽을 때 **어디를 봐야 하는지** 알려주는 지도 역할을 한다

> **참고**: 그림 0-2의 컨퍼런스 애플리케이션 컨테이너는 그냥 "소프트웨어"라고만 적혀 있다. 보통 C4 컨테이너에는 "자바 스프링 애플리케이션"처럼 종류를 더 자세히 적는다. 이 책은 특정 솔루션을 보여줄 필요가 없으면 기술 명세를 일부러 뺀다 — API와 모던 애플리케이션의 장점이 바로 솔루션 선택의 유연성이기 때문이다.

## 7. ADR: 결정의 동기를 남기기

영국 M62 고속도로를 운전하다 보면 3차선 도로가 갑자기 갈라지면서 한가운데에 15에이커 농장(스캇 홀 농장)이 자리 잡고 있는 광경을 보게 된다. 지역에 전해오는 이야기로는 고집 센 땅 주인이 팔기를 거부해서 엔지니어들이 그냥 우회했다는 것이다. 50년 뒤 다큐멘터리가 밝힌 진짜 이유는 **그 지대의 지질학적 결함**이었다. 그렇게 만들 수밖에 없었던 것이다.

사람들은 무언가가 왜 그렇게 되었는지 모르면 루머와 농담과 비판으로 빈칸을 채운다. 소프트웨어 아키텍처에도 우회해야 할 제약이 많으니, 결정을 투명하게 내리고 **기록**하는 일이 중요하다.

> 프로젝트가 살아있는 동안 추적하기 가장 어려운 것 중 하나는 어떤 의사결정이 내려진 동기다. 프로젝트에 새로 참여한 사람은 과거의 어떤 의사결정으로 인해 당황하거나, 이해를 못 하거나, 기뻐하거나, 혹은 짜증을 낼 수도 있다.<br>— 마이클 나이가드(Michael Nygard), ADR 개념의 창시자

**ADR**(*Architecture Decision Record - 아키텍처 의사결정 기록*)에는 네 개의 핵심 섹션이 있다.

- **상태(*Status*)**: 제안 상태로 만들어지며, 논의를 거쳐 수렴되거나 거부된다. 나중에 새 ADR로 대체할 수도 있다
- **컨텍스트(*Context*)**: 상황을 설정하고 결정해야 할 문제나 범위를 서술한다. 블로그 포스트 같은 장문을 컨텍스트 자리에 넣지는 않는다(첨부는 가능하다)
- **결정사항(*Decision*)**: 어떤 계획을 세웠고 어떻게 실행할지 명확히 정의한다
- **결론(*Consequences*)**: 모든 결정은 아키텍처적 결과나 트레이드오프로 이어진다. 때로는 상당히 잘못된 방향으로 이어지기도 한다

ADR을 리뷰할 때는 기록된 결정에 동의하는지, 놓친 대안은 없는지 확인한다. 대안이 발견되어 ADR이 거부되더라도 **그 기록의 가치는 그대로 남으므로** 대부분의 팀은 거부된 ADR도 관점의 변화를 포착하기 위해 보관한다.

> **참고**: ADR은 언제 쓰는가? 먼저 충분히 논의하고 **그 결과를 기록**하는 편이 낫다. ADR을 넓은 커뮤니티에 공개하면 유관 부서를 넘어선 피드백을 받을 수 있다.

### 사례 연구 ADR: 참석자 기능 분리

그림 0-4의 진화적 단계는 큰 변화이므로 ADR이 필요하다.

**ADR-001: 레거시 컨퍼런스 시스템으로부터 참석자 기능을 분리**

- **상태**: 제안
- **컨텍스트**: 컨퍼런스 주최자로부터 현재 시스템에 지장을 주지 않으면서 두 가지 주요 기능을 추가해 달라는 요청을 받았다. 모바일 애플리케이션을 지원해야 하고, 외부 CFP 시스템과 통합해야 한다. 둘 다 서드파티 서비스에서의 사용자 로그인을 지원하려면 참석자 정보에 접근할 수 있어야 한다
- **결정사항**: 참석자 컴포넌트를 독립형 서비스로 분리한다. 이를 통해 참석자 서비스를 API 우선으로 개발할 수 있고, 레거시 컨퍼런스 서비스도 그 API를 호출하며, 외부 CFP 시스템도 참석자 서비스를 직접 호출해 사용자 정보를 얻을 수 있다
- **결론**: 참석자 서비스 호출이 **아웃 오브 프로세스**가 되므로 레이턴시가 생기고 테스트가 필요하다. 참석자 서비스는 아키텍처의 **단일 실패 지점**(*single point of failure*)이 될 수 있어 인스턴스를 하나만 운영할 때의 영향을 완화할 방법이 필요하다. 다중 소비자 모델에서는 실수로 인한 **단절적 변경**(*breaking change*)을 막기 위해 올바른 설계·버저닝·테스트가 필요하다

이 결론들은 그 자체로 뒤 장들의 주제가 된다. 레이턴시와 테스트는 2장, 단일 실패 지점은 3·4장, 버저닝과 단절적 변경은 1장이 이어받는다.

### ADR 가이드라인이라는 장치

API 기반 아키텍처의 의사결정은 "상황에 따라 다르다"로 끝나기 쉽다. 이 책은 그 결론을 그냥 두지 않기 위해 **ADR 가이드라인**을 각 주제마다 제공한다. 아무 맥락 없이 "다르다"고 말하는 대신, **상황이 어떻게 다를 수 있는지와 왜 그런 결정을 내렸는지**를 설명하게 하는 장치다. 형식은 세 부분이다.

- **결정사항**: 그 주제에서 내려야 할 의사결정이 무엇인지
- **논의사항**: 결정을 내리는 데 필요한 주요 논점
- **권장사항**: 저자들의 경험에 기반한 권고와 그 근거

## 요약

- 아키텍처는 목적지가 없는 여정이다. 변화는 피할 대상이 아니라 이용할 대상이며, API는 그 진화의 핵심 도구다
- API는 구현에 대한 추상화이자 명세로 표현되는 계약이며, **인 프로세스**와 **아웃 오브 프로세스**로 나뉜다. 이 책은 아웃 오브 프로세스에 집중하고, 실제 과제는 대개 인 프로세스를 아웃 오브 프로세스로 바꾸는 일이다
- 컨퍼런스 시스템 사례는 3계층 모놀리스에서 출발한다. 첫 진화적 단계는 참석자 컴포넌트를 독립 서비스로 분리하는 것이며, 이때 트래픽이 **수직(north-south)** 과 **수평(east-west)** 으로 갈린다
- 수직 트래픽은 API 게이트웨이(3장), 수평 트래픽은 서비스 메시·쿠버네티스(4장)가 관리한다. 이 두 축이 책 2부의 뼈대다
- C4 다이어그램(컨텍스트 → 컨테이너 → 컴포넌트)은 상세 수준을 나눠 아키텍처를 소통하는 도구이고, ADR은 **결정의 동기**를 남기는 도구다. 둘 다 진화를 기록하기 위한 산출물이다
- ADR 가이드라인은 "경우에 따라 다르다"를 논점과 권고로 풀어내는 이 책의 장치다

## 다른 챕터와의 관계

- **1장**: ADR-001의 결론 중 "설계·버저닝·테스트가 필요하다"의 앞부분을 이어받아 참석자 API를 설계하고 명세한다
- **2장**: 같은 결론의 "테스트" 부분을 이어받아 계약·컴포넌트·통합 테스트를 다룬다
- **3·4장**: 여기서 정의한 수직/수평 트래픽 구분이 그대로 API 게이트웨이와 서비스 메시의 역할 분담이 된다. 특히 그림 0-3의 API 컨트롤러를 프로세스 밖으로 꺼내는 것이 3장이다
- **8장**: 참석자 서비스 분리라는 결정을 도메인 경계와 결합도 관점에서 다시 정당화한다
- **10장**: 사례 연구가 0장의 그림 0-1에서 어디까지 진화했는지 전체를 되짚는다
