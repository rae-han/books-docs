# Item 66: 타입 선언에 얽힌 세 가지 버전 이해하기 (Understand the Three Versions Involved in Type Declarations)

## 핵심 질문

라이브러리·@types·TypeScript 세 버전이 어긋나면 각각 어떤 증상이 나타나는가? 타입을 번들할 것인가 DefinitelyTyped에 올릴 것인가?

의존성 관리는 어느 언어에서든 즐겁지 않은데, 타입스크립트는 오히려 더 복잡하게 만든다. 걱정할 버전이 하나가 아니라 **최대 셋**이기 때문이다.

1. 패키지의 버전
2. 그 타입 선언(@types)의 버전
3. 타입스크립트의 버전

이 중 어느 것이든 서로 어긋나면 의존성 관리와 무관해 보이는 에러를 만나게 된다. 제대로 된 모습은 이렇다.

```
$ npm install react
+ react@18.2.0
$ npm install --save-dev @types/react
+ @types/react@18.2.23
```

**메이저·마이너 버전(18.2)은 일치하고 패치 버전(.0과 .23)은 다르다** — 정확히 원하는 모습이다. @types의 18.2는 이 선언이 react 18.2의 API를 기술한다는 뜻이다. react가 시맨틱 버저닝을 잘 지킨다면 패치 버전은 공개 API를 바꾸지 않으므로 타입 선언 업데이트가 필요 없다. 반면 타입 선언 자체의 버그·누락을 고치는 것이 @types의 패치 버전이다(이 경우 라이브러리보다 훨씬 많았다 — 23 대 0).

## 1. 버전이 어긋나는 네 가지 방식

**① 라이브러리는 업데이트했는데 타입 선언을 잊음** — Dependabot 같은 자동 업데이트 도구의 흔한 결과다. 라이브러리의 새 기능을 쓰려 할 때마다 타입 에러가 나고, 파괴적 변경이 있었다면 타입 체크는 통과하는데 런타임 에러가 날 수도 있다. 해법은 보통 타입 선언을 업데이트해 버전을 맞추는 것. 타입 선언이 아직 안 나왔다면 보강으로 새 함수·메서드를 직접 추가하거나(Item 71) 커뮤니티에 기여하라.

**② 타입 선언이 라이브러리보다 앞서감** — 타이핑 없이 라이브러리를 쓰다가(`declare module`로 any를 줬다가) 나중에 설치할 때 생길 수 있다. 증상은 ①의 반대다 — 타입 체커는 최신 API에 대조하는데 런타임에서는 옛 API를 쓴다. 라이브러리를 올리거나 타입 선언을 내려 맞춘다.

**③ 타입 선언이 내 프로젝트보다 새 TypeScript를 요구** — 타입 시스템 발전의 상당 부분이 Lodash·React·Ramda 같은 인기 라이브러리를 더 정밀하게 타이핑하려는 시도에서 왔으니, 이런 라이브러리의 타입 선언이 최신 기능을 쓰고 싶어 하는 것은 당연하다. 증상은 **@types 선언 자체의 타입 에러**다. 해법: 타입스크립트 업그레이드, 옛 버전의 타입 선언 사용, 정 안 되면 `declare module`로 스텁 처리. 라이브러리가 `typesVersions`로 타입스크립트 버전별 선언을 제공할 수도 있는데 드물다(DefinitelyTyped의 1% 미만). 특정 타입스크립트 버전용 @types 설치는:

```
npm install --save-dev @types/react@ts4.9
```

**④ @types 중복** — `@types/foo`와 `@types/bar`에 의존하는데 `@types/bar`가 호환되지 않는 버전의 `@types/foo`에 의존하면, npm은 한쪽을 중첩 폴더에 설치해 해결하려 한다. 런타임 모듈에는 가끔 통해도 **평평한 전역 네임스페이스에 사는 타입 선언에는 거의 확실히 안 통한다.** 중복 선언 또는 병합 불가 선언 에러로 나타난다. `npm ls @types/foo`로 중복의 원인을 추적하고, 보통 한쪽 의존성을 업데이트해 호환시킨다. 이런 이행적 @types 의존성은 골칫거리의 단골이다(공개하는 입장에서 피하는 법은 Item 70, 대량 중복의 컴파일러 성능 문제는 Item 78).

## 2. 타입 번들 vs DefinitelyTyped

일부 패키지는(특히 타입스크립트로 작성된 것들) 타입 선언을 **직접 번들**한다 — package.json의 `"types": "index.d.ts"` 필드가 표시다. 번들은 버전 불일치 문제를 풀어 준다. 특히 라이브러리가 타입스크립트로 작성되고 선언이 tsc로 생성된다면(declaration 설정). 하지만 번들 고유의 문제도 있다.

1. **번들된 타입에 보강으로 못 고치는 에러가 있다면?** 공개 당시엔 괜찮았는데 새 타입스크립트 버전이 에러를 낸다면? @types라면 구현에는 의존하되 타입 선언에는 의존하지 않을 수 있었지만 번들은 그 선택지가 없다. 나쁜 타입 선언 하나가 옛 타입스크립트에 발을 묶을 수 있다. 대조적으로 DefinitelyTyped는 타입스크립트가 개발되는 동안 마이크로소프트가 모든 선언에 대해 돌려 보고, 깨지면 빨리 고쳐진다.
2. **내 타입이 다른 라이브러리의 타입 선언에 의존한다면?** 보통 devDependency일 텐데(Item 65), 모듈을 공개하면 다른 사용자는 내 devDependencies를 받지 못해 타입 에러가 난다. 직접 의존성으로 만들자니 자바스크립트 사용자들이 쓸데없이 @types를 설치하게 된다(표준 우회는 Item 70). DefinitelyTyped에 공개한다면 아예 문제가 아니다 — 타입 의존성을 거기서 선언하면 타입스크립트 사용자만 받는다.
3. **옛 버전의 타입 선언 문제를 고쳐야 한다면?** 돌아가서 패치를 낼 수 있는가? DefinitelyTyped에는 같은 라이브러리의 여러 버전용 선언을 동시에 유지하는 메커니즘이 있다.
4. **타입 선언 패치를 받는 데 얼마나 헌신할 수 있는가?** react보다 @types/react의 패치가 훨씬 많았다는 것을 기억하라. DefinitelyTyped는 커뮤니티가 유지하며 이 볼륨을 감당한다 — 라이브러리 유지자가 5일 안에 패치를 안 보면 글로벌 유지자가 본다. 내 라이브러리에 비슷한 처리 속도를 약속할 수 있는가?

> **핵심 통찰**: 공식 권고는 **라이브러리가 타입스크립트로 작성됐을 때만 타입을 번들**하라는 것이다. tsc가 선언을 자동 생성해 주니 실전에서 잘 통한다. 자바스크립트 라이브러리의 손수 만든 타입 선언은 에러가 있을 가능성이 높고 업데이트도 더 필요하다 — DefinitelyTyped에 공개하면 커뮤니티가 지원과 유지를 도와준다.

## 기억해야 할 것들

- @types 의존성에는 세 가지 버전이 얽힌다: 라이브러리 버전, @types 버전, 타입스크립트 버전.
- 버전 불일치 유형별 증상을 알아차릴 수 있게 하라.
- 라이브러리를 업데이트하면 대응하는 @types도 업데이트하라.
- 타입 번들과 DefinitelyTyped 공개의 장단점을 이해하라. 라이브러리가 타입스크립트로 작성됐다면 번들을, 아니라면 DefinitelyTyped를 선호하라.
