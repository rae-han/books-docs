# Item 1: 타입스크립트와 자바스크립트의 관계 이해하기 (Understand the Relationship Between TypeScript and JavaScript)

## 핵심 질문

"타입스크립트는 자바스크립트의 슈퍼셋"이라는 말은 정확히 무슨 뜻인가? 타입 체커는 무엇을 목표로 하고, 무엇을 보장하지 못하는가?

타입스크립트는 특이한 언어다. 인터프리터로 실행되지도 않고(파이썬·루비처럼), 저수준 언어로 컴파일되지도 않는다(자바·C처럼). 또 다른 고수준 언어인 자바스크립트로 컴파일되며, **실제로 실행되는 것은 타입스크립트가 아니라 그 자바스크립트다**. 두 언어는 워낙 밀접하게 얽혀 있어서, 서로 어떤 관계인지 깊이 이해하는 것이 타입스크립트를 잘 쓰기 위한 토대가 된다.

## 1. 타입스크립트는 자바스크립트의 슈퍼셋이다

"타입스크립트는 자바스크립트의 슈퍼셋(*superset - 상위집합. B의 모든 것이 A에도 속하면 A는 B의 슈퍼셋*)이다"라는 말은 **문법적인** 의미다. 자바스크립트 프로그램에 문법 오류가 없다면 그것은 곧 유효한 타입스크립트 프로그램이다. 타입 체커가 그 코드에서 문제를 지적할 수는 있지만, 그것은 별개의 문제다 - 타입스크립트는 여전히 코드를 파싱하고 자바스크립트를 만들어 낸다(Item 3).

이 관계에서 두 가지 실용적 결론이 나온다.

1. **`.js` 파일의 코드는 이미 타입스크립트다**: `main.js`를 `main.ts`로 바꿔도 달라지는 것은 없다. 기존 자바스크립트 코드베이스를 타입스크립트로 마이그레이션할 때, 어떤 코드도 다른 언어로 다시 쓸 필요가 없다는 뜻이다. 자바 같은 언어로 갈아탔다면 불가능했을 이 **점진적 마이그레이션 경로**가 타입스크립트 최고의 장점 중 하나다(Chapter 10).
2. **역은 성립하지 않는다**: 타입스크립트는 타입을 명시하는 문법을 추가하므로, 자바스크립트가 아닌 타입스크립트 프로그램이 존재한다.

```typescript
function greet(who: string) {
  console.log('Hello', who);
}
```

이 코드를 자바스크립트를 기대하는 `node` 같은 프로그램에 넣으면 `SyntaxError: Unexpected token :` 에러가 난다. `: string`은 타입스크립트 고유의 타입 구문(*type annotation - 심벌에 타입을 명시하는 표기*)이기 때문이다.

집합으로 표현하면 다음과 같다.

- **모든 자바스크립트 프로그램 ⊂ 모든 타입스크립트 프로그램** (역은 성립하지 않는다)
- **타입 체커를 통과하는 프로그램**은 타입스크립트 프로그램의 부분집합으로, 자바스크립트 집합의 경계에 걸쳐 있다 - 타입 구문 없는 순수 자바스크립트도 타입 체크를 통과할 수 있고, 타입 구문을 쓴 코드(자바스크립트가 아닌 타입스크립트)도 통과할 수 있기 때문이다

"타입스크립트는 자바스크립트의 슈퍼셋이다"라는 말이 어색하게 느껴진다면, 일상적으로 우리가 신경 쓰는 집합이 세 번째 집합(타입 체커를 통과하는 프로그램)이기 때문이다. 타입스크립트를 쓸 때는 보통 코드가 모든 타입 체크를 통과하는 상태를 유지하려 하니까.

## 2. 타입 구문 없이도 오류를 잡는다

타입 체커는 타입 구문이 전혀 없는 순수 자바스크립트에서도 문제를 찾아낸다.

```typescript
let city = 'new york city';
console.log(city.toUppercase());
//               ~~~~~~~~~~~ Property 'toUppercase' does not exist on type
//                           'string'. Did you mean 'toUpperCase'?
```

`city`가 `string`이라고 알려 주지 않았지만 초깃값으로부터 **타입을 추론**했다(Chapter 3). 타입스크립트 타입 시스템의 목표는 **코드를 실행하지 않고도 런타임에 예외를 던질 코드를 찾아내는 것**이다. "정적(static)" 타입 시스템이라는 말이 가리키는 능력이 바로 이것이다.

## 3. 타입 구문은 "의도"를 알려 준다

예외를 던지지 않더라도 의도와 다르게 동작하는 코드가 있다. 타입스크립트는 이런 것도 잡으려 하는데, 이때 타입 구문이 있으면 훨씬 잘 잡는다.

```typescript
const states = [
  {name: 'Alabama', capital: 'Montgomery'},
  {name: 'Alaska',  capitol: 'Juneau'},
  {name: 'Arizona', capital: 'Phoenix'},
];
for (const state of states) {
  console.log(state.capital);
  //                ~~~~~~~ Property 'capital' does not exist on type
  //                        '{ name: string; capitol: string; } | ...'.
  //                        Did you mean 'capitol'?
}
```

같은 속성을 두 가지 철자(`capital`/`capitol`)로 썼기 때문에 타입스크립트는 어느 쪽이 맞는지 알 수 없고, 추측이 틀리면 위처럼 정반대 방향의 수정을 제안한다. 해법은 타입을 명시적으로 선언해서 **의도를 분명히 하는 것**이다.

```typescript
interface State {
  name: string;
  capital: string;
}
const states: State[] = [
  {name: 'Alabama', capitol: 'Montgomery'},
  //                ~~~~~~~ Object literal may only specify known properties,
  //                        but 'capitol' does not exist in type 'State'.
  //                        Did you mean to write 'capital'?
  {name: 'Alaska',  capitol: 'Juneau'},
  {name: 'Arizona', capitol: 'Phoenix'},
];
```

이제 에러가 문제 지점을 정확히 가리키고 제안된 수정도 올바르다. 오타가 배열에서 한 번만 나왔다면 타입 구문 없이는 에러조차 없었을 것이다.

> **핵심 통찰**: 타입 체커에게 정보를 많이 줄수록 더 많은 문제를 찾아 준다. 타입 구문은 "내 의도가 이것이다"를 알려 주는 수단이며, 타입스크립트는 코드의 동작이 그 의도와 어긋나는 지점을 찾아낸다.

## 4. 타입 시스템은 자바스크립트의 런타임 동작을 모델링한다

다른 언어에서 넘어온 사람에게는 놀라울 수 있는 부분이다.

```typescript
const x = 2 + '3';  // OK
//    ^? const x: string
const y = '2' + 3;  // OK
//    ^? const y: string
```

두 문장 모두 런타임에 문자열 `"23"`이 되므로, 다른 언어라면 에러였을 코드가 타입 체커를 통과한다. 반면 런타임에 예외를 던지지 않는데도 에러로 잡는 경우도 있다.

```typescript
const a = null + 7;   // JS에서는 7로 평가
//        ~~~~ The value 'null' cannot be used here.
const b = [] + 12;    // JS에서는 '12'로 평가
//        ~~~~~~~ Operator '+' cannot be applied to types ...
alert('Hello', 'TypeScript');  // "Hello" 경고창 표시
//             ~~~~~~~~~~~~ Expected 0-1 arguments, but got 2
```

기본 원칙은 **자바스크립트의 런타임 동작을 모델링하는 것**이지만, 위 사례들처럼 "이상한 사용은 개발자의 의도라기보다 오류일 가능성이 높다"고 판단하면 런타임 동작 모델링을 넘어서까지 잡아 준다. 어디까지 갈지는 결국 취향의 문제이고, 타입스크립트를 채택한다는 것은 그 판단을 내리는 팀을 신뢰한다는 뜻이다.

## 5. 타입 체크를 통과해도 런타임 에러는 날 수 있다

```typescript
const names = ['Alice', 'Bob'];
console.log(names[2].toUpperCase());
// 런타임: TypeError: Cannot read properties of undefined (reading 'toUpperCase')
```

타입스크립트는 배열 접근이 범위 안이라고 가정했지만 실제로는 아니었다. `any` 타입도 이런 미검출 에러의 단골 원인이다(Item 5, Chapter 5).

이런 예외들의 근본 원인은 **정적 타입(타입스크립트가 이해한 타입)과 런타임의 실제 타입이 어긋나는 것**이다. 정적 타입의 정확성을 보장할 수 있는 타입 시스템을 건전(*sound - 정적 타입이 런타임 값의 실제 타입을 항상 보장하는 성질*)하다고 하는데, 타입스크립트의 타입 시스템은 건전하지 않고 애초에 그럴 의도도 없었다(Item 48). 건전성이 중요하다면 Reason·PureScript·Dart 같은 언어를 볼 수도 있지만, 런타임 안전성 보장의 대가로 타입 체커를 설득하는 데 더 많은 일이 필요하고, 자바스크립트의 슈퍼셋이 아니므로 마이그레이션도 훨씬 복잡해진다.

## 기억해야 할 것들

- 타입스크립트는 자바스크립트의 슈퍼셋이다. 모든 자바스크립트 프로그램은 문법적으로 유효한 타입스크립트 프로그램이지만, 역은 성립하지 않는다.
- 타입스크립트는 자바스크립트의 런타임 동작을 모델링하는 정적 타입 시스템을 추가하며, 런타임에 예외를 던질 코드를 찾아내려 한다.
- 타입 체크를 통과한 코드도 런타임에 예외를 던질 수 있다.
- 인수 개수가 틀린 함수 호출처럼, 합법이지만 수상한 자바스크립트 구문은 에러로 잡는다.
- 타입 구문은 타입스크립트에게 의도를 알려 주어 올바른 코드와 틀린 코드를 구별하게 돕는다.
