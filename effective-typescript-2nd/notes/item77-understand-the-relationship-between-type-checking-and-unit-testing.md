# Item 77: 타입 체크와 유닛 테스트의 관계 이해하기 (Understand the Relationship Between Type Checking and Unit Testing)

## 핵심 질문

타입스크립트를 도입하면 유닛 테스트를 대부분 지워도 되는가? 반대로 어차피 테스트를 쓸 거면 타입이 무슨 소용인가?

두 주장 모두 극단이지만, 그 허세 뒤에 흥미로운 구별이 숨어 있다. 유닛 테스트와 타입 체크는 둘 다 **프로그램 검증**의 형태다. 둘의 관계는 무엇이고, 언제 테스트를 쓰고 언제 타입에 기대야 하는가?

## 1. add 함수 — 각자가 잡는 것과 못 잡는 것

```typescript
/** Returns the sum of the two numbers. */
function add(a, b) {
  // 구현 생략
}

test('add', () => {
  expect(add(0, 0)).toEqual(0);
  expect(add(123, 456)).toEqual(579);
  expect(add(-100, 90)).toEqual(-10);
});
```

테스트하기엔 너무 단순해 보인다면 IEEE 754 부동소수점 명세를 잠깐 보라 — 코너 케이스가 꽤 많다! 이 테스트가 통과하면 add의 정확성을 얼마나 확신해야 할까? 자바스크립트의 숫자는 64비트 부동소수점이므로 매개변수당 2^64, 총 **2^128가지 입력**이 가능하다. 테스트 케이스 셋은 극미한 비율만 커버한다. 이 틈으로 버그가 스며든다.

```typescript
function add(a, b) {
  if (isNaN(a) || isNaN(b)) {
    return 'Not a number!';
  }
  return (a|0) + (b|0);
}
```

이 구현은 유닛 테스트를 통과한다. 하지만 NaN 처리는 뜻밖이고 비트 연산은 입력을 0 쪽으로 반올림해 버린다 — 비정수도 더해야 할 텐데. 이런 케이스의 테스트를 따로 쓰지 않는 한 못 잡는다.

타입을 붙이면:

```typescript
function add(a: number, b: number): number {
  if (isNaN(a) || isNaN(b)) {
    return 'Not a number!';
    // ~~~ Type 'string' is not assignable to type 'number'.
  }
  return (a|0) + (b|0);
}
```

타입 구문 덕에 버그 하나가 잡혔다. 타입스크립트는 **구현 오류의 부류 전체**(잘못된 타입 반환, 입력에 대한 무효한 연산)를 예방한다. add가 number를 반환하는지 유닛 테스트로 확인할 수도 있지만 2^128가지 입력 전부에 대해서는 불가능하다 — **타입스크립트는 했다.** 물론 타입 체커가 못 잡는 실수도 많다 — 정수 반올림 문제도 못 잡고, 이 명백히 틀린 구현도 통과한다.

```typescript
function add(a: number, b: number): number {
  return a - b;  // 이런!
}
```

b가 0이 아닌 어떤 유닛 테스트라도 이 버그를 잡지만 타입 체커는 눈뜬장님이다.

> **핵심 통찰**: 유닛 테스트와 타입 체크는 상호 보완적이다. **유닛 테스트는 최소한 어떤 상황에서 코드가 올바르게 동작함을 보여 준다 — 정확성의 하한을 제공한다.** **타입 체커는 특정 부류의 오류를 저지르지 않았음을 증명한다 — 부정확성의 상한을 제공한다.** 코드가 충분히 잘 동작한다고 만족할 때까지 두 과정이 양쪽 끝에서 버그를 깎아 낸다고 생각하면 된다.

## 2. 무효한 입력은 테스트하지 마라 — 예외 하나만 빼고

문서나 타입이 뭐라 하든 자바스크립트에서 함수는 아무 타입의 인수로나 호출될 수 있다. `add(null, null)`은 0, `add('ab', 'cd')`는 'abcd'… 이런 동작을 테스트해야 할까? 테스트하려 하면 타입스크립트가 불평한다 — 그리고 그것이 맞다. **유닛 테스트는 기대되는 동작의 시연이고, 무효한 입력에는 시연할 기대 동작이 없다.** 무효한 호출은 타입 체커가 막게 하라. 이런 유닛 테스트는 쓸 필요가 없다.

중요한 예외: **잠재적으로 해로운 부수효과가 있는 함수**다. DB의 사용자 레코드를 갱신하는 함수를 보자.

```typescript
interface User {
  id: string;
  name: string;
  memberSince: string;
}
declare function updateUserById(
  id: string,
  update: Partial<Omit<User, 'id'>> & {id?: never}
): Promise<User>;
```

update 매개변수의 정교한 타입("옵셔널 never" 트릭은 Item 63)의 의도는 이 함수로 사용자 ID를 바꾸지 못하게 하는 것이다 — ID 변경은 충돌이나, 한 사용자가 다른 사용자를 사칭하게 되는 보안 문제까지 일으킬 수 있다. 하지만 이것은 **타입 수준에서만** 강제된다. 자바스크립트에서, 어쩌면 신뢰할 수 없는 사용자 입력으로 호출된다면 update에 id 속성이 있을 수 있다. DB를 오염시키느니 예외를 던지는(거부하는) 편이 낫다. **타입이 금지하더라도 명세하고 테스트할 가치가 있는 동작이다.** 테스트에서 `@ts-expect-error` 지시어로 타입 에러임을 단언하면서 테스트할 수 있다.

```typescript
test('invalid update', () => {
  // @ts-expect-error updateUserById로 ID를 바꿀 수 없다.
  expect(() => updateUserById('123', {id: '234'})).toReject();
});
```

## 3. 가능한 한 빨리 잡기 — 검증의 사다리

소프트웨어 품질 보증(QA)의 주요 목표는 고치는 비용이 쌀 때, 최대한 빨리 문제를 찾는 것이다. 버그를 알게 되는 최악의 방법은 이미 프로덕션에 있는데 최종 사용자(또는 보안 연구자!)가 신고하는 것이다. 수동 QA는 낫지만 여전히 비싸고, 자동화된 QA(통합 테스트)는 더 낫고, 유닛 테스트는 더 이르고 빠르게 잡는다. 그리고 **타입 체크가 가장 즉각적이다** — 편집기 안에서, 바라건대 실수한 바로 그 자리에서 버그를 보고한다.

버그를 최대한 빨리 잡으려면 가능한 곳에서는 타입 체커에 기대라. 타입스크립트는 많은 에러를 잡지만 가끔 도움이 필요하다 — Item 59(소진 체크)·61(Record 동기화)·64(브랜드)가 타입 체커에게 새로운 부류의 오류를 잡게 하는 기법들이다. 타입 체크에 기댈 수 없는 곳, 즉 **동작의 테스트**에는 유닛 테스트가 차선이다.

타입 자체에 로직이 있다면(Chapter 6의 주제) **타입에 대한 테스트**를 반드시 써야 한다 — 유닛 테스트와는 다른 종류의 테스트다(Item 55). 마지막으로, 타입과 유닛 테스트 모두 리팩터링에서 버그를 잡아 주지만, 타입은 언어 서비스까지 구동한다 — Item 6에서 봤듯 리팩터링을 대신 해 주기까지 한다!

## 기억해야 할 것들

- 타입 체크와 유닛 테스트는 프로그램 정확성을 입증하는 서로 다른 상호 보완적 기법이다. 둘 다 필요하다.
- 유닛 테스트는 특정 입력에서의 올바른 동작을 시연하고, 타입 체크는 잘못된 동작의 부류 전체를 제거한다.
- 타입은 타입 체커에 맡겨라. 타입으로 검사할 수 없는 동작에 유닛 테스트를 써라.
- 보안이나 데이터 손상의 우려가 없다면 타입 에러가 될 입력은 테스트하지 마라.
