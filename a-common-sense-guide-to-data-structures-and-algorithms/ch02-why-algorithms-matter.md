# Chapter 2: Why Algorithms Matter (알고리즘이 중요한 까닭)

## 핵심 질문

자료 구조를 이미 정했더라도 코드는 여전히 극적으로 빨라질 수 있는가? "값이 항상 순서대로"라는 제약 하나가 어떤 새 알고리즘을 가능하게 하는가? 데이터가 두 배로 늘 때 단계 수가 한 단계만 늘어나는 검색은 어떻게 가능한가?

---

## 1. 알고리즘이란 무엇인가

Ch1이 "올바른 **자료 구조** 선택"으로 성능을 바꿨다면, 이 장은 자료 구조를 결정한 뒤에도 남는 요인, **알고리즘 선택**을 다룬다.

**알고리즘(*algorithm - 어떤 과제를 완수하는 명령어 집합*)**은 어렵게 들리지만 단순한 개념이다. 시리얼 한 그릇을 준비하는 과정(① 그릇을 집는다 ② 시리얼을 따른다 ③ 우유를 붓는다 ④ 숟가락을 넣는다)도 정해진 단계로 과제를 달성하므로 엄연히 알고리즘이다. 컴퓨팅 관점에서는 특정 과제를 달성하기 위해 컴퓨터에 제공되는 명령어 집합을 뜻한다.

같은 과제를 둘 이상의 알고리즘으로 완수할 수 있고(Ch1의 짝수 출력 두 버전), 이번 장에서는 한쪽이 **훨씬** 빠른 두 검색 알고리즘을 비교한다. 그 전에 새 자료 구조가 하나 필요하다.

## 2. 정렬된 배열 — 삽입은 느려진다

**정렬된 배열(*ordered array - 값이 항상 순서대로 유지되는 배열*)**은 전형적인 배열과 거의 같고, 값을 추가할 때마다 적절한 셀에 넣어 정렬 상태를 유지한다는 점만 다르다.

`[3, 17, 80, 202]`에 75를 삽입해 보자. 전형적인 배열이면 끝에 붙이면 그만(1단계)이지만, 정렬된 배열은 **올바른 위치를 먼저 찾고, 공간을 만들기 위해 값들을 옮겨야** 한다.

1. 인덱스 0(값 3)과 **비교(*comparison - 삽입하려는 값과 배열에 이미 있는 값을 견주는 단계*)** → 75가 크므로 오른쪽
2. 인덱스 1(값 17)과 비교 → 오른쪽
3. 인덱스 2(값 80)와 비교 → 75보다 큰 첫 값 발견, 80 왼쪽에 넣어야 함
4. 202를 오른쪽으로 이동
5. 80을 오른쪽으로 이동
6. 75 삽입

원소 4개에 6단계 — 일반화하면 **원소 N개의 정렬된 배열 삽입은 총 N+2단계** 정도다. 흥미롭게도 삽입 위치가 어디든 단계 수는 비슷하다: 앞쪽에 놓이면 비교가 줄고 이동이 늘며, 뒤쪽에 놓이면 비교가 늘고 이동이 준다. 맨 끝에 놓일 때가 가장 적은 N+1단계(비교 N + 삽입 1)다.

삽입에서는 정렬된 배열이 명백히 손해다. 그런데 이 손해를 감수하는 이유가 **검색**에 있다.

## 3. 정렬된 배열의 검색 — 선형 검색도 조금 빨라진다

전형적인 배열 `[17, 3, 75, 202, 80]`에서 없는 값 22를 찾으려면 어디에 있을지 모르므로 **모든** 원소를 확인해야 한다. 그러나 정렬된 배열 `[3, 17, 75, 80, 202]`라면 75에 도달한 순간 "22는 더 이상 오른쪽에 있을 수 없다"고 판단하고 **일찍 중단**할 수 있다.

```typescript
function linearSearch(array: number[], searchValue: number): number | null {
  for (let index = 0; index < array.length; index++) {
    const element = array[index];
    if (element === searchValue) {
      return index;               // 찾으면 인덱스 반환
    } else if (element > searchValue) {
      break;                      // 찾는 값보다 큰 원소 → 조기 종료
    }
  }
  return null;                    // 배열에 없음
}
```

다만 찾는 값이 마지막 값이거나 그보다 크면 여전히 전부 확인해야 하므로, **최악의 시나리오는 두 배열 모두 N단계**다. 정렬된 배열의 진짜 힘은 선형 검색이 아니라 **다른 알고리즘을 쓸 수 있다는 것**이다.

## 4. 이진 검색 — 절반씩 제거한다

어릴 적 하던 숫자 알아맞히기 게임을 떠올리자. 1~100 사이의 수를 맞힐 때 1부터 부르는 사람은 없다 — **한가운데 50부터** 부른다. 어떤 답("커"/"작아")이 나오든 남은 후보의 절반이 제거되기 때문이다. 이것이 **이진 검색(*binary search - 정렬된 배열에서 가운데 값과 비교해 후보의 절반씩 제거해 나가는 검색*)**이다.

원소 9개 정렬 배열에서 7 찾기: ① 가운데 셀 확인(9) → 7은 왼쪽, 오른쪽 절반 제거 ② 왼쪽 절반의 가운데 확인(4) → 오른쪽 ③ 남은 두 칸 중 왼쪽 확인(6) ④ 마지막 칸 확인(7 발견) = 4단계.

```typescript
function binarySearch(array: number[], searchValue: number): number | null {
  // 찾으려는 값이 있을 수 있는 하한선과 상한선을 정한다
  let lowerBound = 0;
  let upperBound = array.length - 1;

  // 범위가 남아 있는 동안 가운데 값을 계속 확인한다
  while (lowerBound <= upperBound) {
    const midpoint = Math.floor((upperBound + lowerBound) / 2);
    const valueAtMidpoint = array[midpoint];

    if (searchValue === valueAtMidpoint) {
      return midpoint;                    // 발견
    } else if (searchValue < valueAtMidpoint) {
      upperBound = midpoint - 1;          // 왼쪽 절반으로 좁힘
    } else {
      lowerBound = midpoint + 1;          // 오른쪽 절반으로 좁힘
    }
  }
  return null;  // 범위가 소진되면 배열에 없다
}
```

> **핵심 통찰**: 이진 검색은 **정렬된 배열에서만** 쓸 수 있다. 전형적인 배열은 값의 순서가 뒤죽박죽이라 주어진 값의 왼쪽/오른쪽 어디를 봐야 할지 알 수 없다. "정렬 유지"라는 제약(삽입이 느려지는 비용)이 이진 검색이라는 강력한 알고리즘(검색이 빨라지는 이득)을 사준다 — 자료 구조의 제약과 알고리즘의 능력은 거래 관계다.

## 5. 이진 검색 대 선형 검색

원소 100개짜리 배열의 최대 단계 수: **선형 검색 100단계 vs 이진 검색 7단계.**

패턴을 보자. 크기 3 → 최대 2단계, 크기 7 → 3단계, 크기 15 → 4단계…

> **핵심 통찰**: **배열 크기를 두 배로 늘릴 때마다 이진 검색은 딱 한 단계만 늘어난다.** 확인할 때마다 남은 원소의 절반이 제거되기 때문이다. 반면 선형 검색은 원소 수만큼 단계가 필요해서 데이터가 두 배면 단계도 두 배다.

| 원소 수 | 선형 검색 (최대) | 이진 검색 (최대) |
|---------|-----------------|-----------------|
| 100 | 100단계 | 7단계 |
| 10,000 | 10,000단계 | 13단계 |
| 1,000,000 | 1,000,000단계 | 20단계 |

그래프로 그리면 선형 검색은 대각선 직선(원소 1개 추가 = 1단계 추가), 이진 검색은 데이터가 많아져도 거의 평평하게 기어가는 곡선이다.

**깜짝 퀴즈**: 원소 100개의 정렬된 배열에서 이진 검색이 7단계 걸렸다. 원소 200개면 몇 단계일까? — 직관적으로 14라고 답하기 쉽지만 정답은 **8단계**. 두 배로 늘어난 데이터는 첫 번째 검사에서 전부 제거된다.

덤: 이진 검색이 생기면 정렬된 배열의 **삽입도** 빨라진다 — 삽입 전 위치 검색을 선형에서 이진으로 업그레이드할 수 있기 때문이다. (물론 이동 비용은 남으므로 여전히 일반 배열 삽입보다는 느리다.)

## 6. 그래서 무엇을 선택하나

모든 상황에 완벽한 단 하나의 자료 구조나 알고리즘은 거의 없다. 정렬된 배열에 이진 검색을 쓸 수 있다고 항상 정렬된 배열을 써야 하는 것은 아니다 — 검색은 거의 없고 추가만 한다면 삽입이 빠른 일반 배열이 낫다. **"소프트웨어에서 삽입이 자주 일어나는가? 검색이 중대한 기능인가?"**를 항상 분석하라.

## 요약

- **알고리즘 = 과제를 완수하는 명령어 집합.** 같은 과제도 알고리즘에 따라 속도가 극적으로 다르다
- **정렬된 배열**은 삽입 시 위치 검색+이동이 필요해 삽입은 느리지만(N+2단계), **이진 검색**을 가능하게 한다
- **이진 검색**: 가운데 값과 비교해 후보 절반씩 제거 — 정렬된 배열 전용
- 데이터 2배 → 선형 검색은 단계 2배, **이진 검색은 +1단계** (1,000,000개도 최대 20단계)
- 자료 구조 선택 = 연산 빈도 분석: 삽입 위주면 일반 배열, 검색 위주면 정렬된 배열
- 경쟁 알고리즘의 성능 비교 방법은 단계 수 세기 — 이를 표현할 공식 언어(빅 오)가 Ch3에서 나온다

## 연습 문제 (해답 예시)

1. **정렬된 배열 `[2, 4, 6, 8, 10, 12, 13]`에서 선형 검색으로 8을 찾는 단계 수는?** — **4단계.** 왼쪽부터 차례로 확인하며 8이 네 번째 원소다.
2. **같은 문제를 이진 검색으로 풀면?** — **1단계.** 이진 검색은 중앙 원소부터 확인하는데 8이 마침 중앙(인덱스 3)에 있다.
3. **크기 100,000인 배열의 이진 검색 최대 단계 수는?** — **약 16단계.** 100,000을 2로 계속 나누면 16번 만에 1 근처(약 1.53)에 도달한다.

## 다른 챕터와의 관계

- **Ch1 (자료 구조가 중요한 까닭)**: Ch1의 "단계 수 세기" 도구를 그대로 사용해 알고리즘끼리 비교했다
- **Ch3 (빅 오 표기법)**: 선형 검색의 "N단계"·이진 검색의 "크기 2배당 +1단계"가 각각 O(N)·O(log N)이라는 공식 표기로 정리된다
- **Ch13 (속도를 높이는 재귀 알고리즘)**: "절반씩 제거"의 사촌 격인 "분할" 아이디어가 퀵 정렬로 이어진다
- **Ch15 (이진 탐색 트리)**: 이진 검색의 "가운데에서 절반 제거" 아이디어를 자료 구조 자체에 새긴 것이 BST다
