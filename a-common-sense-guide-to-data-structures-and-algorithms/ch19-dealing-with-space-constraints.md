# Chapter 19: Dealing with Space Constraints (공간 제약 다루기)

## 핵심 질문

알고리즘이 "얼마나 빠른가" 말고 "메모리를 얼마나 먹는가"는 어떻게 측정하는가? 시간과 공간이 충돌할 때 무엇을 기준으로 고르는가? 새 자료 구조를 하나도 안 만들었는데 메모리가 고갈되는 재귀의 숨은 비용은 무엇인가?

---

## 1. 공간 복잡도의 빅 오

지금까지는 오로지 시간 복잡도(속도)만 분석했지만, 또 하나의 효율성 척도가 있다 — **공간 복잡도(*space complexity - 알고리즘이 얼마나 많은 메모리를 소모하는가*)**. 대량의 데이터를 다루거나 메모리가 제한된 작은 장치를 프로그래밍할 때 중요해진다.

공간 복잡도도 **같은 빅 오 표기법**으로 표현하되, 핵심 질문만 바꾼다:

- 시간 복잡도의 핵심 질문: "데이터 원소가 N개일 때 알고리즘에 **몇 단계**가 필요할까?"
- 공간 복잡도의 핵심 질문: "데이터 원소가 N개일 때 알고리즘은 **메모리 단위를 얼마나** 소모할까?"

문자열 배열을 모두 대문자로 바꾸는 함수 두 버전:

```typescript
// 버전1 — 새 배열 생성: 공간 O(N)
function makeUpperCase(array: string[]): string[] {
  const newArray: string[] = [];
  for (let i = 0; i < array.length; i++) {
    newArray[i] = array[i].toUpperCase();
  }
  return newArray;
}

// 버전2 — 원래 배열을 제자리 수정: 공간 O(1)
function makeUpperCase(array: string[]): string[] {
  for (let i = 0; i < array.length; i++) {
    array[i] = array[i].toUpperCase();
  }
  return array;
}
```

버전1은 원소 N개짜리 `newArray`를 **추가로** 생성하므로 O(N), 버전2는 데이터 크기와 무관하게 추가 메모리가 상수(0!)이므로 O(1)이다.

> **핵심 통찰**: 공간 복잡도의 빅 오는 **알고리즘이 새로 생성한 데이터만** 센다. 입력으로 받은 원래 배열(원소 N개)은 어차피 존재하므로 계산에 넣지 않는다 — 이 추가 공간을 공식적으로는 **보조 공간(auxiliary space)**이라 부른다. (원래 입력까지 포함해 계산하는 책도 있으니, 자료를 읽을 때 어느 쪽 관례인지 먼저 확인하자.)

| 버전 | 시간 복잡도 | 공간 복잡도 |
|------|-------------|-------------|
| 버전1 | O(N) | O(N) |
| 버전2 | O(N) | O(1) |

두 버전의 시간은 같은데 공간은 버전2가 우수하다 — 속도를 희생하지 않는 공간 개선이니 따질 것 없는 깔끔한 승리다.

## 2. 시간과 공간 트레이드오프

하지만 늘 이렇게 공짜는 아니다. `hasDuplicateValue()`(Ch4)의 세 구현을 비교하자:

```typescript
// 버전1 — 중첩 루프: 시간 O(N²), 공간 O(1)
function hasDuplicateValue(array: number[]): boolean {
  for (let i = 0; i < array.length; i++) {
    for (let j = 0; j < array.length; j++) {
      if (i !== j && array[i] === array[j]) {
        return true;
      }
    }
  }
  return false;
}

// 버전2 — 해시 테이블: 시간 O(N), 공간 O(N)
function hasDuplicateValue(array: number[]): boolean {
  const existingValues: Record<number, boolean> = {};
  for (let i = 0; i < array.length; i++) {
    if (!existingValues[array[i]]) {
      existingValues[array[i]] = true;
    } else {
      return true;
    }
  }
  return false;
}

// 버전3 — 정렬 후 이웃 비교: 시간 O(N log N), 공간 O(log N)
function hasDuplicateValue(array: number[]): boolean {
  array.sort((a, b) => (a < b ? -1 : 1));
  for (let i = 0; i < array.length - 1; i++) {
    if (array[i] === array[i + 1]) {
      return true;
    }
  }
  return false;
}
```

| 버전 | 시간 복잡도 | 공간 복잡도 |
|------|-------------|-------------|
| 버전1 | O(N²) | O(1) |
| 버전2 | O(N) | O(N) |
| 버전3 | O(N log N) | O(log N) |

- **버전2**: 시간 최속이지만 해시 테이블이 값 N개를 담을 수 있어 공간 O(N)
- **버전1**: 가장 느리지만 추가 메모리 0 — 공간 최강
- **버전3**: 시간·공간 모두 중간 — 둘 다 신경 써야 할 때의 균형점. (정렬의 공간은 알고리즘마다 다르다 — 버블·선택 정렬은 제자리라 O(1)이지만, 더 빠른 퀵 정렬은 대개 O(log N) 공간을 쓴다. 이유는 다음 절에서.)

> **핵심 통찰**: 어떤 버전이 "정답"인지는 없다 — **상황에 따라 다르다.** 속도가 최우선이고 메모리가 넉넉하면 버전2, 메모리가 귀하고 속도는 덜 중요하면 버전1, 둘 다 적당히 필요하면 버전3. 각 상황의 **최소 허용 속도와 메모리 한도**를 알아야 알고리즘을 고를 수 있다.

## 3. 재귀에 숨겨진 비용

새 배열도 해시 테이블도 안 만드는 이 단순한 재귀는 공간 O(1)일까?

```typescript
function recurse(n: number): void {
  if (n < 0) {
    return;
  }
  console.log(n);
  recurse(n - 1);
}
```

아니다. Ch10에서 배웠듯 **재귀 호출마다 호출 스택에 항목이 쌓인다** — `recurse(100)`은 recurse(-1)에 도달하는 순간 호출 스택에 101개 항목이 쌓여 있다. 즉 이 함수는 **O(N) 공간**을 차지한다. 명시적으로 데이터를 만들지 않아도 재귀는 호출 스택으로 메모리를 눈 깜짝할 새에 집어삼킨다.

> **핵심 통찰**: **재귀 함수는 재귀 호출 횟수만큼 공간을 차지한다.** 공간을 계산하려면 호출 스택이 **최대 얼마나 커지는지**를 보면 된다. 저자의 최신 노트북에서도 `recurse(20000)`은 약 15,000개 항목에서 `RangeError: Maximum call stack size exceeded`로 죽었다 — 20,000은 큰 수도 아니다.

같은 일을 하는 루프는 추가 메모리를 안 쓰므로 아무리 큰 수도 끝까지 처리한다:

```typescript
function loop(n: number): void {
  while (n >= 0) {
    console.log(n);
    n--;
  }
}
```

이 관점에서 **퀵 정렬이 O(log N) 공간**을 쓰는 이유도 설명된다 — 재귀 호출을 O(log N)번 수행하므로 호출 스택의 최고점이 log N이다.

재귀를 부정하자는 게 아니다. 재귀에는 Ch11의 "마법 같은" 하향식 사고가 있지만, 대용량 데이터를 처리할 때는 호출 스택 한계 때문에 알맞지 않을 수 있다 — 매 상황마다 장단을 저울질하자.

## 요약

- **공간 복잡도** = "원소 N개일 때 메모리 단위를 얼마나 소모하는가" — 시간과 같은 빅 오로 표현
- 기본 관례: **새로 생성한 데이터(보조 공간)만** 계산, 원래 입력은 제외
- 시간과 공간은 자주 **트레이드오프** 관계다(중복 검사: O(N²)/O(1) vs O(N)/O(N) vs O(N log N)/O(log N)) — 상황의 속도·메모리 제약이 선택 기준
- **재귀의 숨은 비용**: 호출 스택도 메모리다 — 재귀 함수의 공간 = 최대 호출 스택 깊이 (단순 카운트다운 재귀 O(N), 퀵 정렬 O(log N))
- 스택 한계(대략 수만 호출)에 걸릴 수 있는 대용량 처리라면 루프를 고려하라

## 연습 문제 (해답 예시)

1. **wordBuilder(이중 루프로 두 글자 조합 생성)의 공간 복잡도** — **O(N²).** N²개 문자열을 담는 `collection` 배열을 생성하기 때문이다.
2. **배열을 역순 배열로 반환하는 함수의 공간 복잡도** — **O(N).** 항목 N개짜리 `newArray`를 생성한다.
3. **추가 공간 O(1)로 배열 뒤집기** — 첫↔마지막, 둘째↔끝에서 둘째… 를 **제자리 교환**한다. 새 데이터를 만들지 않으므로 O(1):

   ```typescript
   function reverse<T>(array: T[]): T[] {
     for (let i = 0; i < array.length / 2; i++) {
       [array[i], array[array.length - 1 - i]] =
         [array[array.length - 1 - i], array[i]];
     }
     return array;
   }
   ```

4. **각 숫자를 2배로 만드는 세 구현의 시간·공간** — 셋 다 시간은 O(N). 공간: 버전1(새 배열) **O(N)**, 버전2(제자리 루프) **O(1)**, 버전3(제자리 수정이지만 **재귀**) — 호출 스택이 N까지 쌓이므로 **O(N)**.

   | 버전 | 시간 복잡도 | 공간 복잡도 |
   |------|-------------|-------------|
   | 버전1 | O(N) | O(N) |
   | 버전2 | O(N) | O(1) |
   | 버전3 | O(N) | O(N) |
