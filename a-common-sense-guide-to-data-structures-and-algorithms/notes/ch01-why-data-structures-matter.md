# Chapter 1: Why Data Structures Matter (자료 구조가 중요한 까닭)

## 핵심 질문

같은 일을 하는 두 코드 중 하나가 더 "좋다"고 말할 수 있는 근거는 무엇인가? 데이터를 어떻게 조직하느냐가 코드의 실행 속도를 어떻게 바꾸는가? 그리고 그 속도는 무엇으로 측정해야 하는가?

## 1. 코드 품질의 또 다른 축 - 효율성

코딩을 처음 배울 때의 목표는 "코드가 실제로 동작하는가"다. 경험이 쌓이면 **유지 보수성**(가독성·조직·모듈화)이라는 품질 축을 배운다. 이 책이 다루는 것은 세 번째 축, **코드 효율성**이다 - 같은 목표를 달성해도 두 코드 중 하나가 더 빠르게 실행될 수 있다.

2부터 100 사이의 짝수를 출력하는 두 함수를 보자.

```typescript
function printNumbersVersionOne(): void {
  let number = 2;
  while (number <= 100) {
    // number가 짝수면 출력한다
    if (number % 2 === 0) {
      console.log(number);
    }
    number += 1;
  }
}

function printNumbersVersionTwo(): void {
  let number = 2;
  while (number <= 100) {
    console.log(number);
    // 정의에 따라 다음 짝수로 2씩 증가시킨다
    number += 2;
  }
}
```

두 번째 버전이 더 빠르다. 첫 번째 버전은 루프를 100번 돌지만 두 번째는 50번만 돈다 - 첫 번째가 두 배 더 많은 단계를 거친다.

빠른 코드를 작성하는 첫 번째 단계는 **자료 구조가 무엇인지, 다양한 자료 구조가 코드 속도에 어떤 영향을 미치는지** 이해하는 것이다.

## 2. 자료 구조와 4대 연산

데이터는 모든 유형의 정보를 망라하는 용어이며, 가장 기초적으로는 수와 문자열로 이뤄진다. **자료 구조란 데이터를 조직하는 방법**이다. 같은 문자열 세 개도 변수 세 개에 담을 수도, 배열 하나에 담을 수도 있다 - 그리고 이 조직 방식에 따라 프로그램은 수십, 수백 배 더 빠르게 혹은 느리게 실행될 수 있다.

배열 같은 자료 구조의 성능을 알려면 코드가 자료 구조와 일반적으로 어떻게 상호작용하는지 분석해야 한다. 대부분의 자료 구조에는 네 가지 기본 사용 방법, 즉 **연산(operation)**이 있다.

- **읽기(read)**: 자료 구조 내 **특정 위치**를 찾아보는 것. 배열이라면 "인덱스 2에 뭐가 들어 있지?"
- **검색(search)**: 자료 구조 내에서 **특정 값**을 찾는 것. "`"dates"`가 배열에 있나? 있다면 몇 번 인덱스지?"
- **삽입(insertion)**: 자료 구조에 새로운 값을 추가하는 것
- **삭제(deletion)**: 자료 구조에서 값을 제거하는 것

이 장은 이 4대 연산을 배열과 집합에 적용했을 때 각각 얼마나 빠른지 분석한다.

## 3. 속도는 시간이 아니라 단계 수로 잰다

> **핵심 통찰**: 이 책에서 오직 한 가지만 배워야 한다면 이것이다 - 연산이 얼마나 "빠른가"는 **시간이 아니라 단계(step) 수**로 측정한다. 같은 연산도 하드웨어에 따라 5초가 걸리기도, 훨씬 빠르기도 하므로 시간 기준은 신뢰할 수 없다. 반면 연산 A가 5단계, 연산 B가 500단계라면 **모든 하드웨어에서** A가 B보다 빠르다고 가정할 수 있다.

연산의 속도 측정은 **시간 복잡도(*time complexity - 주어진 연산에 필요한 계산 단계 수*)** 측정이라고도 부른다. 이 책 전반에서 속도·시간 복잡도·효율성·성능은 모두 같은 의미(단계 수)로 쓰인다.

## 4. 배열의 4대 연산 분석

배열(*array - 데이터 원소들의 단순 리스트*)의 기본 용어부터. **크기(size)**는 원소 개수, **인덱스(index)**는 특정 데이터가 배열 어디에 있는지 알려주는 숫자다(대부분의 언어에서 0부터 시작).

```typescript
const array = ["apples", "bananas", "cucumbers", "dates", "elderberries"];
// 크기 5, "apples"는 인덱스 0, "elderberries"는 인덱스 4
```

### 4.1 읽기 - 1단계

컴퓨터는 배열의 어떤 인덱스든 **딱 한 단계**로 읽는다. 그 이유는 컴퓨터 메모리의 구조에 있다.

1. 컴퓨터 메모리는 **주소가 붙은 셀들의 거대한 컬렉션**이고, 컴퓨터는 모든 메모리 주소에 한 번에 갈 수 있다(오른손 새끼손가락을 들 때 손가락을 일일이 확인하지 않는 것처럼).
2. 배열을 선언하면 컴퓨터는 **연속된** 빈 셀 묶음을 할당하고, **시작 메모리 주소를 기록**해 둔다.
3. 셀 주소는 1씩 증가하므로, 인덱스 3의 주소는 `시작 주소 + 3`이라는 **간단한 덧셈**으로 즉시 계산된다.

예: 배열이 주소 1010에서 시작하면 인덱스 3은 1010+3=1013 → 바로 접근해 `"dates"`를 읽는다. 한 단계로 끝나는 연산은 가장 빠른 연산 유형이며, 배열 읽기가 그렇다.

### 4.2 검색 - 최대 N단계 (선형 검색)

검색은 읽기와 반대다. 읽기는 인덱스를 주고 값을 받지만, 검색은 값을 주고 인덱스를 받는다. 둘은 비슷해 보여도 효율은 어마어마하게 다르다.

> **핵심 통찰**: 컴퓨터는 모든 메모리 주소에 한 번에 접근할 수 있지만, **각 주소에 어떤 값이 들어 있는지는 바로 알지 못한다**. 그래서 값을 찾으려면 셀을 한 번에 하나씩 확인하는 수밖에 없다.

`"dates"`를 찾으려면 인덱스 0(`"apples"`)부터 순서대로 확인해 인덱스 3에서 발견 - 4단계. 이렇게 한 번에 한 셀씩 확인하는 방법을 **선형 검색(*linear search - 처음부터 끝까지 차례로 확인하는 검색*)**이라 부른다.

최악의 경우는 찾는 값이 마지막 셀에 있거나 아예 없을 때다 - 모든 셀을 확인해야 한다. 즉 **N개의 셀로 이뤄진 배열의 선형 검색은 최대 N단계**다.

### 4.3 삽입 - 위치에 따라 1 ~ N+1단계

삽입의 효율은 **어디에 삽입하느냐**에 따라 다르다.

- **맨 끝 삽입 = 1단계.** 컴퓨터는 배열의 시작 주소와 크기를 알고 있으므로 마지막 다음 주소를 즉시 계산해 값을 넣는다. (원래 할당한 셀이 부족하면 추가 할당이 필요할 수 있는데, 많은 언어가 내부에서 자동 처리한다.)
- **중간 삽입.** 공간을 만들기 위해 삽입 지점 오른쪽의 데이터를 전부 한 칸씩 옮겨야 한다. 인덱스 2에 `"figs"`를 넣으려면: ① `"elderberries"` 이동 ② `"dates"` 이동 ③ `"cucumbers"` 이동 ④ 삽입 = 4단계.
- **맨 앞 삽입 = 최악의 시나리오, N+1단계.** 모든 원소 N개를 오른쪽으로 옮기고(N단계) 삽입(1단계).

### 4.4 삭제 - 최대 N단계

삭제 자체는 1단계지만, 배열 중간에 빈 셀을 남겨둘 수 없다는 문제가 있다. 인덱스 2의 `"cucumbers"`를 삭제하면: ① 삭제 ② `"dates"` 왼쪽 이동 ③ `"elderberries"` 왼쪽 이동 = 3단계.

최악의 시나리오는 첫 번째 원소 삭제 - 삭제 1단계 + 남은 N-1개 이동 = **최대 N단계**.

## 5. 집합 - 규칙 하나가 효율성을 바꾼다

**배열 기반 집합(*array-based set - 중복 값의 삽입을 절대 허용하지 않는 배열*)**은 배열과 거의 같지만 단 하나의 규칙이 있다: 중복 금지. `["a", "b", "c"]`에 또 `"b"`를 추가하려 하면 거부된다. 전화번호부처럼 같은 값이 두 번 나오면 안 되는 데이터에 유용하다.

> 저자의 실제 경험담: 지역 전화번호부에 저자의 집 전화번호가 저자 이름과 Zirkind라는 가족 이름 양쪽에 등록돼 버렸다. Zirkind를 찾는 전화와 음성 메일에 시달리고, Zirkind 가족은 왜 전화가 안 오는지 궁금해한다. 전화번호부 프로그램이 집합만 썼다면 일어나지 않았을 일이다.

집합의 읽기(1단계)·검색(최대 N단계)·삭제(최대 N단계)는 배열과 완전히 같다. **다른 것은 삽입뿐이다.**

> **핵심 통찰**: 집합은 **모든 삽입에 검색이 선행**된다. 중복을 막으려면 삽입하려는 값이 이미 있는지 전체를 검색해 확인해야 하기 때문이다. 규칙(제약) 하나가 연산 하나의 효율을 바꾼다.

- **맨 끝 삽입(최선)**: 검색 N단계 + 삽입 1단계 = **N+1단계** (배열은 1단계)
- **맨 앞 삽입(최악)**: 검색 N단계 + 전체 이동 N단계 + 삽입 1단계 = **2N+1단계** (배열은 N+1단계)

그렇다고 집합을 쓰지 말아야 할까? 물론 아니다. **중복이 없어야 한다는 요구사항이 있으면 집합이 답이다.** 그런 요구가 없다면 삽입이 더 빠른 배열이 낫다. 애플리케이션의 요구사항을 먼저 분석한 후 어떤 자료 구조가 적합한지 결정해야 한다.

## 6. 연산별 단계 수 정리

| 연산 | 배열 | 배열 기반 집합 |
|------|------|----------------|
| 읽기 | 1단계 | 1단계 |
| 검색 | 최대 N단계 | 최대 N단계 |
| 삽입 (맨 끝) | 1단계 | N+1단계 |
| 삽입 (맨 앞, 최악) | N+1단계 | 2N+1단계 |
| 삭제 (최악) | N단계 | N단계 |

## 요약

- 코드 품질에는 유지 보수성 외에 **효율성**이라는 축이 있고, 효율성의 기초는 자료 구조 이해다
- **자료 구조 = 데이터를 조직하는 방법.** 조직 방식이 실행 속도를 수십~수백 배 바꿀 수 있다
- 속도는 시간이 아니라 **단계 수**로 잰다(= 시간 복잡도). 하드웨어가 바뀌어도 단계 수 비교는 유효하다
- 분석 도구는 **4대 연산**: 읽기, 검색, 삽입, 삭제
- 배열: 읽기 1단계(주소 덧셈), 검색 최대 N단계(선형 검색), 삽입/삭제는 위치에 따라 1~N+1단계
- 집합: 중복 금지 규칙 때문에 **삽입 전 항상 검색** - 맨 끝 삽입도 N+1단계
- 자료 구조 선택은 벤치마크 수치가 아니라 **요구사항 분석**(중복 허용 여부 등)에서 출발한다

## 연습 문제 (해답 예시)

1. **원소 100개 배열에서 각 연산의 단계 수는?**
   - a. 읽기: **1단계**
   - b. 없는 값 검색: **100단계** (모든 셀 확인)
   - c. 맨 앞 삽입: **101단계** (100개 이동 + 삽입)
   - d. 맨 뒤 삽입: **1단계**
   - e. 맨 앞 삭제: **100단계** (삭제 1 + 99개 이동)
   - f. 맨 뒤 삭제: **1단계**
2. **원소 100개 배열 기반 집합에서는?**
   - a. 읽기: **1단계** / b. 없는 값 검색: **100단계** (배열과 동일)
   - c. 맨 앞 삽입: **201단계** (중복 확인 검색 100 + 이동 100 + 삽입 1)
   - d. 맨 뒤 삽입: **101단계** (검색 100 + 삽입 1)
   - e. 맨 앞 삭제: **100단계** / f. 맨 뒤 삭제: **1단계** (배열과 동일)
3. **배열에서 특정 값의 "모든" 인스턴스를 찾는 데 걸리는 단계 수는?** 항상 **N단계**. 첫 인스턴스를 찾아도 멈출 수 없고, 모든 인스턴스를 찾으려면 전체 셀을 검사해야 한다.

## 다른 챕터와의 관계

- **Ch2 (알고리즘이 중요한 까닭)**: 이 장이 "자료 구조 선택"으로 속도를 바꿨다면, Ch2는 **같은 자료 구조에서 알고리즘 선택**으로 속도를 바꾼다 (정렬된 배열 + 이진 검색)

- **Ch8 (해시 테이블)**: 집합 삽입의 "검색 선행" 비용은 해시 테이블 기반 집합으로 극적으로 줄어든다
- **Ch19 (공간 제약)**: 이 장은 시간(단계 수)만 쟀지만, Ch19에서 메모리(공간) 축이 추가된다
