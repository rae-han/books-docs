# Chapter 12: Why Write Comments? The Four Excuses (왜 주석을 써야 하는가: 네 가지 변명) - 요약

> 상세 노트: [ch12-why-write-comments.md](../notes/ch12-why-write-comments.md)

**핵심 질문**: "좋은 코드는 스스로 설명한다"는 말은 사실인가? 주석을 쓰지 않는 이유는 정당한가?

## 핵심

- **주석은 설계 도구다**: 단순한 문서화가 아니라 추상화를 정의하는 수단이다. 주석 없이는 추상화를 정의할 수 없고, 추상화 없이는 복잡성을 관리할 수 없다.
- **변명 1 "좋은 코드는 스스로 설명한다"**: 코드는 무엇을/어떻게는 표현하지만, 왜 이 방식인지, 제약 조건(유효 범위, 호출 순서), 높은 수준의 의도, 비자명한 동작(경계 조건, 성능 특성)은 표현할 수 없다. 사용자가 모듈을 쓰기 위해 구현을 읽어야 한다면 추상화가 없는 것이다.
- **변명 2 "시간이 없다"**: 주석은 전략적 프로그래밍의 설계 투자다. 작성 비용(1명 x 5분)이 부재 비용(독자 N명 x 30분씩 코드 해독)보다 훨씬 싸다.
- **변명 3 "주석은 금방 구식이 된다"**: 부분적 사실이지만 답은 포기가 아니라 유지 습관이다. 주석을 코드 가까이 두고, 변경 시 함께 갱신하고, 리뷰에서 확인한다. 인터페이스 주석은 구현 변경에 영향을 덜 받아 더 안정적이다.
- **변명 4 "내가 본 주석은 다 쓸모없었다"**: 대부분의 주석이 나쁜 건 사실이지만, 답은 안 쓰는 게 아니라 잘 쓰는 것이다(Ch13).
- **나쁜 주석 vs 좋은 주석**: 코드를 한국어로 번역한 주석(`count++; // count를 증가`)은 가치가 0이다. 좋은 주석은 코드에 없는 정보를 더한다: 용어의 정확한 정의, 성능 특성, 사용 가이드, 값 선택의 이유.

> **핵심 통찰**: 주석의 가장 중요한 역할은 추상화 정의다. 인터페이스 주석만 읽고 모듈을 올바르게 쓸 수 있어야 하며, 그래야 구현의 복잡성이 진짜로 숨겨진다.
