# Chapter 4: Modules Should Be Deep (모듈은 깊어야 한다) - 요약

> 상세 노트: [ch04-modules-should-be-deep.md](../notes/ch04-modules-should-be-deep.md)

**핵심 질문**: 좋은 모듈과 나쁜 모듈의 차이는 무엇인가? 모듈의 인터페이스와 기능 사이에 어떤 관계가 있어야 하는가?

## 핵심

- **모듈 = 인터페이스 + 구현**: 인터페이스는 모듈을 사용하기 위해 알아야 하는 것, 구현은 그 약속을 이행하는 내부 세부사항이다. 이상적인 모듈러 설계에서 개발자는 한 번에 하나의 모듈만 다루면 된다.
- **인터페이스의 비공식적 부분**: 메서드 시그니처·타입(공식적 부분) 외에 동작 설명·제약·부수효과·성능 특성(비공식적 부분)도 인터페이스다. 비공식적 부분이 부실하면 Unknown Unknowns가 발생한다.
- **추상화**: 중요하지 않은 세부사항을 생략한 단순화된 관점. 중요한 것을 빠뜨려도(이체 실패 조건 미명시), 중요하지 않은 것을 노출해도(버퍼 크기·인코딩 강제) 나쁜 추상화다.
- **깊은 모듈(deep module)**: 단순한 인터페이스 뒤에 강력한 기능을 숨긴 모듈. 직사각형 비유로 너비(인터페이스 복잡성)는 좁고 높이(기능의 양)는 높다. 예: Unix 파일 I/O - 함수 5개(open/read/write/lseek/close) 뒤에 수십만 줄의 커널 코드. GC는 인터페이스가 0인 극단적 깊은 모듈.
- **얕은 모듈(shallow module)**: 기능 대비 인터페이스가 복잡한 모듈. 내부를 몰라도 된다는 이득이 인터페이스 학습 비용으로 상쇄된다. 예: Java I/O - 파일 하나 읽는 데 FileInputStream + BufferedInputStream + ObjectInputStream 3개를 조합해야 한다.
- **Classitis(클래스염)**: "클래스는 작아야 한다"를 극단적으로 적용해 얕은 클래스를 양산하는 병. 작지만 얕은 클래스 10개보다 크지만 깊은 클래스 2개가 낫다.
- **깊은 모듈을 만드는 자문 세 가지**: 인터페이스를 더 단순하게 만들 수 있는가, 호출자가 처리하는 로직을 모듈 안으로 흡수할 수 있는가, 이 모듈이 숨기는 정보는 무엇인가(숨기는 게 거의 없다면 얕은 모듈이다).

## Red Flags

- 🚩 **Shallow Module**: 제공하는 기능에 비해 인터페이스가 복잡한 모듈

> **핵심 통찰**: 클래스의 가치는 크기가 아니라 깊이로 판단한다 - 기준은 인터페이스의 복잡성 대비 제공하는 기능의 양이다.
