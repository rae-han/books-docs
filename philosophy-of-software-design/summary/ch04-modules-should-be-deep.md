# Chapter 4: Modules Should Be Deep (모듈은 깊어야 한다) - 요약

**핵심 질문**: 좋은 모듈과 나쁜 모듈의 차이는 무엇인가? 모듈의 인터페이스와 기능 사이에 어떤 관계가 있어야 하는가?

## 모듈 = 인터페이스 + 구현

소프트웨어 시스템은 모듈(클래스, 함수, 서브시스템, 서비스, 패키지)로 구성된다. 이상적인 모듈러 설계에서 개발자는 **한 번에 하나의 모듈만** 다루면 되고 나머지 모듈의 세부사항은 알 필요가 없다. 그러려면 각 모듈이 독립적으로 이해 가능하고, 모듈 간 의존성이 최소화되며, 복잡성이 모듈 내부에 갇혀야 한다.

모든 모듈은 두 부분으로 나뉜다. **인터페이스**는 모듈을 사용하기 위해 알아야 하는 것이고, **구현**은 인터페이스의 약속을 이행하는 코드다. 여기서 놓치기 쉬운 것이 인터페이스에 두 층이 있다는 사실이다.

- **공식적 인터페이스**: 언어가 강제하는 부분 - 메서드 시그니처, 타입
- **비공식적 인터페이스**: 주석, 문서, 관례로 전달되는 부분 - 동작 설명, 제약 조건, 부수 효과, 성능 특성

`V get(K key)`라는 시그니처만으로는 그 캐시를 올바르게 쓸 수 없다. "없으면 null을 반환한다", "반환값은 스레드 안전하지 않다", "LRU 정책을 따른다" 같은 것이 비공식적 인터페이스다.

> **핵심 통찰**: 인터페이스의 비공식적 부분은 공식적 부분만큼, 때로는 더 중요하다. 비공식적 인터페이스가 부실하면 사용자는 무엇을 모르는지조차 모르는 Unknown Unknowns에 빠진다.

모듈의 인터페이스는 곧 그 모듈의 **추상화**다. 추상화는 실체의 단순화된 관점으로, 중요하지 않은 세부사항을 생략한 것이다. 나쁜 추상화는 두 방향으로 생긴다. 중요한 세부사항을 빠뜨리거나(잔액 부족 시 어떻게 되는지 알려주지 않는 `transfer`), 중요하지 않은 세부사항을 노출하거나(파일 하나 읽는 데 버퍼 크기와 인코딩과 mmap 사용 여부를 요구하는 `FileReader`).

## 깊은 모듈: 이 책의 중심 개념

모듈을 직사각형으로 그려 보면 이해가 빠르다. **너비는 인터페이스의 복잡성, 높이(깊이)는 제공하는 기능의 양**이다.

```
      ←───── 인터페이스의 복잡성 ─────→
┌─────────────────────────────────────┐ ─┐
│           얕은 모듈                   │  │ 기능의 양
└─────────────────────────────────────┘ ─┘

      ←── 인터페이스 ──→
      ┌─────────────┐ ─┐
      │              │  │
      │   깊은 모듈   │  │ 기능의 양
      │              │  │
      └─────────────┘ ─┘
```

**깊은 모듈은 단순한 인터페이스 뒤에 강력한 기능을 숨긴다.** 교과서적 사례가 Unix 파일 I/O다. 단 다섯 개의 시스템 콜이 거의 모든 I/O를 처리한다.

```c
int     open(const char *path, int flags);
ssize_t read(int fd, void *buf, size_t count);
ssize_t write(int fd, const void *buf, size_t count);
off_t   lseek(int fd, off_t offset, int whence);
int     close(int fd);
```

이 다섯 함수 뒤에는 저장 장치 드라이버, 디스크 블록 할당, 파일 시스템 구현(ext4, NTFS, ZFS), 디렉토리 탐색, 페이지 캐시, 동시 접근 제어, 네트워크 파일 시스템, 권한 관리, 저널링과 크래시 복구가 숨어 있다. 수십만 줄의 커널 코드가 다섯 개의 함수 뒤에 있는 것이다. 더 극단적인 예가 가비지 컬렉터다 - **인터페이스가 아예 없으면서** 메모리 관리라는 거대한 복잡성을 통째로 흡수한다.

## 얕은 모듈과 Classitis

반대편이 얕은 모듈이다. 제공하는 기능에 비해 인터페이스가 복잡해서, "내부를 몰라도 된다"는 이득이 "인터페이스를 배우고 쓰는 비용"으로 상쇄되어 버린다.

```java
// 얕은 모듈: 파일 하나 읽는 데 세 클래스를 조합해야 한다
FileInputStream   fileStream     = new FileInputStream("data.txt");
BufferedInputStream bufferedStream = new BufferedInputStream(fileStream);
ObjectInputStream objectStream   = new ObjectInputStream(bufferedStream);

// Unix라면 두 줄
int fd = open("data.txt", O_RDONLY);
read(fd, buffer, size);
```

`FileInputStream`이 버퍼링조차 제공하지 않아 별도의 `BufferedInputStream`이 필요하다는 것이 문제의 핵심이다. 각 클래스가 얕아서 인터페이스 비용 대비 제공하는 가치가 적다.

이 문제가 습관이 되면 **Classitis(클래스염)**가 된다. "클래스는 작아야 한다"는 조언을 극단적으로 적용해 최소한의 기능만 가진 작은 클래스를 양산하는 병이다. 증상은 명확하다 - 간단한 작업에 여러 클래스를 조합해야 하고, 클래스 수가 많아 전체 구조를 파악하기 어렵고, 각 클래스의 인터페이스를 배우는 비용이 얻는 이점보다 크다.

> **핵심 통찰**: 클래스의 가치는 크기가 아니라 **깊이**로 판단한다. 작지만 얕은 클래스 10개는 10개의 인터페이스를 배우게 하고 별 기능이 없지만, 크지만 깊은 클래스 2개는 단순한 인터페이스 2개 뒤에 강력한 기능을 숨긴다.

## 실전: 깊은 모듈 만들기

새 모듈을 설계할 때 세 가지를 자문한다.

1. **이 모듈의 인터페이스를 더 단순하게 만들 수 있는가?** 불필요한 파라미터를 제거하거나 기본값을 제공할 수 있는가, 여러 메서드를 하나로 합칠 수 있는가
2. **이 모듈이 더 많은 기능을 내부에 흡수할 수 있는가?** 호출자가 지금 처리하는 로직 중 모듈 안으로 옮길 것이 있는가
3. **이 모듈이 숨기는 정보는 무엇인가?** 숨기는 것이 거의 없다면 그 모듈은 얕다

```python
# 얕은 모듈 셋 - 사용하려면 세 클래스를 다 알아야 한다
class HttpConnectionManager:
    def create_connection(self, host, port, timeout): ...
class HttpRequestBuilder:
    def set_method(self, method): ...
    def set_headers(self, headers): ...
class HttpResponseParser:
    def parse_status(self, raw): ...

# 깊은 모듈 하나 - 커넥션 관리, 요청 빌드, 응답 파싱이 모두 내부에 숨겨진다
class HttpClient:
    def get(self, url, headers=None) -> HttpResponse: ...
    def post(self, url, body, headers=None) -> HttpResponse: ...

response = client.get("https://api.example.com/users")
```

## Red Flags

- 🚩 **Shallow Module**: 제공하는 기능에 비해 인터페이스가 복잡한 모듈

> **핵심 통찰**: 모듈을 설계할 때 물어야 할 것은 "이 클래스가 얼마나 작은가"가 아니라 "이 인터페이스 뒤에 얼마나 많은 복잡성을 숨겼는가"다.
