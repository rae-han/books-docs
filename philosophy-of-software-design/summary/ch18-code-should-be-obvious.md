# Chapter 18: Code Should be Obvious (코드는 명확해야 한다) - 요약

> 상세 노트: [ch18-code-should-be-obvious.md](../notes/ch18-code-should-be-obvious.md)

**핵심 질문**: "명확한 코드"란 무엇이고, 무엇이 명확성을 해치는가?

## 핵심

- **명확성의 정의**: 독자가 코드를 빠르게 읽었을 때 의미와 동작에 대한 첫 번째 추측이 맞는 것. 명확한 코드는 Unknown Unknowns를 최소화한다.
- **명확성을 높이는 것**: 좋은 이름(Ch14), 일관성(Ch17), 구조가 드러나는 공백/포매팅, 코드로 표현 못하는 부분을 보충하는 주석(Ch12-13).
- **이벤트 기반 코드**: 등록과 핸들러가 떨어져 있어 제어 흐름을 읽기만으로 추적하기 어렵다. 명확한 이름과 이벤트-핸들러 관계 문서화로 완화한다.
- **제네릭 컨테이너 남용**: `Pair<String, Integer>`의 getFirst/getSecond는 의미를 전달하지 못한다. 의미가 드러나는 전용 타입(record 등)을 쓴다.
- **선언 타입과 할당 타입 불일치**: 독자가 두 타입의 관계와 선택 이유(왜 LinkedHashMap인가)를 추가로 알아야 한다면 명확성이 깎인 것이다.
- **기대 위반이 최악**: `get`으로 시작하는 메서드가 세션 정리와 캐시 쓰기 같은 부수 효과를 가지면, 독자의 합리적 기대가 배신당하며 Unknown Unknowns가 생긴다.
- **판정은 독자가 한다**: 작성자는 맥락을 너무 많이 알아서 자기 코드를 객관적으로 평가할 수 없다. 리뷰어가 "이해가 안 된다"고 하면 그것이 곧 불명확하다는 증거다.

## Red Flags

- 🚩 **Nonobvious Code**: 빠르게 읽었을 때 의미와 동작을 이해할 수 없는 코드

> **핵심 통찰**: 소프트웨어는 쓰기 쉽게가 아니라 읽기 쉽게 설계해야 한다. 명확성은 작성자의 주장이 아니라 독자의 경험으로 판정된다.
