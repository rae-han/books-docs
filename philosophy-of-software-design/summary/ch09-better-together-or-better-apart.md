# Chapter 9: Better Together Or Better Apart? (합치는 게 나은가, 분리하는 게 나은가?) - 요약

> 상세 노트: [ch09-better-together-or-better-apart.md](../notes/ch09-better-together-or-better-apart.md)

**핵심 질문**: 두 개의 관련된 기능을 하나의 모듈에 합칠 것인가, 별도 모듈로 분리할 것인가? 기준은 무엇인가?

## 핵심

- **유일한 기준은 전체 복잡성**: 합치든 분리하든 시스템 전체의 복잡성이 줄어드는 방향을 택한다. 코드 줄 수나 클래스 크기가 기준이 아니다.
- **합치는 것이 나은 경우**: 같은 정보/지식을 공유할 때(분리하면 정보 누출), 항상 함께 사용될 때(검증+정제), 개념적으로 같은 상위 문제의 부분들일 때, 한쪽 없이 다른 쪽을 이해할 수 없을 때.
- **분리하는 것이 나은 경우**: 각각 독립적으로 이해/사용 가능할 때, 완전히 다른 목적일 때, 합치면 너무 커질 때(단, 분리 기준은 크기가 아니라 추상화의 깔끔함).
- **"작은 클래스/메서드" 맹신의 함정**: 3줄짜리 private 메서드 5개로 쪼개면 읽는 사람이 메서드들을 오가야 하고, 실행 순서 의존성이 숨고, 각 메서드가 얕아진다. 차라리 한 메서드에 전체 흐름을 담는 게 나을 수 있다. 메서드 추출이 정당한 건 추출된 것이 독립적인 범용 기능일 때다.
- **Special-General Mixture**: 범용 메커니즘(캐시) 안에 특정 용도(세션 만료) 코드가 섞이면 메커니즘이 복잡해지고 정보 누출이 생긴다. 특수 로직은 상위 계층으로.
- **반복은 누락된 추상화의 신호**: 같은 코드 패턴(에러 처리 등)이 여러 곳에 반복되면 아직 발견하지 못한 추상화가 있다는 뜻이다.

## Red Flags

- 🚩 **Conjoined Methods**: 한 메서드를 이해하려면 다른 메서드의 구현도 읽어야 함
- 🚩 **Special-General Mixture**: 범용 메커니즘에 특수 목적 코드가 섞여 있음
- 🚩 **Repetition**: 같은 코드 패턴이 여러 곳에서 반복됨

> **핵심 통찰**: 합치기와 분리하기의 판단 기준은 코드 줄 수가 아니라 복잡성의 총량이다. 정보를 공유하는 것들은 모으고, 독립적인 것들은 나눈다.
