# Chapter 19: Software Trends (소프트웨어 트렌드) - 요약

> 상세 노트: [ch19-software-trends.md](../notes/ch19-software-trends.md)

**핵심 질문**: 업계의 주요 트렌드들은 복잡성 관리에 도움이 되는가, 해가 되는가?

## 핵심

- **평가 기준은 하나**: "이 트렌드가 소프트웨어의 복잡성을 줄이는가?" 어떤 트렌드도 무조건 좋거나 나쁘지 않다.
- **OOP**: private과 인터페이스 상속(다형성)은 정보 은닉과 추상화에 좋다. 구현 상속은 부모-자식 간 강한 결합을 만드므로 주의. 구현 상속보다 조합(composition)을 선호하라.
- **애자일**: 증분적 개발과 빠른 피드백은 저자의 증분적 설계와 일치한다. 다만 "동작하는 소프트웨어 우선"이 극단화되면 설계 경시와 전술적 프로그래밍으로 빠진다. 방법론은 취하되 설계 품질은 양보하지 마라.
- **단위 테스트**: 강하게 지지. 리팩토링의 안전망이자 경계 조건의 문서이며 변경의 자신감을 준다.
- **TDD**: 유보적. 기능 구현에 초점을 맞춰 전술적 프로그래밍을 유도할 수 있고, 인터페이스가 깔끔한 추상화가 아니라 테스트 용이성에 의해 결정될 위험이 있다. 테스트는 설계를 검증하는 도구지 이끄는 도구가 아니다.
- **디자인 패턴**: 공유 어휘와 검증된 해법을 주지만 가장 큰 위험은 과잉 적용이다. 패턴은 도구지 목표가 아니다.
- **getter/setter 자동 생성 반대**: 모든 필드에 getter/setter를 만들면 private이어도 내부 상태가 사실상 전부 노출된다. 정말 필요한 경우에만, 내부 표현이 아닌 의미 있는 추상화 수준으로 제공하라.

> **핵심 통찰**: 유행하는 방법론이라도 복잡성이라는 렌즈로 다시 평가하라. 좋은 아이디어도 극단적으로 적용하면 얕은 모듈과 전술적 코드를 낳는다.
