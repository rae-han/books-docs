# Chapter 3: Working Code Isn't Enough (동작하는 코드만으로는 부족하다) - 요약

> 상세 노트: [ch03-working-code-isnt-enough.md](../notes/ch03-working-code-isnt-enough.md)

**핵심 질문**: "일단 동작하게 만들자"는 접근법이 왜 장기적으로 더 느린가? 좋은 설계를 위한 투자는 얼마가 적절한가?

## 핵심

- **전술적 프로그래밍**: 기능을 최대한 빨리 동작하게 만드는 것이 목표. "나중에 리팩토링하면 되지", "이 정도 해킹은 괜찮겠지"의 사고방식이다.
- **전략적 프로그래밍**: 훌륭한 설계를 만드는 것이 목표. 동작하는 코드는 필요 조건이지 충분 조건이 아니다.
- **전술적 접근의 문제**: 변경 하나하나가 작은 복잡성을 추가한다. 개별적으로는 "별거 아닌" 타협이 수백 번 쌓이면 시스템이 이해 불가능해진다.
- **전술적 토네이도**: 엄청난 속도로 코드를 쏟아내 관리자에게 영웅으로 보이지만, 지나간 자리에 파괴의 흔적(읽기/테스트/수정이 어려운 코드)을 남기는 개발자 유형. 그 뒷정리 비용이 처음부터 전략적으로 짠 비용보다 크다.
- **투자 마인드셋**: 선제적 투자(설계 대안 비교, 명확한 문서, 깔끔한 추상화)와 반응적 투자(버그의 근본 원인 해결, 불명확한 코드 발견 즉시 개선)를 병행한다.
- **투자량은 10~20%**: 거대한 선행 설계(Big Design Up Front)가 아니라 매일의 코딩에서 조금씩 더 나은 설계를 선택하는 것. 단기적으로 10~20% 느리지만 수개월 내에 회수된다.
- **"빨리 출시" 반론 반박**: "나중에 정리"는 거의 오지 않고, 기술 부채는 몇 달이면 쌓이며, 스타트업의 성패는 여러 번의 방향 전환 뒤에 결정되므로 깨끗한 코드가 오히려 빠른 pivot을 가능하게 한다. Facebook은 "Move fast and break things"를 결국 "Move fast with stable infra"로 바꿔야 했고, Google과 VMware는 전략적 접근으로 장기 속도를 얻었다.
- **하지 말 것**: "일단 동작하게 하고 TODO"(영원히 안 고쳐짐), "이번만 예외로"(예외가 규칙이 됨), "나중에 리팩토링 스프린트"(거의 승인 안 됨).

> **핵심 통찰**: 전략적 프로그래밍은 특별한 행사가 아니라 매일의 습관이다. 코드를 쓸 때마다 "더 깔끔한 방법이 있을까?"를 잠시 멈추고 묻는 것이 전부다.
