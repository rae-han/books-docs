# Chapter 13: Comments Should Describe Things That Aren't Obvious (주석은 명확하지 않은 것을 설명해야 한다) - 요약

> 상세 노트: [ch13-comments-should-describe-things-that-arent-obvious.md](../notes/ch13-comments-should-describe-things-that-arent-obvious.md)

**핵심 질문**: 좋은 주석은 무엇을 담아야 하는가?

## 핵심

- **대원칙**: 주석은 코드에서 명확하지 않은 정보를 전달한다. 코드를 반복하는 주석(설명 대상의 이름과 같은 단어를 쓰는 주석)은 가치가 없다.
- **주석 유형 네 가지**: 인터페이스 주석(클래스/메서드 선언 앞, 사용자용 추상화), 데이터 멤버 주석(필드의 의미와 제약), 구현 주석(비자명한 로직의 이유), 모듈 간 주석(모듈 사이 의존성). 팀 차원의 규칙으로 일관되게 쓴다.
- **하위 수준 주석은 정밀성**: 변수에 단위(밀리초), 유효 범위(음수 불가), 특수값의 의미(0이면 무한 대기), 경계 조건(모든 항목 처리 시 len과 같아짐)을 더한다.
- **상위 수준 주석은 직관**: 모듈이 무엇이고 어떤 개념으로 동작하는지(우선순위 순서 실행, 스레드 안전) 전달해서, 구현을 읽지 않고도 올바르게 사용할 수 있게 한다.
- **인터페이스 주석은 WHAT**: 호출자 관점에서 파라미터 의미와 제약, 반환값(빈 리스트인지 null인지), 예외, 부수 효과를 명시한다. 구현 세부사항은 넣지 않는다.
- **구현 주석은 HOW와 WHY**: 캐시를 먼저 보는 이유(적중률 85%), 100개만 조회하는 이유(그 이상은 0.1% 미만) 같은 결정의 근거를 남긴다.
- **모듈 간 주석**: 가장 어렵지만 가장 중요하다. 호출 순서가 다른 모듈의 프로토콜과 일치해야 한다는 식의 교차 의존을 명시하고, 중앙 설계 문서를 코드에서 참조하게 한다.

## Red Flags

- 🚩 **Comment Repeats Code**: 주석이 코드를 그대로 반복함

> **핵심 통찰**: 주석을 쓰기 전에 물어라 - "이 주석은 코드를 읽어서 알 수 없는 무엇을 말해 주는가?" 답이 없으면 그 주석은 지워도 된다.
