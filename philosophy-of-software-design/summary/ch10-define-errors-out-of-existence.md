# Chapter 10: Define Errors Out Of Existence (에러를 정의 밖으로 내보내라) - 요약

> 상세 노트: [ch10-define-errors-out-of-existence.md](../notes/ch10-define-errors-out-of-existence.md)

**핵심 질문**: 예외 처리가 왜 복잡성의 주요 원인인가? 예외의 수를 근본적으로 줄이는 설계 기법은 무엇인가?

## 핵심

- **예외는 복잡성의 주범**: 예외 경로는 재현/테스트가 어렵고, 개발자가 소홀히 하며, 호출 체인을 따라 전파되면서 각 계층에 복잡성을 더한다. 던지는 예외는 인터페이스의 일부라서 예외가 많을수록 모듈이 얕아진다.
- **기법 1 - 에러를 정의 밖으로**: 예외를 처리하는 최선의 방법은 예외가 발생할 수 없도록 API의 의미를 재정의하는 것. 파일 삭제를 "지워라"가 아니라 "없는 상태를 보장하라"로 정의하면 이미 없는 파일은 에러가 아니다. Python 슬라이싱은 범위를 자동 조정해 인덱스 예외가 없고, Unix unlink는 "디렉토리 항목 제거"로 정의해 열린 파일 삭제 에러를 없앴다(Windows와 대조).
- **기법 2 - 예외 마스킹**: 하위 계층에서 예외를 감지해 내부 처리하고 위로 전파하지 않는다. TCP가 패킷 손실을 재전송으로 흡수하므로 모든 앱이 재전송 로직을 안 짜도 된다. "복잡성을 아래로"(Ch8)의 구체적 적용이다.
- **기법 3 - 예외 집약**: 핸들러마다 개별 try/catch를 두지 않고 상위 디스패처 한 곳에서 일괄 처리한다. "예외는 발생 지점 가까이서 처리하라"는 전통적 조언과 반대로, 위로 모으는 쪽이 더 단순할 수 있다.
- **기법 4 - 그냥 크래시**: 메모리 부족, 데이터 손상 같은 복구 불가능한 에러는 복구를 시도하지 말고 종료한다. 복구 코드는 복잡하고, 검증이 어렵고, 거의 실행되지 않아 테스트도 안 되며, 잘못된 복구가 더 위험하다.
- **설계 시 질문 순서**: 에러가 아닌 것으로 재정의할 수 있나, 모듈 내부에서 처리할 수 있나, 한 곳에 모아 처리할 수 있나, 복구 불가능한가.

> **핵심 통찰**: 목표는 예외를 잘 처리하는 것이 아니라 예외가 처리되어야 하는 횟수 자체를 최소화하는 것이다.
