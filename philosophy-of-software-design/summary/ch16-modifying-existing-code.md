# Chapter 16: Modifying Existing Code (기존 코드 수정하기) - 요약

> 상세 노트: [ch16-modifying-existing-code.md](../notes/ch16-modifying-existing-code.md)

**핵심 질문**: 기존 코드를 수정할 때 설계를 유지하고 개선하려면 어떤 원칙을 따라야 하는가?

## 핵심

- **개발의 대부분은 수정이다**: 새 코드 작성보다 기존 코드 수정에 훨씬 많은 시간을 쓴다. 수정할 때의 태도가 시스템의 장기 품질을 결정한다.
- **캠핑 규칙**: 코드를 발견했을 때보다 더 나은 상태로 남겨라. 기능 추가나 버그 수정 중에 주변의 설계 문제가 보이면 함께 개선한다.
- **전술적 수정의 유혹**: "여기에 if 하나만 추가하면 되는데"를 반복하면 특수 케이스가 쌓인다. 이상적인 질문은 "처음부터 설계했다면 어떤 구조였을까"이고, 그 구조에 가깝게 수정한다.
- **주석도 코드 변경의 일부다**: 동작이 바뀌면 인터페이스 주석을, 변수 의미가 바뀌면 변수 주석을 함께 갱신한다. 이것을 빼먹는 것이 "주석은 구식이 된다"는 문제의 최대 원인이다.
- **설계 일관성**: 새 코드는 기존 설계 패턴에 맞춘다. 기존 설계가 새 코드를 깔끔하게 수용하지 못하면(if 체인이 계속 길어지는 상황) 설계를 먼저 개선한 뒤 추가한다(핸들러 맵 등).
- **변경 후 점검**: 설계가 여전히 깔끔한가, 특수 케이스가 늘지 않았나, 주석이 최신인가, 처음 보는 사람이 이해할 수 있나.

> **핵심 통찰**: 수정할 때마다 시스템은 조금 좋아지거나 조금 나빠진다. 중립은 없다. 캠핑 규칙이 지켜지는 코드베이스만 시간이 지나도 깨끗하게 남는다.
