# Chapter 8: Pull Complexity Downwards (복잡성을 아래로 끌어내려라) - 요약

> 상세 노트: [ch08-pull-complexity-downwards.md](../notes/ch08-pull-complexity-downwards.md)

**핵심 질문**: 복잡성이 반드시 어딘가에 존재해야 한다면, 인터페이스와 구현 중 어디에 두는 것이 나은가?

## 핵심

- **원칙**: 모듈의 인터페이스가 단순한 것이 구현이 단순한 것보다 중요하다. 복잡성은 구현(아래)에 둔다. 구현의 복잡성은 모듈 개발자 한 명이 한 번 감당하지만, 인터페이스의 복잡성은 모든 사용자가 매번 감당한다(N명 x M번).
- **설정 파라미터는 복잡성을 위로 밀어올린다**: max_connections, idle_timeout 같은 파라미터 뭉치는 "적절한 값 결정"이라는 어려운 문제를 사용자에게 전가한 것이다. 사용자는 대부분 그 값을 모르고, 모듈 개발자조차 모를 수 있다.
- **설정이 정말 필요하면**: 합리적인 기본값을 반드시 제공하고, 설정은 선택적으로 두고, 가능하면 모듈이 자동으로 최적값을 계산하게 한다. 파라미터 추가 전 항상 "모듈이 이 값을 스스로 결정할 수 있는가?"를 묻는다(대부분 답은 예).
- **에러 처리도 아래로**: 발생 가능한 모든 에러를 호출자에게 던지면 호출자마다 처리 코드가 반복된다. 모듈 내부에서 흡수하면(기본값 반환 등) 호출자가 단순해진다. Ch10의 "에러를 정의로 없애기"로 이어지는 원칙이다.
- **끌어내리면 안 되는 경우**: 하위 모듈이 올바른 결정을 내릴 맥락이 없을 때(로그 레벨은 호출자만 안다), 끌어내리면 상위 지식이 하위로 새는 정보 누출이 생길 때, 구현이 지나치게 복잡해져 전체 복잡성이 오히려 늘 때.
- **복잡성 공식과의 연결**: 인터페이스 복잡성은 모든 사용처에서 시간 가중치가 높지만, 구현 복잡성은 모듈 내부에서만 높다. 같은 양이면 구현에 두는 쪽이 전체 복잡성을 낮춘다.

> **핵심 통찰**: 판단 기준은 "이 복잡성을 누가 처리하는 것이 전체 시스템에 가장 이득인가"다. 대부분 모듈 내부가 답이지만, 모듈에 결정할 맥락이 없다면 예외다.
