# Chapter 6: General-Purpose Modules are Deeper (범용 모듈이 더 깊다) - 요약

> 상세 노트: [ch06-general-purpose-modules-are-deeper.md](../notes/ch06-general-purpose-modules-are-deeper.md)

**핵심 질문**: 모듈을 범용으로 만들 것인가, 특수 목적으로 만들 것인가? 균형점은 어디인가?

## 핵심

- **답은 "somewhat general-purpose"**: 기능(구현)은 현재 필요한 것만 만들되(YAGNI), 인터페이스는 미래의 사용까지 자연스럽게 지원하도록 범용적으로 설계한다.
- **텍스트 에디터 버퍼 예시**: `backspace()`, `typeCharacter()`, `pasteFromClipboard()`처럼 UI 동작마다 메서드를 만들면 인터페이스만 복잡해지고 각 메서드는 얕다. `insert(position, text)`와 `delete(start, end)` 두 범용 연산이면 모든 UI 동작을 조합으로 구현할 수 있다.
- **범용이 더 깊은 이유**: 적은 수의 메서드로 더 많은 상황을 지원하므로 인터페이스 폭은 좁아지고 기능량은 유지된다. UI 개념이 하위 모듈로 새는 정보 누출도 막는다.
- **점검 질문 세 가지**: 이 메서드가 사용될 상황은 몇 가지인가(하나뿐이면 너무 특수적), 현재 필요를 충족하는 가장 단순한 인터페이스는 무엇인가, 이 API는 현재 필요에 사용하기 쉬운가.
- **특수화는 위로**: 범용 코드는 하위 계층에, 특수 목적 코드는 상위 계층에 둔다. 하위 모듈(TextBuffer)은 UI를 모르고, 상위 계층이 범용 연산을 조합해 특수 동작을 만든다. 하위 모듈이 깊어지고, 변경에 강해지고, 재사용 가능해진다.
- **과도한 범용성 경계**: 안 쓸 기능을 미리 구현하거나, 범용성 명목으로 파라미터를 잔뜩 늘리거나, 현재의 일반적 사용을 불편하게 만들면 역효과다. 범용적인 인터페이스가 오히려 더 단순한 경우가 많다.

> **핵심 통찰**: 구현은 현재에, 인터페이스는 미래에 맞춰라. 범용 인터페이스는 메서드 수를 줄여 모듈을 깊게 만들고, 상위 계층의 특수화로부터 하위 모듈을 지킨다.
