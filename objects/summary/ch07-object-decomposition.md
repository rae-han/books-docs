# Chapter 7: Object Decomposition (객체 분해) - 요약

> 상세 노트: [ch07-object-decomposition.md](../notes/ch07-object-decomposition.md)

**핵심 질문**: 시스템을 어떤 기준으로 분해해야 하는가? 기능 분해, 모듈, 추상 데이터 타입, 클래스는 각각 무엇을 해결하고 어디서 한계를 드러내는가?

## 핵심

- **왜 분해하는가**: 단기 기억은 5~9개(매직 넘버 7)의 청크만 다룰 수 있다(조지 밀러). 인지 과부하를 막으려면 추상화(핵심만 남기기)와 분해(작은 문제로 나누기)가 필요하다.
- **두 추상화 축**: 프로시저 추상화(무엇을 하는가)를 중심에 두면 기능 분해로, 데이터 추상화(무엇을 아는가)를 중심에 두면 ADT 또는 객체지향으로 간다.
- **하향식 기능 분해의 다섯 가지 문제**(급여 관리 시스템 예제): 시스템에 하나의 메인 함수란 없다("실제 시스템에 정상은 없다" - 마이어), 새 기능마다 메인 함수를 재설계해야 하고, 비즈니스 로직이 UI와 결합되며, 너무 이른 시기에 실행 순서(시간 제약)가 고정되고, 전역 데이터 변경의 파급 효과를 추적할 수 없다(아르바이트 추가가 sumOfBasePays를 몰래 망가뜨린 사례).
- **모듈**(파나스의 정보 은닉): 기능이 아니라 변경의 방향에 맞춰 분해하고, 복잡성과 변경 가능성이라는 두 비밀을 감춘다. 데이터 파급 효과를 통제하고 관심사를 분리하지만, 인스턴스 개념이 없다(전체 직원 뭉치일 뿐 개별 직원을 다룰 수 없다).
- **추상 데이터 타입**(리스코프): 타입 정의, 오퍼레이션 집합, 데이터 보호, 다수 인스턴스 생성을 지원해 추상화 수준을 올렸다. 하지만 여전히 데이터와 기능을 분리하는 절차적 설계의 틀 안에 있다.
- **ADT vs 클래스**: ADT는 오퍼레이션을 기준으로 타입을 묶고(타입 추상화 - 하나의 Employee 안에 정규직/아르바이트가 조건문으로 공존), 클래스는 타입을 기준으로 오퍼레이션을 묶는다(절차 추상화 - Salaried/HourlyEmployee가 각자 구현). 클래스 안에 타입을 표현하는 변수(hourly)가 있고 조건문으로 분기한다면 클래스를 써도 객체지향이 아니다.
- **변경의 축으로 선택하라**: 새 타입 추가가 빈번하면 객체지향(클래스 추가만으로 확장 - OCP), 새 오퍼레이션 추가가 빈번하면 ADT가 유리하다.
- **협력이 목적이다**: 타입 계층과 다형성은 협력 안에서 책임을 수행하는 방법을 고민한 결과물이어야지 그 자체가 목적이 되면 안 된다.

> **핵심 통찰**: 시스템은 기능이 아니라 변경의 방향에 맞춰 분해해야 한다. 기능 분해에서 클래스까지의 역사는 "변경을 어디에 가둘 것인가"에 대한 답의 진화다.
