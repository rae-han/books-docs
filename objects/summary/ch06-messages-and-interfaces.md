# Chapter 6: Messages and Interfaces (메시지와 인터페이스) - 요약

> 상세 노트: [ch06-messages-and-interfaces.md](../notes/ch06-messages-and-interfaces.md)

**핵심 질문**: 유연하고 재사용 가능한 퍼블릭 인터페이스를 설계하려면 어떤 원칙을 따라야 하는가?

## 핵심

- **애플리케이션은 클래스가 아니라 메시지로 정의된다**: 용어 구분 - 메시지(협력의 매개체), 오퍼레이션(인터페이스의 추상적 서비스), 메서드(오퍼레이션의 구현), 시그니처(이름+파라미터 목록). 다형성이란 동일한 오퍼레이션 호출에 서로 다른 메서드가 실행되는 것이다.
- **디미터 법칙**: 내부 구조에 결합되지 않도록 협력 경로를 제한한다. 메시지는 this, 매개변수, 인스턴스 변수(와 그 컬렉션 요소), 지역 생성 객체에게만 보낸다. `screening.getMovie().getDiscountConditions()` 같은 기차 충돌은 수신자의 캡슐을 부순다.
- **묻지 말고 시켜라**: 상태를 물어서 외부에서 결정하지 말고 원하는 것을 시켜라. 절차적 코드는 정보를 얻은 후 결정하고, 객체지향 코드는 객체에게 하도록 시킨다. 자연스럽게 정보 전문가에게 책임이 가고 응집도가 높아진다.
- **의도를 드러내는 인터페이스**: "어떻게"(isSatisfiedByPeriod)가 아니라 "무엇을"(isSatisfiedBy) 기준으로 이름 짓는다. 같은 목적의 메서드들이 같은 이름을 가지면 타입 계층으로 묶여 대체 가능해진다. 티켓 도메인의 setTicket 3형제도 클라이언트 의도에 맞춰 sellTo, buy, hold로 바뀐다.
- **명령-쿼리 분리(CQS)**: 상태를 바꾸는 명령은 반환 값이 없고, 정보를 반환하는 쿼리는 상태를 바꾸지 않는다. "질문이 답변을 수정해서는 안 된다." isSatisfied가 몰래 reschedule까지 하던 일정 관리 버그가 대표 사례로, 분리하면 쿼리가 참조 투명성을 얻어 예측/디버깅이 쉬워진다.
- **원칙의 함정**: 도트가 여러 개라도 내부 구조를 노출하지 않으면(배열 메서드 체이닝) 디미터 위반이 아니다. 맹목적 위임 메서드는 오히려 응집도를 깎는다(기간 판단을 Screening에 넘기면 Screening의 본질적 책임이 아님). 자료 구조라면 당연히 물어야 한다. "경우에 따라 다르다"가 몇 안 되는 법칙이다.
- **통합 지침**: 메시지를 먼저 선택하면 위 네 원칙을 자연스럽게 따르게 된다. 수신자를 모른 채 메시지를 정하므로 내부 구조를 알 수 없고, 클라이언트 의도가 이름에 담긴다.

> **핵심 통찰**: 훌륭한 인터페이스의 비결은 원칙 암기가 아니라 순서다. 협력에 적합한 메시지를 먼저 정하고 객체가 그것을 따라오게 하라.
