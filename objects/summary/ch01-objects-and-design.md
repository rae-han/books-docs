# Chapter 1: Objects and Design (객체, 설계) — 요약

> 상세 노트: [ch01-objects-and-design.md](../notes/ch01-objects-and-design.md)

**핵심 질문**: 좋은 객체지향 설계란 무엇이며, 절차적 프로그래밍의 문제를 객체의 자율성과 캡슐화를 통해 어떻게 해결하는가?

## 핵심

- **이론보다 실무가 먼저**: 설계 원칙 대부분은 실무에서 반복 적용되던 기법의 이론화다(로버트 글래스). 설계를 설명하는 가장 유용한 도구는 이론이 아니라 코드다.
- **모듈의 세 가지 목적**(로버트 마틴): 제대로 동작하고, 변경이 용이하고, 읽는 사람과 의사소통해야 한다. 극장 예제의 초기 코드는 첫 번째만 만족한다.
- **절차적 코드의 문제**: Theater의 `enter`가 모든 처리를 도맡는 프로세스가 되고 나머지 객체는 수동적 데이터로 전락한다 → 자기 일은 스스로 처리하리라는 직관에 위배되고, 프로세스가 모든 데이터에 의존해 변경에 취약해진다.
- **해결 = 자율적인 객체 (책임의 이동)**: 데이터를 소유한 객체에게 그 데이터를 처리할 책임을 옮긴다. 캡슐화로 내부를 감추고 인터페이스(공개 메시지)만 노출하면 구현 변경이 외부로 파급되지 않는다.
- **결합도와 응집도**: 불필요한 의존성이 많으면 결합도가 높다 → 낮춘다. 자신의 데이터를 스스로 처리하면 응집도가 높다 → 높인다. 목표는 의존성 제거가 아니라 **최소한의 의존성만 유지**하는 것.
- **설계는 트레이드오프의 산물**: TicketOffice의 자율성을 높이자 Audience와의 새 의존성이 생겼다 → 자율성보다 결합도 감소를 우선해 롤백. 모든 것을 만족시키는 설계는 없다.
- **의인화**: 가방·매표소 같은 무생물도 자율적으로 행동하는 존재로 설계한다(레베카 워프스브록). 객체지향 세계에서 모든 객체는 능동적 에이전트다.

## 코드 한 컷

```typescript
// Before — Theater가 남의 내부에 직접 손을 뻗는다 (절차적)
enter(audience: Audience): void {
    if (audience.getBag().hasInvitation()) {
        // 가방을 열어 보고, 매표소를 뒤지고, 돈을 옮기고...
    }
}

// After — 메시지로만 협력하는 자율적 객체 (객체지향)
enter(audience: Audience): void {
    this.ticketSeller.sellTo(audience);   // 판매는 판매원이 알아서
}
// 연쇄 위임: TicketSeller.sellTo() → Audience.buy() → Bag.hold()
```

> **핵심 통찰**: 훌륭한 객체지향 설계란 협력하는 객체 사이의 의존성을 적절하게 관리하는 설계다. 데이터와 프로세스를 한 덩어리로 모으는 것은 첫걸음일 뿐이다.
