# Chapter 10: Inheritance and Code Reuse (상속과 코드 재사용) - 요약

> 상세 노트: [ch10-inheritance-and-code-reuse.md](../notes/ch10-inheritance-and-code-reuse.md)

**핵심 질문**: 코드 재사용을 위한 상속은 어떤 문제를 낳으며, 상속의 피해를 최소화하며 재사용하는 방법은 무엇인가?

## 핵심

- **중복의 기준은 변경이다**: 모양이 비슷한 것은 징후일 뿐, 요구사항이 바뀔 때 함께 수정해야 하면 중복이다(DRY, "모든 지식은 단일하고 믿을 만한 표현 양식을 가져야 한다"). 전화 요금 시스템에서 Phone을 복사해 NightlyDiscountPhone을 만들자, 세금 요구사항 하나에 두 클래스를 다르게 고치는 사고(한쪽은 더하고 한쪽은 뺌)가 바로 났다.
- **타입 코드 통합도 답이 아니다**: 요금제 타입 코드로 한 클래스에 합치면 응집도가 낮아지고 결합도가 높아진다.
- **무계획한 상속의 함정**: NightlyDiscountPhone이 Phone을 상속하며 super로 전체를 일반 요금으로 계산한 뒤 차액을 빼는 식의 직관에 어긋난 구현이 됐다. 부모 개발자의 가정을 정확히 알아야 재사용이 가능하므로 상속은 결합도를 높인다.
- **취약한 기반 클래스 문제**: 부모의 변경이 자식을 망가뜨리는 현상. 대표 사례 세 가지 - 불필요한 인터페이스 상속(Vector를 상속한 Stack은 LIFO 규칙을 깰 수 있고, Hashtable을 상속한 Properties는 String 규칙이 깨진다), 메서드 오버라이딩 오작용(HashSet.addAll이 내부에서 add를 호출해 InstrumentedHashSet의 카운트가 6이 되는 이펙티브 자바 사례), 부모-자식 동시 수정(Playlist 확장이 자식 수정을 강제).
- **상속을 위한 경고 4가지**: super 직접 호출은 강한 결합, 상속받은 부모 메서드가 자식의 규칙을 깰 수 있음, 오버라이딩하면 부모의 self-use 방식에 결합됨, 상속하면 부모-자식을 함께 변경하거나 영원히 동결하거나 둘 중 하나다.
- **완화책은 추상화**: 두 유사 메서드의 차이를 메서드로 추출하고(calculateCallFee), 공통 코드를 추상 클래스로 올린다(내리지 말고 올려라 - 샌디 메츠). 결과적으로 각 클래스가 하나의 변경 이유만 갖고(SRP), 부모도 자식도 추상 메서드에 의존하며(DIP), 새 요금제는 클래스 추가만으로 들어온다(OCP). 이름도 의도를 드러내게(AbstractPhone은 Phone으로, Phone은 RegularPhone으로).
- **한계는 남는다**: 부모에 인스턴스 변수(taxRate)가 추가되면 자식 생성자들이 전부 영향받는다. 그래도 초기화 로직 변경이 핵심 로직 중복보다 낫다.

> **핵심 통찰**: 상속은 코드 재사용을 위해 캡슐화를 희생한다. 차이에 의한 프로그래밍은 매력적이지만, 정말 필요한 경우에만 상속을 쓰고 대부분은 합성(11장)이 답이다.
