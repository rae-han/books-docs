# Appendix C: Dynamic Collaboration, Static Code (동적인 협력, 정적인 코드) - 요약

> 상세 노트: [appendix-c-dynamic-collaboration-static-code.md](../notes/appendix-c-dynamic-collaboration-static-code.md)

**핵심 질문**: 동적인 객체의 세계를 정적인 코드로 담아낼 때 어떤 모델이 우선인가?

## 핵심

- **두 모델**: 동적 모델(객체와 협력 - 실행 구조)과 정적 모델(타입과 관계 - 코드 구조). 정적 모델은 동적 모델이라는 토대 위에 세워져야 하며, 협력이 코드의 윤곽을 그린다.
- **행동이 코드를 결정한다**: 개념 분류만 따르면 "날 수 있는 펭귄"이 생긴다(Bird-Penguin). 객체가 외부에 제공하는 행동이 상속 계층을 결정해야 하며, 그 결과 FlyingBird 같은 어색한 이름의 클래스가 필요하다면 그렇게 하라.
- **변경도 함께 고려하라**: 행동이 같은 두 정적 모델(상속 vs 합성의 과금 시스템)이 있다면 변경을 부드럽게 수용하는 쪽을 택한다.
- **도메인 모델은 출발점이지 목표가 아니다**: 도메인 모델은 개념의 이름, 의미, 관계에 대한 힌트를 주는 역할로 끝나야 한다. "모델은 옳고 그른 것이 아니라 유용하거나 유용하지 않을 뿐"(파울러). 개념 분류 체계가 아니라 객체들의 협력이 코드 구조를 이끈다.
- **TYPE OBJECT 패턴**: 몬스터 종류마다 클래스를 추가하는 대신 Monster가 Breed 인스턴스를 합성한다. 타입을 클래스가 아니라 **인스턴스**로 표현하는 것으로, 새 타입 추가가 클래스 작성이 아니라 인스턴스 생성(심지어 JSON 데이터 한 줄)이 된다. 타입 구현의 또 다른 방법이다(부록 B의 확장).
- **도메인 모델은 형식이 자유롭다**: 합성 구조 + JSON 데이터의 조합도, 요금 계산의 실행 순서를 표현한 동적 모델도 훌륭한 도메인 모델이다. 중요한 것은 도메인 개념과 코드가 함께 이해되는 구조다.
- **분석/설계/구현 모델을 분리하지 마라**: 셋을 명확히 구분하는 것은 가능하지도 않고 품질에 해롭다. 객체지향의 가장 큰 힘은 전 개발 주기에 동일한 모델링 방법을 쓸 수 있다는 것이며, 프로그래밍은 설계의 한 과정이다. 코드와 대응하지 않는 다이어그램은 폐기하라 - 코드가 곧 모델이다.

> **핵심 통찰**: 모든 단계에서 행동과 변경에 초점을 맞춰라. 도메인 모델, 설계, 코드가 하나의 모델로 수렴할수록 소프트웨어는 이해하기 쉽고 변경하기 쉬워진다.
