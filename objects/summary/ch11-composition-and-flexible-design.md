# Chapter 11: Composition and Flexible Design (합성과 유연한 설계) - 요약

> 상세 노트: [ch11-composition-and-flexible-design.md](../notes/ch11-composition-and-flexible-design.md)

**핵심 질문**: 상속의 클래스 폭발 문제를 합성은 어떻게 해결하며, 믹스인은 둘의 특성을 어떻게 결합하는가?

## 핵심

- **상속 vs 합성**: 상속(is-a)은 부모의 구현에 의존하는 화이트박스 재사용으로 관계가 컴파일타임에 고정된다. 합성(has-a)은 포함된 객체의 퍼블릭 인터페이스에 의존하는 블랙박스 재사용으로 런타임에 관계를 바꿀 수 있다. "객체 합성이 클래스 상속보다 더 좋은 방법이다"(GOF).
- **10장의 세 문제를 합성으로 해결**: Properties/Stack은 Hashtable/Vector를 필드로 품으면 불필요한 인터페이스가 사라져 규칙 위반이 불가능해지고, InstrumentedHashSet은 Set 인터페이스 실체화 + 내부 HashSet + 포워딩으로 오버라이딩 오작용을 없앤다. Playlist류의 동시 수정은 합성으로도 다 안 풀리지만, 그래도 파급 효과를 내부로 캡슐화하므로 인터페이스 결합이 구현 결합보다 낫다.
- **클래스 폭발**: 기본 정책(일반/심야)과 부가 정책(세금/기본 요금 할인, 선택적/조합 가능/순서 자유)을 상속으로 구현하면 조합마다 클래스가 필요하다(TaxableAndRateDiscountableRegularPhone...). 새 기본 정책 하나에 클래스 5개, 그보다 나쁜 건 중복 코드도 기하급수로 는다는 것. 세금 정책 변경 하나에 여러 클래스를 찾아 고쳐야 한다.
- **합성 기반 재설계**: RatePolicy 인터페이스 아래 기본 정책(BasicRatePolicy)과 부가 정책(AdditionalRatePolicy - next로 다른 정책을 참조)을 두고, Phone은 RatePolicy만 합성한다. 부가 정책이 기본 정책과 같은 역할을 수행하므로 Phone은 상대가 뭔지 모른 채 협력한다. 조합은 인스턴스 조립으로: `new Phone(new TaxablePolicy(0.05, new RateDiscountablePolicy(1000, new RegularPolicy(...))))`.
- **효과**: 새 정책은 클래스 하나 추가, 정책 변경은 클래스 하나 수정(SRP). 컴파일 구조와 실행 구조의 거리가 멀어져 이해는 어려워지지만, 변경의 고통이 복잡성의 혼란을 넘는 상황이라면 유연성이 옳다.
- **믹스인**: 합성이 실행 시점 조합이라면 믹스인은 컴파일 시점에 코드 조각을 섞는 재사용이다. 스칼라 트레이트는 믹스인될 대상을 고정하지 않고(제약만 걸고), super가 동적으로 바인딩되어 선형화 순서에 따라 "쌓을 수 있는 변경"(stackable modification)이 가능하다. 트레이트 순서만 바꿔 부가 정책 적용 순서를 바꿀 수 있고 중복 코드가 생기지 않는다.
- **단서**: 이 장의 상속 비판은 전부 구현 상속에 국한된다. 인터페이스 상속은 13장에서 별도로 다룬다.

> **핵심 통찰**: 상속이 조합의 결과를 클래스 안에 미리 밀어 넣는 방식이라면, 합성은 조합의 요소들을 독립 클래스로 만들고 실행 시점에 조립하는 방식이다. 조합이 필요한 문제에서 상속은 폭발하고 합성은 확장된다.
