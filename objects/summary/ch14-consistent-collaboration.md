# Chapter 14: Consistent Collaboration (일관성 있는 협력) - 요약

> 상세 노트: [ch14-consistent-collaboration.md](../notes/ch14-consistent-collaboration.md)

**핵심 질문**: 유사한 기능이 서로 다른 패턴으로 구현되면 어떤 문제가 생기고, 협력에 일관성을 부여하려면 어떻게 해야 하는가?

## 핵심

- **비일관성의 탄생**: 과금 시스템에 기본 정책 4종(고정요금, 시간대별, 요일별, 구간별)을 개발자마다 다르게 구현했다 - 인스턴스 변수 2개, List 4개의 병렬 인덱스, 규칙 객체, 코드 재사용용 상속(구간별이 FixedFeePolicy 상속 - 10장이 경고한 오용). 클래스 하나하나는 그럭저럭 괜찮은데 모아 놓으면 문제가 보인다.
- **비일관성의 비용**: 새 구현을 추가할 때 어떤 방식을 따라야 할지 지침이 없고, 유사한 요구사항인데 코드가 다르면 이해에 심리적 장벽이 생긴다(요구사항이 유사하다는 사실 자체를 의심하게 됨).
- **두 가지 지침**: 변하는 개념을 변하지 않는 개념으로부터 분리하라, 그리고 변하는 개념을 캡슐화하라.
- **조건 로직을 객체 탐색으로**: 절차적 코드는 조건문 분기로 변경을 처리하지만, 객체지향은 조건 판단을 객체 사이의 이동(다형성)으로 바꾼다. 객체지향적인 코드는 조건을 판단하지 않고 다음 객체로 이동할 뿐이다.
- **캡슐화는 데이터 은닉 이상**: 네 종류가 있다 - 데이터 캡슐화(private 필드), 메서드 캡슐화(protected), 객체 캡슐화(합성 - 객체 사이 관계를 감춤), 서브타입 캡슐화(다형성 - 서브타입의 종류를 감춤). 협력의 일관성은 주로 **서브타입 캡슐화 + 객체 캡슐화의 조합**(인터페이스 상속 + 합성)으로 만든다.
- **일관성 있는 재설계**: 공통점 - 기본 정책은 규칙(FeeRule)들로 구성되고 규칙은 적용 조건 + 단위 요금이다. 차이점 - 적용 조건의 형식. 그래서 변하는 적용 조건을 FeeCondition 인터페이스로 추상화하고(TimeOfDay/DayOfWeek/DurationFeeCondition), 변하지 않는 FeeRule이 그것을 합성한다. 새 정책 추가 = FeeCondition 구현체 하나 추가.
- **패턴에 맞추기**: 규칙 개념이 필요 없는 고정요금 정책도 별도 구조를 만들지 않고 FixedFeeCondition으로 기존 패턴에 맞췄다. 개념적 부조화를 조금 수용하더라도 개념적 무결성(브룩스)을 지키는 편이 낫다. 일관성 있는 협력은 확장 포인트를 강제하여 규칙을 어기는 것이 지키는 것보다 어렵게 만든다.
- **지속적 개선**: 협력 패턴은 고정이 아니다. 새 요구사항이 패턴에 금을 내면 그것은 리팩터링의 신호다.

> **핵심 통찰**: 유사한 기능은 유사한 협력 패턴으로 구현하라. 하나의 협력을 이해하면 나머지가 공짜로 이해되는 것, 그것이 일관성의 힘이다.
