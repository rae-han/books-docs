# Appendix B: Implementing Type Hierarchies (타입 계층의 구현) - 요약

> 상세 노트: [appendix-b-implementing-type-hierarchies.md](../notes/appendix-b-implementing-type-hierarchies.md)

**핵심 질문**: 타입과 클래스는 같은가? 타입 계층을 구현하는 다양한 방법은 각각 언제 적합한가?

## 핵심

- **타입은 클래스가 아니다**: 타입은 퍼블릭 인터페이스(무엇을 할 수 있는가), 클래스는 그 타입을 구현하는 한 방법(어떻게 하는가)이다. 구현 방법이 하나뿐일 때만 둘을 동일시해도 무방하다. 어떤 구현 방법을 쓰든 LSP 준수는 도구가 아니라 설계자의 책임이다.
- **클래스 + 상속**: 가장 간단하지만 구체 클래스 상속은 부모 구현에 강하게 결합된다. 피하고, 가급적 추상 클래스나 인터페이스로 가라.
- **인터페이스**: 게임 예제(GameObject, Displayable, Collidable, Effect)처럼 한 클래스가 여러 타입에 속해야 할 때(Explosion은 Displayable이자 Effect) 다중 상속 딜레마 없이 타입 계층을 만든다. 여러 클래스가 같은 타입을, 한 클래스가 여러 타입을 구현할 수 있다.
- **추상 클래스**: 구체 클래스 상속과의 차이는 자식이 부모의 내부 구현이 아니라 추상 메서드 시그니처에 의존한다는 것(DIP의 변형), 그리고 처음부터 상속을 위해 설계된다는 것. 모든 구체 클래스의 부모는 추상 클래스로 만들려고 노력하라.
- **인터페이스 + 골격 구현 추상 클래스**(이펙티브 자바): 인터페이스로 타입을 정의하고 추상 클래스(DefaultDiscountPolicy)로 중복을 제거한다. 구현 방식이 여럿 필요하거나 이미 부모가 있는 클래스를 새 타입으로 확장할 때 유리하다. 이 복잡성이 필요 없으면 둘 중 하나만 써라.
- **덕 타이핑**: "오리처럼 걷고 꽥꽥거리면 오리다." 동적 타입 언어는 시그니처가 같으면 같은 타입으로 취급하고, TypeScript의 구조적 타이핑은 이를 컴파일 타임 안전성과 함께 제공한다(implements 없이도 구조가 호환되면 같은 타입). C++ 템플릿도 컴파일 시점 덕 타이핑이다. 클래스에 대한 의존을 메시지에 대한 의존으로 바꾼다(샌디 메츠).
- **믹스인과 타입**: 트레이트 믹스인은 행동(퍼블릭 인터페이스)을 공유시키므로 타입 정의이기도 하다. 스칼라 Ordered처럼 간결한 인터페이스를 풍부한 인터페이스로 만든다. Java 8 디폴트 메서드는 하위 호환용이지 추상 클래스 대체가 아니다 - 내부용 메서드가 public으로 강제되고(캡슐화 약화) 인스턴스 변수를 못 가져 중복이 남는다.

> **핵심 통찰**: 중요한 것은 클래스가 아니라 타입이다. 타입을 먼저 식별하고, 언어가 제공하는 도구 중 그 타입 계층에 맞는 구현 방법을 골라라.
