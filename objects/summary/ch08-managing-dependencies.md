# Chapter 8: Managing Dependencies (의존성 관리하기) - 요약

> 상세 노트: [ch08-managing-dependencies.md](../notes/ch08-managing-dependencies.md)

**핵심 질문**: 협력에 필요한 의존성은 유지하면서 변경을 방해하는 의존성은 어떻게 제거하는가?

## 핵심

- **의존성이란**: 한 요소가 다른 요소의 변경에 영향을 받을 수 있는 가능성. 방향성을 가지며 항상 단방향이다. UML의 여러 관계(연관, 실체화, 의존 등)가 전부 이 의미의 의존성을 포함한다.
- **의존성 전이**: A가 B에 의존하면 B가 의존하는 대상에도 간접적으로 의존하게 될 수 있다(직접 vs 간접 의존성). 전이 여부는 캡슐화의 정도가 결정한다 - 캡슐화가 전이를 차단하는 무기다.
- **컴파일타임과 런타임 의존성의 분리**: 코드의 Movie는 추상 클래스 DiscountPolicy만 알지만 실행 시점엔 Amount/PercentDiscountPolicy 인스턴스와 협력한다. 두 구조 사이의 거리가 멀수록 설계는 유연해진다. 클래스가 실행 문맥에 대해 최소한만 가정하는 것이 컨텍스트 독립성이다.
- **의존성 해결 방법**: 생성자 주입, setter(생성 후 교체 가능하지만 불완전 상태 위험), 메서드 인자(일시적 의존일 때). 권장은 생성자로 완전한 객체를 만들고 setter로 교체 가능성을 여는 혼합 방식.
- **지식이 결합을 낳는다**: 결합도는 상대에 대해 아는 정보의 양으로 결정된다. 더 많이 알수록 더 적은 컨텍스트에서 재사용된다. 해법은 추상화 - 구체 클래스, 추상 클래스, 인터페이스 순으로 알아야 할 지식이 줄고 결합이 느슨해진다.
- **의존성은 명시적으로**: 타입은 추상으로 선언해 놓고 생성자 안에서 `new AmountDiscountPolicy(...)`를 하면 숨겨진 의존성이 생긴다. 의존성 자체가 아니라 의존성을 감추는 것이 문제다.
- **new는 해롭다**: new는 구체 클래스 이름과 생성자 인자(그리고 그 인자의 구체 클래스들까지)를 알도록 강제한다. 생성 로직과 사용 로직을 분리하고 생성 책임을 클라이언트로 옮겨라. 단, 기본 정책을 주는 생성자 체이닝(사용성과 결합도의 트레이드오프)과 표준 라이브러리 클래스(변경 확률 거의 0)는 예외다.
- **조합 가능한 행동**: 잘 관리된 의존성 위에서는 코드 수정 없이 조합만 바꿔 행동이 달라진다(None/Overlapped 정책을 클래스 추가만으로 수용). 객체 생성 코드만 읽어도 무엇을 하는지 선언적으로 드러난다.

> **핵심 통찰**: 유연한 설계란 의존성이 없는 설계가 아니라, 추상화에 의존하고 그 의존성이 퍼블릭 인터페이스에 명시적으로 드러나는 설계다.
